## Authentication

Inference endpoints require a bearer API key:

```http
Authorization: Bearer <stogas_api_key>
Content-Type: application/json
```

`/v1/catalog` and `/v1/models` are public. API keys are not accepted in query parameters or cookies.

## Browser access

The public API allows cross-origin requests and uses bearer authentication rather than cookies:

```http
Access-Control-Allow-Origin: *
```

Do not expose a privileged API key in public browser code. Use a narrowly limited key or your own server when users must not receive the credential.

## Request handling

- The MVP API accepts text input and returns text output. Catalog modalities describe upstream capabilities; they do not enable image, audio, video, file, or PDF content on the public API.
- Unknown top-level JSON fields are accepted and ignored for SDK compatibility. They are never forwarded to a provider.
- Meaningful values for known unsupported features are rejected before authorization. Optional `null` values and selected empty SDK defaults are treated as omission.
- Compressed bodies are checked after decompression; oversized bodies return `413`.
- Unrecognized client headers are accepted and ignored for SDK and browser compatibility.
- Client headers are never forwarded to providers.
- Provider response headers are not returned to clients.
- Client-supplied private Stogas and Bifrost control headers are rejected.

## Limits

Requests have a 128-MiB decoded JSON ceiling. Binary E2EE applies the same payload ceiling with
separately bounded framing and authentication overhead. It does not wrap keys for the entire fleet
or base64-encode the body. Compressed bodies are measured after decompression.

The gateway also checks the selected model's context limits and the organization's policy.
The default platform allowance is shared across the organization, including requests from different
API keys. See [limits](/docs/policies/limits).

## Confidential transport

Native attested TLS requires TLS 1.3 with X25519MLKEM768. Ordinary HTTPS and E2EE outer carriage
support hardened TLS 1.2 and TLS 1.3. E2EE provides its own hybrid protection inside outer HTTPS.

Use a managed Stogas transport. It establishes a fresh verified session, then sends encrypted
credentials, request metadata and body records to the owning gateway. Responses, errors and SSE
content remain encrypted until the client verifies them. Only the owner can decrypt the session;
a new session can use another gateway without moving conversation state.

Record ordering, replay protection and an authenticated terminal record prevent a truncated or
modified exchange from reporting successful completion. The client rejects unexpected trailing
bytes. The SDK never repeats an inference after an ambiguous disconnect.

See the [security model](/docs/confidential-security-model) and [SDK guide](/docs/sdk-overview).

## Optional metadata

```http
Stogas-Metadata: v1
```

This single option requests a final `stogas` object containing useful usage, routing and available
provider information, plus a content receipt. Standard API `usage` remains available independently.
A buffered response appends the object to JSON. A stream carries it in a `: stogas {...}` SSE comment
before its terminal marker. Ordinary SSE parsers can ignore the comment.

The nested `receipt` uses `stogas.receipt.v1` and contains `boot_sha256`, `request_sha256`,
`response_sha256` and `signature`. One signature covers the request hash, response hash and
SHA-256 of the RFC 8785 canonical `stogas` object with its top-level `receipt` removed. Metadata
and keepalive comments are excluded from the response hash; the endpoint's terminal frame is
included. The managed SDK checks requested receipts automatically.
