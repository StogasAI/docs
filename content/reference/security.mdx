## Authentication

Inference endpoints require a bearer API key:

```http
Authorization: Bearer <stogas_api_key>
Content-Type: application/json
```

`/v1/catalog` and `/v1/models` are public. API keys are not accepted in query parameters or cookies.

## Browser access

The public API allows cross-origin requests and uses bearer authentication rather than cookies:

```http
Access-Control-Allow-Origin: *
```

Do not expose a privileged API key in public browser code. Use a narrowly limited key or your own server when users must not receive the credential.

## Request handling

- Unknown top-level JSON fields are rejected.
- Compressed bodies are checked after decompression; oversized bodies return `413`.
- Unrecognized client headers are accepted and ignored for SDK and browser compatibility.
- Client headers are never forwarded to providers.
- Provider response headers are hidden unless they are on the safe diagnostics allowlist.
- Client-supplied private Stogas and Bifrost control headers are rejected.

## Application E2EE

Stogas application E2EE protects the API key, request body, response body, streamed events, and response errors between the client and the verified confidential gateway process. It uses the same `/v1/chat/completions` and `/v1/responses` paths as ordinary OpenAI-compatible requests.

Use a Stogas managed transport or SDK. Applications should not construct the wire envelope directly.

For each request, the client:

1. verifies the current public trust bundle locally;
2. encrypts the API key and request once with a fresh content key;
3. wraps that key to every eligible node in the verified bundle; and
4. sends one opaque request that any eligible relay can route without reading the prompt.

The outer envelope reveals only routing and protocol metadata such as the request ID, bundle hash, deadline, recipient key IDs, and ciphertext length. The authenticated inner envelope contains the credential, API request, and negotiated options. Responses, SSE events, and the final proof frame remain encrypted until they reach the client.

The response receipt binds the exact request bytes, response bytes, request ID, route, resolved catalog nodes, freshness beacon, and E2EE transcript. The managed transport verifies that receipt against the same trust state used to encrypt the request.

Version 1 uses HPKE with P-256, HKDF-SHA-256, and AES-256-GCM. It does not claim post-quantum protection.

See the [security and trust model](/docs/confidential-security-model) for detailed guarantees and
[Verify a gateway](/docs/verification) for the practical setup.

## Optional diagnostics

Request safe response metadata with:

```http
X-Stogas-Return-Extra-Fields: provider,model_requested,latency
```

For request transformation debugging, `raw_request` and `raw_response` may also be requested. These fields can contain prompt or model-output data and should not be logged without an appropriate data policy.
