## Authentication

Inference endpoints need an API key in the `Authorization` header:

```http
Authorization: Bearer <stogas_api_key>
```

Query parameters and cookies cannot carry an API key. `/v1/catalog`, `/v1/catalog/parts/{sha256}`
and `/v1/models` need no key.

## Browser access

The API allows requests from any origin (`Access-Control-Allow-Origin: *`) and never uses cookies.
Do not put a key with wide permissions in public browser code. Give browsers a key with narrow
[policies](/docs/policies), or call the API from your own server.

## Request handling

- An unknown top-level JSON field returns `400` before any charge, as on OpenAI and Anthropic, so a
  field that the gateway cannot honor is never dropped without notice.
- A known field that the selected deployment cannot accept also returns `400` before any charge.
  `null` and the empty defaults that SDKs send count as omitted.
- Unknown headers are ignored, as HTTP asks, so SDK, proxy and tracing headers keep working.
- Client headers are never forwarded to providers, and provider headers are never returned.
- Headers that start with `x-stogas-` or `x-bf-` are rejected, and so is `anthropic-beta`, because
  it asks for Claude features that the gateway enables from request fields instead.
- The gateway never downloads attachments. Providers download file URLs themselves.

## Limits

| Limit                                          | Value     |
| ---------------------------------------------- | --------- |
| Request body, after decompression              | 128 MiB   |
| Entries in `messages`, or in `input` as a list | 100,000   |
| JSON values in the body                        | 1,000,000 |
| JSON nesting depth                             | 128       |
| E2EE response body                             | 64 MiB    |
| Time to send the request body                  | 5 minutes |

Objects, arrays and scalar values each count as one JSON value. Property names and text inside
strings do not. A request over a size limit returns `413`, and a body that takes longer than five
minutes returns `408`. Base64 attachments count toward the body size. When a gateway runs short of
memory, it ends the slowest uploads first with `503 gateway_capacity_exceeded`.

Each gateway also limits each IP address. Clients on a shared network share these limits:

| Limit                                 | Rate           | Burst |
| ------------------------------------- | -------------- | ----- |
| HTTP requests                         | 1,000 a second | 2,000 |
| New TLS connections and E2EE sessions | 100 a second   | 200   |

Over the request limit, the gateway returns `429 ip_rate_limit_exceeded` with `Retry-After`. Over
the connection limit, it closes the TLS handshake. Reuse connections and E2EE sessions to stay under
it. These limits never stop a stream that has started.

Each gateway also accepts up to 240 requests a second from each organization. Over that, it returns
`429 rate_limit_exceeded` with `Retry-After`.

Providers apply their own limits on files, context and output. Your organization's
[limits](/docs/policies/limits) also apply.

## Transport

- Native attested TLS requires TLS 1.3 with X25519MLKEM768.
- Ordinary HTTPS, and the outer HTTPS of E2EE, accept TLS 1.2 and TLS 1.3. E2EE provides its own
  hybrid protection inside outer HTTPS.
- E2EE records are ordered and authenticated, and every exchange ends with an authenticated
  terminal record. A cut or changed exchange cannot report success, and trailing bytes are
  rejected.
- The SDK never repeats an inference after an ambiguous disconnect.

See [Connection modes](/docs/connection-modes).

## Receipt format

Send `Stogas-Metadata: v1` to get a final `stogas` object with usage, routing and provider details,
and a receipt. A buffered response adds the object to the JSON. A stream sends it in a
`: stogas {...}` SSE comment before the last event.

The `receipt` field has the schema `stogas.receipt.v1`:

| Field             | Value                                                              |
| ----------------- | ------------------------------------------------------------------ |
| `boot_sha256`     | The boot record of the gateway that signed the receipt             |
| `request_sha256`  | SHA-256 of the exact request body                                  |
| `response_sha256` | SHA-256 of the exact response, including the endpoint's last event |
| `signature`       | The gateway's signature                                            |

One signature covers the request hash, response hash and SHA-256 of the RFC 8785 canonical
`stogas` object without its `receipt` field. Metadata and keepalive comments are not part of the
response hash. See [Receipts](/docs/receipts).

## Signed documents

Key manifests, evidence documents and boot records share one format:

- A `{document, signature, inclusion}` JSON envelope with snake_case fields, where `inclusion` is
  the Rekor proof.
- The evidence document contains the key manifest, Sigstore's keys, the hardware policies, AMD's
  certificates and revocation lists, and each approved gateway release and catalog as
  `{document, provenance}`, where `provenance` is GitHub's build proof. Its `revision` increases by
  one with each change.
- Each document names its schema. Release artifacts list their SHA-256 and size in bytes.
- The signature covers the RFC 8785 canonical JSON of `document` with the purpose label
  `stogas signed document v1`. The final newline of a file is not signed.
- Rekor logs the SHA-256 of the RFC 8785 canonical JSON of `{document, signature}`.
- Signatures are composite [ML-DSA-65 and Ed25519](https://datatracker.ietf.org/doc/draft-ietf-lamps-pq-composite-sigs/).
  Both parts must verify.
- A release's identity is the hash of its manifest, so a new signing key does not change the
  identity of an existing release.

GitHub, Rekor and AMD evidence keep their own standard formats.
