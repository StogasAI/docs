## Authentication

Inference endpoints need an API key in the `Authorization` header:

```http
Authorization: Bearer <stogas_api_key>
```

Query parameters and cookies cannot carry an API key. `/v1/catalog`, `/v1/catalog/parts/{sha256}`
and `/v1/models` need no key.

## Browser access

The API allows requests from any origin (`Access-Control-Allow-Origin: *`) and never uses cookies.
Do not put a key with wide permissions in public browser code. Give browsers a key with narrow
[policies](/docs/policies), or call the API from your own server.

## Request handling

- An unknown top-level JSON field returns `400` before any charge, as on OpenAI and Anthropic, so a
  field that the gateway cannot honor is never dropped without notice.
- A known field that the selected deployment cannot accept also returns `400` before any charge.
  `null` and the empty defaults that SDKs send count as omitted.
- Unknown headers are ignored, as HTTP asks, so SDK, proxy and tracing headers keep working.
- Client headers are never forwarded to providers, and provider headers are never returned.
- Headers that start with `x-stogas-` or `x-bf-` are rejected, and so is `anthropic-beta`, because
  it asks for Claude features that the gateway enables from request fields instead.
- The gateway never downloads attachments. Providers download file URLs themselves.

## Limits

| Limit                                          | Value     |
| ---------------------------------------------- | --------- |
| Request body, after decompression              | 128 MiB   |
| Entries in `messages`, or in `input` as a list | 100,000   |
| JSON values in the body                        | 1,000,000 |
| JSON nesting depth                             | 128       |
| E2EE response body                             | 64 MiB    |
| Time to send the request body                  | 5 minutes |

Objects, arrays and scalar values each count as one JSON value. Property names and text inside
strings do not. A request over a size limit returns `413`, and a body that takes longer than five
minutes returns `408`. Base64 attachments count toward the body size. When a gateway runs short of
memory, it ends the slowest uploads first with `503 gateway_capacity_exceeded`.

Each gateway also limits each IP address. Clients on a shared network share these limits:

| Limit                                 | Rate           | Burst |
| ------------------------------------- | -------------- | ----- |
| HTTP requests                         | 1,000 a second | 2,000 |
| New TLS connections and E2EE sessions | 100 a second   | 200   |

Over the request limit, the gateway returns `429 ip_rate_limit_exceeded` with `Retry-After`. Over
the connection limit, it closes the TLS handshake. Reuse connections and E2EE sessions to stay under
it. These limits never stop a stream that has started.

Each gateway also accepts an API key's requests at up to twice its organization's
[platform limit](/docs/policies/limits#requests), and an organization's at up to four times it.
Over that, it returns `429 rate_limit_exceeded` with `Retry-After`.

Providers apply their own limits on files, context and output. Your organization's
[limits](/docs/policies/limits) also apply.

## Transport

- Native attested TLS requires TLS 1.3 with X25519MLKEM768.
- Ordinary HTTPS, and the outer HTTPS of E2EE, accept TLS 1.2 and TLS 1.3. E2EE provides its own
  hybrid protection inside outer HTTPS.
- E2EE records are ordered and authenticated, and every exchange ends with an authenticated
  terminal record. A cut or changed exchange cannot report success, and trailing bytes are
  rejected.
- The SDK never repeats an inference after an ambiguous disconnect.

See [Connection modes](/docs/connection-modes).

## Receipt format

Send `Stogas-Metadata: v2` to get a final `stogas` object with usage, routing and provider details,
a receipt and its salts. A buffered response adds the object to the JSON. A stream sends it in a
`: stogas {...}` SSE comment before the last event.

The `receipt` field has the schema `stogas.receipt.v2`:

| Field                 | Value                                          |
| --------------------- | ---------------------------------------------- |
| `boot_sha256`         | The boot record whose key signed the receipt   |
| `request_commitment`  | The request's commitment, as lowercase hex     |
| `response_commitment` | The response's commitment, as lowercase hex    |
| `signature`           | The gateway's signature, as unpadded base64url |

`salts.request` and `salts.response` are 32 random bytes each, as lowercase hex. Only the client
receives them.

Each side's commitment is the SHA-256 of `stogas.receipt.v2.commitment`, a zero byte, `request` or
`response`, a zero byte, the side's salt and the SHA-512 of the side's content as RFC 8785 JSON.
Content is one JSON object without duplicate keys or invalid Unicode, at most 128 levels deep, whose
integers are from -9007199254740991 to 9007199254740991:

- A request is its body without the top-level `encryption_keys`.
- A buffered response is its body without the top-level `stogas`.
- A Responses stream is the `response` of its `response.completed` or `response.incomplete` event.
- A Chat Completions stream is the `chat.completion` that its chunks assemble to. `id`, `created`,
  `model` and `system_fingerprint` come from the first chunk that sets them, where `""` and `0` set
  nothing. `service_tier`, `speed`, `inference_geo`, `usage` and `prompt_filter_results` come from
  the last chunk that has them. Choices are matched by `index`: each keeps its last
  `finish_reason`, appends the `content` and `refusal` of its `logprobs`, and lists each chunk's
  `content_filter_results`. Its deltas build its `message`: `role` must not change, `content`,
  `refusal`, `reasoning` and `reasoning_content` are joined, and `annotations` and `images` are
  appended. `tool_calls` and `reasoning_details` are matched by `index`: their `id`, `type`,
  function `name` and `cache_control` must not change, and their text is joined. A field that is
  null or missing in every chunk is left out, and a chunk with any other field cannot be assembled.
- A Messages stream is the message that its events assemble to. `message_start` gives the message,
  and each `content_block_start` adds its block to `content`, with an `index` equal to the number
  of blocks before it. Each `content_block_delta` changes the unfinished block at its `index`:
  `text_delta`, `thinking_delta` and `input_json_delta` join their text, `citations_delta` adds its
  citation to `citations`, and `signature_delta` and `compaction_delta` replace the fields that they
  hold. When a block stops, or the message stops before it, input text that is a JSON object
  becomes its `input`, and any other input text becomes `input` as a string. `message_delta` sets
  each field of its `delta` that is not null on the message, and each field of its `usage` that is
  not null on the message's `usage`. Its other fields that are not null, and those of
  `message_stop`, are set on the message. `ping` carries nothing, and any other event, delta type
  or delta field cannot be assembled.

Comment lines, such as keepalives and the `stogas` comment, are not part of a stream's content.

The signature covers `stogas.receipt.v2`, a zero byte, the request commitment, the response
commitment and the SHA-512 of the RFC 8785 `stogas` object without its `receipt` and `salts`.
That object's `policy_versions_sha512` is the SHA-512 of the RFC 8785 canonical JSON of the request
record's `policy_versions`. See [Receipts](/docs/receipts).

## Signed documents

Key manifests, evidence documents and boot records share one format:

- A `{document, signature, inclusion}` JSON envelope with snake_case fields, where `inclusion` is
  the Rekor proof.
- The evidence document contains the key manifest, Sigstore's keys, the hardware policies, AMD's
  certificates and revocation lists, and each approved gateway release and catalog as
  `{document, provenance}`, where `provenance` is GitHub's build proof. Its `revision` increases by
  one with each change.
- Each document names its schema. Release artifacts list their SHA-256 and size in bytes.
- The signature covers the RFC 8785 canonical JSON of `document` with the purpose label
  `stogas signed document v1`. The final newline of a file is not signed.
- Rekor logs the SHA-512 of the RFC 8785 canonical JSON of `{document, signature}` in a
  `hashedrekord` entry. The root's submission key logs key manifests, and the signing key's
  submission key logs every other document. Entries from any other key are rejected.
- Signatures are composite [ML-DSA-65 and Ed25519](https://datatracker.ietf.org/doc/draft-ietf-lamps-pq-composite-sigs/).
  Both parts must verify.
- A release's identity is the hash of its manifest, so a new signing key does not change the
  identity of an existing release.

GitHub, Rekor and AMD evidence keep their own standard formats.
