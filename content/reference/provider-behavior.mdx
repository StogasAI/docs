---
title: Compatibility notes
description: Where the API differs from calling a provider directly.
---

The gateway accepts the OpenAI Chat Completions and Responses formats for every provider, and
Anthropic's [Messages](#messages) format for Claude. It checks each request against the selected
deployment before it calls the provider. A field that decides
what the reply holds, which tools the model can call, what the request costs or where its data is
kept returns `400` when the deployment cannot honor it, and costs nothing. A
[setting that only tunes the reply](#settings-that-a-deployment-lacks) never fails a request. Each
[provider page](/docs/providers) lists the fields and tools that only that provider accepts.

## Rejected fields

| Endpoint                    | Field                                  | Use instead                                                          |
| --------------------------- | -------------------------------------- | -------------------------------------------------------------------- |

| All                         | `container`                            | Not available. See [Tools](/docs/model-tools#unavailable-tools)      |
| All                         | `inference_geo`                        | A `-us` deployment ID, or a [routing policy](/docs/policies/routing) |
| Chat Completions, Responses | `speed`                                | A [service tier](/docs/service-tiers)                                |
| Chat Completions, Responses | `moderation`                           | Not available. Requests and responses are not moderated              |
| Chat Completions            | `functions`, `function_call`           | `tools` and `tool_choice`                                            |
| Chat Completions            | `audio`                                | Not available. Output is text only                                   |
| Chat Completions            | `prompt_cache_isolation_key`           | [`prompt_cache_key`](/docs/prompt-caching)                           |
| Chat Completions            | `instructions`                         | A `system` or `developer` message                                    |
| Chat Completions            | `max_output_tokens`                    | `max_completion_tokens`                                              |
| Chat Completions            | `text`                                 | `response_format` and `verbosity`                                    |

## Settings that a deployment lacks

```json
{
	"model": "gpt-5.6-sol",
	"messages": [{ "role": "user", "content": "Name three rivers." }],
	"temperature": 0.2,
	"seed": 7,
	"verbosity": "low"
}
```

A setting tunes how the model samples, how much it writes or reasons, or how the provider caches
the prompt. A deployment that has no control for a setting runs the request without it, so one set
of settings works for every model and a fallback never fails over one of them.

| Left out where a deployment lacks it                                                                   | Returns `400` where a deployment lacks it  |
| ------------------------------------------------------------------------------------------------------ | ------------------------------------------ |
| `temperature`, `top_p`, `top_k`, `frequency_penalty`, `presence_penalty`, `repetition_penalty`, `seed` | `logit_bias`, `logprobs`, `top_logprobs`   |
| `verbosity`, `prediction`, `task_budget`, `truncation`                                                 | `response_format`, `tools`, `tool_choice`  |
| `cache_control`, `prompt_cache_retention`, `prompt_cache_options`, `prompt_cache_breakpoint`           | `web_search_options`, `context_management` |
| A message's `name`                                                                                     | `include`, images and files                |

- A [reasoning](/docs/reasoning) control becomes the nearest setting of each deployment.
- A value in the wrong form returns `400` on every deployment, so a request never depends on
  which deployment runs it.
- The [request record](/docs/request-records) shows the settings that the provider received.
- The catalog says which deployments take a setting. To use only those, filter on the field in a
  [routing policy](/docs/policies/routing):

```json title="Only deployments that take a seed"
{
	"routing": {
		"filter": "deployment.sampling.seed"
	}
}
```

## Fields that the gateway changes

- An unknown top-level field returns `400` with the field in `param`, as on OpenAI. `null` counts as
  omitted. Unknown headers are ignored, and no client header reaches the provider. On Chat
  Completions and Responses, `anthropic-beta` returns `400`.
- `client_metadata`, which Codex sends with each Responses request, is accepted and never sent to
  the provider.
- `null`, and the defaults that SDKs send, such as `n: 1`, `parallel_tool_calls: true` or a
  plain-text `response_format`, count as omitted. So do `parallel_tool_calls: false`, and
  `tool_choice` set to `auto` or `none`, in a request without tools.
- `prompt_cache_key` works with every model, and only the models that use it receive it. See
  [Prompt caching](/docs/prompt-caching#provider-controls).
- `store` accepts only `false`. The gateway never asks a provider to store a response.
- `safety_identifier`, `user` and the `metadata.user_id` of Messages tell the provider which of your
  users sent a request, so the provider can act on that user instead of your whole account. Send an opaque value, such as a hash
  of your user ID: redaction doesn't change these fields. With your own credential, providers that
  accept them receive them. With a Stogas-managed credential, the gateway removes them.

- [`session_id`](/docs/request-records#sessions), and the
  [`metadata`](/docs/request-records#metadata) of Chat Completions and Responses, go to the request
  record, not to the provider.
- `max_tokens` is another name for `max_completion_tokens` on Chat Completions.
- Streamed Chat Completions always include usage.
- Sampling values, such as `temperature`, reach the provider unchanged. The provider decides which
  values its model accepts.
- `stop_sequences` is another name for `stop` on Chat Completions.

## Conversation state

The gateway keeps no conversation state, so each request must contain the whole conversation. Every
tool call needs its result in the same request, before the next message. Function arguments
must be a JSON object encoded as a string.

## Output

Models return text, tool calls and citations. Image and audio output are not available. See
[Images and files](/docs/input-files) for the input that each provider accepts.

## Streams and cancellation

Errors before the response starts use an HTTP status. Later errors arrive as an event in the
stream. A cancelled request can still be billed for the usage that the provider reports. See
[Streaming](/docs/streaming) and [Errors](/docs/reference/errors).

## Messages

```json title="A refused anthropic-beta value"
{
	"type": "error",
	"error": {
		"type": "invalid_request_error",
		"code": "unsupported_request",
		"message": "capability_rejected: beta_header:context-1m-2025-08-07"
	},
	"request_id": "019a3a6b-6b2e-7c4d-8a1b-2c3d4e5f6a7b"
}
```

`POST /v1/messages` takes Anthropic's request format and returns Claude's own response or events.

- Only deployments whose [route](/docs/policies/routing-fields#route-and-provider) serves the
  `messages` interface take the request, so another model returns `model_unavailable`.
- Anthropic's other endpoints, such as token counting, Message Batches and Files, are not
  available.
- A field that the gateway does not take returns `400` at any depth, with Anthropic's message, such
  as `betas: Extra inputs are not permitted`.
- An `anthropic-beta` value that the gateway does not take returns `400`. The
  [reference](/docs/reference/anthropic-compatible/createMessage) lists the values that it takes.
  `anthropic-version` is optional.
- Errors have Anthropic's shape and types, and keep the gateway's [`code`](/docs/reference/errors).
  Each response has a `request-id` header.
- Send your key in `x-api-key` or `Authorization`. Two different keys return `400`.
- The response's `model` is the model ID that served the request, such as `claude-sonnet-5-5`, on
  every provider.
