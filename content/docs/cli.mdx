title: CLI

Use `stogas` to run a verified local endpoint, encrypt customer content, or check evidence offline.
Your OpenAI-compatible client keeps its normal API surface; only the base URL changes.

## Install

Download the archive for your platform from [GitHub Releases](https://github.com/StogasAI/verifier/releases), verify `SHA256SUMS`, and place `stogas` on your `PATH`.

Supported targets are Linux x86-64 and ARM64, macOS x86-64 and ARM64, and Windows x86-64.

## Start

```console
stogas serve
```

The command prints a private URL such as:

```text
OpenAI base URL: http://127.0.0.1:8787/<random-capability>/v1
```

Use the complete printed URL in your OpenAI-compatible client and disable its automatic retries.
The listener accepts only loopback traffic with the capability. It installs no certificate authority.
Native mode verifies fresh attestation during a hybrid TLS 1.3 handshake before sending credentials
or content.

## Options

```console
stogas serve --security tls --max-connections 4
stogas serve --security e2ee
```

`tls` is the default. `e2ee` uses the same verified binary encryption protocol as the browser SDK.
Connections open as needed up to the configured maximum. Chat Completions, Responses, and the optional policy validation endpoint
are accepted; unsupported routes do not bypass verification.
Stop the process with Ctrl+C or, on Unix, SIGTERM. Both close the listener and
allow up to five seconds for transport cleanup. A cancelled request is not a
successful completion.

When launching the CLI as a child process, pass `--exit-on-stdin-close` and keep
its stdin connected to a pipe owned by the parent. Closing the pipe requests the
same cleanup, including when the parent crashes. Ordinary foreground use does
not need this option.

The CLI loads evidence from our R2 endpoint first and uses the AWS replica for recovery.
It does not poll. A setup failure can trigger one bounded evidence refresh before request
submission. The separately printed refresh URL accepts a manual `POST` from a local application.

The optional `--upstream` accepts an HTTPS origin without a path, credentials or query.
It does not change trusted evidence origins or signing roots. `--environment staging` requires
a build with staging support; the public build selects production.

## Browser applications

```console
stogas serve --browser-origin https://app.example.com
```

Use the complete printed capability URL. Only the specified browser origin is permitted.
The CLI handles CORS and local-network preflights without forwarding those headers to the gateway.
It keeps the selected native transport mode; browser access does not change the mode implicitly.
The browser may require local-network permission.

```js
import OpenAI from 'openai';

const client = new OpenAI({
	apiKey: userProvidedStogasKey,
	baseURL: pastedCliBaseUrl,
	dangerouslyAllowBrowser: true,
	maxRetries: 0
});
```

An HTTP loopback browser origin is accepted for local applications. Public origins require HTTPS.
Never embed a shared API key in shipped browser code.

## Encrypt credentials and plugins

Generate a customer encryption key locally:

```console
stogas encryption-key --output org.key
```

The command creates a private file and prints only its public identifier. Keep a secure backup;
we cannot recover the key. Add the printed identifier to the organization policy, preserving
its other settings:

```json title="Organization policy"
{
	"version": 1,
	"encryption": { "keys": { "providers": "THE_PRINTED_IDENTIFIER" } }
}
```

Only the organization policy registers key identifiers. Labels use a lowercase letter followed
by up to 47 lowercase letters, digits, underscores or hyphens. Register each identifier once.
Generate and register separate keys when credentials and plugins need different access.
Encrypt each credential or plugin object with the appropriate key:

```console
stogas encrypt --key-file org.key --organization YOUR_ORGANIZATION_ID \
  --purpose plugins --input plugins.json --output plugins.encrypted.json
```

| Purpose          | Input                                                       |
| ---------------- | ----------------------------------------------------------- |
| `plugins`        | The inner plugin JSON object, without a `plugins` wrapper.  |
| `byok/openai`    | The exact OpenAI credential, without a trailing newline.    |
| `byok/anthropic` | The exact Anthropic credential, without a trailing newline. |
| `byok/chutes`    | The exact Chutes credential, without a trailing newline.    |

Neither command uploads the key or input. They refuse to overwrite an existing output file.
Follow [encrypted plugins](/docs/policies/plugins#encrypted-plugins) or
[customer-encrypted BYOK](/docs/byok#customer-encryption) to save the resulting envelope.

### Send the key with a request

Include the required keys under their registered labels in `encryption_keys` in each inference
request's JSON body. Keep your API key in the `Authorization` header. The gateway removes this
map before provider dispatch and never stores the roots in its cache, database or analytics.

```json title="Responses request body"
{
	"model": "openai/gpt-5-mini",
	"input": "Hello",
	"encryption_keys": { "providers": "CONTENTS_OF_ORG_KEY_FILE" }
}
```

The gateway accepts this field over ordinary HTTPS, attested TLS, and binary E2EE. You choose
the transport before sending it. We recommend locally verified **attested TLS** or **binary E2EE**
to keep the key inside the verified gateway connection. Ordinary HTTPS protects the connection
to its TLS endpoint; it does not verify the gateway, and TLS intermediaries can read the body.
With E2EE, `encryption_keys` is inside the encrypted body.

Supply every root needed by applicable encrypted plugins. An encrypted provider credential is
eligible only when its matching root is supplied. Other registered roots are optional. Every
supplied label must match its registered identifier, including on cache hits.

The optional [policy check](/docs/policies/editing#check-execution-before-saving) accepts the
same field. Keep the key out of URLs, command-line arguments, and application logs.

### Key sharing and rotation

Anyone who obtains both a root and its ciphertext can decrypt that content. Separate roots
provide separate cryptographic access; labels alone do not. Removing a member cannot make
them forget a root. A caller must know any root needed for that caller's redaction policy.

Keep original policies and provider credentials for replacement or rotation. Prepare new
ciphertexts locally and register the new root under a new label. Update clients to supply both
roots, replace affected plugin sections and credentials, then remove the old registration and
stop sending it. These are separate saves; each checks the current policy revisions.

Each encryption uses a fresh salt and nonce to derive an AES-256-GCM key with HKDF-SHA-256.
The authenticated context binds the organization, purpose, and root identifier. ML-KEM protects
key establishment in verified transports; it does not replace content encryption.

## Verify an evidence file

```console
stogas verify bundle.json --json
```

Use `-` for standard input. This command performs no network access. It verifies the root-signed
key manifest, complete signed approvals, release evidence, hardware policy and bundled collateral.
It reports approved software, not a list of live gateways; fresh session verification establishes
a gateway's identity. `--environment` selects an authority already compiled into the build.

## Verify a saved receipt

```console
stogas proof --bundle bundle.json --boot boot-archive.json \
  --request request.json --response response.json --json
```

Supply the immutable boot archive and the exact evidence bundle named by its `evidence_sha256`.
The command verifies the boot at its authenticated transparency-log time, so later key rotations
or expired archived revocation lists do not invalidate the saved receipt. This historical check
does not authorize a new connection.

The default reads a buffered response with its final `stogas` metadata. Add `--stream` for a
complete SSE response, including metadata and the terminal event. For detached verification,
pass the complete `stogas` bag with `--proof metadata.json` and the exact signed response bytes
with `--response`.
Preserve the original request and response bytes; reformatting JSON changes their hashes.

The result confirms the signed content, metadata and boot identity. It does not establish
when the request ran.

## Metadata and shutdown

Send `Stogas-Metadata: v1` to request final metadata and a signed content receipt. The transport
verifies the receipt before releasing normal completion. SSE keepalive comments are safe to ignore.

Ctrl-C stops new work and allows bounded graceful cleanup of active streams and encrypted sessions.
A disconnect after submission may mean the inference executed; do not automatically replay it.

```console
stogas serve --help
```
