The `stogas` CLI runs a local endpoint that verifies the gateway and protects each request. Point
any OpenAI-compatible client at it; only the base URL changes. Use it from languages without an
[SDK](/docs/sdk-overview), or from tools you cannot change. It also checks evidence and receipts
offline, encrypts secrets for [customer encryption](/docs/customer-encryption), edits policies in
your own editor, and manages your account.

## Install

A package manager installs a release archive and checks its SHA-256:

```console tab="macOS and Linux" tab-group="os"
brew install stogasai/tap/stogas
```

```console tab="Windows" tab-group="os"
scoop bucket add stogas https://github.com/StogasAI/homebrew-tap
scoop install stogas/stogas
```

To check the archive yourself, install it by hand:

<Steps>
<Step>

### Download the archive

Each [release](https://github.com/StogasAI/stogas/releases) has an archive for each platform:
`linux-amd64`, `linux-arm64`, `linux-musl-amd64`, `linux-musl-arm64`, `darwin-amd64`,
`darwin-arm64`, `windows-amd64` and `windows-arm64`. Use a `linux-musl` archive on Alpine and other
musl systems.

```console
gh release download v<version> --repo StogasAI/stogas --pattern 'stogas-v<version>-linux-amd64.tar.gz'
```

</Step>
<Step>

### Verify it

Check that the release workflow built the archive from its tag:

```console
gh attestation verify stogas-v<version>-linux-amd64.tar.gz --repo StogasAI/stogas \
  --signer-workflow StogasAI/stogas/.github/workflows/release.yml \
  --source-ref refs/tags/v<version> --deny-self-hosted-runners
```

</Step>
<Step>

### Put it on your PATH

```console
tar -xzf stogas-v<version>-linux-amd64.tar.gz
sudo install stogas-v<version>-linux-amd64/stogas /usr/local/bin/
```

</Step>
</Steps>

With a Rust toolchain, `cargo install stogas-cli --locked` builds the CLI from source instead, and
with Nix, `nix run github:StogasAI/stogas -- serve` does.

## Serve

```console
stogas serve
```

```text
OpenAI base URL: http://127.0.0.1:8787/<random-capability>/v1
```

Use the complete URL as your client's base URL, and turn off the client's automatic retries. The
endpoint accepts only local connections that include the random part of the URL, and passes on the
API key that your client sends. It serves Chat Completions, Responses and the policy check
endpoint, and installs no certificate authority.

| Option                  | Default          | Effect                                                                           |
| ----------------------- | ---------------- | -------------------------------------------------------------------------------- |
| `--security`            | `tls`            | `tls` or `e2ee`. See [Connection modes](/docs/connection-modes).                 |
| `--max-connections`     | `4`              | The most connections or E2EE sessions, opened as requests wait                   |
| `--listen`              | `127.0.0.1:8787` | The loopback address and port                                                    |
| `--upstream`            |                  | Another HTTPS origin, with no path. The trusted evidence stays the same.         |
| `--browser-origin`      |                  | The only [web origin](#browser-applications) that may call the endpoint          |
| `--exit-on-stdin-close` |                  | Stop when the parent process closes stdin, for a CLI that another program starts |

The CLI loads evidence when a session starts, and again only when a session needs newer evidence.
A `POST` to the separately printed refresh URL loads it now.

Ctrl+C or SIGTERM stops new work and allows active streams and sessions up to five seconds to
close. A cancelled request may have run, so do not send it again automatically.

### Browser applications

Give the web page the complete printed URL. A page without it cannot read any response. The
endpoint holds no API key, so the page sends the user's own. To let only your application call it:

```console
stogas serve --browser-origin https://app.example.com
```

The CLI answers CORS and local-network preflight requests, and the browser can ask the user for
local-network permission. Local applications can use an HTTP loopback origin; public origins need
HTTPS.

```js
import OpenAI from 'openai';

const client = new OpenAI({
	apiKey: userApiKey,
	baseURL: pastedCliBaseUrl,
	dangerouslyAllowBrowser: true,
	maxRetries: 0
});
```

## Global options

These options work with every command, and their environment variables set them for every run:

| Option          | Environment variable | Effect                                                                                            |
| --------------- | -------------------- | ------------------------------------------------------------------------------------------------- |
| `--tor`         | `STOGAS_TOR`         | Connect through [Tor](#connect-through-tor), and reach Stogas at its onion address                |
| `--proxy <url>` | `STOGAS_PROXY`       | A proxy for every connection: `socks5h://host:port` or `http://host:port`, with an optional login |
| `--onion`       | `STOGAS_ONION`       | Reach Stogas at its onion address through the proxy                                               |

Without `--tor` or `--proxy`, the CLI uses the proxy that `https_proxy`, `HTTPS_PROXY`, `all_proxy`
or `ALL_PROXY` names, as curl does, except for the hosts that `no_proxy` or `NO_PROXY` names.

### Connect through Tor

```console
stogas --tor serve
```

`--tor` sends every connection through Tor: the dashboard, evidence, attested TLS and E2EE. It
finds the tor service on port 9050, or Tor Browser on port 9150. Give another port or address as
`--tor=9150` or `--tor=[::1]:9150`. Each run gets its own Tor circuits.

Stogas has no production onion address yet, so traffic leaves Tor through an exit relay, still
encrypted. The local endpoint takes connections from your machine only, so your client needs no
proxy. The [SDKs](/docs/sdk-overview#connect-through-a-proxy-or-tor) take the same proxies.

## Check gateway availability

```console
stogas probe --security e2ee
```

`probe` verifies current evidence and a fresh session, then sends a fixed invalid credential to the
inference route. It succeeds when the gateway rejects the credential after its readiness and memory
admission checks, so no API key or provider is involved. It does not measure provider health or
the success rate of your requests.

| Option         | Default                         | Effect                                            |
| -------------- | ------------------------------- | ------------------------------------------------- |
| `--security`   | `tls`                           | The connection mode to check                      |
| `--timeout-ms` | `8000`, or `32000` with a proxy | The deadline for evidence, setup and the response |
| `--upstream`   |                                 | As for `serve`                                    |

It prints a `stogas.probe.v1` JSON report with `security`, `ready`, the verified `node_id` when
available, `http_status` and a fixed [`error_code`](/docs/sdk-overview#errors), and exits with
status 0 only when `ready` is `true`.

## Check evidence and receipts

These commands make no network requests unless a description says so.

| Command                                                      | Effect                                                                                                                                     |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `stogas verify <file> [--json]`                              | Checks saved evidence, or `-` for standard input. See [Gateway verification](/docs/verification).                                          |
| `stogas proof [--request <file>] --response <file> [--json]` | Checks a saved [receipt](/docs/receipts#check-a-receipt-later). Downloads the evidence it needs unless you pass `--boot` and `--evidence`. |
| `stogas download-evidence --boot <sha256> [--output <dir>]`  | Downloads the boot record and evidence that a receipt names                                                                                |
| `stogas verify-release <dir> [--evidence <file>]`            | Checks a [downloaded SDK release](/docs/reproducible-builds#verify-an-sdk-download). Downloads current evidence without `--evidence`.      |

`proof` also takes `--stream` for an SSE response, `--proof <file>` for a `stogas` object saved on
its own or a [request record's proof](/docs/receipts#prove-a-request-log), and `--share <dir>` to
write a proof that someone else can check, with `--hide request` or `--hide response` to leave a
side out of it. Without `--request`, the request stays unchecked. See
[Share a proof](/docs/receipts#share-a-proof).

## Encrypt secrets

```console
stogas encryption-key create --organization <id> --label prod
stogas encrypt --key prod --organization <id> --purpose byok/openai \
  --input secret.txt --output credential.json
```

`encryption-key create` creates an organization key for
[customer encryption](/docs/customer-encryption), saves it in the system keychain under the label
that you register it with, and prints its public identifier. With `--output <file>`, it also
writes the key to a new file that only you can read; where there is no keychain, use only
`--output`. `encryption-key import` saves a key from a file, or as you type or pipe it in.
`export` copies a saved key to a new file, or with `--output -` pipes it to another program, such
as your secret manager. `delete` removes a saved key, and `logout` keeps them all.

`encrypt` encrypts a file with the key saved under `--key`, or with the key file that `--key-file`
names. `--purpose` is `plugins/export` or `plugins/redaction` for
[an export or a redaction](/docs/customer-encryption#encrypt-plugin-settings), or `byok/openai`,
`byok/anthropic`, `byok/chutes`, `byok/aws`, `byok/azure` or `byok/google-cloud` for a
[provider credential](/docs/byok#customer-encryption). `byok/azure` takes what
`az ad sp create-for-rbac` prints, as [Azure](/docs/providers/azure#customer-encryption) shows.
Before it encrypts a plugin's settings, `encrypt` has a gateway check them, which needs you signed
in. It encrypts a credential without connecting anywhere.

## Use your account

```console
stogas register
stogas login
stogas login --device-code
stogas logout
```

`register` creates an account, prints its password once, which cannot be recovered, and signs the
CLI in for 7 days. `login` opens the dashboard in your browser, where you approve the sign-in and
choose the organizations, access and expiry of its access token. Over SSH, through Tor, without a
display or with `--device-code`, it prints a code to enter on any device instead. Approve only a
code that your own `stogas login` printed, since approving a code signs in the CLI that printed it.

Each sign-in creates an access token named `Stogas CLI on <host>` unless you name it otherwise. The
CLI keeps it in the system keychain, or prints it where there is none, as on most servers. Signing
in again deletes the token that the new one replaces, and `logout` deletes the current one.

For servers and CI, create a token on the **Account** page with only the access that the job needs,
and set it as `STOGAS_TOKEN`. The CLI then uses it, and `register`, `login` and `logout` refuse to
run. See [Access tokens](/docs/reference/dashboard#access-tokens).

### Add credit

```console
stogas topup 25 BTC
stogas topup 25 USDT --network TRX
stogas topup 25 XMR --organization <organization-id>
```

The amount is the USD credit that you want. The CLI prints the coin amount, the fees on top, and
the address with any memo and a QR code, then waits until the payment is credited. Bitcoin and
Monero go to a [deposit address](/docs/billing#payment-methods), and other coins through CCPayment.
`--network` picks a network for a coin that has several. Without `--organization`, the credit goes
to your personal organization. If the organization has no billing country, state and ZIP code yet,
the CLI asks for them.

### Edit a policy

```console
stogas policy edit key <key-id>
stogas policy edit organization --organization <organization-id>
```

`policy edit` opens a [policy](/docs/policies) as JSON in your `$VISUAL` or `$EDITOR`, or in `vi`
(`notepad` on Windows) without either, and saves it when you close the file. The scope is
`organization`, `folder`, `grant`, `role`, `member`, `credential` or `key`. **Copy ID** in the menu of
a key, grant, member or credential copies its ID, and
[List folders](/docs/reference/dashboard/folders/listFolders) and
[List roles](/docs/reference/dashboard/roles/listRoles) return the others. Without
`--organization`, the policy is in your personal organization.

- The file starts with the [schema link](/docs/policies/editing#use-an-external-editor), so
  editors such as VS Code complete and check fields. Close the file unchanged to keep the policy,
  empty it to cancel, or replace it with `null` to clear the policy.
- If the JSON is invalid or the dashboard refuses the policy, the CLI shows why and offers to open
  your text again.
- If someone saved the policy while you edited it, your changes apply to their version, as in the
  [dashboard's editor](/docs/policies/editing#save-a-policy). The CLI lists the settings that you
  both changed, where your values stay, and opens the result for you to review before it saves.
- When an edit is not saved, the CLI prints the path of the file with your text, which only you
  can read.
- An editor that opens a window must wait until you close the file, as `code --wait` does.

### Check a credential

```console
stogas byok check <credential-id> --organization <organization-id>
stogas byok check <credential-id>... --organization <organization-id> --key-file org.key
```

`byok check` checks [provider credentials](/docs/byok#checks) with the same free call to the
provider as **Check credential** on the dashboard, and prints whether the provider accepted each.
**Copy ID** in a credential's menu copies its ID. A stored credential needs nothing else. For a
customer-encrypted credential, the CLI uses the key saved for the organization under the label that
it registered. Otherwise pass the key's file with `--key-file`, or enter the key when prompted, once
for each key. The CLI sends the key over a verified connection to a gateway,
the only place that can open the credential, and the gateway saves the result. An Azure
credential's check also finds its account's deployments, and the CLI prints how many targets are
selected, how many of those are unavailable, and how many models have none, with a link to choose
them. You need permission to manage the credentials. A failed check leaves the others to run, and
the command then exits with status 1. Without `--organization`, the credentials are in your
personal organization.

### Call the dashboard API

```console
stogas api /api/account
stogas api {org}/keys --paginate --slurp
stogas api POST {org}/keys --input key.json
stogas api {org}/analytics -f filter='outcome:failed' -F limit=20
```

The CLI sends the request with your token and prints the response: formatted JSON on a terminal,
and the exact bytes otherwise, ready for `jq` or a file. The path is under `/api/`, which you can
leave out. `{org}` in the path or in a `-F` value becomes the ID of the organization that
`--organization` or `STOGAS_ORG` names, or of your personal organization without either. A
refused request prints the response and the error, and exits with status 1. The
[Dashboard API](/docs/reference/dashboard) lists every operation.

| Option                          | Effect                                                                                                                                               |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `-X`, `--method`                | `GET`, `POST`, `PUT`, `PATCH` or `DELETE`, which can also come before the path. The default is `GET`, or `POST` when fields or `--input` add a body. |
| `-f`, `--raw-field <key=value>` | A string field                                                                                                                                       |
| `-F`, `--field <key=value>`     | A typed field. `true`, `false`, `null` and whole numbers become JSON values, `@file` reads a file and `@-` reads standard input.                     |
| `--input <file>`                | The JSON body, from a file or from standard input with `-`. Fields then go in the query.                                                             |
| `-H`, `--header "Name: value"`  | A request header. The CLI keeps its own token and content type.                                                                                      |
| `--paginate`                    | Gets every page of a list, following each page's next cursor                                                                                         |
| `--slurp`                       | With `--paginate`, prints one JSON array of the pages                                                                                                |
| `-i`, `--include`               | Prints the status and the response headers before the body                                                                                           |
| `-q`, `--silent`                | Prints no body                                                                                                                                       |

Fields go in the query of a `GET` request and in the JSON body of any other. A key can nest as in
`gh api`: `limits[requests]=10` sets a field of an object, `models[]=a` adds to a list, and
`rules[][name]=a` adds an object to a list.
