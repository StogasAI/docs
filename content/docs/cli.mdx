The `stogas` CLI runs a local endpoint that verifies the gateway and protects each request. Point
any OpenAI-compatible client at it by changing only the base URL. Use it from languages without an
[SDK](/docs/sdk-overview), or from tools you cannot change. It also checks evidence and receipts
offline, encrypts secrets for [customer encryption](/docs/customer-encryption), edits policies in
your own editor, and manages your account.

## Install

The install script downloads the newest release archive and checks its SHA-256 against the
release manifest:

```console tab="macOS and Linux" tab-group="os"
curl -fsSL https://raw.githubusercontent.com/StogasAI/stogas/main/install.sh | sh
```

```console tab="Windows" tab-group="os"
irm https://raw.githubusercontent.com/StogasAI/stogas/main/install.ps1 | iex
```

It installs into `~/.local/bin`, or on Windows into `%LOCALAPPDATA%\Programs\stogas`, which it adds
to your user PATH. On macOS and Linux, `sh -s -- --version <version> --dir <directory>` picks another
release or directory. On Windows, set `STOGAS_VERSION` and `STOGAS_INSTALL_DIR` first.

Package managers install the same CLI:

| Package manager | Command                                                                                                |
| --------------- | ------------------------------------------------------------------------------------------------------ |
| Homebrew        | `brew install stogasai/tap/stogas`                                                                     |
| Scoop           | `scoop bucket add stogas https://github.com/StogasAI/homebrew-tap`, then `scoop install stogas/stogas` |
| pipx or uv      | `pipx install stogas`, or `uvx stogas <command>` without installing                                    |
| cargo-binstall  | `cargo binstall stogas-cli`                                                                            |
| Docker          | `docker run --rm ghcr.io/stogasai/stogas <command>`                                                    |

The container image holds only the CLI. It has no keychain, and `serve` listens on the container's
own loopback address, so on Linux run `serve` with `--network host`.

To check the archive yourself, install it by hand:

<Steps>
<Step>

### Download the archive

Each [release](https://github.com/StogasAI/stogas/releases) has a CLI archive for each platform:
`linux-amd64`, `linux-arm64`, `linux-musl-amd64`, `linux-musl-arm64`, `darwin-amd64`,
`darwin-arm64`, `windows-amd64` and `windows-arm64`. Use a `linux-musl` archive on Alpine and other
musl systems.

```console
gh release download v<version> --repo StogasAI/stogas --pattern 'stogas-cli-v<version>-linux-amd64.tar.gz'
```

</Step>
<Step>

### Verify it

Check that the release workflow built the archive from its tag:

```console
gh attestation verify stogas-cli-v<version>-linux-amd64.tar.gz --repo StogasAI/stogas \
  --signer-workflow StogasAI/stogas/.github/workflows/release.yml \
  --source-ref refs/tags/v<version> --deny-self-hosted-runners
```

The same command checks the container image as `oci://ghcr.io/stogasai/stogas:<version>`. The
release notes name the image's digest, so you can pull exactly that image.

[Verify an SDK download](/docs/reproducible-builds#verify-an-sdk-download) also checks the second
builder's proof and our signature, and covers every SDK package.

</Step>
<Step>

### Put it on your PATH

```console
tar -xzf stogas-cli-v<version>-linux-amd64.tar.gz
sudo install stogas-cli-v<version>-linux-amd64/stogas /usr/local/bin/
```

</Step>
</Steps>

With a Rust toolchain, `cargo install stogas-cli --locked` builds the CLI from source instead, and
with Nix, `nix run github:StogasAI/stogas -- serve` does.

## Serve

```console
stogas serve
```

```text
OpenAI base URL: http://127.0.0.1:8787/<random-capability>/v1
Anthropic base URL: http://127.0.0.1:8787/<random-capability>
```

Use the complete URL that fits your client as its base URL, and turn off the client's automatic
retries. Anthropic's clients, such as [Claude Code](/docs/coding-agents#claude-code), add `/v1`
themselves. The endpoint accepts only local connections that include the random part of the URL,
and passes on the API key that your client sends. It serves Chat Completions, Responses, Messages,
policy validation, routing simulation, the model list and the catalog, and installs no certificate
authority.

| Option                  | Default          | Effect                                                                           |
| ----------------------- | ---------------- | -------------------------------------------------------------------------------- |
| `--security`            | `tls`            | `tls` or `e2ee`. See [Connection modes](/docs/connection-modes).                 |
| `--max-connections`     | `4`              | The most connections or E2EE sessions, opened as requests wait                   |
| `--listen`              | `127.0.0.1:8787` | The loopback address and port                                                    |
| `--upstream`            |                  | Another HTTPS origin, with no path. The trusted evidence stays the same.         |
| `--browser-origin`      |                  | The only [web origin](#browser-applications) that may call the endpoint          |
| `--exit-on-stdin-close` |                  | Stop when the parent process closes stdin, for a CLI that another program starts |
| `--encryption-key`      |                  | The label of a saved [key](#send-your-encryption-keys) to send. Repeat it.       |
| `--organization`        |                  | The organization whose keys `--encryption-key` names                             |
| `--encryption-key-file` |                  | A [key](#send-your-encryption-keys) file to send, as `LABEL=FILE`. Repeat it.    |

With `--service-key`, the endpoint sends a [workload's access token](#use-a-service-key-without-its-secret)
with every request in place of the API key that your client sends.

The CLI loads evidence when a session starts, and again only when a session needs newer evidence.
A `POST` to the separately printed refresh URL loads it now.

Ctrl+C or SIGTERM stops new work and allows active streams and sessions up to five seconds to
close. A cancelled request may have run, so do not send it again automatically.

### Send your encryption keys

```bash
stogas serve --encryption-key-file providers=/run/secrets/providers.key
```

The endpoint adds each key file's key under its registered label to each Chat Completions,
Responses, Messages and policy validation request, as
[`encryption_keys`](/docs/customer-encryption#send-the-key-with-a-request). Your application then
needs only the base URL and never holds a key. A request that sends its own `encryption_keys` goes
unchanged, and a compressed body is decoded first and sent uncompressed. For keys that [`stogas
encryption-key`](#encrypt-secrets) saved in your keychain, pass `--organization <id>` and
`--encryption-key <label>` for each instead.

### Browser applications

Give the web page the complete printed URL. A page without it cannot read any response. The
endpoint holds no API key, so the page sends the user's own. To let only your application call it:

```console
stogas serve --browser-origin https://app.example.com
```

The CLI answers CORS and local-network preflight requests, and the browser can ask the user for
local-network permission. Local applications can use an HTTP loopback origin, and public origins
need HTTPS.

```js
import OpenAI from 'openai';

const client = new OpenAI({
	apiKey: userApiKey,
	baseURL: pastedCliBaseUrl,
	dangerouslyAllowBrowser: true,
	maxRetries: 0
});
```

## Use a service key without its secret

```console
stogas token --service-key <key-id> --identity-token-file /var/run/secrets/tokens/stogas
stogas serve --service-key <key-id> --identity-token-file /var/run/secrets/tokens/stogas
```

A workload that a service key [trusts](/docs/workload-identity) needs no stored API key. `token`
exchanges the platform's token and prints an access token, which lasts 1 hour, and `--json` prints
the whole response with `expires_in`. `serve` exchanges it too, sends the access token with every
request, and renews it 2 minutes before it expires. If a renewal fails, `serve` keeps the token
until 30 seconds before it expires and tries again on the next request.

| Option                  | Environment variable         | Effect                                                            |
| ----------------------- | ---------------------------- | ----------------------------------------------------------------- |
| `--service-key`         | `STOGAS_SERVICE_KEY`         | The ID of the service key                                         |
| `--identity-token-file` | `STOGAS_IDENTITY_TOKEN_FILE` | The file with the platform's token, read again for every exchange |
| `--audience`            |                              | The audience of the token that the CLI requests in GitHub Actions |

`token` reads the platform's token from standard input when the file is `-`. In a GitHub Actions
job with the `id-token: write` permission, leave the file out: the CLI requests the job's token for
`--audience`, which is `stogas` unless you set it.

## Global options

These options work with every command, and their environment variables set them for every run:

| Option          | Environment variable | Effect                                                                                            |
| --------------- | -------------------- | ------------------------------------------------------------------------------------------------- |
| `--tor`         | `STOGAS_TOR`         | Connect through [Tor](#connect-through-tor), and reach Stogas at its onion address                |
| `--proxy <url>` | `STOGAS_PROXY`       | A proxy for every connection: `socks5h://host:port` or `http://host:port`, with an optional login |
| `--onion`       | `STOGAS_ONION`       | Reach Stogas at its onion address through the proxy                                               |

Without `--tor` or `--proxy`, the CLI uses the proxy that `https_proxy`, `HTTPS_PROXY`, `all_proxy`
or `ALL_PROXY` names, as curl does, except for the hosts that `no_proxy` or `NO_PROXY` names.

### Connect through Tor

```console
stogas --tor serve
```

`--tor` sends every connection through Tor: the dashboard, evidence, attested TLS and E2EE. It
finds the tor service on port 9050, or Tor Browser on port 9150. Give another port or address as
`--tor=9150` or `--tor=[::1]:9150`. Each run gets its own Tor circuits.

Traffic leaves Tor through an exit relay, still encrypted. The local endpoint takes connections from
your machine only, so your client needs no proxy. The
[SDKs](/docs/sdk-overview#connect-through-a-proxy-or-tor) take the same proxies.

## Check gateway availability

```console
stogas probe --security e2ee
```

`probe` verifies current evidence and a fresh session, then sends a fixed invalid credential to the
inference route. It succeeds when the gateway rejects the credential after its readiness and memory
admission checks, so no API key or provider is involved. It does not measure provider health or
the success rate of your requests.

| Option         | Default                         | Effect                                            |
| -------------- | ------------------------------- | ------------------------------------------------- |
| `--security`   | `tls`                           | The connection mode to check                      |
| `--timeout-ms` | `8000`, or `32000` with a proxy | The deadline for evidence, setup and the response |
| `--upstream`   |                                 | As for `serve`                                    |

It prints a `stogas.probe.v1` JSON report with `security`, `ready`, the verified `node_id` when
available, `http_status` and a fixed [`error_code`](/docs/sdk-overview#errors), and exits with
status 0 only when `ready` is `true`.

## Check evidence and receipts

These commands make no network requests unless a description says so.

| Command                                                      | Effect                                                                                                                                     |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `stogas verify <file> [--json]`                              | Checks saved evidence, or `-` for standard input. See [Gateway verification](/docs/verification).                                          |
| `stogas proof [--request <file>] --response <file> [--json]` | Checks a saved [receipt](/docs/receipts#check-a-receipt-later). Downloads the evidence it needs unless you pass `--boot` and `--evidence`. |
| `stogas download-evidence --boot <sha256> [--output <dir>]`  | Downloads the boot record and evidence that a receipt names                                                                                |
| `stogas verify-release <dir> [--evidence <file>]`            | Checks a [downloaded SDK release](/docs/reproducible-builds#verify-an-sdk-download). Downloads current evidence without `--evidence`.      |

`proof` also takes these flags. Without `--request`, the request stays unchecked.

| Flag                                | Use                                                                                                                                                  |
| ----------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--stream`                          | Check an SSE response.                                                                                                                               |
| `--proof <file>`                    | Read a `stogas` object saved on its own, or a [request record's proof](/docs/receipts#prove-a-request-record).                                       |
| `--request-id <id>`                 | Read and check the proof of a request's record, which needs you signed in. `--organization <id>` names an organization other than your personal one. |
| `--share <dir>`                     | Write a proof that someone else can check.                                                                                                           |
| `--hide request`, `--hide response` | Leave that side out of a shared proof.                                                                                                               |

See
[Share a proof](/docs/receipts#share-a-proof).

## Encrypt secrets

```console
stogas encryption-key create --output prod.key
stogas encrypt --key-file prod.key --organization <id> --policy policy.json --path /plugins/export
stogas encrypt --key-file prod.key --organization <id> --credential openai
```

`encryption-key create` creates an organization key for
[customer encryption](/docs/customer-encryption), writes it to a new file that only you can read,
and prints the key's ID, which you register. With `--organization` and `--label` in place of
`--output`, it saves the key in the system keychain under the label that you register it with, and
with all three it does both. `encryption-key import` saves a key in the keychain from a file, or as
you type or pipe it in. `export` copies a saved key to a new file, or with `--output -` pipes it to
another program, such as your secret manager. `id` prints the ID of a saved key, or of the key file
that `--key-file` names. `delete` removes a saved key, and `logout` keeps them all.

`encrypt` uses the key file that `--key-file` names, or the key saved under `--key`, and prints the
result, or writes it to the new file that `--output` names.

- With `--policy`, it encrypts parts of the policy in that file. Each `--path` is a JSON Pointer to
  an export or redaction plugin, or to a value inside one. Without `--path`, it encrypts every
  export and redaction plugin in the policy. Before it encrypts them, a gateway checks the plugins
  that hold the parts, which needs you signed in.
  [Encrypt a policy file](/docs/customer-encryption#encrypt-a-policy-file) gives the rules. For a
  policy that the dashboard stores, [`policy edit --key-file`](#edit-a-policy) encrypts as it saves.
- With `--credential`, it encrypts a [provider credential](/docs/byok#customer-encryption) of
  `openai`, `anthropic`, `chutes`, `aws`, `azure` or `google-cloud`, without connecting anywhere.
  It reads the file that `--input` names or what you pipe in, and without either asks for an API
  key without showing it. `azure` takes what `az ad sp create-for-rbac` prints, as
  [Azure](/docs/providers/azure#customer-encryption) shows.

## Use your account

```console
stogas register
stogas login
stogas login --device-code
stogas logout
```

`register` creates an account, prints its password once, which cannot be recovered, and signs the
CLI in for 7 days. `login` opens the dashboard in your browser, where you approve the sign-in and
choose the organizations, access and expiry of its access token. Over SSH, through Tor, without a
display, in GitHub Codespaces, Google Cloud Shell, Gitpod or a VS Code dev container, or with
`--device-code`, it prints a code to enter on any device instead. Approve only a code that your own
`stogas login` printed, since approving a code signs in the CLI that printed it.

Each sign-in creates an access token named `Stogas CLI on <host>` unless you name it otherwise. The
CLI keeps it in the system keychain, where signing in again replaces it and `logout` deletes it.
Where there is no keychain, as on most servers, the CLI prints the token for you to set as
`STOGAS_TOKEN`. The token stays valid until it expires or you delete it.

For servers and CI, create an access token with only the access that the job needs, and set it as
`STOGAS_TOKEN`. The CLI then uses it, and `register`, `login` and `logout` refuse to run. See
[Access tokens](/docs/reference/dashboard#access-tokens).

### Add credit

```console
stogas topup 25 BTC
stogas topup 25 USDT --network TRX
stogas topup 25 card
stogas topup 25 XMR --organization <organization-id>
```

The amount is the USD credit that you want. For a coin, the CLI prints the coin amount, the fees on
top, and the address with any memo and a QR code. Bitcoin and Monero go to a
[deposit address](/docs/billing#payment-methods), and other coins through CCPayment. `--network`
picks a network for a coin that has several, by its code, its name or the name that exchanges give
it, such as `TRC20`. For `card`, the CLI prints a link to Stripe's payment
page and its QR code, so you can pay in any browser or on your phone, within 31 minutes. The CLI
then waits until the payment is credited. It stops earlier, with an error, when the payment is under
review, its credit is pending under the prepaid limits, or it adds no credit.

Without `--organization`, the credit goes to your personal organization. If the organization has no
billing country, state and ZIP code yet, the CLI asks for them.

### Edit a policy

```console
stogas policy edit key <key-id>
stogas policy edit organization --organization <organization-id>
stogas policy edit key <key-id> --key-file prod.key
```

`policy edit` opens a [policy](/docs/policies) as JSON in your `$VISUAL` or `$EDITOR`, or in `vi`
(`notepad` on Windows) without either, and saves it when you close the file. The scope is
`organization`, `folder`, `grant`, `role`, `member`, `credential` or `key`, and the ID is the
resource's `id` in its [Dashboard API](/docs/reference/dashboard) list, such as
`stogas api {org}/keys` for keys. Without `--organization`, the policy is in your personal
organization.

- The file starts with the [schema link](/docs/policies/editing#use-an-external-editor), so
  editors such as VS Code complete and check fields. Close the file unchanged to keep the policy,
  empty it to cancel, or replace it with `null` to clear the policy.
- If the JSON is invalid or the dashboard refuses the policy, the CLI shows why and offers to open
  your text again.
- If someone saved the policy while you edited it, your changes apply to their version, as in the
  [dashboard's editor](/docs/policies/editing#save-a-policy). The CLI lists the settings that you
  both changed, where your values stay, and opens the result for you to review before it saves.
- When an edit is not saved, the CLI prints the path of the file with your text, which only you
  can read.
- An editor that opens a window must wait until you close the file, as `code --wait` does.
- With `--key-file`, or `--key` for a key saved under that label, the file shows each value that
  the key encrypts in plain text as `{ "encrypt": value }`, and saving encrypts every value of an
  export or redaction plugin that is written so. Before it saves, the CLI lists the values that
  saving encrypts and asks you to confirm.
  [Encrypt plugin settings](/docs/customer-encryption#encrypt-plugin-settings) gives the rules.
  Repeat the option with a new key first to move the values of the other keys to it, which saves
  even when you close the file unchanged.

### Check a credential

```console
stogas byok check <credential-id> --organization <organization-id>
stogas byok check <credential-id>... --organization <organization-id> --key-file org.key
```

`byok check` checks [provider credentials](/docs/byok#checks) with a free call to the provider, and
prints whether the provider accepted each. `stogas api {org}/byok` lists the credentials with their
IDs. A stored credential needs nothing else. For a customer-encrypted credential, the CLI uses the
key saved for the organization under the label that it registered. Otherwise pass the key's file
with `--key-file`, or enter the key when prompted, once for each key. The CLI sends the key over a
verified connection to a gateway, the only place that can open the credential, and the gateway saves
the result. An Azure credential's check also finds its account's deployments. The CLI prints how
many models its deployments serve and how many stopped serving, with a link to its targets. You need
permission to manage the credentials. A failed check leaves the others to run, and the command then
exits with status 1. Without `--organization`, the credentials are in your personal organization.

### Call the dashboard API

```console
stogas api /api/account
stogas api {org}/keys --paginate --slurp
stogas api POST {org}/keys --input key.json
stogas api GET {org}/analytics -f filter='outcome:failed' -F limit=20
```

The CLI sends the request with your token and the API version that it was built for. It prints
formatted JSON or text on a terminal, and the exact bytes otherwise, ready for `jq` or a file. A
binary response, such as a Parquet export, needs a file. The path is under `/api/`, which you can
leave out. `{org}` in the path or in a `-F` value becomes the ID of the organization that
`--organization` or `STOGAS_ORG` names, or of your personal organization without either. A refused
request prints the response and the error, and exits with status 1. The [Dashboard
API](/docs/reference/dashboard) lists every operation.

| Option                          | Effect                                                                                                                                                                   |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `-X`, `--method`                | `GET`, `POST`, `PUT`, `PATCH` or `DELETE`, which can also come before the path. The default is `GET`, or `POST` when fields or `--input` add a body.                     |
| `-f`, `--raw-field <key=value>` | A string field                                                                                                                                                           |
| `-F`, `--field <key=value>`     | A typed field. `true`, `false`, `null` and integers such as `42` become JSON values, while `007` and `+1` stay text. `@file` reads a file and `@-` reads standard input. |
| `--input <file>`                | The JSON body, from a file or from standard input with `-`. Fields then go in the query.                                                                                 |
| `-H`, `--header "Name: value"`  | A request header. The CLI keeps its own token, content type and `Accept-Encoding`, and `Stogas-Version` replaces the [API version](/docs/reference/dashboard#versions).  |
| `--paginate`                    | Gets every page of a list, following each page's next cursor                                                                                                             |
| `--slurp`                       | With `--paginate`, prints one JSON array of the pages, and only when every page arrives                                                                                  |
| `-i`, `--include`               | Prints the status and the response headers before the body                                                                                                               |
| `--silent`                      | Prints no body                                                                                                                                                           |

Fields go in the query of a `GET` request and in the JSON body of any other. A key can nest as in
`gh api`: `limits[requests]=10` sets a field of an object, `models[]=a` adds to a list, and
`rules[][name]=a` adds an object to a list. `rules[][tags][]=x` adds to the list in that object.

## Exit status

| Status | When                                                                                    |
| ------ | --------------------------------------------------------------------------------------- |
| `0`    | The command succeeded                                                                   |
| `1`    | The command failed, `api` got a refused request, or `probe` found the gateway not ready |
| `2`    | An option or argument is wrong                                                          |
