Gateways run inside AMD SEV-SNP confidential VMs. The processor encrypts the VM's memory, so
the host, the cloud operator and our staff cannot read your API key, prompts or responses while
the gateway handles them. Before your client sends anything, the SDK checks hardware evidence that
the gateway runs an approved release built [reproducibly](/docs/reproducible-builds) from public
source.

## How a request is protected

| Stage                  | Protection                                                                                                                         |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Your device to gateway | [Attested TLS or E2EE](/docs/connection-modes), which ends inside the verified gateway                                             |
| Inside the gateway     | SEV-SNP memory encryption. Policies, PII redaction, routing and billing run here.                                                  |
| Gateway to provider    | TLS 1.3, with post-quantum key exchange or E2EE where the [provider](/docs/providers) supports it                                  |
| After the request      | The [request record](/docs/request-records) has no prompt or response. A [receipt](/docs/receipts) signs both, if you ask for one. |

Without the SDK, plain HTTPS still reaches the gateway, but you trust our routing and TLS
certificate instead of the hardware evidence. A receipt cannot show afterwards that no one else
read the request.

## What you trust

- **AMD:** the processor, its firmware and AMD's signing keys.
- **The gateway source code**, which is public. You can [rebuild it](/docs/reproducible-builds) to
  the same launch measurement, so you do not have to trust the builds that we or GitHub publish.
- **Our signing keys**, which approve releases, catalogs and hardware policies. Every approval is
  in the public, append-only Rekor log.
- **The model provider**, which receives the prompt under its [data terms](/docs/providers).
- **Your own device**, and the device or service that runs the SDK.

## Design rules

- **You can use Stogas without trusting us.** The SDK checks every claim on your device. To read
  your data, we would have to publicly approve a release that does so, built from source that
  anyone can inspect.
- **Proof where possible, signed public commitments elsewhere.** We sign and log what you cannot
  check yourself, such as our decision to approve a release or start a gateway, so a false claim
  stays on record.
- **Everything you trust is in a public log.** Signing keys, evidence revisions, gateway and SDK
  releases, catalogs, hardware policy and gateway boots are in the append-only Rekor log. The SDK
  rejects evidence and boot records that are not in it.
- **All software we release is reproducible.** Gateway images and SDK packages
  [rebuild](/docs/reproducible-builds) from public source to the same bytes.
- **We don't trust our own infrastructure.** Any of our servers, our database, our hosting
  providers, GitHub, Sigstore, Rekor or the evidence hosts can be compromised. None of them alone
  can read your data or get a gateway approved that differs from its public source. The evidence
  hosts can delay an update but cannot change it.
- **Strict hardware settings.** Each release fixes the VM's policy, such as debugging and migration
  off, and the hardware policy sets each chip's minimum firmware. The SDK checks both in every
  hardware report, and a gateway serves you only after its boot is in the public log.
- **Defense in depth.** E2EE adds forward secrecy and post-compromise security to memory
  encryption.
- **Post-quantum.** Attested TLS, E2EE and our signatures use
  [hybrid post-quantum algorithms](#post-quantum-protection).

## What the hardware does not protect

- **Availability.** The host can stop, slow or block a gateway.
- **Traffic patterns.** Network observers see addresses, timing and unpadded message sizes.
- **Location.** A gateway's region, such as `FR` or `US-VA`, is a statement by the operator. AMD
  evidence does not prove where a machine is.
- **Time.** Gateways set their clock from five independent
  [Network Time Security](https://www.rfc-editor.org/rfc/rfc8915) servers and start only after
  three agree. A host that blocks them can slow the clock and delay expiry checks, which the SDK
  repeats with your device clock.
- **Side channels.** Depending on the processor generation, the host can watch memory ciphertext
  and cache timing, and steer branch prediction, while a gateway runs. Published attacks have used
  such access to recover keys from protected VMs.
- **Bugs.** Evidence proves which code runs, not that it is correct.

## Chain of trust

The SDK has our root key, Sigstore's root keys and AMD's root certificates built in.

<Steps>
<Step>

### Root key

Our root signs a key manifest that authorizes the online signing key and logs it to Rekor with the
root's own submission key. The key manifest expires 24 hours after signing, and we renew it several
times a day. Only the root can authorize or retire a signing key.

</Step>
<Step>

### Evidence

The online key signs one evidence document that holds the key manifest, the approved gateway
releases, catalogs and hardware policies, Sigstore's keys and AMD's certificates and revocation
lists. Each change gets the next revision number, and we log every revision to Rekor, so every
version that a client could have received is public. The evidence expires with the key manifest
it contains. The online key cannot authorize itself or another key. Gateways recheck the evidence
every two minutes and stop accepting new requests when their release is withdrawn, so your client
does not need to poll for changes.

</Step>
<Step>

### Build proofs

GitHub attests both the IGVM and manifest of each gateway release, which links them to the public
source tag and workflow. We approve the release only after our own independent build matches. The
SDK requires both, so neither GitHub nor we alone can get an image approved that differs from its
public source.

</Step>
<Step>

### Hardware evidence

AMD's signed report shows the VM's launch measurement, the chip, its firmware versions and the keys
that the gateway generated.

</Step>
<Step>

### Fresh connection

A random challenge from your client goes into a new report, which binds this connection to the
hardware evidence and to the gateway's logged boot record.

</Step>
</Steps>

[Gateway verification](/docs/verification) lists each check and shows how to inspect the evidence
yourself.

## Post-quantum protection

| Part                                                                 | Algorithms                                                       | Post-quantum |
| -------------------------------------------------------------------- | ---------------------------------------------------------------- | ------------ |
| Attested TLS                                                         | TLS 1.3 with X25519MLKEM768 and an ML-DSA-65 certificate         | Yes          |
| E2EE                                                                 | X-Wing (X25519 and ML-KEM-768), then a ratchet with ML-KEM-768   | Yes          |
| Our signatures on key manifests, evidence, boot records and receipts | Composite ML-DSA-65 and Ed25519                                  | Yes          |
| Gateway to provider                                                  | X25519MLKEM768 where the [provider](/docs/providers) supports it | Varies       |
| AMD reports, GitHub build proofs and Rekor                           | Classical signatures                                             | No           |

Hybrid key exchange protects recorded traffic from future quantum computers, but AMD, GitHub and
Rekor still sign with classical algorithms, so the chain of trust is not yet quantum safe.
