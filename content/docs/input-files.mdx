---
title: Images and files
description: Send images and documents to models that accept them, inline, by URL or by file ID.
icon: Paperclip
---

Add images and documents to a message as content blocks. The gateway sends the request only to
[candidates that can read every attachment](#when-no-candidate-reads-a-file). The provider checks
the file itself.

| Input    | Chat Completions | Responses     |
| -------- | ---------------- | ------------- |
| Image    | `image_url`      | `input_image` |
| Document | `file`           | `input_file`  |

## Send an image

```json tab="Chat Completions"
{
	"model": "gpt-5.6-sol",
	"messages": [
		{
			"role": "user",
			"content": [
				{ "type": "text", "text": "What does this chart show?" },
				{
					"type": "image_url",
					"image_url": { "url": "https://example.com/chart.png", "detail": "high" }
				}
			]
		}
	]
}
```

```json tab="Responses"
{
	"model": "gpt-5.6-sol",
	"input": [
		{
			"role": "user",
			"content": [
				{ "type": "input_text", "text": "What does this chart show?" },
				{ "type": "input_image", "image_url": "data:image/png;base64,iVBORw0KGgo..." }
			]
		}
	]
}
```

An image can be an HTTP(S) URL or a base64 data URL. On Responses, `file_id` also works[^sources].

## Send a document

```jsonc tab="Chat Completions"
{
	"model": "gpt-5.6-sol",
	"messages": [
		{
			"role": "user",
			"content": [
				{ "type": "text", "text": "List the deadlines in this contract." },
				{
					"type": "file",
					"file": {
						"filename": "contract.pdf",
						// A base64 data URL that names the MIME type.
						"file_data": "data:application/pdf;base64,JVBERi0xLjcK..."
					}
				}
			]
		}
	]
}
```

```jsonc tab="Responses"
{
	"model": "gpt-5.6-sol",
	"input": [
		{
			"role": "user",
			"content": [
				{ "type": "input_text", "text": "List the deadlines in this contract." },
				// The provider downloads the file. The gateway does not.
				{ "type": "input_file", "file_url": "https://example.com/contract.pdf" }
			]
		}
	]
}
```

Give each document exactly one source:

| Field       | Contents                                                     | Works on                                 |
| ----------- | ------------------------------------------------------------ | ---------------------------------------- |
| `file_data` | A base64 data URL, such as `data:application/pdf;base64,...` | Every deployment that accepts documents  |
| `file_url`  | An HTTP(S) URL                                               | Responses[^sources]                      |
| `file_id`   | A file that you uploaded to the provider                     | [BYOK](/docs/byok) credentials[^sources] |

If the data URL has no MIME type or uses `application/octet-stream`, `filename` must end in an
extension that the route accepts, unless the file is a [text file](#text-files).

## Text files

```jsonc
{
	"type": "input_file",
	"filename": "main.zig",
	// Any text type works, and so does no type at all.
	"file_data": "data:text/x-zig;base64,Y29uc3Qgc3RkID0gQGltcG9ydCgic3RkIik7"
}
```

Every deployment that reads plain text reads every
[text file](/docs/text-extraction#what-counts-as-a-text-file), such as source code, Markdown, CSV
and configuration files. Where the provider does not list the file's type or extension, the gateway
sends the file as `text/plain`, and the content and `filename` stay as they are.

A deployment that reads no text files needs [text extraction](/docs/text-extraction), which sends
the file as prompt text.

## Supported formats

Each catalog route lists the document types that it reads as `documentFormats`, and each
deployment lists its input types as `inputModalities`. Search the
[catalog](https://stogas.ai/catalog) to find them:

| Search                                  | Finds                        |
| --------------------------------------- | ---------------------------- |
| `deployment.inputModalities:image`      | Deployments that read images |
| `route.documentFormats.extensions:.pdf` | Routes that read PDFs        |

The provider can convert a document before the model reads it, so a model that reads only text can
still accept a PDF. The [provider pages](/docs/providers) list each provider's file rules.

## Allow or deny file types

Set `input.mediaTypes` in a policy to refuse attachments by type, such as to keep SVG images or
office documents away from a model:

```json title="Policy"
{
	"input": {
		"mediaTypes": {
			"allow": ["image/*", "application/pdf", "text/*"],
			"deny": ["image/svg+xml"]
		}
	}
}
```

- Each entry is a lowercase media type, such as `image/png`, or a class, such as `image/*`. A list
  holds up to 64 entries.
- An attachment passes when `allow` names its type and `deny` does not. Without `allow`, every type
  that `deny` does not name passes. An empty `allow` refuses every attachment.
- When several policies set lists, an attachment must pass each of them. A [rule](/docs/policies/rules)
  can set lists for some candidates only, and routing then leaves out the candidates that refuse an
  attachment.

The gateway reads the type from the data URL or `file_type`, and checks it against the start of the
content. A type whose files start with a fixed signature, such as PNG, JPEG, HEIC, PDF, MP3 or a
Word document, must show it, so other data cannot pass a list by declaring that type. Text formats
have no signature, so a client can send any text file as `text/plain`, and a list cannot tell one
text format from another. A `filename` never sets the type.

| Attachment                                                                        | Type the lists check                                                                       |
| --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| Inline data                                                                       | The declared type. With no type or `application/octet-stream`, the type the content shows. |
| Inline data whose content is another type, such as a PDF declared as `text/plain` | None. The request fails.                                                                   |
| `input_audio`                                                                     | `audio/mpeg` for `mp3`, otherwise `audio/` and the `format`                                |
| An image URL or file ID                                                           | Only `image/*`, because the gateway never downloads it                                     |
| A document URL or file ID                                                         | None                                                                                       |

An attachment whose type the lists cannot check is refused, so a list that names `image/png`
refuses an image URL. Send such a file inline with its media type.

A refusal fails the request with `attachment_unsupported`. The error's `param` names the attachment,
and its message gives the type, such as
`messages[0].content[1] is image/svg+xml, which input.mediaTypes refuses`.

## When no candidate reads a file

[Routing](/docs/policies/routing) leaves out each candidate that cannot read an attachment. This
uses none of the [fallbacks](/docs/policies/routing#retries-and-fallbacks). A candidate cannot read
an attachment when:

- Its deployment or route does not take the input type or the [source](#send-a-document). See
  [Supported formats](#supported-formats).
- The attachment is a `file_id`, and the candidate's credential is not [BYOK](/docs/byok).
- Its policy [refuses the attachment's type](#allow-or-deny-file-types).
- Its policy sets [ASCII-only input](/docs/pii-redaction#ascii-only-input) or
  [PII redaction](/docs/pii-redaction). These need text, so they refuse URLs, file IDs and files
  that the gateway does not [extract](/docs/text-extraction).

When no candidate is left that can read an attachment, the request fails at once with
`attachment_unsupported`, and `param` names the attachment. If a candidate that can read it left
for another reason, such as a disabled credential, the error gives that reason. If every attachment
has a candidate but no candidate reads them all, the error names them. Send them in separate
requests.

A file ID names a file in one provider account, so a request with a `file_id` also fails with
`attachment_unsupported` when more than one BYOK credential can serve it. Name the provider in the
model, such as `provider:openai gpt-5.6-sol`, or use a key with one credential for the provider.

## Limits

- URLs, file IDs and files other than UTF-8 text files reserve the deployment's full input limit
  in the [hold](/docs/usage#how-a-request-is-charged), because the gateway cannot count their
  tokens.
- Base64 and JSON encoding count toward the [128 MiB request limit](/docs/reference/security#limits).
  The provider applies its own file, page and size limits.
- Audio input (`input_audio` on Chat Completions) works only on deployments that list `audio` in
  `inputModalities`.
- Models return text, tool calls and citations. Image and audio output are not available.

[^sources]:
    Anthropic models also take `file_url` on Chat Completions, and do not take an image
    `file_id`. Claude that AWS or Google runs takes neither URLs nor file IDs, and Claude that
    Azure runs takes no file IDs.
