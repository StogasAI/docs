---
title: Tools
description: Let a model call your functions, or use web tools that the provider runs.
icon: Wrench
---

A request can give the model two kinds of tools:

- **Your tools** run in your application. `function` tools work on both endpoints and every
  provider. `custom` tools take free-form text input and work on Responses[^custom]. Some models
  also know a shell tool and a file editing tool of their provider[^provider-tools]. You pay only
  for tokens.
- **Hosted tools**, such as web search, run at the provider during the request. They can have a
  price per call.
- **Remote MCP servers** give the model the tools of a server that you choose. The provider calls
  them during the request.

## Call a function

<Steps>
<Step>

### Describe the function

```jsonc title="Chat Completions"
{
	"model": "claude-sonnet-5-5",
	"messages": [{ "role": "user", "content": "Is it raining in Lisbon?" }],
	"tools": [
		{
			"type": "function",
			"function": {
				"name": "get_weather",
				"description": "Current weather for a city.",
				"parameters": {
					"type": "object",
					"properties": { "city": { "type": "string" } },
					"required": ["city"]
				}
			}
		}
	]
}
```

Add `"strict": true` to a function to make the model's arguments always match its `parameters`.
Most models enforce it.[^strict] On Responses, some models make a function strict when you leave
`strict` out and its schema allows it. Send `"strict": false` to turn that off. With a model
that does not enforce it, check the tool call error rate in [Analytics](/docs/analytics).

</Step>
<Step>

### Run the call

The response has `finish_reason: "tool_calls"` and the calls in `message.tool_calls`. Run each call
in your application.

</Step>
<Step>

### Send the result

Send the conversation again, with the model's call and your result after it:

```jsonc
"messages": [
	{ "role": "user", "content": "Is it raining in Lisbon?" },
	{
		"role": "assistant",
		"tool_calls": [
			{
				"id": "call_1", // Copy the ID from the response.
				"type": "function",
				"function": { "name": "get_weather", "arguments": "{\"city\":\"Lisbon\"}" }
			}
		]
	},
	// The result must come right after the call.
	{ "role": "tool", "tool_call_id": "call_1", "content": "{\"rain\":false,\"temp_c\":21}" }
]
```

</Step>
</Steps>

On Responses, the call is a `function_call` output item, and you send the result as a
`function_call_output` input item with the same `call_id`. Its `output` is a string, or a list of
text, image and file parts ([Files in tool results](/docs/input-files#files-in-tool-results)).

Request records link each call to the request that sends its result by a
[hash of the call ID](/docs/request-records#tool-calls), so analytics shows how long your app took.

`tool_choice` accepts `auto`, `none`, `required` or a named function. Some models cannot be forced
to call a tool[^forced], and a request with `required` or a named function leaves their deployments
out. On some deployments the model can still call a tool under `none`, or write a call into its
text, most often after an earlier call. A request with tools and `none` goes only to deployments
whose `capabilities.toolChoiceNone` is true.

On Responses, an `additional_tools` input item can also declare tools, as Codex does for some
models. Its `tools` count as tools of the request on every provider, and a later declaration of a
tool replaces the earlier one.

## Group tools in namespaces

On Responses, a `namespace` tool groups your tools under one name:

```jsonc title="Responses"
{
	"model": "gpt-5.6-sol",
	"input": "Find customer 42.",
	"tools": [
		{
			"type": "namespace",
			"name": "crm",
			"description": "Tools for the customer database.",
			"tools": [
				{
					"type": "function",
					"name": "find_customer",
					"parameters": {
						"type": "object",
						"properties": { "id": { "type": "string" } },
						"required": ["id"]
					}
				}
			]
		}
	]
}
```

The call is a `function_call` item with `"namespace": "crm"` and `"name": "find_customer"`. Send it
back with both. Models without namespaces[^namespaces] get each tool as a function with a name such
as `crm__find_customer` and the namespace's description before its own. The gateway returns their
calls with your namespace and name, and a call in `input` must name a tool that `tools` declares in
its namespace.

- A namespace holds `function` and `custom` tools, with names of up to 128 letters, digits,
  underscores or hyphens. Tools in one namespace need different names, and so do namespaces.
- The tools of a namespace named `functions` are top-level tools, so their names must differ from
  the names of the other top-level tools.
- `tool_choice` can name only top-level tools.
- [Policies](#restrict-tools-with-a-policy) read a tool in a namespace by its own name.

## Tool search

On some models[^tool-search], a `tool_search` tool keeps tools with `defer_loading` out of the
input until the model searches for them:

```jsonc title="Responses"
{
	"model": "gpt-5.6-sol",
	"input": "Find customer 42.",
	"tools": [
		{
			"type": "namespace",
			"name": "crm",
			"description": "Tools for the customer database.",
			"tools": [
				{
					"type": "function",
					"name": "find_customer",
					"defer_loading": true,
					"parameters": {
						"type": "object",
						"properties": { "id": { "type": "string" } },
						"required": ["id"]
					}
				}
			]
		},
		{ "type": "tool_search" }
	]
}
```

The reply holds a `tool_search_call` and a `tool_search_output` that loads the tools, and then the
model's call. Send all of them back in `input` with the rest of the reply.

With `"execution": "client"`, your app runs the search. Give the tool a `description` and
`parameters` for the model. Answer its `tool_search_call` in the next request with the call and a
`tool_search_output` that names the same `call_id` and holds the tools to load:

```jsonc
"input": [
	{ "role": "user", "content": "Find customer 42." },
	{
		"type": "tool_search_call",
		"call_id": "call_1",
		"execution": "client",
		"arguments": { "goal": "Look up a customer" }
	},
	{
		"type": "tool_search_output",
		"call_id": "call_1",
		"execution": "client",
		"tools": [
			{
				"type": "namespace",
				"name": "crm",
				"description": "Tools for the customer database.",
				"tools": [{ "type": "function", "name": "find_customer", "defer_loading": true }]
			}
		]
	}
]
```

- A request takes one `tool_search` tool, and a deferred tool needs it.
- A `tool_search_output` loads `function`, `custom` and `namespace` tools, which the model then
  calls as tools of the request. Your app's search can load tools that `tools` does not declare.
- A search costs only its tokens.
- MCP tools cannot be deferred.

## Hosted tools

| Tool                 | Endpoint                             |
| -------------------- | ------------------------------------ |
| `web_search`         | Responses                            |
| `web_search_preview` | Responses                            |
| `web_search_options` | Chat Completions, search models only |
| `web_fetch`          | Responses                            |

[Compare providers](/docs/providers) shows which providers run each tool, and the
[catalog](https://stogas.ai/catalog) lists the hosted tools of each route. A request that lists a
hosted tool goes only to deployments that run it, even when `tool_choice` lets the model call no
tool. When no deployment for the request runs a tool, the gateway returns `400` with
`unsupported_tool`. For example, when only one of a provider's deployments of a model runs
`web_fetch`, a request for that provider and model with `web_fetch` goes to that deployment and
never to the others.

```jsonc title="Responses"
{
	"model": "gpt-5.6-sol",
	"input": "Summarize this week's Go release notes.",
	"tools": [{ "type": "web_search" }],
	"max_tool_calls": 3 // At most three searches. This also lowers the hold.
}
```

The gateway accepts only tool versions with a price in the catalog, and returns `400` for an
unknown version. Each provider's page lists its prices and versions.

### Send hosted calls back

On Responses, a reply returns each hosted call as a `web_search_call` or `web_fetch_call` item. Send
these items back in `input` with the rest of the reply. Each deployment gets only the calls that it
can read: calls of a tool that its route runs, in the form that its provider returns them[^replay].
The gateway leaves the other calls out and keeps the rest of the conversation, so a conversation can
move to another model.

### Domain filters

`web_search` and `web_fetch` take `filters.allowed_domains`, `filters.blocked_domains` or both:

```jsonc title="Responses"
{
	"model": "gpt-5.6-sol",
	"input": "What changed in the latest Go release?",
	"tools": [
		{
			"type": "web_search",
			"filters": {
				"allowed_domains": ["go.dev", "github.com"],
				"blocked_domains": ["gist.github.com"] // A subdomain of an allowed domain stays blocked.
			}
		}
	]
}
```

- Each entry is a bare domain, such as `go.dev`, and also covers its subdomains. A scheme, path or
  wildcard returns `400`.
- Some providers take only one of the lists in a tool[^lists]. `web_search_preview` takes no
  filters.
- The gateway checks every source, citation and fetched page in the response against the filters,
  and returns `502` instead of a response that breaks them.
- A block list covers only the domains it names. Copies of a site on other domains can still appear.

### Data handling of hosted tools

A hosted tool can send request content to services other than the model. A search or a fetch
can run in a place that the provider does not name, and a fetched site's owner can keep the URLs
that the tool fetches.
Your [routing policies](/docs/policies/routing) read a deployment's [data
handling](/docs/policies/routing-fields#data-handling) joined with that of each hosted tool that
the request lets the model call. The catalog shows each tool's data handling with its route. For
example, this filter keeps only deployments that process content in the US. A request that lets
the model call a `web_search` whose processing location is unknown then goes to none of that
route's deployments:

```json title="policy.json"
{
	"routing": {
		"filter": "'US' in deployment.dataHandling.processingWithin"
	}
}
```

`tool_choice: "none"` lets the model call no tool, and an `allowed_tools` choice only the tools that
it lists, so the other tools' data handling does not count. An [`mcp` tool](#your-data-and-the-server)
always counts. `request.hostedTools` lists the hosted
tools that the model may call, so a policy can also refuse a tool by name:

```json title="policy.json"
{
	"routing": {
		"filter": "!('web_fetch' in request.hostedTools)"
	}
}
```

### Holds for hosted tools

Hosted tools can make many calls in one request, so the [hold](/docs/usage#how-a-request-is-charged)
reserves for them:

- Without `max_tool_calls`, the hold covers ten calls of the most expensive hosted tool in the
  request, and the model decides how many calls it makes. `max_tool_calls` limits the calls, and a
  value under ten lowers the hold.
- The hold also covers 8,000 tokens of content for each call[^content], or a fetch's
  `max_content_tokens`. Larger results cost more than the hold.
- `tool_choice: "none"` turns hosted tools off, so they cost nothing.

The provider does not stop at the hold. Settlement charges the calls and tokens that the provider
reports, even when they are more than the hold.

## Remote MCP servers

```jsonc title="Responses"
{
	"model": "gpt-5.6-sol",
	"input": "Which pull requests wait for my review?",
	"tools": [
		{
			"type": "mcp",
			"server_label": "tracker", // Each server needs its own label.
			"server_url": "https://mcp.example.com/sse",
			"authorization": "<the server's token>",
			"allowed_tools": ["list_pull_requests"] // Optional. The model sees only these tools.
		}
	]
}
```

The provider connects to each server, lists its tools for the model and makes the calls that the
model asks for. Responses accepts `mcp` tools on the routes that run the `mcp` hosted tool in the
[catalog](https://stogas.ai/catalog)[^mcp]. `connector_id` or `tunnel_id` can name the server
instead of `server_url`. Two servers can offer tools with the same name, because each call names
its server.

<Steps>
<Step>

### Read the approval request

By default, each call waits for your approval. The response has an `mcp_approval_request` item
with the tool's name and arguments, and the call has not run.

</Step>
<Step>

### Send your decision

Send the request again with the response's output items after your input, and an
`mcp_approval_response` for each approval request:

```jsonc
"input": [
	{ "role": "user", "content": "Which pull requests wait for my review?" },
	// The output items of the response, unchanged.
	{ "type": "mcp_list_tools", "id": "mcpl_1", "server_label": "tracker", "tools": [ /* ... */ ] },
	{
		"type": "mcp_approval_request",
		"id": "mcpr_1",
		"server_label": "tracker",
		"name": "list_pull_requests",
		"arguments": "{\"state\":\"open\"}"
	},
	{ "type": "mcp_approval_response", "approval_request_id": "mcpr_1", "approve": true }
]
```

Keep the `mcp` tool in `tools`, with its `authorization`, because the provider keeps no copy of it.
The approved call runs, and the response has its `mcp_call` item. An approval whose call has not run
must answer an `mcp_approval_request` in the same input, from a server that `tools` declares, or
the request gets `400`.

</Step>
</Steps>

### Calls without approval

`require_approval: "never"` lets the provider call any tool of the server without asking. To skip
approval only for some tools, name them:

```jsonc
"require_approval": { "never": { "tool_names": ["list_pull_requests"] } }
```

A filter's `tool_names` must name at least one tool. `tool_choice` can select a server, as in
`{ "type": "mcp", "server_label": "tracker" }`, and an `allowed_tools` choice can list servers.

### Holds for MCP

A server decides how long its tool list and its results are, so the
[hold](/docs/usage#how-a-request-is-charged) reserves 8,000 input tokens for each of these:

- The tool list of each server in `tools`. A server whose `mcp_list_tools` item you send back in
  `input` adds none.
- Each `mcp_approval_response` with `approve: true` whose call has not run. A call has run when an
  `mcp_call` in the input names its `approval_request_id`, so the approvals of earlier turns that
  you send again add nothing.
- Ten calls when some tool runs without approval, or `max_tool_calls` if you set it. Hosted tools
  share that limit, so a request that also searches the web reserves these calls once.

`tool_choice: "none"`, or a choice of another tool, leaves calls without approval out of the hold.
Tool lists still count, because the provider fetches them whatever `tool_choice` says, and so do
approved calls, because they answer earlier requests. You pay for the tokens of tool lists and
results, with no price per call. Settlement charges what the provider reports, even when it is more
than the hold.

### Your data and the server

- The server receives the arguments that the model writes, and what it returns goes to the model.
  [Redaction](/docs/pii-redaction) and [policies](/docs/policies) cover what you send, not what
  the server returns.
- Your request names the server, so the catalog states every data handling fact of the `mcp` tool
  as unknown. A [routing filter](/docs/policies/routing) on data handling refuses every request
  that lists an `mcp` tool, whatever `tool_choice` says.
- To use a server under such a policy, connect to it in your application and pass its tools as
  [functions](#call-a-function). Redaction, [exports](/docs/export) and policies then cover its
  tools and results as they cover your other tools.
- The gateway sends `authorization`, `headers` and `server_url` to the provider unchanged, and
  redaction skips the server's settings. The response returns the tool as the provider does, with
  `<redacted>` for `authorization` and for each header value.
- Exports and provider error messages show `[omitted]` for those values. An export keeps only the
  scheme, host and port of `server_url`, because a URL can carry a token too.
- With redaction on, the arguments of an `mcp_approval_request` that you send back are redacted
  too, so the approved call runs with the redacted arguments.
- The gateway returns `502` instead of a response with an item from a server that the request did
  not declare, or with a call from a server that `tool_choice` leaves out.

## Restrict tools with a policy

A [routing filter](/docs/policies/routing) can read the tools that a request lets the model call. A
request that the filter refuses gets `model_unavailable`. This policy allows only one MCP server
and one connector:

```json title="policy.json"
{
	"routing": {
		"filter": "request.mcpServers.all(server, server in ['mcp.example.com/mcp', 'connector:connector_googledrive'])"
	}
}
```

`request.mcpServers` names each server by one of these:

| The tool sets  | Name                                                                      |
| -------------- | ------------------------------------------------------------------------- |
| `server_url`   | The host and the path, such as `mcp.example.com/mcp`                      |
| `connector_id` | `connector:` and the ID in lowercase, such as `connector:connector_gmail` |
| `tunnel_id`    | `tunnel:` and the ID in lowercase                                         |

- The host is in lowercase, and the path is as the request wrote it. A URL without a path reads as
  `mcp.example.com/`.
- A port shows only when it is not the default of `https` or `http`, as in
  `mcp.example.com:8443/mcp`. The query string is left out.
- One host can serve many servers, each at its own path, so a name holds the path. To allow every
  server of a host, compare the start of the name: `server.startsWith('mcp.example.com/')`.

This one refuses one tool of a server. `request.mcpTools` names a tool by its server, `#` and the
tool's name. A server whose `allowed_tools` names no tools reads as `mcp.example.com/mcp#*`,
because the model can call any of its tools, so the filter refuses that too:

```json title="policy.json"
{
	"routing": {
		"filter": "!request.mcpTools.exists(tool, tool in ['mcp.example.com/mcp#*', 'mcp.example.com/mcp#delete_repo'])"
	}
}
```

This one lets only one server run calls without your application's approval:

```json title="policy.json"
{
	"routing": {
		"filter": "request.mcpServersWithoutApproval.all(server, server == 'mcp.example.com/mcp')"
	}
}
```

| Filter                                                                                   | Effect                                                             |
| ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| `size(request.clientTools) == 0`                                                         | Refuses every tool that your application runs                      |
| `!('mcp' in request.hostedTools)`                                                        | Refuses remote MCP servers                                         |
| `size(request.mcpServersWithoutApproval) == 0`                                           | Refuses MCP calls that run without approval                        |
| `!('run_shell' in request.clientTools)`                                                  | Refuses requests that let the model call `run_shell`               |
| `request.clientTools.all(tool, tool.startsWith('crm_'))`                                 | Allows only tools whose names start with `crm_`                    |
| `!request.clientTools.exists(tool, tool.matches('^(run\|exec)_.*$'))`                    | Refuses tools whose names match a regular expression               |
| `request.mcpServers.all(server, server.startsWith('mcp.example.com/'))`                  | Allows only the servers of one host                                |
| `request.mcpTools.all(tool, tool.startsWith('mcp.example.com/mcp#get_'))`                | Allows only the tools of one server whose names start with `get_`  |
| `!request.mcpTools.exists(tool, tool.endsWith('#*') \|\| tool.endsWith('#delete_repo'))` | Refuses a server that offers `delete_repo` or every tool           |
| `size(request.hostedTools) == 0`                                                         | Refuses hosted tools, remote MCP servers included                  |
| `!(provider.id == 'anthropic' && size(request.hostedTools) > 0)`                         | Sends requests with hosted tools to providers other than Anthropic |

- A filter compares names with `==`, `in`, `startsWith`, `endsWith`, `contains` and `matches`.
  `matches` takes an [RE2](https://github.com/google/re2/wiki/Syntax) regular expression and finds
  it anywhere in a name, so begin it with `^` and end it with `$` to match the whole name.
- List the MCP servers and tools to allow rather than those to refuse, because one server can have
  many addresses and a list of refused tools must also refuse `#*`.
- A `server_url` that the gateway cannot name returns `400`: one with a backslash, a `.` or `..`
  path segment, an empty path segment, or an encoded slash.
- Where one address serves every account and the token selects the account, a filter cannot tell
  one account from another.
- `tool_choice: "none"` empties `request.clientTools` and takes web tools out of
  `request.hostedTools`, because the model can call none of them. A choice of one function still
  counts every function.
- An `mcp` tool counts whenever the request lists it, whatever `tool_choice` says, because the
  provider can connect to a listed server before the model chooses a tool.
- `request.clientTools` lists the tools of a namespace by their own names, without the namespace,
  and the tools that a [tool search](#tool-search) in `input` loaded.
- A provider's shell or file editing tool[^provider-tools] counts under its name: `shell`,
  `apply_patch`, `bash` or `str_replace_based_edit_tool`.
- Your application names its tools, so a filter on `request.clientTools` cannot stop an
  application that gives a tool another name.
- An MCP server names its tools too, so a filter on `request.mcpTools` holds only while the server
  keeps those names. Allow the servers that you trust with `request.mcpServers`, because the
  provider connects only to the servers that the request lists.

## Unavailable tools

These tools return `400` before the gateway calls a provider:

- Remote MCP servers on routes that do not run the `mcp` hosted tool
- File search and hosted retrieval
- Code interpreter, hosted shell and standalone code execution
- Computer use and image generation
- Provider memory

[^custom]: On OpenAI models, at [OpenAI](/docs/providers/openai#tools) and [Azure](/docs/providers/azure).

[^provider-tools]:
    [OpenAI's `shell` and `apply_patch`](/docs/providers/openai#shell-and-apply_patch), and
    [Anthropic's bash and text editor](/docs/providers/anthropic#bash-and-text-editor).

[^forced]: Some Claude models. See [Anthropic](/docs/providers/anthropic#tools).

[^strict]:
    [Gemini on Google Cloud](/docs/providers/google-cloud#gemini) does not enforce it, and Claude
    on Google's Agent Platform also needs
    [your organization policy to allow it](/docs/providers/google-cloud#differences-from-anthropic).

[^namespaces]:
    [Claude](/docs/providers/anthropic#tools), and deployments that take Responses
    [through Chat Completions](/docs/providers#responses-through-chat-completions).

[^lists]: [Anthropic](/docs/providers/anthropic#tools) returns `400` for both lists in one tool.

[^tool-search]: [OpenAI](/docs/providers/openai#tools). Other models return `400` for deferred tools.

[^replay]: [Claude](/docs/providers/anthropic#tools) reads a search again only with the encrypted content of its results.

[^mcp]: [OpenAI](/docs/providers/openai#tools) runs remote MCP servers.

[^content]:
    [Claude](/docs/providers/anthropic#tools) reads every earlier result again in each later step
    of its tool loop, so its hold covers each step with the content of every call before it. With
    caching on, the content that a step reads again is held at the cache-read rate. A search model
    on Chat Completions reserves its whole input limit.
