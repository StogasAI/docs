---
title: How gateway verification works
description: How a Stogas client decides which gateways it can safely use.
---

Before sending a protected request, a Stogas client downloads a public trust bundle. It verifies
the bundle locally and accepts only gateways that prove they are running approved software inside
genuine confidential-computing hardware.

```text
https://evidence.stogas.ai/bundles/latest.json
https://evidence2.stogas.ai/bundles/latest.json
```

The first endpoint is delivered by Cloudflare from R2. The second is an independent AWS
CloudFront distribution backed by a private S3 bucket. Official managed clients choose one at
random for each refresh and try the other after a network, HTTP, verification, or sequence
regression failure.

Neither CDN is trusted. After retrieval, verification is entirely local: the verifier does not
contact GitHub, AMD, Sigstore, drand, or Stogas while deciding whether to accept the bytes.

## Independent delivery

Each bundle is written to both object stores. A destination advances its `latest.json` alias only
after accepting that bundle's immutable version. A transient failure at one store does not prevent
the other from publishing, and the next one-minute cycle repairs freshness with a new bundle.

The mutable alias normally remains at an edge for no more than five seconds. During an origin
error, a CDN may serve its last response for at most the remainder of one publication interval.
The verifier still applies the complete cryptographic policy and retains an earlier accepted bundle
only until its authenticated expiry.

## What the trust bundle proves

The bundle contains:

- approved gateway releases and their build records;
- AMD certificate chains and SEV-SNP reports for each gateway;
- an explicit AMD processor profile binding report CPUID, the generation-specific hardware identifier and TCB layout, and a pinned product root; unknown processor generations fail closed;
- recent drand evidence;
- TLS, response-signing, and E2EE public keys created by each gateway; and
- an expiration time.

The bundle has no outer signature. Its body SHA-256 identifies the exact bytes and detects
corruption, while each release, node, certificate, and drand claim verifies to its own embedded
cryptographic root.

The verifier returns the gateways that are safe to use as `nodes`. Older or unusable records may
appear as `excluded_nodes`, but they never authorize a connection.

## Freshness rules

The verifier applies three separate time limits:

| Check            | Rule                                                                        | Why it matters                                            |
| ---------------- | --------------------------------------------------------------------------- | --------------------------------------------------------- |
| Bundle creation  | No more than three minutes behind or one minute ahead of the client's clock | Rejects a delayed, replayed, or implausibly future bundle |
| Gateway evidence | The drand round is no more than two minutes older than bundle creation      | Requires recent evidence from every accepted gateway      |
| Bundle expiry    | No more than 15 minutes after creation                                      | Sets a hard deadline for an accepted bundle               |

Every accepted gateway certificate and required AMD certificate or revocation list remains valid
through the bundle's complete actual lifetime. That lifetime is at most 15 minutes and may end
sooner at one of those validity deadlines. It does not mean clients should wait 15 minutes before
checking for an update.

## Keeping verification current

Managed transports check every minute by default and make another attempt before the active bundle
expires. Applications can choose an interval from 1 through 840 seconds or request an immediate
refresh. More frequent polling normally provides newer evidence without changing any verification
or expiry rule.

If the downloaded bytes have not changed, the transport reuses the existing verified result. A
failed update can keep using the last accepted bundle only until that bundle expires.

## Verifying a response later

Every response can include a compact receipt:

- non-streaming responses use `X-Stogas-Proof`;
- streaming responses end with a `stogas.proof` SSE event.

The receipt identifies the gateway and signs hashes of the exact request and response, the API
route, the selected model route, current freshness evidence, and the encrypted-connection transcript
when E2EE is used.

Reuse the verifier that accepted the active bundle:

```ts
const receipt = verifier.verify_response_proof(
	proofBytes,
	requestBytes,
	responseBytes,
	e2eeTranscriptSHA256
);
```

The verifier calculates the request and response hashes again from the bytes you provide. For an
older response, download its node record from the Trust Center and use
`verify_historical_response_proof`. When E2EE is enabled, also keep the locally calculated
`X-Stogas-E2EE-Transcript-SHA256` response header.
