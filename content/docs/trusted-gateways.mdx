---
title: Trusted Gateways
description: How clients discover and verify the gateways they can trust.
---

Stogas publishes one public JSON snapshot containing every proof a client needs to authorize the current gateway fleet. A new snapshot is normally published every minute.

```text
https://evidence.stogas.ai/bundles/latest.json
```

Verification is local and networkless after this fetch. The verifier does not contact GitHub, AMD, Sigstore, or drand.

## What the snapshot contains

- Approved gateway releases and their independent build evidence.
- AMD certificate chains and SEV-SNP reports for admitted gateways.
- Fresh drand evidence.
- TLS, response-signing, and E2EE public keys generated inside each guest.
- One absolute expiration time.

The verified result separates usable `nodes` from older `excluded_nodes`. Excluded records may remain in the publication for recovery, but they never authorize a connection.

## Three independent clocks

| Clock                    | Fixed policy                                                             | Purpose                                                 |
| ------------------------ | ------------------------------------------------------------------------ | ------------------------------------------------------- |
| Snapshot anti-replay     | Creation is no more than three minutes behind the verifier's wall clock  | Rejects delayed or replayed publications                |
| Gateway authorization    | The drand round is no more than two minutes older than snapshot creation | Keeps every trusted node's drand-backed quote fresh     |
| Accepted snapshot expiry | Expiry is no more than 15 minutes after creation                         | Places a hard deadline on an already accepted trust set |

These are separate comparisons. Gateway eligibility never uses fetch time or verifier capture time: every verifier compares the authenticated drand round time directly with the authenticated snapshot creation time. The verifier clock is used only for snapshot anti-replay, future-skew, and expiry checks. Holding a snapshot longer does not weaken the node rule.

<Callout type="info">
	The 15-minute lifetime supports safe fleet rollouts and temporary publication failures. It does
	not mean clients should wait 15 minutes between normal refreshes.
</Callout>

## Refresh behavior

Managed transports check every five minutes by default. The supported scheduled interval is any whole number from 1 through 840 seconds. An application may also request an immediate refresh at any time.

When the fetched bytes are unchanged, the transport reuses the active verification instead of repeating cryptography. A failed fetch leaves the last accepted snapshot active only until its authenticated expiry, and the transport makes an additional replacement attempt before that deadline.

## Verify a response later

Every response can carry one compact receipt:

- non-streaming responses use `X-Stogas-Proof`;
- streaming responses end with a `stogas.proof` SSE event.

The receipt signs hashes of the exact request and response bytes, request ID and endpoint, resolved catalog route, current drand round, and the E2EE transcript when used. It also identifies the attested signing key.

Reuse the SDK verifier that accepted the current snapshot:

```ts
const receipt = verifier.verify_response_proof(
	proofBytes,
	requestBytes,
	responseBytes,
	e2eeTranscriptSHA256
);
```

Successful verification returns only `request_id`, `node_id`, `request_sha256`, `response_sha256`, and `proof_hash`. The hashes are calculated again from the exact caller-supplied bytes; they are not trusted merely because the gateway placed them in the receipt.

For an older response, download the matching node record from the Trust Center and call `verify_historical_response_proof`. For E2EE, preserve the locally computed `X-Stogas-E2EE-Transcript-SHA256` response header. The verifier checks the complete historical release, hardware, drand, and key-binding chain before accepting the receipt.
