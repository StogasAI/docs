---
title: How gateway verification works
description: How a Stogas client decides which gateways it can safely use.
---

Before sending a protected request, a Stogas client downloads a public trust bundle. The client
checks the bundle locally and accepts only gateways that prove they are running approved software
inside genuine confidential-computing hardware.

```text
https://evidence.stogas.ai/bundles/latest.json
```

After the download, verification is local. The verifier does not contact GitHub, AMD, Sigstore, or
drand while checking the bundle.

## What the trust bundle proves

The bundle contains:

- approved gateway releases and their build records;
- AMD certificate chains and SEV-SNP reports for each gateway;
- recent drand evidence;
- TLS, response-signing, and E2EE public keys created by each gateway; and
- an expiration time.

The verifier returns the gateways that are safe to use as `nodes`. Older or unusable records may
appear as `excluded_nodes`, but they never authorize a connection.

## Freshness rules

The verifier applies three separate time limits:

| Check | Rule | Why it matters |
| --- | --- | --- |
| Bundle creation | No more than three minutes behind the client's clock | Rejects a delayed or replayed bundle |
| Gateway evidence | The drand round is no more than two minutes older than bundle creation | Requires recent evidence from every accepted gateway |
| Bundle expiry | No more than 15 minutes after creation | Sets a hard deadline for an accepted bundle |

The 15-minute lifetime allows safe gateway updates and short publication failures. It does not mean
clients should wait 15 minutes before checking for an update.

## Keeping verification current

Managed transports check every five minutes by default and make another attempt before the active
bundle expires. Applications can choose an interval from 1 through 840 seconds or request an
immediate refresh.

If the downloaded bytes have not changed, the transport reuses the existing verified result. A
failed update can keep using the last accepted bundle only until that bundle expires.

## Verifying a response later

Every response can include a compact receipt:

- non-streaming responses use `X-Stogas-Proof`;
- streaming responses end with a `stogas.proof` SSE event.

The receipt identifies the gateway and signs hashes of the exact request and response, the API
route, the selected model route, current freshness evidence, and the encrypted-connection transcript
when E2EE is used.

Reuse the verifier that accepted the active bundle:

```ts
const receipt = verifier.verify_response_proof(
	proofBytes,
	requestBytes,
	responseBytes,
	e2eeTranscriptSHA256
);
```

The verifier calculates the request and response hashes again from the bytes you provide. For an
older response, download its node record from the Trust Center and use
`verify_historical_response_proof`. When E2EE is enabled, also keep the locally calculated
`X-Stogas-E2EE-Transcript-SHA256` response header.
