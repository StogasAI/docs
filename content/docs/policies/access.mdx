Every resource that applies to a request must be enabled and unexpired. Enabled state and
expiration are settings of the resource. Weekly periods, networks, countries and connection modes
are in its policy, under `access.schedule`, `access.networks`, `access.countries` and
`access.transports`.

## Enable or disable access

A disabled resource, or a disabled parent, blocks new requests, and requests that are running
continue.

## Blocked requests

A blocked request fails with `403` and the code of the resource that blocks it, such as
`folder_disabled` or `grant_expired`. When several resources block it, the code names the first of
the organization, folder, grant, role, member and key. A resource that is both disabled and expired
reports that it expired. A key's status in the dashboard names the same resource, and so does
`denial` in the [dashboard API](/docs/reference/dashboard/api-keys/getApiKey).

## Set an expiration

Set an expiration time on a key, grant or other resource, such as `2026-12-01T00:00:00Z`. From
that time, new requests are blocked and requests that are running continue. The earliest
expiration of every resource that applies wins, so removing a key's expiration does not remove its
grant's.

### Expiration or a rule on `request.time`

A [conditional rule](/docs/policies/rules#conditional-rules) can also change requests from a set
time, because its condition can read `request.time`. From December 1, this rule makes requests skip
OpenAI:

```json title="policy.json"
{
	"rules": {
		"leave_openai": {
			"when": "request.time >= timestamp('2026-12-01T00:00:00Z')",
			"routing": { "filter": "provider.id != 'openai'" }
		}
	}
}
```

Use an expiration when everything under a resource should stop, and a rule when only some requests
or deployments should change:

|                                         | Expiration                                  | Rule on `request.time`                                                             |
| --------------------------------------- | ------------------------------------------- | ---------------------------------------------------------------------------------- |
| Blocks                                  | Every request under the resource            | Only the requests and deployments that it matches                                  |
| Shown                                   | With the resource in the dashboard          | Only in the policy                                                                 |
| Saving                                  | Adds no policy version                      | Adds a policy version, which request logs record                                   |
| [Delegation](/docs/policies/delegation) | Does not apply                              | The scope must be allowed to save the rule's sections, such as `routing.filter`    |
| Error                                   | `key_expired`, `grant_expired` and the like | The error of the rule's settings, such as `schedule_denied` or `model_unavailable` |

## Weekly periods

This policy accepts requests only during business hours in Paris, except a lunch break:

```json title="policy.json"
{
	"access": {
		"schedule": {
			"allow": [
				{
					"days": ["mon", "tue", "wed", "thu", "fri"],
					"start": "09:00",
					"end": "18:00",
					"timeZone": "Europe/Paris"
				}
			],
			"deny": [
				{
					"days": ["mon", "tue", "wed", "thu", "fri"],
					"start": "12:00",
					"end": "13:00",
					"timeZone": "Europe/Paris"
				}
			]
		}
	}
}
```

| List    | Effect                                                            |
| ------- | ----------------------------------------------------------------- |
| `allow` | Only requests in one of these periods pass.                       |
| `deny`  | Requests in these periods fail, even when `allow` holds them.     |

Use lowercase day names: `mon`, `tue`, `wed`, `thu`, `fri`, `sat`, and `sun`. Every field is
required. The start is included and the end is excluded, so the example accepts requests at 13:00
if all other policies allow them. Use `00:00` to `24:00` for an entire day.

## Overnight periods

A period cannot cross midnight. Split Friday 20:00 through Saturday 08:00 into two entries:

```json title="policy.json"
{
	"access": {
		"schedule": {
			"deny": [
				{
					"days": ["fri"],
					"start": "20:00",
					"end": "24:00",
					"timeZone": "UTC"
				},
				{
					"days": ["sat"],
					"start": "00:00",
					"end": "08:00",
					"timeZone": "UTC"
				}
			]
		}
	}
}
```

The second entry uses the following day. Equal start and end times are invalid and do not mean
all day.

## Daylight saving time

IANA time zones follow daylight saving time. A local hour that repeats is in a period both times,
and a local hour that is skipped never occurs. Use `UTC` for a schedule that does not shift.

## How periods combine

A request must fall in a period of every `allow` list and in no `deny` period of the policies that
apply, so two `allow` lists that share no time block every request. A refused request fails with
`403 schedule_denied`. A schedule with an empty `deny` list replaces default periods only. A
permitted [request policy](/docs/policies/request-policies) can add periods.

A period in a [conditional rule](/docs/policies/rules#conditional-rules) or a credential's policy
blocks only the deployments and credentials it applies to. The gateway tries the others, and fails
with `schedule_denied` when none remain. If a filter or list also removes a candidate, or the
candidate cannot read an [attachment](/docs/input-files#when-no-candidate-reads-a-file), the error
gives that reason instead.

## Networks

This policy accepts requests only from one address, two ranges and the onion service, except one
part of the first range:

```json title="policy.json"
{
	"access": {
		"networks": {
			"allow": ["203.0.113.7", "198.51.100.0/24", "2001:db8:5::/48", "onion"],
			"deny": ["198.51.100.128/25"]
		}
	}
}
```

This one accepts every network except Tor exit relays, VPN and hosting providers, and one
autonomous system:

```json title="policy.json"
{
	"access": {
		"networks": { "deny": ["tor", "vpn", "hosting", "AS64496"] }
	}
}
```

| List    | Effect                                                            |
| ------- | ----------------------------------------------------------------- |
| `allow` | Only requests from these networks pass.                           |
| `deny`  | Requests from these networks fail, even where `allow` holds them. |

| Entry                        | Matches                                                                             |
| ---------------------------- | ----------------------------------------------------------------------------------- |
| `203.0.113.7`, `2001:db8::7` | One IPv4 or IPv6 address.                                                           |
| `198.51.100.0/24`            | A CIDR range.                                                                       |
| `onion`                      | Requests to the [onion address](/docs/sdk-overview#connect-through-a-proxy-or-tor). |
| `AS64496`                    | The addresses of an autonomous system.                                              |
| `tor`                        | Tor exit relays.                                                                    |
| `vpn`                        | The autonomous systems of VPN providers.                                            |
| `hosting`                    | The autonomous systems of hosting, cloud and data center providers.                 |

Both lists take every entry. Anyone can rent a server in a cloud provider's autonomous system, so
an `allow` list of your own addresses, ranges or autonomous system limits where a stolen key works
more than an `allow` list of `hosting`.

- A range starts at its first address, such as `198.51.100.0/24`, and an IPv4 address takes its
  IPv4 form, not `::ffff:198.51.100.7`.
- The gateway reads the address from the connection, never from headers such as
  `X-Forwarded-For`. For a server behind a NAT gateway or proxy, list the address that the NAT
  gateway or proxy sends from.
- The API accepts connections over IPv4 only, so your requests come from an IPv4 address even on
  a network with IPv6.
- Requests to the onion address have no client address, so only `onion` matches them. `tor`
  refuses Tor exit relays and leaves the onion service open, and an `allow` list without `onion`
  refuses it.
- `tor` follows the Tor Project's list of exit relays, which the gateway reads again every hour.
  AS numbers come from [DB-IP](https://db-ip.com)'s monthly data. `vpn` and `hosting` are the
  autonomous systems that [X4BNet's lists](https://github.com/X4BNet/lists_vpn) name, except
  AS13335, AS20940, AS36183 and AS54113, through which iCloud Private Relay carries people's
  traffic. Many VPN services rent servers from hosting providers, so `hosting` refuses more of them
  than `vpn` does.
- A refused request fails with `403 network_denied`, and the message names the address that the
  gateway saw and why, such as `Request is not allowed from 203.0.113.7, a Tor exit relay`. An
  address that you allow, or remove from `deny`, applies
  [within three minutes](/docs/policies/scopes#when-changes-take-effect).
- A list can hold as many entries as the [policy size](/docs/policies/editing#document-rules)
  allows. To follow a published list of ranges, such as a cloud provider's, save the policy again
  through the [dashboard API](/docs/reference/dashboard) when the list changes.
- A policy whose `deny` holds every network of its `allow` cannot be saved. Disable the resource
  to block every request.

## Countries

This policy accepts requests only from the European Union, Switzerland and the United Kingdom:

```json title="policy.json"
{
	"access": {
		"countries": { "allow": ["eu", "CH", "GB"] }
	}
}
```

- List a country by its uppercase ISO 3166-1 alpha-2 code, such as `DE`, `GB` for the United
  Kingdom or `XK` for Kosovo. List a region by its lowercase ID, such as `eu`, `europe` or `apac`,
  for every country that it covers. A [place's page](https://stogas.ai/locations/eu) shows the
  countries of a region.
- The gateway finds the country of the address that it reads from the connection in
  [DB-IP](https://db-ip.com)'s monthly data. A VPN, proxy or Tor exit relay has the country of its
  own address, so add `"networks": { "deny": ["tor", "vpn", "hosting"] }` to refuse requests that
  hide where they come from.
- Requests to the onion address, and addresses that DB-IP places in no country, are in no country:
  an `allow` list refuses them and a `deny` list accepts them.
- A refused request fails with `403 country_denied`, and the message names the address and its
  country, such as `Request is not allowed from 203.0.113.7 in RU`.
- A policy whose `deny` holds every country of its `allow` cannot be saved.

## How networks and countries combine

The client's address must be in every `allow` list and in no `deny` list of the policies that
apply, for networks and for countries. Two `allow` lists that share no network or country block
every request, and no `allow` list takes back a network or country that another policy denies.

A [default rule](/docs/policies/rules#defaults) can list networks or countries, and they apply
until a required policy sets `access.networks` or `access.countries`. To replace them without a
restriction, set an empty `deny` list: `{ "deny": [] }`.

Networks and countries in a [conditional rule](/docs/policies/rules#conditional-rules) or a
credential's policy block only the deployments and credentials it applies to. The gateway tries the
others, and fails with `network_denied` or `country_denied` when none remain.

## Connection modes

This policy refuses requests that the [SDK or CLI](/docs/connection-modes) does not protect:

```json title="policy.json"
{
	"access": {
		"transports": { "deny": ["https"] }
	}
}
```

| Mode           | Requests                                                                        |
| -------------- | ------------------------------------------------------------------------------- |
| `https`        | Ordinary HTTPS, such as an OpenAI client that sends to the API without the SDK. |
| `attested_tls` | [Attested TLS](/docs/connection-modes#attested-tls).                            |
| `e2ee`         | [E2EE over HTTPS](/docs/connection-modes#e2ee-over-https).                      |

`allow` and `deny` work as they do for [networks](#networks): a request must use a mode that
`allow` lists, when the policy has an `allow` list, and no mode that `deny` lists.

- The policy stops clients that send requests without the SDK or CLI, such as a script that a
  member wrote with an OpenAI client. A refused request fails with `403 transport_denied` before it
  reaches a provider, and the message names the mode that the gateway saw.
- The gateway sees the mode of a request, not whether the client checked the gateway's evidence.
  Someone who intercepts a request can send it on in any mode, so only the check in your client
  protects a request. The SDK and CLI always check, and never fall back to ordinary HTTPS.
- A mode that you allow, or remove from `deny`, applies
  [within three minutes](/docs/policies/scopes#when-changes-take-effect).
- [Request history](/docs/analytics) shows the mode of each request, so you can find the keys
  that still use ordinary HTTPS before you deny it.
- A policy whose `deny` holds every mode of its `allow` cannot be saved. Disable the resource to
  block every request.

## How connection modes combine

A request must use a mode in every `allow` list and in no `deny` list of the policies that apply.
Two `allow` lists that share no mode block every request.

A [default rule](/docs/policies/rules#defaults) can list modes, and they apply until a required
policy sets `access.transports`. To replace them without a restriction, set an empty `deny` list:
`{ "deny": [] }`.

Modes in a [conditional rule](/docs/policies/rules#conditional-rules) or a credential's policy
block only the deployments and credentials it applies to. The gateway tries the others, and fails
with `transport_denied` when none remain.

## Timestamps and time zones

`expiresAt` and recurring `anchor` values are ISO 8601 timestamps with `Z` or an explicit offset
in years 1 to 9999 UTC, for example `2026-12-01T00:00:00Z` or `2026-12-01T09:00:00+09:00`. Local
times without an offset are invalid. Saved timestamps are normalized to UTC with millisecond
precision.

`timeZone` accepts `UTC` or an IANA name with its exact capitalization, such as `America/New_York`
or `Europe/Berlin`, up to 64 characters. Abbreviations such as `CET` and offsets such as `+05` are
invalid. The timestamp's offset identifies an instant, and the time zone determines the local
schedule and its daylight-saving rules.
