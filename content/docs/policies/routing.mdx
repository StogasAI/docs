A **candidate** is one deployment with one of your provider credentials. For each request, the gateway:

1. Starts with the candidates that can serve the request's `model`, interface, service tier,
   reasoning mode and output limit.
2. Removes the candidates that `allowedCatalogNodes` or `filter` exclude, and those that cannot
   read the request's [images and files](/docs/input-files#when-no-candidate-reads-a-file).
3. Puts the rest in [order](#ordering) and sends the request to the first.

```jsonc title="policy.json"
{
	"routing": {
		"allowedCatalogNodes": { "providers": ["openai", "chutes"] },
		"filter": "deployment.dataHandling.trainingUse == false", // Providers that do not train on prompts.
		"sort": [{ "by": "deployment.pricing.output_tokens.per_mill_tokens", "direction": "asc" }]
	}
}
```

Filter on what you require, then sort by what you prefer. For example, require zero data retention
and sort by price, instead of writing a filter that matches exactly one deployment. Filters and
sorts are [expressions](/docs/policies/expressions) over the fields in the
[field reference](/docs/policies/routing-fields).

## When no deployment fits

| Error                                     | Cause                                                                                                  | Fix                                                                       |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------- |
| `model_unavailable`                       | No candidate is left.                                                                                  | Check the model, the key's credentials and the key's **Combined policy**. |
| `model_ambiguous`, `deployment_ambiguous` | The [order](#ties) leaves a tie among the candidates that the request would try.                       | Name a model, or add a sort criterion. The error names the tied IDs.      |
| `model_retired`                           | What the `model` field selects retired. The error gives the date unless the provider retired it early. | Choose another model.                                                     |
| `attachment_unsupported`                  | No candidate can read an attachment, named by `param`.                                                 | See [Images and files](/docs/input-files#when-no-candidate-reads-a-file). |

Filters and lists from every policy apply together, so an OpenAI-only policy and a Chutes-only
policy leave no candidate. Sending the request again does not help, and a policy cannot widen the
request's `model`. A [routing simulation](/docs/policies/editing#simulate-routing) shows the
candidates that remain with a draft.

## Allowed catalog nodes

`allowedCatalogNodes` takes lists of catalog IDs: `authors`, `models`, `deployments`, `routes` and
`providers`.

- A candidate must match every list. Lists from several policies intersect.
- Use exact IDs. Names, aliases and wildcards do not match, and IDs that are not in the current
  catalog match nothing.
- `"providers": []` allows no provider. `"allowedCatalogNodes": {}` replaces default lists only.

## Ordering

The gateway tries candidates in the order that `sort` gives. Each criterion orders the candidates
that the criteria before it leave tied:

```json title="Prefer two deployments, then the cheapest"
{
	"routing": {
		"sort": [
			{ "deployments": ["openai-gpt-5.6-sol", "anthropic-claude-sonnet-4-6"] },
			{ "by": "blended_price(3, 1)" }
		]
	}
}
```

A criterion is one of these:

| Criterion                                                                                                                    | Orders candidates by                                                                                        |
| ---------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `{ "by": "<expression>", "direction": "asc" }`                                                                               | The value of an [expression](/docs/policies/expressions). `direction` is `asc` or `desc`, `asc` by default. |
| `{ "authors": [...] }`, `{ "models": [...] }`, `{ "deployments": [...] }`, `{ "routes": [...] }` or `{ "providers": [...] }` | Their place in the list of catalog IDs. Candidates that are not listed come last.                           |

- A policy can have up to four criteria. Each list kind can appear once per policy, and a list takes
  no `direction`.
- A list skips IDs that the request cannot use. It never adds a candidate that the request's
  `model`, filters, allowed lists or credentials exclude.
- `order`, an older form, is a `deployments` list at the start of the policy's `sort`. It counts
  toward the four criteria, and a policy that sets it cannot also set a `deployments` list.
- The credentials of one deployment stay together, in the order that the key assigns them. The
  [fallbacks](#retries-and-fallbacks) follow the same order.

### Default order

A new organization's policy starts with this [default rule](/docs/policies/rules#defaults):

```json title="Organization policy"
{
	"rules": {
		"default_order": {
			"mode": "default",
			"routing": {
				"sort": [
					{ "by": "model.releaseDate", "direction": "desc" },
					{ "by": "blended_price(3, 1)" },
					{ "by": "deployment.id" }
				]
			}
		}
	}
}
```

- A [group](/docs/models#groups) such as `claude` reaches its newest model, and a request without a
  model reaches the newest model that the key can use.
- Among the deployments of one model, the cheapest comes first. When prices are equal, the
  deployment whose ID sorts first comes first, so requests keep reaching the same provider and its
  prompt cache.
- The criteria of every other policy come before these. To change the default for the whole
  organization, edit or remove the rule.

### Ties

When the criteria leave a tie that decides which candidates a request tries, or in which order, the
request fails before any provider call:

| Error                  | Tied candidates           | Fix                                                                                                                      |
| ---------------------- | ------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `model_ambiguous`      | Deployments of two models | Name one model, or add a criterion that orders the models, such as `{ "by": "model.releaseDate", "direction": "desc" }`. |
| `deployment_ambiguous` | Deployments of one model  | Add a criterion that orders them, such as a `providers` list or `{ "by": "random()" }`.                                  |

The error message names up to three of the tied models or deployments. Ties among candidates past
the [fallbacks](#retries-and-fallbacks) change nothing, so they do not fail the request.

### Sort by an expression

Each `by` expression reads `author`, `model`, `deployment`, `route` or `provider` fields:

```json title="Cheapest output, then largest context"
{
	"routing": {
		"sort": [
			{ "by": "deployment.pricing.output_tokens.per_mill_tokens" },
			{ "by": "deployment.contextWindowTokens", "direction": "desc" }
		]
	}
}
```

- Missing values sort last. Booleans sort `false` first when ascending. Lists cannot be sorted.
- An expression that two policies use orders candidates once. A later copy is left out, in either
  direction, because it cannot break the ties of the first.

When a request names no model, the criteria choose the model:

```json title="Cheapest Claude model"
{
	"routing": {
		"filter": "'claude' in model.groupIds",
		"sort": [{ "by": "blended_price(3, 1)" }]
	}
}
```

### Random order

`random()` as the last criterion puts deployments in a random order, which spreads requests evenly.
`random(weight)` gives each deployment a chance to come first in proportion to an integer weight:

```json title="Azure three times as often as each other provider"
{
	"routing": {
		"sort": [{ "by": "random(provider.id == 'azure' ? 3 : 1)" }]
	}
}
```

With one Azure and one OpenAI deployment, Azure comes first in about three of four requests, and
the other deployment is its fallback.

- Each deployment draws once, so its number of credentials does not change its chance.
- A weight below 1 puts the deployment after the others.
- `random` takes no `direction`, and filters and rule conditions cannot use it.
- Criteria before `random()` come first:
  `[{ "by": "provider.id == 'azure'", "direction": "desc" }, { "by": "random()" }]` tries Azure
  deployments in random order, then the others in random order.
- No two deployments tie after `random()`, so criteria after it, from other policies, change
  nothing.
- Requests that alternate between providers do not share a provider's prompt cache.
- Each gateway draws on its own, without shared state.

### Orders from several policies

Organization, folder, grant, key and request policies can each set criteria in two places:

- At the top level, the criteria are required.
- In one rule with `"mode": "default"` and no `when`, they are
  [defaults](/docs/policies/rules#defaults).

The criteria of every policy apply, in this order:

1. Required criteria, from the organization policy down to the request policy.
2. The request's [`provider.order`](/docs/models#how-the-gateway-chooses-a-deployment), as a
   `providers` list.
3. Default criteria, from the request policy up to the organization policy.

| Criteria that policies set                                                                    | Combined order                                                                                   |
| --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| Key requires `[{ "providers": ["azure"] }]`. The organization has the default order.          | Azure deployments first, then the others. Within each, the default order.                        |
| Organization requires zero data retention first. A request sets `provider.order: ["openai"]`. | Zero-retention deployments first. Among each, OpenAI first, then the default order.              |
| Grant default `[{ "by": "blended_price(3, 1)" }]`. The organization has the default order.    | Cheapest first, then newest model, then deployment ID. The repeated price criterion is left out. |

- On a key, **Combined policy** shows the combined criteria in `routing.sort`, and the policy that
  set each run of them in `routing.sortFrom`.
- To decide the order for every request, end the organization's required criteria with a criterion
  that leaves no tie, such as `random()`.
- To stop other policies from adding criteria, remove `routing.order` and `routing.sort` from the
  organization's [delegation](/docs/policies/delegation) for every resource type and for `request`.

## Retries and fallbacks

When a call fails, the gateway can call the same candidate again, a **retry**, or call the next
candidate in routing order, a **fallback**:

```json title="Retry each candidate up to twice, then try one other candidate"
{
	"routing": {
		"retries": 2,
		"fallbacks": 1
	}
}
```

By default, the gateway makes no retries and up to 2 fallbacks. The failure decides the next step:

| Failure                                | Examples                                                                                                                                                                                                                                                        | Next step                                  |
| -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------ |
| Another call can succeed               | A lost connection, or a `408`, `409`, `429` or `5xx` response                                                                                                                                                                                                   | A retry. With no retries left, a fallback. |
| The candidate cannot serve the request | A `401`, `402`, `403`, `404` or `410` response, a retired model, a provider account out of credit or past its spend limit, a provider account that refuses the deployment's region, or a prompt, body or image beyond the deployment's context window or limits | A fallback.                                |
| The gateway refuses the candidate      | A [limit](/docs/policies/limits), your balance, or a credential that is disabled, expired or unavailable                                                                                                                                                        | A fallback, which can cost less.           |
| The request cannot succeed             | Other `4xx` responses, such as an invalid request or a content filter                                                                                                                                                                                           | The request ends with the error.           |

- Before a retry, the gateway waits about half a second, doubled for each retry up to 8 seconds,
  or longer when the provider asks with `Retry-After`. If the provider asks for more than 8
  seconds, or the wait would pass a [timeout](/docs/policies/timeouts), the gateway uses a
  fallback at once.
- When the provider sends an `x-should-retry` header, it decides whether the gateway retries. A
  fallback can still follow.
- The gateway makes no further call after you disconnect, after a timeout expires, or after a
  provider starts a successful response or reports usage. A failure in the gateway also ends the
  request.
- A candidate that the gateway refuses before its call counts as a fallback.
- When a provider asks for more than 8 seconds on your own credential, the gateway node that got
  the answer passes over that credential and deployment for later requests until the wait ends,
  without a call, while another candidate remains. The candidate still counts as a fallback, a
  request's last candidate still gets its call, and a successful call ends the wait early.
- When no candidate succeeds, the response has the error that ended the request, or the first
  candidate's error unless a later one passes sooner when you wait. See
  [Retries](/docs/reference/errors#retries).
- Each call is one of the request's [provider attempts](/docs/request-records), with its start
  time and duration. A request makes at most twelve calls: three candidates with four calls each.

<Callout type="warn">
	After a lost connection or a `408` or `5xx` response, the provider may have run the request. A
	retry or fallback then runs it again, and the provider can bill your own credential for both
	calls. We bill only the usage we measure. To prevent this, set both fields to 0.
</Callout>

When several policies set a field, the smallest value applies. Credential policies, and rules
whose `when` reads `author`, `model`, `deployment`, `route` or `provider` fields, can set `retries`
but not `fallbacks`, because one fallback count applies to the whole request:

```json title="Retry Chutes TEE deployments up to three times"
{
	"rules": {
		"chutes_tee": {
			"when": "provider.id == 'chutes' && deployment.dataHandling.tee == true",
			"routing": { "retries": 3 }
		}
	}
}
```

[Chutes](/docs/providers/chutes#retries) also retries on another instance when it proves that the
first did not run the request. Those calls count as retries.

## Missing encryption keys

A [customer-encrypted credential](/docs/byok#customer-encryption) and an
[encrypted export or redaction](/docs/customer-encryption#encrypt-plugin-settings) need their key in
each request that uses them. By default, a request that could use such a candidate but doesn't send
its key fails with `encryption_key_required` before any provider call. An app that forgets a key
then finds out at once, instead of quietly using another credential that may bill you differently.

To let those requests use their other candidates instead, set `missingEncryptionKeys` to `skip`.
The gateway then leaves out each candidate whose key the request doesn't send, which doesn't use one
of the fallbacks:

```json title="Use the key's other credentials when a request doesn't send an encryption key"
{
	"routing": { "missingEncryptionKeys": "skip" }
}
```

- When every candidate is left out, the request fails with `encryption_key_required`, which names
  the keys it needs.
- A key sent under the wrong label, or one that doesn't match its label's registered identifier,
  still fails the request.
- When policies differ, `fail` applies. A credential policy, or a rule whose `when` reads the
  candidate, sets the field for its own candidates only. A credential policy with `skip` lets
  requests without its key use the key's other credentials.
