A **candidate** is one deployment with one of your provider credentials. For each request, the gateway:

1. Starts with the candidates that can serve the request's `model`, endpoint, service tier and
   output limit.
2. Removes the candidates that `allowedCatalogNodes` or `filter` exclude.
3. Puts the rest in [order](#ordering) and sends the request to the first.

```jsonc title="policy.json"
{
	"routing": {
		"allowedCatalogNodes": { "providers": ["openai", "chutes"] },
		"filter": "deployment.dataHandling.trainingUse == false", // Providers that do not train on prompts.
		"sort": [{ "by": "deployment.pricing.output_tokens.per_mill_tokens", "direction": "asc" }]
	}
}
```

Filter on what you require, then sort by what you prefer. For example, require zero data retention
and sort by price, instead of writing a filter that matches exactly one deployment.

## When no deployment fits

| Error               | Cause                                                                                                   | Fix                                                                                   |
| ------------------- | ------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| `model_unavailable` | No candidate is left.                                                                                   | Check the model, the key's credentials and the key's **Combined policy**.             |
| `model_ambiguous`   | The request names no model, or a [group](/docs/models#groups) whose newest models share a release date. | Name a model, filter to one, or add an `order` or `sort`. The error lists the models. |

Filters and lists from every policy apply together, so an OpenAI-only policy and a Chutes-only
policy leave no candidate. The error does not say which policy removed a deployment, and sending the
request again does not help. A policy cannot widen the request's `model`.

## Allowed catalog nodes

`allowedCatalogNodes` takes lists of catalog IDs: `authors`, `models`, `deployments`, `routes` and
`providers`.

- A candidate must match every list. Lists from several policies intersect.
- Use exact IDs. Names, aliases and wildcards do not match, and IDs that are not in the current
  catalog match nothing.
- `"providers": []` allows no provider. `"allowedCatalogNodes": {}` replaces default lists only.

## Query syntax

Filters, sorts and rule conditions use [CEL](https://cel.dev/). Put the expression in a JSON string,
with single quotes inside it:

```cel
provider.id in ['openai', 'chutes'] && deployment.capabilities.streaming == true
```

| Expression                                                            | Meaning                               |
| --------------------------------------------------------------------- | ------------------------------------- |
| `provider.id == 'openai'`                                             | Compare a string                      |
| `deployment.contextWindowTokens >= 128000`                            | Compare an integer                    |
| `deployment.pricing.output_tokens.per_mill_tokens <= decimal('2.50')` | Compare an exact price                |
| `'image' in deployment.inputModalities`                               | Check whether a list contains a value |
| `author.headquarteredCountry in ['US', 'FR']`                         | Match one of several values           |
| `model.name.contains('mini')`                                         | Check whether a string contains text  |
| `has(deployment.deprecationDate)`                                     | Check whether a field is present      |
| `deployment.inputModalities.exists(m, m == 'text')`                   | Check whether any list item matches   |
| `request.time.getHours('UTC') < 18`                                   | Read the request time in a time zone  |

- Combine conditions with `&&`, `||`, `!` and parentheses.
- Write prices as `decimal('...')`. You can compare and sort prices, but not calculate with them;
  use [`blended_price`](#blended-price) to weigh input and output prices.
- Names and strings are case sensitive. Unknown fields and wrong types are rejected when you save.
- Write a time zone as a quoted IANA name, such as `'America/New_York'`, or a UTC offset, such as
  `'-05:00'`. Unknown time zones are rejected when you save.
- The [field reference](/docs/policies/routing-fields) lists every field.

### Missing values

A filter keeps a candidate only when it returns `true`. A comparison with a missing field is
unknown, and `!` does not make it true. To also accept deployments that do not state a value:

```cel
!has(deployment.dataHandling.retentionDays) || deployment.dataHandling.retentionDays <= 30
```

Without the `has(...)` check, only deployments that state 30 days or fewer pass.

## Ordering

The gateway tries candidates in this order:

1. Deployments in `order`, in list order.
2. The rest by `sort`.
3. Ties by the default order: newest model, model ID, the request's
   [`provider.order`](/docs/models#how-the-gateway-chooses-a-deployment), cheapest
   [blended price](#blended-price) at 3:1, and deployment ID.

The credentials of one deployment stay together, in the order that the key assigns them. The
[fallbacks](#retries-and-fallbacks) follow the same order.

```json title="Prefer OpenAI, then Claude, then the cheapest"
{
	"routing": {
		"order": ["openai-gpt-5.6-sol", "anthropic-claude-sonnet-4-6"],
		"sort": [{ "by": "blended_price(3, 1)" }]
	}
}
```

`order` skips listed deployments that the request cannot use. It never adds a deployment that the
request's `model`, filters, lists or credentials exclude.

### Sort

A sort has up to three criteria. Each has a CEL expression in `by` and a `direction`, `asc` by
default or `desc`:

```json title="Cheapest output, then largest context"
{
	"routing": {
		"sort": [
			{ "by": "deployment.pricing.output_tokens.per_mill_tokens" },
			{ "by": "deployment.contextWindowTokens", "direction": "desc" }
		]
	}
}
```

- Each `by` expression must read an `author`, `model`, `deployment`, `route` or `provider` field.
- Missing values sort last. Booleans sort `false` first when ascending. Lists cannot be sorted.

When a request names no model, a sort can choose the model:

```json title="Newest OpenAI model"
{
	"routing": {
		"filter": "author.id == 'openai'",
		"sort": [{ "by": "model.releaseDate", "direction": "desc" }]
	}
}
```

```json title="Cheapest Claude model"
{
	"routing": {
		"filter": "'claude' in model.groupIds",
		"sort": [{ "by": "blended_price(3, 1)" }]
	}
}
```

### Random order

`random()` as the last criterion puts deployments in a random order, which spreads requests evenly.
`random(weight)` gives each deployment a chance to come first in proportion to an integer weight:

```json title="Azure three times as often as each other provider"
{
	"routing": {
		"sort": [{ "by": "random(provider.id == 'azure' ? 3 : 1)" }]
	}
}
```

With one Azure and one OpenAI deployment, Azure comes first in about three of four requests, and
the other deployment is its fallback.

- Each deployment draws once, so its number of credentials does not change its chance.
- A weight below 1 puts the deployment after the others.
- `random` takes no `direction`, and filters and rule conditions cannot use it.
- Criteria before `random()` come first:
  `[{ "by": "provider.id == 'azure'", "direction": "desc" }, { "by": "random()" }]` tries Azure
  deployments in random order, then the others in random order.
- Each gateway draws on its own, without shared state.

### Orders from several policies

`order` and `sort` together form one order. Organization, folder, grant, key and request policies
can each set one order:

- At the top level, the order is required.
- In one rule with `"mode": "default"` and no `when`, it is a
  [default](/docs/policies/scopes#required-settings-and-defaults).

One order applies to the whole request: the broadest required order, or without one, the closest
default.

| Orders that policies set               | Order that applies |
| -------------------------------------- | ------------------ |
| Organization required, key required    | Organization       |
| Organization default, key required     | Key                |
| Organization default, grant default    | Grant              |
| Organization default, request required | Request            |

- A request policy that sets a different order than a saved required order fails.
- On a key, **Combined policy** shows the policy whose order applies in `routing.orderFrom`.
- To make every request use one order, set it at the top level of the organization policy.
- To stop other policies from setting an order, remove `routing.order` and `routing.sort` from the
  organization's [delegation](/docs/policies/scopes#permission-to-edit-saved-policies) for every
  resource type and for `request`.

## Blended price

`blended_price(inputWeight, outputWeight)` weighs a deployment's input and output prices into one
price per million tokens. With a 3:1 ratio, GPT-6 Sol's input price of $2 and output price of $10
blend to `(3 × 2 + 10) / 4 = $4`:

```cel
blended_price(3, 1) < decimal('5')
```

Some models charge more for every token of a request whose prompt is long. GPT-6 Sol charges $4
for input and $15 for output when the prompt is over 272,000 tokens. Add a prompt size in tokens to
blend the prices that a prompt of that size pays:

```cel
blended_price(3, 1, 300000) < decimal('5')
```

At 300,000 tokens, GPT-6 Sol blends to `(3 × 4 + 15) / 4 = $6.75`, so this filter removes it.
Without a prompt size, the function blends the prices for short prompts.

- Weights and the prompt size are constant integers. At least one weight must be positive, and a
  zero weight ignores that price.
- If a price with a positive weight is missing, the result is unknown.
- It compares prices only. It does not estimate the cost of a request.

## Request facts and context

Filters and conditions can read `request.model`, `request.route`, `request.time` and
`request.bodyBytes`, the size of the JSON body as sent. They cannot read token estimates or costs,
because the gateway calculates those only after it selects a candidate.

## Query bounds

| Bound                                                            | Limit              |
| ---------------------------------------------------------------- | ------------------ |
| One expression                                                   | 16 KiB             |
| Work for one expression                                          | 10,000 cost units  |
| Expression nodes in one policy, and in all policies of a request | 4,096 and 8,192    |
| Work for all expressions of one request                          | 100,000 cost units |

A request over a bound fails before the gateway holds any funds.

## Retries and fallbacks

When a call fails, the gateway can call the same candidate again, a **retry**, or call the next
candidate in routing order, a **fallback**:

```json title="Retry each candidate up to twice, then try one other candidate"
{
	"routing": {
		"retries": 2,
		"fallbacks": 1
	}
}
```

| Field       | Values | Default | Meaning                                                |
| ----------- | ------ | ------- | ------------------------------------------------------ |
| `retries`   | 0–3    | 0       | Calls to the same candidate after its first call fails |
| `fallbacks` | 0–2    | 2       | Other candidates to try, in routing order              |

The failure decides the next step:

| Failure                                | Examples                                                                                                 | Next step                                  |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------- | ------------------------------------------ |
| Another call can succeed               | A lost connection, or a `408`, `409`, `429` or `5xx` response                                            | A retry. With no retries left, a fallback. |
| The candidate cannot serve the request | A `401`, `402`, `403` or `404` response, or a provider account out of credit                             | A fallback.                                |
| The gateway refuses the candidate      | A [limit](/docs/policies/limits), your balance, or a credential that is disabled, expired or unavailable | A fallback, which can cost less.           |
| The request cannot succeed             | Other `4xx` responses, such as an invalid request, a prompt that is too long, or a content filter        | The request ends with the error.           |

- Before a retry, the gateway waits about half a second, doubled for each retry up to 8 seconds,
  or longer when the provider asks with `Retry-After`. If the provider asks for more than 8
  seconds, or the wait would pass a [timeout](/docs/policies/timeouts), the gateway uses a
  fallback at once.
- When the provider sends an `x-should-retry` header, it decides whether the gateway retries. A
  fallback can still follow.
- The gateway makes no further call after you disconnect, after a timeout expires, or after a
  provider starts a successful response or reports usage. A failure in the gateway also ends the
  request.
- A candidate that the gateway refuses before its call counts as a fallback.
- Each call is one of the request's [provider attempts](/docs/request-records), with its start
  time and duration. A request makes at most twelve calls: three candidates with four calls each.

<Callout type="warn">
	After a lost connection or a `408` or `5xx` response, the provider may have run the request. A
	retry or fallback then runs it again, and the provider can bill your own credential for both
	calls. We bill only the usage we measure. To prevent this, set both fields to 0.
</Callout>

When several policies set a field, the smallest value applies. Credential policies, and rules
whose `when` reads `author`, `model`, `deployment`, `route` or `provider` fields, can set `retries`
but not `fallbacks`, because one fallback count applies to the whole request:

```json title="Retry Chutes TEE deployments up to three times"
{
	"rules": {
		"chutes_tee": {
			"when": "provider.id == 'chutes' && deployment.dataHandling.tee == true",
			"routing": { "retries": 3 }
		}
	}
}
```

[Chutes](/docs/providers/chutes#retries) also retries on another instance when it proves that the
first did not run the request. Those calls count as retries.
