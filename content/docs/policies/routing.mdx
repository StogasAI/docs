title: Routing
description: Filter eligible deployments with CEL and choose a complete ordering.
---

Use `routing.allowedCatalogNodes` for exact catalog IDs, `routing.filter` for a CEL condition,
and `routing.sort` to order the candidates that remain. These settings apply together.

```json title="policy.json"
{
	"routing": {
		"allowedCatalogNodes": {
			"providers": ["openai", "chutes"]
		},
		"filter": "deployment.dataHandling.trainingUse == false"
	}
}
```

A **candidate** is one deployment paired with one eligible provider credential.
Several credential choices can therefore belong to the same deployment.
The request's model or deployment selector, service tier, interface and output-token limit narrow
the choices before their complete policies apply. An encrypted credential with no matching
supplied root is ineligible. A policy cannot widen an explicit request selector. Other
provider-specific parameters are validated against the selected deployment; they are not
automatic routing preferences.

Selection has three separate inputs:

| Input                          | What it decides                                                                                                        |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------- |
| Deployment filters             | Which deployment and credential pairs are eligible, including their privacy and location requirements.                 |
| Deployment ordering            | Which eligible deployment to choose first: a policy sort, or the request's provider order when it resolves the choice. |
| Ordered credential assignments | Which eligible credential to prepare first for the chosen deployment.                                                  |

An ineligible pair is filtered out without consuming a preparation attempt. A local credential
preparation failure consumes an attempt and can advance only with the explicit allowance below.
Credential preference never chooses between two deployments and cannot override either one's policy.

Several deployments may satisfy the same privacy requirements. Keep all matching deployments
eligible, then order them. For example, require zero retention in the filter and sort by price;
there is no need to weaken privacy checks or write a filter that happens to match exactly one ID.
Catalog data-handling fields describe the resolved deployment and route, including inherited facts.

For Chat Completions and Responses, `model` is optional. Omission considers all compatible
active deployments. A model slug limits selection to that model; a deployment slug pins that
deployment. Empty or null selectors are invalid. If several deployments remain without an order
that chooses one, the request returns `model_ambiguous` with usable deployment selectors.
There is no automatic preference for the model author's provider.

A `model_unavailable` error means no eligible deployment remains. Check the requested model,
assigned provider credentials and **Combined** policy. Required lists and filters all apply:
an OpenAI-only requirement and a Chutes-only requirement leave no shared provider, and
contradictory body-size filters reject every candidate. The error alone does not identify which
restriction excluded a deployment. Repair the conflicting sources; retrying an unchanged
request does not resolve that conflict.

## Allowed catalog nodes

Supported lists are `authors`, `models`, `deployments`, `routes`, and `providers`. They share the
[policy size limits](/docs/policies/editing#document-rules) without a separate ID-count cap.
Use unique canonical IDs matching `^[a-z0-9][a-z0-9._:-]{0,127}$`. Names, aliases, wildcards, and
HTTP paths are not IDs here.

Every present list must match. Required lists intersect across applicable policies. Omission
adds no restriction; `"providers": []` permits no providers. An empty `allowedCatalogNodes`
object replaces default lists while preserving other required lists. IDs absent from the active
catalog cannot match.

## Query syntax

Filters use [Common Expression Language](https://cel.dev/), or CEL. For example:

```cel
provider.id in ['openai', 'chutes'] && deployment.capabilities.streaming == true
```

Put the expression in `routing.filter`. JSON requires escaping inner double quotes;
single-quoted CEL strings are often easier to read.

| Expression                                                            | Meaning                                     |
| --------------------------------------------------------------------- | ------------------------------------------- |
| `provider.id == 'openai'`                                             | Compare a string.                           |
| `deployment.contextWindowTokens >= 128000`                            | Compare an integer.                         |
| `deployment.pricing.output_tokens.per_mill_tokens <= decimal('2.50')` | Compare an exact catalog price.             |
| `'image' in deployment.inputModalities`                               | Test list membership.                       |
| `model.name.contains('mini')`                                         | Test a substring.                           |
| `has(deployment.deprecationDate)`                                     | Test field presence.                        |
| `deployment.inputModalities.exists(m, m == 'text')`                   | Test whether any list element matches.      |
| `request.time.getHours('UTC') < 18`                                   | Read the request time in a named time zone. |

Use `&&`, `||`, and `!` for AND, OR, and NOT. Parentheses control grouping. CEL supports typed
arithmetic, field comparisons, list operations and conditional expressions; it cannot perform
network calls or execute application code. Unknown fields and incorrect types are rejected.
Dynamic field access cannot bypass the registered field types.

Prices require `decimal('...')`, with up to 36 fractional digits, rather than a floating-point
number. Exact prices support comparisons, membership and sorting; arithmetic on these values
is not exposed. Use `blended_price` for a weighted price. Integer values use CEL's signed
64-bit range. Names and strings are case-sensitive.

## Missing values

A filter permits a candidate only when it returns `true`. Missing facts produce an unknown value;
negating an unknown comparison does not make it true. To deliberately accept a missing disclosure:

```cel
!has(deployment.dataHandling.trainingUse) || deployment.dataHandling.trainingUse == false
```

Use only `deployment.dataHandling.trainingUse == false` when the declaration is required.
A true branch can resolve `||` despite an unknown branch; a false branch can resolve `&&`.
Otherwise the result remains unknown. A [conditional rule](/docs/policies/scopes#conditional-rules)
with an unknown condition rejects evaluation instead of silently omitting its restrictions.

## Sorting

A sort is an ordered array of up to three criteria: one main criterion and two tie breakers.
Each criterion requires a scalar CEL expression in `by` and `direction: "asc"` or `"desc"`.
Missing values sort last in either direction. Strings sort lexically, numbers numerically,
and Booleans as false before true when ascending. Lists cannot be sorted.

```json title="Prefer lower output prices"
{
	"routing": {
		"sort": [
			{
				"by": "deployment.pricing.output_tokens.per_mill_tokens",
				"direction": "asc"
			},
			{
				"by": "deployment.contextWindowTokens",
				"direction": "desc"
			}
		]
	}
}
```

Top-level settings are required. All active required sort orders must agree on the complete
ordering; a child cannot append criteria or choose an incompatible order. Conflicts reject the
combination. Role order and rule names never decide which policy wins.

To supply a replaceable preference, put the sort in a rule with `mode: "default"`:

```json title="Default organization ordering"
{
	"rules": {
		"prefer_lower_price": {
			"mode": "default",
			"routing": {
				"sort": [
					{
						"by": "blended_price(3, 1, 'per_mill_tokens')",
						"direction": "asc"
					}
				]
			}
		}
	}
}
```

An applicable required sort replaces sort defaults. This includes an explicit `"sort": []`,
which adds no ordering while preserving other required orders. When only defaults apply, their
orders must agree too. Candidate-dependent sorts must define one consistent ordering across
all remaining candidates.

After an explicit sort, deployment ID breaks any remaining tie deterministically. Without a
policy sort, the request's explicit provider order applies. Equal-rank deployments still require
a deployment selector or sort; neither catalog iteration order nor fallback allowance resolves
that ambiguity.

To prohibit descendant policy sorting, the organization must exclude `routing.sort` from its
delegation to all six saved resource types and from `delegation.request`, and suppress its own
sort defaults. `"sort": []` alone only replaces defaults: it does not prohibit another required
sort. With sorting prohibited, requests still need a deployment selector or an unambiguous
provider order. See [Delegation](/docs/policies/scopes#permission-to-edit-saved-policies) for section permissions.

## Blended price

`blended_price(inputWeight, outputWeight, 'rate')` returns an exact weighted catalog price in
USD per million total tokens. For a 3:1 input/output ratio, it is `(3 × input price + output price) / 4`.
An input price of $1/million and output price of $9/million therefore gives $3/million blended.

```cel
blended_price(3, 1, 'per_mill_tokens') < decimal('5')
```

All three arguments must be constants. Each weight is an integer from 0 to 9,007,199,254,740,991;
at least one must be positive. The rate is `per_mill_tokens`, `per_mill_context_lte_272k`, or
`per_mill_context_gt_272k`. Equivalent ratios produce the same exact value. A zero weight ignores
that meter. A missing participating rate produces an unknown result; zero is a valid price.

This comparison does not estimate request cost, output length, cache hits, tools or provider fees.
It never chooses a context price tier from a token estimate. To require both context tiers below $5:

```cel
blended_price(3, 1, 'per_mill_context_lte_272k') < decimal('5') &&
blended_price(3, 1, 'per_mill_context_gt_272k') < decimal('5')
```

To allow flat pricing or two acceptable context tiers:

```cel
blended_price(3, 1, 'per_mill_tokens') < decimal('5') ||
(blended_price(3, 1, 'per_mill_context_lte_272k') < decimal('5') &&
 blended_price(3, 1, 'per_mill_context_gt_272k') < decimal('5'))
```

Prices remain exact even for repeating fractions. See the [field reference](/docs/policies/routing-fields#pricing)
for individual token prices and [spend limits](/docs/policies/limits#spend-allowances) for usage budgets.

## Request facts and context

Routing can read `request.model`, `request.route`, `request.time`, and `request.bodyBytes`.
Body bytes are the exact incoming JSON size, including whitespace and request controls, before
redaction. The [field reference](/docs/policies/routing-fields) lists the full catalog inventory.

Token estimates and estimated total request costs are unavailable to routing and rule conditions.
After selection, redaction and the universal text estimator run once, with separate framing allowances. The resulting estimate
feeds reservations, token limits and the `estimated_input_tokens` usage meter. Redaction can
increase token count. Provider context admission remains authoritative; a large local estimate
does not truncate the request, weaken redaction, or choose another deployment.

## Query bounds

Each CEL expression is limited to 16 KiB of UTF-8 source and 10,000 runtime cost units.
Conditions, filters and sorting share a compilation budget of 4,096 parsed expression nodes
per source and 8,192 across distinct applicable sources. Operators, values and field accesses
count toward that budget; repeated identical expressions in one source compile once.
All conditions, filters and sort evaluations share 100,000 units per request. Exceeding the
allowance rejects the request before a hold. These units bound evaluator work, not elapsed time.
The [document bounds](/docs/policies/editing#document-rules) also apply.

## Candidate checks

There are **no fallback attempts by default**. The gateway prepares one selected candidate. Invalid encryption keys or encrypted content always
stop the request, including when local fallback is enabled.
To allow another local credential attempt, explicitly raise `maxPreDispatchCandidates`:

```json title="policy.json"
{
	"routing": {
		"fallbacks": {
			"maxPreDispatchCandidates": 3
		}
	}
}
```

The accepted values are 1, 2 and 3, including the first candidate. Required values combine by
minimum; defaults apply only when no requirement supplies that setting. Fallback allowance does
not select an order. A failed local credential preparation can advance within the allowance.

Redaction, tokenization and authorization begin only after a credential is selected. Failures
from those stages do not select another candidate. Once dispatch begins, the provider result is
final for this request. Context errors and budget declines never trigger an automatic retry.
