Save each policy where it should apply. An organization policy covers every key in the
organization, and a key policy covers one key. See [Edit a policy](/docs/policies/editing) for where
to save, and [Scopes and inheritance](/docs/policies/scopes) for how policies combine.

## Budgets and rates

### Cap monthly spending for the organization

All keys share $1,000 a month. Each month starts on the 1st at 00:00 UTC.

```json title="Organization policy"
{
	"limits": {
		"monthly": { "usd": "1000", "per": { "count": 1, "unit": "month" } }
	}
}
```

### Give one key a daily budget and a total cap

The key can spend $20 a day and $500 in total. The organization's limits still apply.

```json title="Key policy"
{
	"limits": {
		"daily": { "usd": "20", "per": { "count": 1, "unit": "day" } },
		"total": { "usd": "500" }
	}
}
```

### Reset a budget every quarter

The key can spend $3,000 a quarter. Quarters start on January 1, April 1, July 1 and October 1 at
midnight in New York.

```json title="Key policy"
{
	"limits": {
		"quarterly": {
			"usd": "3000",
			"per": {
				"count": 3,
				"unit": "month",
				"anchor": "2027-01-01T05:00:00Z",
				"timeZone": "America/New_York"
			}
		}
	}
}
```

### Limit the request rate

One request a second on average, in bursts of up to 10, and at most 5 requests at the same time.

```json title="Key policy"
{
	"limits": {
		"rate": { "requests": 10, "per": { "count": 10, "unit": "second", "refill": "gradual" } },
		"parallel": { "concurrentRequests": 5 }
	}
}
```

See [Limits](/docs/policies/limits) for token limits, refills and reset schedules.

## Providers and data handling

### Use only providers that keep no data

Every request skips deployments whose provider does not commit to zero data retention.

```json title="Organization policy"
{
	"routing": {
		"filter": "deployment.dataHandling.zeroDataRetention == true"
	}
}
```

### Use providers in Europe

`processingWithin` and `storageWithin` list where a deployment processes and keeps content, each
with every place that contains it. This accepts deployments in Europe, in the EU or in one European
country, and deployments that keep nothing. To choose only where models run, keep the first check.
See [location values](/docs/policies/routing-fields#location-values).

The filter chooses the provider's deployment. Each request also passes through a gateway, and your
request records stay with your account, both in the region that the sign-in page shows, which is
the United States today.

```json title="Organization policy"
{
	"routing": {
		"filter": "'europe' in deployment.dataHandling.processingWithin && 'europe' in deployment.dataHandling.storageWithin"
	}
}
```

### Use only some providers

```json title="Organization policy"
{
	"routing": {
		"allowedCatalogNodes": { "providers": ["openai", "anthropic"] }
	}
}
```

## Order and fallbacks

### Try OpenAI first, then Azure

A request for `gpt-5.6-sol` goes to OpenAI first. If OpenAI refuses the request, for example with a
`429` rate limit, the gateway tries your Azure deployment. The key needs an OpenAI and an Azure
credential.

```json title="Key policy"
{
	"routing": {
		"sort": [{ "deployments": ["openai-gpt-5.6-sol", "azure-gpt-5.6-sol"] }]
	}
}
```

### Use the cheapest deployment

Deployments are ordered by price, with input and output prices weighed 3 to 1. A request that names
a model uses its cheapest deployment first. A request without a model uses the cheapest model.

```json title="Key policy"
{
	"routing": {
		"sort": [{ "by": "blendedPrice(3, 1)" }]
	}
}
```

See [Routing](/docs/policies/routing) for filters, sorts, weighted random order and fallbacks.

## Schedules

### Allow requests only during working hours

Requests work from 08:00 to 18:00 Berlin time, Monday to Friday.

```json title="Organization policy"
{
	"access": {
		"schedule": {
			"deny": [
				{
					"days": ["mon", "tue", "wed", "thu", "fri"],
					"start": "00:00",
					"end": "08:00",
					"timeZone": "Europe/Berlin"
				},
				{
					"days": ["mon", "tue", "wed", "thu", "fri"],
					"start": "18:00",
					"end": "24:00",
					"timeZone": "Europe/Berlin"
				},
				{
					"days": ["sat", "sun"],
					"start": "00:00",
					"end": "24:00",
					"timeZone": "Europe/Berlin"
				}
			]
		}
	}
}
```

## Content

### Redact email addresses and phone numbers

The provider receives placeholders such as `<EMAIL_ADDRESS>` instead of the values.

```json title="Organization policy"
{
	"plugins": {
		"redaction": { "presets": ["email_address", "phone_number"] }
	}
}
```

See [PII redaction](/docs/pii-redaction) for every preset, your own terms and patterns.

### Refuse system messages

Requests that send a `system` or `developer` message, or `instructions`, get `model_unavailable`.

```json title="Key policy"
{
	"routing": {
		"filter": "!request.systemMessages"
	}
}
```

### Refuse hosted tools

Requests that let the model call a hosted tool, such as web search, get `model_unavailable`.

```json title="Organization policy"
{
	"routing": {
		"filter": "size(request.hostedTools) == 0"
	}
}
```

See [Restrict tools with a policy](/docs/model-tools#restrict-tools-with-a-policy) for filters on
tool names and hosted tools.

## Rules and permissions

### Set a separate budget for one model family

Requests to Claude Opus models can spend $200 in total. Other requests do not count against it.

```json title="Organization policy"
{
	"rules": {
		"opus_budget": {
			"when": "'claude-opus' in model.groupIds",
			"limits": { "spend": { "usd": "200" } }
		}
	}
}
```

### Set a default order

Keys try the cheapest deployment first. A `sort` that a folder, grant, key or request policy sets
comes first, and this default orders the deployments that it leaves tied.

```json title="Organization policy"
{
	"rules": {
		"cheapest_first": {
			"mode": "default",
			"routing": { "sort": [{ "by": "blendedPrice(3, 1)" }] }
		}
	}
}
```

See [Rules](/docs/policies/rules) for conditions and defaults.

### Exempt one key from an organization setting

A required setting applies to every key below it, and no policy can exempt itself. Make the
setting a default instead. A key then leaves it by requiring the
[neutral value](/docs/policies/rules#replace-a-default-without-adding-a-restriction).

```json title="Organization policy"
{
	"rules": {
		"redact_email": {
			"mode": "default",
			"plugins": { "redaction": { "presets": ["email_address"] } }
		}
	},
	"delegation": {
		"keys": {
			"default": ["limits"],
			"exceptions": {
				"0195ef30-7b1a-7000-8000-000000000001": ["limits", "plugins.redaction"]
			}
		}
	}
}
```

```json title="Policy of the exempt key"
{
	"plugins": { "redaction": {} }
}
```

The delegation lets only that key set redaction. Restrict the other resource types in the same
way, because a redaction setting in a folder, grant, role, member or credential policy also
replaces the default for the keys that it covers.

### Let key managers change only limits

Key managers, and organization administrators, can save limits on keys, but no other section.

```json title="Organization policy"
{
	"delegation": {
		"keys": ["limits"]
	}
}
```

### Let requests add redaction

Requests can send their own redaction settings in a [request policy](/docs/policies/request-policies).

```json title="Organization policy"
{
	"delegation": {
		"request": ["plugins.redaction"]
	}
}
```

See [Delegation](/docs/policies/delegation) for exceptions by ID and what happens to sections that
were saved before a change.
