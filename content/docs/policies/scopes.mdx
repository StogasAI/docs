You can save a policy on an organization, folder, grant, role, member, provider credential or API
key. Each is a scope. A request must follow every policy that applies to it, and a
[request policy](/docs/policies/request-policies) can add settings for one request.

## Which policies apply

| Key         | Policies that apply                                                                                                                       |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| Service key | The organization, the key's folder, the selected provider credential and the key                                                          |
| Member key  | The organization, the grant's folder, the grant, the key's owner, each of the owner's roles, the selected provider credential and the key |

- Every role of a member applies to all of that member's keys. A role that gives access to grant A
  and allows only OpenAI also restricts the member's keys under grant B. To restrict one grant, save
  the policy on that grant or its folder.
- Only the credential that serves the request applies its policy.
- The members who view or manage a service key add no policies to it.

## Scope differences

| Scope                         | `limits` | Registers `encryption.keys` | Can restrict the saved policies of                    |
| ----------------------------- | -------- | --------------------------- | ----------------------------------------------------- |
| Organization                  | Yes      | Yes                         | Folders, grants, roles, members, credentials and keys |
| Folder                        | Yes      | No                          | Its grants and keys                                   |
| Grant                         | Yes      | No                          | Its member keys                                       |
| Role, member, credential, key | Yes      | No                          | -                                                     |
| Request                       | No       | No                          | -                                                     |

- Every scope accepts `access`, `input`, `timeouts`, `routing`, `plugins` and `rules`, but
  credential policies cannot [set an order](/docs/policies/routing#orders-from-several-policies).
- Every saved scope can [permit request policies](/docs/policies/request-policies#grant-permission).
- A saved policy can be up to 256 KiB, and a request policy up to 16 KiB. See
  [Document rules](/docs/policies/editing#document-rules).
- Managed providers have no credential, so they have no credential policy.

## Shared limits

A limit counts every request that uses its resource. An organization limit counts all the
organization's keys, a grant limit counts the grant's member keys, and a key limit counts only that
key.

For example, an organization allows $1,000 a month, a grant $200 a month and a key $10 a day. A
request must fit all three, and other keys can use up the shared amounts first. The same limit
name at two scopes is two separate limits. Anyone who can read a key can see the usage of every
limit that applies to it. See [Limits](/docs/policies/limits).

## Required settings and defaults

Settings are required unless they are in a rule with `"mode": "default"`. A default applies only
when no required setting of the same kind applies:

```json title="Organization policy"
{
	"rules": {
		"prefer_long_context": {
			"mode": "default",
			"routing": { "sort": [{ "by": "deployment.contextWindowTokens", "direction": "desc" }] }
		}
	}
}
```

A key policy with its own `routing.sort` or `routing.order` replaces this default. Each of these is
one kind of setting: `access`, `input`, each timeout, each routing field, and `plugins`, except that
`routing.order` and `routing.sort` are one kind. Replacing a default filter does not replace a
default sort. All plugin settings are one kind, because encrypted plugin settings do not show which
plugins they set. So a required plugin setting, such as text extraction, also replaces default
redaction and default export destinations.

When several policies set the same kind of setting, they combine. No policy wins because of its
scope, role or order:

| Setting                                                               | Result                                                                 |
| --------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| [Routing filters](/docs/policies/routing)                             | Every filter must match.                                               |
| [Allowed catalog nodes](/docs/policies/routing#allowed-catalog-nodes) | Only nodes in every list. An empty list allows none.                   |
| [Order](/docs/policies/routing#orders-from-several-policies)          | Every policy that sets an order must set the same one.                 |
| [Deny periods](/docs/policies/access#deny-periods)                    | Every period applies.                                                  |
| [Redaction](/docs/pii-redaction)                                      | Every preset, literal and pattern applies to the original text.        |
| [ASCII-only input](/docs/pii-redaction#ascii-only-input)              | Required if any policy requires it.                                    |
| [Retries and fallbacks](/docs/policies/routing#retries-and-fallbacks) | The smallest value of each. Without one, no retries and two fallbacks. |
| [Limits](/docs/policies/limits)                                       | Every limit applies. Limits cannot be defaults.                        |

To replace defaults without adding a restriction, set a neutral value: `input.asciiOnly: false`,
`access.deny: []`, `routing.filter: "true"`, `routing.sort: []`, `routing.allowedCatalogNodes: {}`
or `plugins.stogasRedaction: {}`. A neutral value never removes a required setting from another
policy.

## Conditional rules

Rules apply settings only to the requests that match their condition:

```json title="policy.json"
{
	"rules": {
		"working_hours": {
			"when": "request.time.getHours('UTC') >= 9 && request.time.getHours('UTC') < 17",
			"limits": { "spend": { "lifetimeUsd": "100" } }
		},
		"redact_openai": {
			"when": "provider.id == 'openai'",
			"plugins": { "stogasRedaction": { "email_address": true } }
		}
	}
}
```

The first rule caps spending during working hours at $100. The second redacts email addresses only
when the request goes to OpenAI.

- `when` is a [CEL expression](/docs/policies/routing#query-syntax) that returns `true` or `false`.
  A rule without `when` always applies.
- Conditions read the same [request facts](/docs/policies/routing#request-facts-and-context) as
  routing filters, before redaction. They cannot read usage, balances, token estimates or provider
  responses. If a missing fact leaves a condition undecided for a deployment or credential, the
  gateway skips that choice and tries the others. Check optional facts with `has(...)`. An error
  in a condition, such as division by zero, fails the request.
- Rules can contain `access`, `input`, `timeouts`, `limits`, `plugins` and `routing`, but not
  other rules, `delegation` or `encryption`. A rule that
  [sets an order](/docs/policies/routing#orders-from-several-policies) or
  [fallbacks](/docs/policies/routing#retries-and-fallbacks) can test only `request` fields.
- Rules have no order. A name only identifies a rule and its [limits](/docs/policies/limits#conditional-limits).
  Names use 1–48 lowercase letters, digits, `_` or `-`, start with a letter, and cannot be
  `constructor` or `prototype`.

## Permission to edit saved policies

`delegation` limits which sections managers can save on the resources below a scope. It gives no
access by itself:

```json title="Organization policy"
{
	"delegation": {
		"keys": ["limits", "routing.filter"],
		"grants": false
	}
}
```

With this policy, key managers can save only limits and routing filters, and grant policies cannot
be changed. Use `true` for every section, `false` for none, or a list of section paths. Without
`delegation`, managers can save every section.

A section must be allowed by every parent that sets `delegation`, even for organization
administrators. Delegation never lets a scope use a field that it does not support.
[Encrypted plugin settings](/docs/customer-encryption#encrypt-plugin-settings) need permission for
all of `plugins`, because they can hold any plugin setting.

### ID exceptions

Give specific resources other permissions:

```json
{
	"delegation": {
		"keys": {
			"default": false,
			"exceptions": {
				"0195ef30-7b1a-7000-8000-000000000001": ["routing.filter"]
			}
		}
	}
}
```

- Each ID must be a resource inside the parent's scope.
- Each parent decides for itself. An exception cannot override another parent's denial.
- To allow a new resource under `"default": false`, create it, add its exception, then save its
  policy.

### Settings that become prohibited

If a delegation change prohibits settings that resources below already have, the editor lists those
resources. When you confirm, we clear their policies as it saves the change. Their names,
enabled state, expiration and usage stay.

## Request order

<Steps>
<Step>

### Check the key

The gateway checks the key and loads the policies that apply to it.

</Step>
<Step>

### Choose a deployment

Each candidate is a deployment with one credential. The gateway applies each candidate's rules, filters
and sort, then selects one. See [Routing](/docs/policies/routing).

</Step>
<Step>

### Prepare the input

The gateway checks ASCII-only input and redacts the text once, for the selected candidate.

</Step>
<Step>

### Hold

The gateway [holds](/docs/usage#how-a-request-is-charged) funds and tokens against every limit at once.
If one limit fails, no limit is charged.

</Step>
<Step>

### Send and settle

The gateway sends the request, then charges the usage to the limits that held it.

</Step>
</Steps>

## When changes take effect

- Every request checks the current enabled state, expiration, limits and policy versions. Disabling
  a resource blocks new requests at once, and requests that are running continue.
- Saving does not wait for gateways to load the change. A request that reaches a gateway with an
  older version gets `503 key_configuration_changed` and costs nothing. Send it again after a
  moment.
- A request keeps the limits that it held, even if a later edit changes them.
