A request must fit every limit of every [scope](/docs/policies/scopes) that applies to it. Limits
count [held](/docs/usage#how-a-request-is-charged) funds and tokens as well as settled usage, so a
request is declined when its hold does not fit, even if its final charge would.

## Write a limit

Each entry in `limits` has a name and counts one thing:

```jsonc title="policy.json"
{
	"limits": {
		// $500 a month, from midnight on the 1st in New York.
		"monthly": {
			"usd": "500",
			"per": { "count": 1, "unit": "month", "timeZone": "America/New_York" }
		},
		// 60 requests a minute, given back steadily.
		"rpm": { "requests": 60, "per": { "count": 1, "unit": "minute", "refill": "gradual" } },
		// 5 million tokens in total. It never resets.
		"total": { "tokens": 5000000 },
		// 4 requests at a time.
		"parallel": { "concurrentRequests": 4 }
	}
}
```

| Field                                        | Counts                                                                     |
| -------------------------------------------- | -------------------------------------------------------------------------- |
| [`usd`](#spending)                           | Full provider cost at catalog rates, including [BYOK](/docs/byok) requests |
| [`tokens`](#tokens-and-input-text)           | Provider tokens, input and output                                          |
| [`stt`](#tokens-and-input-text)              | [Standard text tokens](/docs/usage#standard-text-tokens) of input          |
| [`requests`](#requests)                      | Requests, when the gateway admits them                                     |
| [`concurrentRequests`](#concurrent-requests) | Requests running at the same time                                          |

- Each limit sets exactly one of these fields.
- Names such as `monthly` use 1–48 lowercase letters, digits, `_` or `-`, and start with a letter.
- A policy can have up to **8 limits**, counting the limits in its rules.
- Limits always apply, so a rule with limits cannot use `mode: "default"`.
  [Request policies](/docs/policies/request-policies) cannot set limits.

## Lifetime or recurring

Without `per`, a limit counts from when you add it and never resets. With `per`, it repeats every
`count` (1 to 1,000) `unit`s: `second`, `minute`, `hour`, `day`, `week`, `month` or `year`.
`refill` chooses how the allowance comes back:

| `refill`          | Behavior                                                                                                    |
| ----------------- | ----------------------------------------------------------------------------------------------------------- |
| `reset` (default) | The whole amount comes back when each period starts.                                                        |
| `gradual`         | The amount comes back steadily, one period's amount over each period, so usage never bunches up at a reset. |

A gradual limit never holds more than its amount: 60 requests a minute allows up to 60 at once, then
one more each second. A new gradual limit starts full.

`concurrentRequests` takes no `per`: a request holds its place only while it runs.

### Reset schedules

```json title="policy.json"
{
	"limits": {
		"quarterly": {
			"usd": "3000",
			"per": {
				"count": 3,
				"unit": "month",
				"anchor": "2027-01-01T05:00:00Z",
				"timeZone": "America/New_York"
			}
		}
	}
}
```

- `anchor` is when a period starts; the others follow on the calendar. They are not rolling windows.
- If you save a limit without an anchor, we set it to the start of the current unit in its time
  zone, such as midnight on the 1st for a month or Monday for a week. Later saves keep it while the
  limit's name, field and unit stay the same.
- `timeZone` defaults to `UTC`. Days, weeks, months and years follow its calendar, including
  daylight saving time. Seconds, minutes and hours are fixed lengths from the anchor.
- Month and year periods keep the anchor's local day and time. A period anchored on January 31
  resets on the last day of February, then on March 31.
- A request counts in the period in which the gateway held its funds or tokens. Unused allowance
  does not carry over.

Gradual limits take no `anchor` or `timeZone`. A gradual month gives back its amount over
2,629,746 seconds, the average Gregorian month, and a gradual year over 31,556,952 seconds. See
[Timestamps and time zones](/docs/policies/access#timestamps-and-time-zones) for the formats.

## Shared limits

A limit counts every request of its resource. An organization limit counts all the organization's
keys, a grant limit counts the grant's member keys, and a key limit counts only that key.

For example, an organization allows $1,000 a month, a grant $200 a month and a key $10 a day. A
request must fit all three. If other keys have used all but $2 of the organization's $1,000, the key
can spend only $2 more that month, even though its own limit allows $10 a day.

- The same limit name at two scopes is two separate limits.
- Anyone who can read a key can see the usage of every limit that applies to it.

## Spending

`usd` limits count the full provider cost at catalog rates, including BYOK requests, where your
balance pays only the BYOK fee. Write amounts as USD decimal strings from `"0"` to
`"1000000000000"`, with up to 36 decimal places, in their shortest form: `"1.5"`, not `"1.50"`,
`"01.5"` or `1.5`. `"0"` blocks every request that has a cost; a gradual limit needs more than `"0"`.

The provider can report more usage than the hold, so a request can go past a limit. A lower output
limit keeps holds, and the possible overrun, small.

## Tokens and input text

`tokens` limits count provider tokens. Input includes cache reads and writes, and output includes
reasoning. Each token counts once.

- The hold is the [estimated input](/docs/usage#input-estimates) plus the output limit: yours, or the
  model's maximum. A lower output limit lets a small request fit.
- Settlement uses the provider's count. If the provider reports no usage, the whole hold counts. A
  request that fails before it reaches the provider counts nothing.

`stt` limits count [standard text tokens](/docs/usage#standard-text-tokens) of input instead: the
request text after redaction, 4 bytes to a token. STT counts the same text the same way on every
model, so one limit means the same amount on every provider. Its hold is exact. It counts when the
provider reports usage or cost, and is released when the request fails.

## Requests

`requests` limits count each request once, when the gateway admits it.

- A request that a limit blocks takes nothing. A failed provider call does not give its request
  back.
- Every organization also has a platform limit, shared by all its keys, grants, Playground requests
  and BYOK requests. It allows 120 requests a second, given back steadily, or the rate we agreed for
  your organization. More keys do not add capacity. When it is used up, a request waits up to two
  seconds to start, and a request that would wait longer gets `429 platform_rate_limited`. Contact
  [ops@stogas.ai](mailto:ops@stogas.ai) for a higher rate.

## Concurrent requests

`concurrentRequests` caps how many requests run at the same time across all gateways, from 1 to
10,000. Each request uses one place until it finishes, whether or not it streams.

- Lowering the cap does not stop requests that are running.
- A request sent on the same connection after a response ends finds that request's place free. On
  another connection, the place can stay taken for a moment, until the finished request's usage is
  recorded.
- If a gateway stops during a request, the place frees when the request's maximum lifetime ends.
- Combine it with a request and a spending limit: short requests can still run many times under a
  small cap.

## Conditional limits

Put limits in a [rule](/docs/policies/rules#conditional-rules) to count only the requests that
match it:

```json title="policy.json"
{
	"rules": {
		"openai_budget": {
			"when": "provider.id == 'openai'",
			"limits": {
				"spend": { "usd": "100" },
				"parallel": { "concurrentRequests": 2 }
			}
		}
	}
}
```

- Other requests do not use these limits.
- Changing the rule's name or condition starts its limits from zero. Changing only the formatting of
  the condition does not.
- Conditions cannot read balances, usage or provider results.

## Change a limit

| Change                                                  | Usage                                                                                                              |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Change the amount, period, refill, anchor or time zone  | Kept.                                                                                                              |
| Change what it counts, or switch lifetime and recurring | Starts from zero.                                                                                                  |
| Rename or remove a limit                                | Deleted. Adding it back starts from zero.                                                                          |
| Add a limit                                             | Starts from zero. A key, grant or organization concurrent-request limit also counts the requests that are running. |

A limit below current usage blocks new requests until usage falls under it. The key's **Overview**
page shows each limit that applies, with its scope and usage.

## Blocked requests

| Status | Cause                                                            | Codes                                                                      |
| ------ | ---------------------------------------------------------------- | -------------------------------------------------------------------------- |
| `402`  | A `usd` limit, or the organization's balance                     | `<scope>_spend_limit`, `insufficient_balance`                              |
| `429`  | A `requests`, `tokens`, `stt` or `concurrentRequests` limit      | `<scope>_rate_limited`, `<scope>_token_limit`, `<scope>_concurrency_limit` |
| `429`  | The platform limit                                               | `platform_rate_limited`                                                    |
| `429`  | A request within 25 ms after a blocked request with the same key | `rate_limit_exceeded`                                                      |

The code names the scope, such as `grant_token_limit`, but not the named limit. A `429` response has
`Retry-After` when waiting can help: until a reset, until a gradual limit has room, or until running
requests finish. When several limits block a request, the code and `Retry-After` come from the one
that frees up last. A retry cannot fit a hold that is larger than the limit, so lower the output limit
or raise the limit. Such a response, and one with a wait longer than a minute, has
`X-Should-Retry: false`. Before it blocks a request, the gateway tries the request's other
candidates as [fallbacks](/docs/policies/routing#retries-and-fallbacks). See
[Errors](/docs/reference/errors) for every code.
