A policy is a JSON document that controls which requests an API key may make, how much it may
use, what text reaches a provider, and which requests are exported. Save shared settings on organizations, folders, grants,
roles, members and credentials, then add key or request settings. Every request must satisfy
all applicable requirements.

## Start with a policy

This policy requires a no-training declaration and caps lifetime upstream spending at $10:

```json title="policy.json"
{
	"routing": {
		"filter": "deployment.dataHandling.trainingUse == false"
	},
	"limits": {
		"spend": {
			"lifetimeUsd": "10"
		}
	}
}
```

On an organization, that $10 is shared across all its keys. On a grant, it is shared across the
grant's member keys. On a key, it applies only to that key. A key cannot override a parent cap.

Use `null` when no policy is configured. An empty object `{}` is saved as `null`; omitted settings add no
restriction at that scope. They do not remove parent restrictions or platform safeguards.

[Edit a policy](/docs/policies/editing) explains how to save it.
[Scopes and inheritance](/docs/policies/scopes) explains shared rules, permissions, and when
changes take effect.

## Request timeouts

Requests default to a **60-minute total wait** and a **five-minute wait for useful provider
output**. These limits control how long the caller waits. Configure either in whole seconds
from 1 through 3600:

```json title="policy.json"
{
	"timeouts": {
		"totalSeconds": 900,
		"outputIdleSeconds": 120
	}
}
```

`totalSeconds` starts after the gateway admits the received request body and includes policy,
preparation, authorization and provider work. It never restarts. If preparation exhausts the
budget, the gateway rejects the request before dispatch.

`outputIdleSeconds` starts when provider work is dispatched and restarts after each useful
output, including text, reasoning, tool output or media. Headers, keepalives, usage-only updates
and empty lifecycle events do not restart it. Buffered requests expose no intermediate output,
so this limit applies until the complete response arrives. Increase it for long silent reasoning;
setting it equal to the total limit leaves the total deadline as the effective bound.

The earlier deadline wins. Required values combine by minimum **for each field** across applicable
policies. A child cannot lengthen a parent's requirement. Conditional defaults can be replaced
independently, and permitted request policies can set either field. See [scopes and inheritance](/docs/policies/scopes).

Expiry ends the response with `request_timeout`: HTTP 504 before the response starts, or an
error event after streaming begins. It never triggers an automatic retry or fallback.
Dispatched provider work continues under the gateway's separate 60-minute execution limit.
Stogas keeps reading its response and bills the returned usage, including usage received after
your response ends. A short timeout does not limit the cost of already dispatched inference.
Client-library retries are separate; configure them to avoid replaying a timed-out request
whose outcome is unknown.

## Plugins

Plugins use the same policy scopes and inheritance rules:

| Plugin                                       | Use it to                                           |
| -------------------------------------------- | --------------------------------------------------- |
| [PII Redaction](/docs/plugins/pii-redaction) | Remove sensitive text before provider dispatch.     |
| [Export](/docs/plugins/export)               | Send request and response JSON to your own webhook. |

[Text extraction](/docs/input-files#text-extraction) converts inline UTF-8 file content before
input checks and redaction. [Encrypt plugin settings](/docs/cli#encrypt-plugin-settings) to keep
private rules and destination credentials unreadable when saved.

## Policies for one request

The optional inference-request `policy` field accepts permitted routing, timeouts, access, input and
plugin settings, including flat conditional rules. It cannot define shared limits. See
[Request policies](/docs/policies/request-policies) for permissions and examples.

A policy governs an existing credential. It does not create keys, grant membership, or add funds.
See [API keys and grants](/docs/api-keys) for credential management and [BYOK](/docs/byok) for
provider credentials.
