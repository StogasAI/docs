## Who can edit

| Scope          | Who can edit                                                                                     |
| -------------- | ------------------------------------------------------------------------------------------------ |
| Organization   | Members who manage all API keys                                                                  |
| Folder         | The folder's managers, and members who manage all API keys                                       |
| Grant          | The grant's managers, its folder's managers, and members who manage all API keys                 |
| Member or role | Members who manage all API keys                                                                  |
| Credential     | Members who manage credentials                                                                   |
| API key        | The key's owner and managers, its folder and grant managers, and members who manage all API keys |

A parent policy can [limit which sections](/docs/policies/delegation) anyone can save.

## Save a policy

- A save replaces the whole policy at that scope. The gateway checks it together with the other
  policies that apply there, and checks
  an [encrypted export or redaction](/docs/customer-encryption#encrypt-plugin-settings) only when
  a request or a [policy check](#check-a-policy-before-saving) sends its key.
- A save names the revision that you edited, and fails with `409 POLICY_CHANGED` if someone saved
  a newer one. The dashboard and the CLI then merge your changes into it for you to review.
- Each save that changes a policy adds a version, and so does creating a key or grant with a
  policy. In any 24 hours your organization can add 10,000 versions and 16 MiB of policy content
  that it has not saved before, and one member can add half of each. A save past a limit fails
  with `429 POLICY_VERSION_LIMIT`, whose message says when the same save fits. A return to an
  earlier policy adds a version and no content, and clearing a policy adds no version.
- Your organization keeps up to 1,024 MiB of policy history, which counts each policy content once
  and 640 bytes for each version. At that limit a save of content that the history does not hold
  fails with `409 POLICY_HISTORY_LIMIT`, and you can still return to an earlier policy or clear
  one. We can raise the limit for your organization, which raises the limits for 24 hours in
  proportion.
- A parent save can make a policy below it invalid. That policy stays readable so that its manager
  can fix it.
- Enabled state and expiration are settings of the resource, not of its policy.
- See [When changes take effect](/docs/policies/scopes#when-changes-take-effect).

## Simulate routing

**Routing simulation** lists the deployments and credentials that a request would try with your
draft, in order. It calls no model and costs nothing.

- The draft replaces the saved policy at its scope. A credential policy draft applies wherever the
  key uses that credential. Enabled state, expiration and other changes apply after you save.
- The request uses Responses and sends every registered encryption key, no `service_tier` and no
  system message. `request.bodyBytes` is 0, and the simulation reads no
  [request policy](/docs/policies/request-policies) or `provider` preference.
- It uses the current catalog and time, so `access.schedule` periods and rules that read
  `request.time` apply as they would now. It routes as a request from an address that every
  `access.networks` setting accepts, in a mode that every `access.transports` setting accepts.
- It does not check [limits](/docs/policies/limits), your balance or provider errors. Retries and
  fallbacks after a failed call happen only on real requests.

## Check a policy before saving

[`POST /v1/policies/validate`](/docs/reference/policies/validatePolicy) checks the policies that
would apply to a request, without saving them or calling a model. Send the draft in place of the
saved version of its scope:

```jsonc title="Request"
// POST https://api.stogas.ai/v1/policies/validate
// Authorization: Bearer $STOGAS_API_KEY
{
	"policySources": [
		{ "scope": "organization", "config": { "input": { "asciiOnly": true } } },
		{ "scope": "role", "id": "<role ID>", "config": { "timeouts": { "totalSeconds": 120 } } },
		{ "scope": "key", "config": null } // null is an empty policy.
	],
	"encryption_keys": { "default": "<key>" } // Optional. Checks encrypted exports and redactions.
}
```

- Include exactly one organization and one key policy, plus each folder, grant, member and
  credential policy that applies. Give each role its own entry with its `id`, up to 30.
- An encrypted export or redaction is checked only with its
  [key](/docs/customer-encryption#send-the-key-with-a-request). Send the key the same way as with
  inference requests.

```json title="Response"
{ "status": "partial", "uncheckedPlugins": [{ "scope": "organization", "plugin": "redaction" }] }
```

| Result                               | Meaning                                                                                     |
| ------------------------------------ | ------------------------------------------------------------------------------------------- |
| `"status": "valid"`                  | Every policy passed, including conditional rules that would not apply now.                  |
| `"status": "partial"`                | The rest passed. `uncheckedPlugins` names each encrypted plugin whose key you didn't send.  |
| `400` with `invalid_policy`          | A policy is invalid. The message does not say which one, to keep encrypted content private. |
| `400` with `encryption_key_required` | A key or label has the wrong format.                                                        |

Saving also checks spending and rate limits, editing permissions and conflicts with other edits.
Validation counts redaction limits as if every conditional rule applied at once.

## Read inherited policies

Anyone who can read a key can read every policy that applies to it. Plaintext settings are visible
to them, so [encrypt the exports and redactions](/docs/customer-encryption#encrypt-plugin-settings)
that only some people should read. Reading a policy does not give permission to change it.

## Document rules

- `null` clears a policy. `{}`, or a document with only `$schema`, saves as `null`.
- Leave out settings that you do not use. No field is required.
- Unknown fields, duplicate keys and invalid expressions are rejected.
- Scope and resource IDs come from where you save the policy, not from fields in it.

| Size                                                         | Limit   |
| ------------------------------------------------------------ | ------- |
| A saved policy, as compact UTF-8 JSON                        | 256 KiB |
| A [request policy](/docs/policies/request-policies), as sent | 16 KiB  |
| All policies that apply to one request, combined             | 512 KiB |

Encrypted settings count by their decrypted size. Settings that several policies share count once.
`policy_work_limit_exceeded` means that the policies of all credentials that a request could use
are too large or complex together. Simplify them, or use fewer distinct credential policies.

## Use an external editor

Add the schema URL to get field completion in any JSON editor:

```json
{
	"$schema": "https://stogas.ai/schemas/key-config-v1.json"
}
```

The schema checks the structure. Saving also checks expressions, permissions and how the policy
combines with others.

[`stogas policy edit`](/docs/cli#edit-a-policy) opens a saved policy in your own editor with the
schema URL already in place, and saves it when you close the file.
