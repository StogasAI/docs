title: Timeouts
description: Limit how long a caller waits for a request and for each provider output.

Requests wait up to **60 minutes in total**. By default no shorter limit applies while a model
works without sending output. Set either limit in whole seconds from 1 through 3600:

```json title="policy.json"
{
	"timeouts": {
		"totalSeconds": 900,
		"outputIdleSeconds": 120
	}
}
```

| Field               | Starts                                                 | Restarts                 |
| ------------------- | ------------------------------------------------------ | ------------------------ |
| `totalSeconds`      | When the gateway admits the request body               | Never                    |
| `outputIdleSeconds` | At each provider call, including retries and fallbacks | After each useful output |

`totalSeconds` includes policy checks, preparation, authorization and provider work. If
preparation uses up the time, the request fails before the gateway calls the provider.

Useful output is text, reasoning, tool output or media. Headers, keepalives, usage-only updates and
empty lifecycle events do not restart `outputIdleSeconds`. A buffered request has no output until
the full response arrives, so the limit covers the whole provider call. If you set it equal to
`totalSeconds`, only the total limit applies.

Many models reason for minutes without sending output, because some send reasoning text only on
request and others never do. A timeout does not stop the provider's work or its charge, so by
default the gateway waits for that work.[^chutes] Set `outputIdleSeconds` for callers that should
give up sooner when a provider stops sending output.

## How policies combine

For each field, the smallest required value of the policies that apply wins, so a child cannot
lengthen a parent's limit. [Defaults](/docs/policies/rules#defaults) can be replaced field by
field, and permitted [request policies](/docs/policies/request-policies) can set either field.

- One `totalSeconds` applies to the whole request. Credential policies, and rules whose condition
  reads more than `request` fields, cannot set it.
- `outputIdleSeconds` can differ by deployment. Each provider call, including a fallback, uses the
  value for its own deployment and credential:

```json title="Shorter output wait for Claude Haiku"
{
	"rules": {
		"fast_models": {
			"when": "'claude-haiku' in model.groupIds",
			"timeouts": { "outputIdleSeconds": 120 }
		}
	}
}
```

## When a timeout expires

The response ends with `request_timeout`: HTTP 504 before the response starts, or an error event
in a stream that has started. The gateway does not retry or try another deployment. A provider's
own `408` or `504` response also ends the request, with
[`upstream_outcome_unknown`](/docs/reference/errors#504-gateway-timeout), because the provider may
have run it.

A timeout ends only your wait. Once the gateway has called the provider, the provider work continues
up to 60 minutes.[^chutes] The gateway keeps reading the response and bills the usage, including
usage that arrives after your response ended, so a short timeout does not limit the cost of a request
that was sent. The response then has `X-Should-Retry: false`, which the OpenAI and Anthropic SDKs
follow. Set other clients so they do not send a timed-out request again when its outcome is unknown.
