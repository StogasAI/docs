Settings at the top level of a policy apply to every request. Put settings in a named rule under
`rules` to change that:

| Rule            | Field               | Settings apply                                              |
| --------------- | ------------------- | ----------------------------------------------------------- |
| Conditional     | `when`              | Only to requests and deployments that match a condition     |
| With exclusions | `exclude`           | To every key except the ones that the rule lists            |
| Default         | `"mode": "default"` | Only when no other policy requires the same kind of setting |

```json title="Organization policy"
{
	"rules": {
		"redact_openai": {
			"when": "provider.id == 'openai'",
			"plugins": { "redaction": { "presets": ["email_address"] } }
		},
		"cheapest_first": {
			"mode": "default",
			"routing": { "sort": [{ "by": "blendedPrice(3, 1)" }] }
		}
	}
}
```

The first rule redacts email addresses only in requests to OpenAI. The second tries the cheapest
deployment first among those that the orders of other policies leave tied.

## Conditional rules

`when` is an [expression](/docs/policies/expressions) that returns `true` or `false`. A rule
without `when` always applies.

```json title="Large requests go only to providers that keep no data"
{
	"rules": {
		"large_requests": {
			"when": "request.bodyBytes > 1000000",
			"routing": { "filter": "deployment.dataHandling.zeroDataRetention == true" }
		}
	}
}
```

What the condition reads decides where the rule applies:

| Condition reads                                                 | Example                       | Rule applies to          |
| --------------------------------------------------------------- | ----------------------------- | ------------------------ |
| Only `request` fields                                           | `request.bodyBytes > 1000000` | The whole request        |
| An `author`, `model`, `deployment`, `route` or `provider` field | `provider.id == 'openai'`     | Each matching deployment |

When a condition reads deployment fields, the rule's settings apply only while a matching deployment
serves the request. A deny period in such a rule removes only the matching deployments, and the
gateway tries the others.

- Conditions read the same [request facts](/docs/policies/expressions#request-facts) as routing
  filters, before redaction. They cannot read usage, balances, token estimates or provider
  responses.
- If a missing value leaves a condition undecided for a deployment or credential, the gateway skips
  that choice and tries the others. Check optional fields with `has(...)`.
- An error in a condition, such as division by zero, fails the request.
- Limits in a rule count only the requests that the rule matches. See
  [Conditional limits](/docs/policies/limits#conditional-limits).

## Exclusions

```json title="Organization policy"
{
	"rules": {
		"redact_email": {
			"exclude": {
				"keys": ["0195ef30-7b1a-7000-8000-000000000001"],
				"grants": ["0195ef30-7b1a-7000-8000-000000000002"]
			},
			"plugins": { "redaction": { "presets": ["email_address"] } }
		}
	}
}
```

Every key in the organization redacts email addresses, except the listed key and the keys under
the listed grant. `exclude` lists resources by ID, and a key skips the whole rule when a list names
the key, its folder, its grant or its owner:

| List      | Keys that skip the rule              | Policies that can use it                    |
| --------- | ------------------------------------ | ------------------------------------------- |
| `folders` | Every key in the folder              | Organization                                |
| `grants`  | The member keys under the grant      | Organization, and the grant's folder        |
| `members` | The member keys that the member owns | Organization, folder and grant              |
| `keys`    | The key                              | Organization, and the key's folder or grant |

- A skipped rule requires nothing for the key, so [defaults](#defaults) of the same kind apply to
  it again.
- Limits in the rule do not count the key's requests. When you remove the exclusion, the limits
  count only the key's later requests. Changing the lists keeps the limits' usage.
- Only the members who can edit the policy can change its lists. Role, member, credential, key and
  request policies cannot use `exclude`, so no key can exempt itself.
- Everyone who can create a key in a listed folder or under a listed grant can create a key that
  skips the rule.
- An ID that you add must name an existing resource under the policy. A list keeps the ID of a
  resource that is deleted later, and that ID matches nothing.
- A rule can have both `when` and `exclude`. A rule that sets `routing.sort` cannot have
  `exclude`.
- In a **Combined policy**, a rule that the key skips has `skipped`, which names the listed
  resource. The combined policy leaves out the lists themselves.

## Defaults

A setting is required unless it is in a rule with `"mode": "default"`. A default applies only when
no policy requires a setting of the same kind:

```json title="Organization policy"
{
	"rules": {
		"prefer_long_context": {
			"mode": "default",
			"routing": {
				"sort": [{ "by": "deployment.contextWindowTokens", "direction": "desc" }]
			}
		}
	}
}
```

Sort criteria never replace each other. A key policy's own `routing.sort` comes first, and this
default orders only the deployments that the key's criteria leave tied. See
[Orders from several policies](/docs/policies/routing#orders-from-several-policies). Other settings
replace defaults of the same kind:

| Kind               | Includes                                                            |
| ------------------ | ------------------------------------------------------------------- |
| Each access field  | `schedule`, `networks`, `countries` or `transports`                 |
| Each input field   | `asciiOnly` or `mediaTypes`                                         |
| Each timeout       | `totalSeconds` or `outputIdleSeconds`                               |
| Each routing field | One field, except `sort`, whose criteria add up                     |
| Each plugin        | `redaction`, `export`, `promptCaching` or `classification`          |
| Each file family   | `text`, `office` or `pdf` of `textExtraction`, with its media types |

- A required plugin setting replaces only the default of the same plugin. A required text
  extraction mode replaces the default modes of the same file family, and leaves the other family,
  default redaction and default export destinations in place.
- When several policies set defaults of the same kind, they
  [combine](/docs/policies/scopes#how-settings-combine) like required settings. Default sort
  criteria apply from the closest policy out.
- [Limits](/docs/policies/limits) cannot be defaults.

### See which defaults apply

In a **Combined policy**, each default rule lists the settings that required settings replace in
`replaced`, with the policy that requires each one and, for a required rule, its name. `others`
counts further requirements that replace the same setting.

### Replace a default without adding a restriction

Set a neutral value. It replaces the defaults of its kind and never removes a required setting of
another policy:

| Kind                    | Neutral value                                  |
| ----------------------- | ---------------------------------------------- |
| ASCII only              | `"input": { "asciiOnly": false }`              |
| Media types             | `"input": { "mediaTypes": { "deny": [] } }`    |
| Deny periods            | `"access": { "schedule": { "deny": [] } }`     |
| Networks                | `"access": { "networks": { "deny": [] } }`     |
| Countries               | `"access": { "countries": { "deny": [] } }`    |
| Connection modes        | `"access": { "transports": { "deny": [] } }`   |
| Each timeout            | `3600`                                         |
| Routing filter          | `"filter": "true"`                             |
| Each catalog ID list    | `"providers": { "deny": [] }`, or another kind |
| Retries                 | `"retries": 3`                                 |
| Fallbacks               | `"fallbacks": 2`                               |
| Missing encryption keys | `"missingEncryptionKeys": "skip"`              |
| Text extraction         | `"textExtraction": { "text": "off" }`          |
| Redaction               | `"redaction": {}`                              |
| Export                  | `"export": { "destinations": [] }`             |
| Prompt caching          | `"promptCaching": "off"`                       |
| Classification          | `"classification": []`                         |

## What rules can contain

- Rules can contain `access`, `input`, `timeouts`, `limits`, `plugins` and `routing`. They cannot
  contain other rules, `delegation` or `encryption`.
- A rule can set `routing.sort` only with `"mode": "default"` and no `when`. See
  [Orders from several policies](/docs/policies/routing#orders-from-several-policies).
- A rule that sets `routing.fallbacks` or `timeouts.totalSeconds` can read only `request` fields,
  because one fallback count and one total wait apply to the whole request.
- Rules have no order. A name identifies a rule and its limits. Names use 1–48 lowercase letters,
  digits, `_` or `-`, start with a letter, and cannot be `constructor` or `prototype`.
