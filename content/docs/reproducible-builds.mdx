Hardware attestation reports a measurement of the software that a gateway VM booted. A measurement
is useful only if you can tell which source code produced it. Every gateway release builds
reproducibly: you can rebuild it from the public source on your own machine and get the same bytes
and the same launch measurement. You do not need to trust the binaries that we or GitHub
publish.

## What runs in a gateway

The gateway VM boots one image with no disk, shell or package manager:

| Layer    | Component                                                                                                                                                   |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Firmware | OVMF from edk2, built for AMD SEV with its own ACPI tables, to boot only the measured kernel and to run no code from the host                               |
| Kernel   | Linux-libre with a reduced guest configuration, no loadable modules and no console output                                                                   |
| Boot     | A unified kernel image built with systemd's `ukify`                                                                                                         |
| Init     | A small init process written in Go                                                                                                                          |
| Clock    | The [ntpd-rs](https://github.com/pendulum-project/ntpd-rs) client, which keeps the guest clock in sync                                                      |
| Gateway  | The [Stogas gateway](https://github.com/StogasAI/gateway), built with Go, with the [Rust verifier](https://github.com/StogasAI/stogas) linked in statically |

The launch measurement covers all of it. Changing one byte in any layer gives a different
measurement, which the SDK rejects. Each release's `stogas/release/pins.lock.json` gives the exact
version of every component.

## How the build stays reproducible

- **Every input is pinned.** The release tag fixes the source tree. `pins.lock.json` fixes each
  upstream source by commit and content hash. `go.sum` and the Cargo lock files fix the version
  and hash of every dependency, and each GitHub Action is pinned by commit.
- **The repository holds no copies of dependencies.** The build downloads each one from its
  upstream project or registry, and each download must match its pinned hash. You fetch the same
  sources that we fetched, instead of trusting a copy in the gateway repository.
- **Patches are small and separate.** Each patched upstream project has one patch file in
  `stogas/release/patches/`. The patches for
  [virt-firmware-rs](https://gitlab.com/kraxel/virt-firmware-rs) and the `igvmmeasure` tool from
  [COCONUT-SVSM](https://github.com/coconut-svsm/svsm) fix how the four-CPU VM is measured, and
  include tests. The edk2 patch makes the firmware boot only the measured kernel and gives the
  guest fixed ACPI tables in place of the ones the host supplies.
- **Compilers trace back to source.** [GNU Guix](https://guix.gnu.org) supplies every compiler and
  tool from a Guix revision fixed by commit in `guix/channels.scm` and authenticated by its signing
  key. Guix builds its compilers, such as GCC and Rust, from a small binary seed through its
  [full-source bootstrap](https://guix.gnu.org/manual/en/html_node/Full_002dSource-Bootstrap.html).
  Go, the kernel, the firmware, the IGVM tools and the verifier build from their pinned sources.
- **Builds run offline.** Only the source downloads use the network. Guix builds every package
  without network access. The build fixes timestamps, locale, time zone and file permissions, and
  removes build paths from the binaries.

## Two independent builds

GitHub Actions and GitLab.com's hosted runners each build every release tag and sign a build proof
for the image and its release manifest. GitHub's build takes prebuilt Guix packages from
ci.guix.gnu.org first and GitLab's from bordeaux.guix.gnu.org first, so a package that both Guix
build farms publish but built differently changes the manifest. We approve a release only when both
proofs name the same `release-manifest.json` and image. The manifest records the source commit and
its SHA-256 digest, every input hash, the compiler and tool versions, the image hash and the launch
measurement.

Your own build is a third, independent check.

## Rebuild a release

You need an x86_64 Linux machine with Git, Node.js, curl and a working Guix daemon.

<Steps>
<Step>

### Get the source

```console
git clone https://github.com/StogasAI/gateway
cd gateway
git checkout v<version>
```

</Step>
<Step>

### Install the pinned Guix

Skip this step if Guix is already installed. The script needs `sudo`:

```console
stogas/release/scripts/install-guix-bootstrap.sh
```

</Step>
<Step>

### Build

```console
stogas/release/scripts/build-release.sh v<version> ../build
```

The script checks the pins, downloads the inputs and builds offline. Read the patches in
`stogas/release/patches/` to see every change to upstream code.

</Step>
<Step>

### Compare

Download `release-manifest.json` from the
[gateway release](https://github.com/StogasAI/gateway/releases) and compare it with yours:

```console
cmp ../build/release-manifest.json release-manifest.json
```

No output means the builds match. The manifest's launch measurement is the value that the
[Trust Center](/docs/verification#trust-center) shows for gateways that run this release.

</Step>
</Steps>

<Callout title="Prebuilt Guix packages">
	{' '}
	Guix downloads its own prebuilt packages, such as GCC and Rust, from its two build farms and
	checks their signatures. The farms build each package separately. The build script takes packages
	from `bordeaux.guix.gnu.org` first, and GitHub's release build takes them from `ci.guix.gnu.org`
	first. A package that both farms publish but built differently therefore enters the two builds as
	different bytes, so matching manifests show that neither farm's copy of it changed the image. A
	package that only one farm publishes enters both builds from that farm. To build every tool on
	your machine instead, run the Guix daemon with `--no-substitutes`. Guix then builds its compilers
	from the small binary seed. This takes much longer.{' '}
</Callout>

## Check the build proofs

To check that GitHub's release workflow built an image from its tag, without a rebuild, use the
[GitHub CLI](https://cli.github.com/):

```console
gh attestation verify gateway.igvm --repo StogasAI/gateway \
  --signer-workflow StogasAI/gateway/.github/workflows/gateway-igvm-release.yml \
  --source-ref refs/tags/v<version> --deny-self-hosted-runners
```

GitLab's proof is `gitlab-attestation.jsonl` in the release. Check it with
[cosign](https://github.com/sigstore/cosign):

```console
cosign verify-blob-attestation gateway.igvm --bundle gitlab-attestation.jsonl \
  --type https://slsa.dev/provenance/v1 --certificate-oidc-issuer https://gitlab.com \
  --certificate-identity https://gitlab.com/stogasai/gateway//.gitlab-ci.yml@refs/tags/v<version>
```

Our signed evidence lists both proofs with each release. The SDK checks both, and our approval,
before it trusts a gateway. See [Gateway verification](/docs/verification).

## Rebuild a catalog

```console
git clone --branch catalog-v<sequence> https://github.com/StogasAI/catalog
cd catalog
node source/scripts/build.mjs --check
node source/scripts/create-proposal.mjs <sequence> release-proposal
gh release download catalog-v<sequence> --repo StogasAI/catalog --dir ../release
cmp release-proposal/catalog-release.json ../release/catalog-release.json
cmp release-proposal/catalog.json ../release/catalog.json
```

You need Git, Node.js, the GitHub CLI and the [CUE](https://cuelang.org) release that
`source/scripts/gitlab.sh` downloads. `build.mjs --check` compiles the catalog from its records
and fails unless the committed catalog equals the result. The manifest `catalog-release.json` names
the source commit and the SHA-256 of the root `catalog.json`, and the root names every part by its
SHA-256, so equal files mean an equal catalog.

GitHub Actions and GitLab.com's hosted runners each build every catalog release from its tag and
sign a build proof for the manifest and the root. We approve a catalog only when both proofs name
the files of our own build. Check the proofs as for a gateway release:

```console
gh attestation verify catalog.json --repo StogasAI/catalog \
  --signer-workflow StogasAI/catalog/.github/workflows/catalog-release.yml \
  --source-ref refs/tags/catalog-v<sequence> --deny-self-hosted-runners
cosign verify-blob-attestation catalog.json --bundle gitlab-attestation.jsonl \
  --type https://slsa.dev/provenance/v1 --certificate-oidc-issuer https://gitlab.com \
  --certificate-identity https://gitlab.com/stogasai/catalog//.gitlab-ci.yml@refs/tags/catalog-v<sequence>
```

## Verify an SDK download

Each [SDK release](https://github.com/StogasAI/stogas/releases) lists every file with its SHA-256
in `release-manifest.json`. GitHub's build proof covers each file. A full release also has GitLab's
build proof of each file and our signature of the manifest. A preview, such as an alpha version, has
no signature, and it has GitLab's proof only when the release lists `gitlab-attestation.jsonl`.
npm, PyPI, crates.io, RubyGems and Maven Central serve the same bytes as the release. NuGet adds its
own repository signature. Maven Central also serves a Sigstore signature of each file,
`<file>.sigstore.json`, which
`https://github.com/StogasAI/stogas/.github/workflows/publish.yml@refs/tags/v<version>` makes. Go
downloads the module from the `go/v<version>` tag, which has the same files as
`stogas-go-v<version>.tar.gz`. The container image `ghcr.io/stogasai/stogas:<version>` is
`stogas-container-v<version>.tar`, an OCI image layout that `docker load` reads, and the registry
serves it under the digest in that file's `index.json`.

Check that the release workflow built a file from its tag. For the container image, use
`oci://ghcr.io/stogasai/stogas:<version>` in place of the file:

```console
gh attestation verify <file> --repo StogasAI/stogas \
  --signer-workflow StogasAI/stogas/.github/workflows/release.yml \
  --source-ref refs/tags/v<version> --deny-self-hosted-runners
```

GitLab.com's hosted runners also build every full release from its tag, and
`gitlab-attestation.jsonl` holds their proof for every file. Check it with
[cosign](https://github.com/sigstore/cosign):

```console
cosign verify-blob-attestation <file> --bundle gitlab-attestation.jsonl \
  --type https://slsa.dev/provenance/v1 --certificate-oidc-issuer https://gitlab.com \
  --certificate-identity https://gitlab.com/stogasai/stogas//.gitlab-ci.yml@refs/tags/v<version>
```

To check both build proofs and our signature of a full release at once, put these release files in
a directory with the files you want to check: `release-manifest.json`, `qualification.json`,
`github-attestation.jsonl`, `gitlab-attestation.jsonl` and `stogas-signature.json`. Then run:

```console
stogas verify-release <directory>
```

The command lists each file it checked and rejects any other file in the directory. It takes
Sigstore's current keys from our published evidence, where Sigstore's own signatures authenticate
them, so it trusts no server for them. To work offline, save
`https://evidence.stogas.ai/evidence/latest.json` and add `--evidence <file>`. Use a `stogas`
[CLI](/docs/cli) that you already trust, and check your first CLI download with
`gh attestation verify`.

We sign an SDK release only when GitLab's build matches GitHub's. GitLab's hosted runners build
every platform except Apple from the tag, package every file again and sign their own build proof,
and every file must match GitHub's build byte for byte. Apple's compilers run only on Apple
hardware, so GitLab packages the compiled Apple libraries from GitHub's build, and its proof lists
them as inputs. A key that our root key
authorizes makes the signature, and Rekor logs it. `qualification.json` records GitHub's tests of the installed
packages on each platform, including Android on an emulator and real iPhones and Android
phones. GitHub makes its build proof only after every test passes, and that one proof covers the
test report too.

## Rebuild an SDK release

```console
git clone --branch v<version> https://github.com/StogasAI/stogas
cd stogas
gh release download v<version> --repo StogasAI/stogas --dir ../release
python3 release/release.py rebuild ../release --out ../rebuild
python3 release/release.py compare ../rebuild/release/packages ../release
```

You need an x86-64 machine with Git, Python 3, the GitHub CLI, Docker and about 45 GB of free disk
space, most of it for the build images. A rebuild takes about 75 minutes with 4 or more CPUs.
`rebuild` builds every platform except Apple from the tag in the pinned Docker images that GitHub's
and GitLab's builds used, and packages every language package again. Apple's compilers run only on
Apple hardware, so it packages the compiled Apple libraries from the release instead. `compare`
fails unless each file matches the release byte for byte.

The build images run x86-64 tools, and their Rust compiler crashes under QEMU, the x86-64 emulation
that Docker uses on ARM Linux. On Windows, run the commands in WSL 2, in a directory in WSL's own
file system, such as your home directory there.

## Closed-source components

| Release                                                 | Closed-source code in its files                               |
| ------------------------------------------------------- | ------------------------------------------------------------- |
| Gateway image                                           | None                                                          |
| Catalog                                                 | None                                                          |
| SDK and CLI for Linux, Android, Windows and WebAssembly | None                                                          |
| SDK and CLI for macOS and iOS                           | None, but Apple's closed-source Xcode compiles and links them |

The Windows files link the open-source mingw-w64 runtime in place of Microsoft's Visual C++
runtime. No one but Apple can inspect the tools that produce the Apple files, and only GitHub's
macOS runners build them. On Windows and Apple systems our files also call the system's own
libraries, as every program there does.

## Scan an SDK download for vulnerable crates

```console
cargo audit bin stogas
```

The CLI, the native libraries, the Python extension and the WebAssembly modules list the Rust crates
they contain and their versions. `cargo audit bin`, Trivy and Grype read that list, and so does
osv-scanner when it scans the CLI's container image. The static libraries for C, Go and iOS carry no
list, so check them against `Cargo.lock` at the release tag.
