---
title: API key configuration
description: Set routing, access periods, limits, and request redaction in one versioned JSON document.
---

Organizations, grants, and API keys use the same versioned JSON policy. Edit the organization policy
from API Keys, the grant policy in its editor, or a key policy on its detail page. Stogas validates
the full intersection before it saves any change.

```json title="key-config.json"
{
	"$schema": "https://stogas.ai/schemas/key-config-v1.json",
	"version": 1,
	"routing": {
		"query": "where deployment.data.dataHandling.trainingUse == false\n  and deployment.data.dataHandling.tee == true\norder by deployment.data.pricing.input_tokens.per_mill_tokens asc",
		"allowedCatalogNodes": {
			"providers": ["openai", "chutes"]
		},
		"fallbacks": {
			"maxPreDispatchCandidates": 2
		}
	},
	"limits": {
		"requests": {
			"max": 60,
			"window": { "count": 1, "unit": "minute" },
			"burst": 10
		},
		"spend": {
			"lifetimeUsd": "500.00",
			"recurring": {
				"maxUsd": "100.00",
				"window": { "count": 1, "unit": "month" },
				"timeZone": "UTC"
			}
		}
	},
	"expiresAt": "2026-12-01T00:00:00Z"
}
```

JSON is the only configuration format in version 1. It gives command-line tools, agents, editors,
and the dashboard one exact schema. Stogas stores canonical JSON, so comments and whitespace are not
preserved.

## Policy scopes

The effective policy is the intersection of organization, grant (for member keys), key, and permitted
request restrictions. Service keys have no grant. An omitted setting inherits its parent restriction;
it does not remove it.

| Setting                    | Combination                                                                                |
| -------------------------- | ------------------------------------------------------------------------------------------ |
| Routing filters            | Every scope must match.                                                                    |
| Allowed catalog nodes      | Intersect each list. An empty list denies all candidates.                                  |
| Sort fields                | Parent fields first; child fields break ties. Repeated fields keep the parent's direction. |
| Expiration                 | Earliest timestamp.                                                                        |
| Deny periods and redaction | Apply every restriction; duplicates are removed.                                           |
| Pre-dispatch candidates    | Smallest explicit maximum; default is one.                                                 |
| Request and spend limits   | Enforce each scope separately, including its own window.                                   |

Organization limits are shared by all its keys. Grant limits are shared by all keys under that grant,
not copied to each member. Key limits apply only to that key. The effective configuration lists limits
under `organization`, `grant`, and `key` so their scope stays clear. Parent edits atomically update all
affected keys. They do not replace a child's saved source or manual enabled setting.

## Request policies

Request policies are disabled by default. Set `routing.requestPolicy` to `filter` to permit request
filters, or `filter_and_sort` to also permit sorting. Set it to `deny` to prohibit both.
The organization can constrain this permission. A grant must explicitly permit it for member keys;
a service key must explicitly permit it for itself. A member key inherits its grant's permission and
can reduce it. No child can increase a parent's permission.

When permitted, Chat Completions and Responses accept a `policy` field:

```json
{
	"model": "gpt-5.5",
	"messages": [{ "role": "user", "content": "Hello" }],
	"policy": {
		"version": 1,
		"routing": {
			"query": "where deployment.data.dataHandling.trainingUse == false",
			"allowedCatalogNodes": { "providers": ["openai"] }
		}
	}
}
```

Only `version`, `routing.query`, and `routing.allowedCatalogNodes` are accepted. A request cannot
change limits, redaction, expiration, or permissions. The document is limited to 16 KiB and the same
query and node-list bounds as a saved source. Stogas consumes it before provider dispatch; it is never
sent upstream. A prohibited request policy returns `403`; invalid permitted policies return `400`.
The standard model and provider selectors remain available and must also satisfy the saved policy.

## Routing query

The query can filter catalog candidates and sort the candidates that remain. It is not SQL and it
cannot run code.

```text
where provider.id in ['openai', 'chutes']
  and deployment.data.capabilities.streaming == true
order by deployment.data.pricing.output_tokens.per_mill_tokens asc
```

Use single quotes for values inside a JSON query string. A provider ID such as `openai` needs no
escaped double quotes.

Version 1 supports only:

- `where` and `order by`;
- `and`, `or`, and `not`;
- `==`, `!=`, `<`, `<=`, `>`, and `>=`;
- `in`, `contains`, and `exists`;
- parentheses;
- string, integer, Boolean, and list values; and
- `asc` and `desc`.

It does not support joins, regular expressions, arithmetic, functions other than `exists`, automatic
type conversion, scripts, network access, random values, or current time.

`and` binds before `or`. Use parentheses when that order is not clear. `contains` checks for a
substring in a string or an exact item in a string list. `in` checks one scalar value against a list.

A missing value does not match any comparison, including `!=`. `not` does not turn a missing value
into a match. Test presence with `exists()`:

```text
where deployment.data.dataHandling.tee == true
  and deployment.data.dataHandling.teeVerified == true
```

Stogas rejects an unknown path or a value of the wrong type when you save the configuration. A query
can contain at most 4,096 characters, 64 expression nodes, 12 nested expressions, 32 values in one
list, four configured sort fields, and 1,024 UTF-8 bytes in one string value. When `order by` is
present, Stogas uses `deployment.id asc` after all scope sort fields as the final tie-breaker. An explicit
`deployment.id asc` ends the order at that scope. A filter-only query keeps the
client's provider order.

`order by` is optional at every configuration scope. An organization does not need a default
provider sort. Without a configured sort or request order, Stogas uses the model author's provider
when it remains usable. If no author provider remains and the choice is still ambiguous, the request
fails with the valid provider-qualified selectors instead of choosing one silently.

### Field paths

The resolved catalog chain has five nodes. Each node exposes its stable ID and its registered catalog
data:

| Root         | Available paths                                                                                     |
| ------------ | --------------------------------------------------------------------------------------------------- |
| `author`     | `author.id`, `author.data.name`, `author.data.aliases`                                              |
| `model`      | `model.id` and scalar or list fields under `model.data`                                             |
| `deployment` | `deployment.id` and scalar or list fields under `deployment.data`                                   |
| `route`      | `route.id`, `route.data.providerId`, `route.data.interfaces`                                        |
| `provider`   | `provider.id`, `provider.data.name`, `provider.data.aliases`, `provider.data.credentialModes`       |
| `request`    | `request.estimatedInputTokens`, `request.maximumOutputTokens`, `request.model`, and `request.route` |

There are no shortcut `pricing` or `capability` roots. For example, use
`deployment.data.capabilities.streaming` and
`deployment.data.dataHandling.trainingUse`. Deployment precision is available as
`deployment.data.weightPrecision` when the catalog defines it.

Deployment pricing paths have this form:

```text
deployment.data.pricing.<meter>.<rate>
```

Token meters are `input_tokens`, `cached_input_tokens`, `cache_write_input_tokens`,
`cache_write_5m_input_tokens`, `cache_write_1h_input_tokens`, `output_tokens`, and
`reasoning_tokens`. Their rate is `per_mill_tokens`, `per_mill_context_lte_272k`, or
`per_mill_context_gt_272k`.

Call meters use `per_1k_calls`. The one exception is
`openai_chat_completion_search_preview_model_calls`, which uses the low, medium, and high search
context rates. A rate that is valid for one meter is not automatically valid for another meter.

The configuration schema exposes only registered scalar and list fields. It does not allow an
unchecked path into catalog JSON. Live health and recent latency are not routing fields in version 1.

A model selector starts with each provider's default deployment. A filter or explicit sort can select
a compatible geography or hosting variant. Stogas does not cross the selected service tier or
reasoning mode. A deployment selector stays pinned to that exact deployment.

The `request` values are safe estimates made before authorization. `estimatedInputTokens` is the
conservative input-token hold estimate. Encrypted reasoning can force it to the deployment's input
limit because Stogas cannot inspect that content. `maximumOutputTokens` is the accepted output
limit. Neither value is final usage.

## Allowed catalog nodes

Use `allowedCatalogNodes` when exact IDs are clearer than a query:

```json
{
	"version": 1,
	"routing": {
		"allowedCatalogNodes": {
			"models": ["gpt-5"],
			"providers": ["openai"]
		}
	}
}
```

A candidate must match every list that is present. An empty list denies all candidates. Omitted lists do not restrict that node type. The
five lists can contain at most 64 IDs in total. IDs are checked against the active catalog at request
time, so an ID that is no longer available cannot route a request.

## Pre-dispatch candidates

`maxPreDispatchCandidates` can be 1, 2, or 3. The default is 1.

This setting does **not** retry a provider request. It lets Stogas check the next resolved candidate
only while all work is still local, before hold authorization or a provider call. An example is a
provider-specific request shape that cannot be prepared. Once Stogas asks the database to authorize
a candidate, that result ends admission for the request. Stogas does not create another hold for a
different candidate.

After a provider call starts, Stogas never sends the request to another provider. This prevents
duplicate charges, duplicate side effects, changed model behavior, and lost prompt-cache affinity.
The client receives the provider error and can decide whether to retry.

Provider attempts contain only real provider calls. A candidate check does not create a provider
attempt or a separate request log. If a request has already created a hold and final setup then
fails, Stogas releases the hold and records one request with an empty provider-attempt list. One
client request can therefore create at most one request log through this setting.

## Request rate

The version 1 request limiter is a token bucket:

```json
{
	"version": 1,
	"limits": {
		"requests": {
			"max": 120,
			"window": { "count": 1, "unit": "minute" },
			"burst": 20
		}
	}
}
```

`max` and `window` set the steady refill rate. `burst` sets the bucket capacity and cannot exceed 120. When `burst` is omitted, the capacity is the smaller of `max` and 120. Supported request windows
range from seconds through weeks. The resulting rate must be between one request per century and 60
requests per second.

Version 1 has one request bucket per configured scope. It does not offer arbitrary named counters.
If key `limits.requests` is absent, the internal safety bucket still
limits a key to 60 requests per second with a burst of 60.

## Spend and expiration

`lifetimeUsd` limits total settled spend for the scope, including outstanding holds when admitting a
request. Grant lifetime spend includes deleted keys. `recurring` limits spend in one anchored period.
Both can be present:

```json
{
	"version": 1,
	"limits": {
		"spend": {
			"lifetimeUsd": "1000.00",
			"recurring": {
				"anchor": "2026-08-31T04:00:00Z",
				"maxUsd": "50.00",
				"window": { "count": 1, "unit": "week" },
				"timeZone": "America/New_York"
			}
		}
	}
}
```

USD values are decimal strings. Do not use JSON numbers for money. `anchor` fixes the phase of every
window; it does not delay enforcement. If it is omitted, Stogas sets it when the configuration is
first saved. Month and year periods keep the anchor's local day and time, clamped to the last day of
shorter months. Recurring windows use minute, hour, day, week, month, or year units and can contain at
most 1,000 units. Spend belongs to the window in which Stogas creates the request hold. A request that
finishes after the next window starts does not consume both windows.

Changing a recurring amount or schedule preserves recorded spend in the current period. Recurring
accounting starts when the limit is enabled and stops when it is removed; it does not reconstruct past usage.
Lifetime totals are not reset by removing and restoring a limit.

`expiresAt` is an absolute timestamp with an offset. An expired effective policy blocks the key without
changing its manual enabled setting. Removing the expiration restriction restores an enabled key.

The request rate, spend limits, expiration, current balance, and current usage are checked in the
same PostgreSQL authorization transaction that creates the hold. PostgreSQL does not parse the JSON
on this path; save-time compilation writes the typed values used by the transaction.

## Deny periods

Time rules use a small structured form instead of adding time functions to the routing language:

```json
{
	"version": 1,
	"access": {
		"deny": [
			{
				"days": ["mon", "tue", "wed", "thu", "fri"],
				"start": "00:00",
				"end": "08:00",
				"timeZone": "America/New_York"
			}
		]
	}
}
```

The start is included and the end is excluded. An end can be `24:00`. A period cannot cross midnight.
Split an overnight period into two entries, such as `20:00`–`24:00` and `00:00`–`08:00`. IANA time
zones apply their daylight-saving rules. Each saved source can have at most 16 deny periods; all 48
may apply to a member key.

## PII redaction

Stogas redacts its secure default set before provider routing. The default covers every built-in group
except IP addresses. Key configuration can add IP detection and bounded custom RE2 patterns; it cannot
disable the secure defaults.

```json
{
	"version": 1,
	"plugins": {
		"stogasPiiRedaction": {
			"patterns": ["ip_address"],
			"customPatterns": ["EMP-[0-9]{6}\\b"]
		}
	}
}
```

Across the full intersection, there can be at most 16 custom patterns, 512 bytes per pattern, and 4,096 bytes in total. Patterns
cannot match empty text or redaction placeholders. RE2 does not support lookarounds or backreferences.
An invalid or excessive expression is rejected before the key is updated. `ip_address` is the only
value accepted in `patterns` in version 1; the other built-in groups are already active.

## Activation and cache behavior

Stogas compiles the saved intersection and writes a digest and increasing generation to each affected key. A gateway
node can cache that compiled result for up to 30 seconds. The authorization transaction compares the
cached generation with the key row. A stale generation cannot create a hold. The node removes the
stale cache entry and returns `503`; the next client request loads the current configuration.

This keeps admission before provider dispatch to one configuration read plus one authorization
transaction on a cold cache, and only the authorization transaction on a warm node. A policy tightening is still enforced
at the hold boundary even when a node has an older cached copy. A relaxed deny period can continue to
reject requests on one node until that node's cached copy expires, for at most 30 seconds. The same
bound applies when any configuration change makes enforcement less restrictive.

The complete JSON Schema is available at
[`https://stogas.ai/schemas/key-config-v1.json`](https://stogas.ai/schemas/key-config-v1.json). It
provides structural editor checks. Save-time validation remains authoritative for query grammar,
IANA time zones, RE2 safety, byte limits, and limits that depend on more than one field.
