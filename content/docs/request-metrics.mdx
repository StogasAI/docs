## Request history

Open **Analytics → Requests** and select a request to inspect its timing, provider attempts,
usage, cost, and plugin results.

The gateway node links to its verified transparency history, including its boot signing
key, gateway launch policy and hardware policy. Receipt verification uses the exact boot
identified by the response receipt. Request logs do not duplicate that key or evidence.
Gateway versions and catalog releases link to Trust Center. A link opens the current approval
or a loaded history record, then searches history when needed. Expand **Catalog** for the
historical configuration identified by each attempt's chain hash.

The header shows the request outcome. Each provider attempt retains its own result:
a provider can succeed before a later gateway failure. Grouped rejections show their
count and exact time range. Provider attempts remain visible with a linked BYOK credential
or **Managed**. Requests without a provider call have no attempts.

In the raw log, `policy_versions` records the loaded API configuration revisions for
routing, access and limits. These counters do not identify launch or hardware policies.

Response mode is **Streaming** or **Non-streaming**. The log's `request_type` already
encodes this distinction: `chat_completion_stream` or `responses_stream` for streaming,
and `chat_completion_request` or `responses_request` for non-streaming requests.

To send request traces to your own collector, configure the [Export plugin](/docs/plugins/export).

## Overview statistics

The overview shows request volume, errors, average duration, and spending for the selected
period, followed by one configurable trend. Select a metric and supported statistic: total
or rate, arithmetic average, minimum, maximum, p50, p95, or p99. **Chart options** contains
the chart type and resolution. Expand **Detailed metrics** for per-request statistics,
token counts, and cost totals. The statistics table includes the observed range and eligible
sample count; selecting a metric opens its average trend.

For a bounded time range, additive totals also offer **Average / hour** and
**Average / day**. These divide the total by elapsed time, including idle periods.
Chart buckets use their overlap with the selected range, so partial hours and days
keep the correct denominator. Per-request averages remain a separate statistic.
Expand **Data** beneath the chart for unabridged totals, each interval's numbers,
and the metric's available statistics. Interval timestamps are UTC.

Percentiles are approximate and use individual requests with a known value. The sample
count shows how many requests qualify; missing values and grouped rejection records do
not become zero-valued samples. Timing and speed require successful, non-cancelled
requests. Time to first token also requires observed streaming output.

Generation speed divides generated tokens by full request duration. Its overall value is
weighted by duration; its arithmetic average and percentiles describe individual request speeds.
Select a chart interval, then **View requests** to open that exact range in Requests.
Selecting an interval keeps the overview's period totals unchanged.

## Breakdowns

In **Analytics → Breakdown**, choose **Group by** to compare API keys, grants, members,
models, final providers, request types, or outcomes. **Rank by** selects the ranking metric;
changes apply immediately. **View options** contains the direction, number of groups,
table columns, and table or bar presentation. Duration and first-token columns show
per-request averages.

The table returns up to 100 groups. Its total always covers all matching requests, including
groups outside the displayed ranking. Requests counts recorded requests, including grouped
rejections; retries do not add requests. Spending remains the recorded charge, counted once.
These counts are analytics, not authoritative admission or quota counters.

Select a named group to open its requests within the same time range and filters. Model
filters use `model:` with a model ID; suggestions include current catalog names. Model
breakdowns combine revisions of the same model. **Final provider** groups each request once;
`provider:` matches any attempt, while `final_provider:` matches only the last attempt.

The same filters and timespan apply to Overview, Breakdown, and Requests. Your grouping,
ranking, metrics, presentation, and timespan are remembered in this browser. Filters are
remembered within the current organization and clear when you switch organizations.
Access is checked on every query. Queries have execution and memory limits; narrow
the timespan or filters if a query cannot finish. A failed query does not return partial totals.

## Meters and cost

Request logs group meters, cost summaries, and Standard Text Tokens under `usage`.
`usage.meters` contains the same meter values as the optional signed `stogas.meters`
response object. Each entry contains a quantity. Priced entries also contain a rate key, the USD price for
that rate, and the resulting USD charge. Quantities and money are decimal strings.

```json
{
	"input_tokens": {
		"quantity": "1000",
		"rateKey": "per_mill_tokens",
		"rateUsd": "2",
		"usd": "0.002"
	},
	"total_tokens": {
		"quantity": "1500"
	}
}
```

A published free price is `"0"`. An informational count omits all three pricing fields. Missing
quantities are unknown; they are not zero. Observed zero quantities remain in the log
and the Usage table. Unreported provider subcounts remain absent when their presence
cannot be established. Sum the available meter charges to recover
the recorded upstream cost. Totals are never charged again.

| Meter                                                        | Meaning                                                                                                                                          |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `input_tokens`                                               | Ordinary input tokens, excluding separately counted cache reads and writes.                                                                      |
| `cached_input_tokens`                                        | Tokens read from the provider's prompt cache.                                                                                                    |
| `cache_write_input_tokens`                                   | Cache-write tokens without a reported duration, excluding the duration-specific counts.                                                          |
| `cache_write_5m_input_tokens`, `cache_write_1h_input_tokens` | Tokens written for the stated cache duration. One request can contain both.                                                                      |
| `output_tokens`                                              | Output tokens excluding separately reported reasoning.                                                                                           |
| `reasoning_tokens`                                           | Reported reasoning tokens.                                                                                                                       |
| `input_text_bytes`                                           | Decoded UTF-8 request text after redaction, before provider conversion. Always unpriced.                                                         |
| `input_file_count`                                           | Declared input attachments, including extracted text files, URLs, and provider file IDs. Always unpriced.                                        |
| `input_file_url_count`                                       | Input attachments supplied as URLs, excluding inline data URLs. Always unpriced.                                                                 |
| `input_inline_file_bytes`                                    | Decoded bytes in inline attachments before extraction. Remote sizes are unknown. Always unpriced.                                                |
| `output_text_bytes`                                          | Observed assistant text, refusals, tool arguments, and generated code, excluding reasoning. Always unpriced.                                     |
| `reasoning_text_bytes`                                       | Observed plain reasoning text, when available without hidden or summarized reasoning. Always unpriced.                                           |
| `estimated_input_tokens`                                     | Local input estimate after redaction, including framing and opaque reasoning; opaque attachments select the full input ceiling. Always unpriced. |
| `total_input_tokens`                                         | Usable observed input, including cache reads and writes once.                                                                                    |
| `total_output_tokens`                                        | Usable observed output, including reasoning once.                                                                                                |
| `total_tokens`                                               | Input plus output, when both totals are known.                                                                                                   |
| `total_cache_write_tokens`                                   | All reported cache writes, with each duration counted once.                                                                                      |
| `hosted_tool_calls`                                          | Distinct provider-hosted calls exposed in the response, including visible failures.                                                              |
| `client_tool_calls`                                          | Distinct function or custom-tool calls returned for your application to handle. This does not confirm execution by your application.             |

Priced tool meters retain the provider's supported tool and rate, such as
`anthropic_web_search_calls` with `per_1k_calls`. Their quantities can differ from the
visible hosted-call total: a provider can report a failed call without charging for it.
Repeated stream updates and the final response count the same call only once. Tool results
you send as input do not count as new calls.

`input_text_bytes` counts text values, including tool descriptions and argument strings.
It excludes JSON syntax, property names, protocol identifiers, protected reasoning replay,
and opaque attachment contents. Extracted text contributes after redaction. File counters
record no filenames, URLs, identifiers, or content hashes. Text bytes cannot be derived by
subtracting file bytes from the JSON request size.
Equivalent literal and JSON-escaped text has the same count. Use it to compare input size
across providers; it does not measure the provider's complete rendered prompt.
Standard Text Tokens (STT) equal decoded UTF-8 bytes divided by four, without rounding.
The log emits exact decimal strings as `usage.standard_text_tokens.input`, `.reasoning`,
and `.output`; request details read those same values.
Unmeasured quantities omit both the STT field and its byte meter. Request details show
only measured quantities, including zero for known empty text. Summaries and encrypted reasoning cannot measure
the underlying reasoning, including native Claude thinking summaries. Output counts only
exposed material; interrupted streams retain the observed prefix, and repeated final
snapshots do not count text twice. STT measures text volume, not semantic meaning or hidden
provider work. [Input STT quotas](/docs/policies/limits#input-stt) use the same quantity for successful
billable requests. Request records retain the exact integer byte count.

Compare `estimated_input_tokens` with `total_input_tokens` for the same `catalog_chain_hash`
and gateway version to check the [universal text estimate](/docs/policies/limits#input-token-estimates)
and framing allowances against provider usage. Opaque reasoning contributes one estimated
token per encoded byte, alongside the visible-text estimate. This is a conservative heuristic,
not a provider-guaranteed count. Context-capped estimates do not measure tokenizer drift above
that cap; the recorded gateway version identifies the estimator implementation. Provider-hosted
tools can introduce additional input after this estimate. Their reservation can exceed the
recorded estimate without another local tokenizer pass.

The estimate limits reservations, not provider context admission. Redaction can increase token
counts; providers check their own context limits on the transformed request. The gateway never
truncates input or weakens redaction to make an estimated count fit.

Priced quantities explain the bill; informational meters preserve estimates and usable reported usage.
Token limits use `total_tokens`;
when that total is unavailable, the original token reservation remains counted. Requests
that never reach a provider consume no token allowance.

Four request-wide amounts accompany the meters inside `usage`:

- `upstream_cost_usd`: the recorded provider cost.
- `billed_cost_usd`: the charge calculated from final usage, which differs for BYOK.
- `cache_read_savings_usd`: savings compared with ordinary input at the applicable rate.
- `cache_write_overhead_usd`: the extra write cost compared with ordinary input.

Request history and signed response metadata describe execution and calculated cost; they do not confirm completion of asynchronous balance settlement.

Cache savings and overhead use the request's applied rates. Unavailable values are omitted;
`"0"` means known zero. A cache write costing $1.25 instead of $1 of ordinary input has
$0.25 overhead, not $1.25.

## Catalog history

`catalog_version` identifies the approved catalog used for the request. Each provider
attempt's `catalog_chain_hash` identifies its exact author, model, deployment, route and provider
settings. Request details retain those historical settings when the live catalog changes.
When the provider fulfills a different offering, such as a different service tier,
`catalog_chain_hash` records the offering used for accounting. The provider attempt
also retains `selected_catalog_chain_hash` for the original selection. That field is
omitted when selection and accounting use the same chain.
The chain supplies catalog node identities without repeating their array in every log.
The separate `node_id` identifies the gateway VM that handled the request.

Select a chain hash, or paste a SHA-256 chain hash into Catalog search, to inspect its
exact historical settings on a separate chain page. Select a node for its JSON, or
open Combined JSON for the complete chain. Catalog releases lists the versions and
manifest hashes containing that chain, with links to their Trust Center evidence.
A request link retains its catalog version; unchanged chains may belong to several
releases. Lookup verifies the content against the chain hash; missing history never
falls back to the current catalog.

## Timing

Request duration starts when the gateway's inference handler receives the decoded request
body. It ends when the gateway captures the final request record.

The `performance` object records `total_ms`, `provider_ms`, nullable `provider_start_ms`,
nullable `first_output_ms`, and nullable `ttft_ms`. The provider start is an offset from the same request start;
its end is that offset plus `provider_ms`. A missing measurement remains null.
Provider time spans the selected provider call, including upstream connection setup.
Current requests dispatch once; an SDK or caller retry creates a separate request. For streams, it also includes response backpressure;
it does not measure model compute alone. The remaining time covers gateway
preparation and final response processing.

Overview charts and request details use the same provider time.
Provider attempts retain their own durations. Historical records can contain several attempts;
their sum can be shorter than `provider_ms` because it excludes time between attempts.
Current local credential fallback happens before dispatch and is not a second provider call.

Total duration excludes the client's connection and TLS handshake, request upload and body
decoding, final response transmission, and asynchronous settlement. It is not end-to-end client
latency. Connection setup is reused across requests and is not reported as a separate request
stage. Measure client-side elapsed time when you need the full user-visible latency.

For streaming requests, **time to first token** runs from the same request start until the
response writer accepts the first generated token-bearing output. It includes admission and
provider work before that output. Unary requests and streams without generated token-bearing
output have no time-to-first-token value.

The timeline separates gateway preparation, provider wait until first output, provider
completion, and gateway completion. `first_output_ms` records the first validated provider
output at ingress; for a unary response, it records arrival of the buffered result. It
includes non-token output such as citations or images. An empty result leaves it null.
TTFT and client cancellation are markers on the same request clock.
Gateway work can continue after the first token, so its combined duration can exceed
time to first token. If the provider start was not recorded, the dashboard cannot
place that interval and does not invent its position.

## Outcomes and billing

`gateway_error` is a nullable `{code, status}` object for gateway processing or admission
failures. Each provider attempt retains its own status independently.

Provider outcome, response delivery, cancellation and the recorded charge describe different parts of a request. A
provider error does not mean the gateway failed to process the request. An error can still have
billable usage, and a stream can return output before failing.

## Redaction

The **Stogas redaction** section shows replaced items and scan/replacement duration in microseconds.
Redaction runs before the billing hold; its duration is included in gateway preparation. Zero replacements means the scan found
no matches; missing metrics mean execution was not recorded. Loading or compiling the policy
is not part of the plugin's scan duration.

Disabled redaction emits no plugin entry. The log omits `plugins` when there are no
recorded plugin metrics. A configured scan with zero replacements remains explicit.
Failed requests with recorded usage still retain their charges.

Export records `plugins.stogas_export.capture_us`: cumulative time copying processed
request and response content. Capture spans the request, so it is listed separately
from the timeline. Final record encoding, queueing, and asynchronous webhook delivery
are outside this metric. Plugin durations overlap the main phases and must not be added
to total request duration.

Filter requests with `redaction:redacted`, `redaction:no_matches`, or
`redaction:not_recorded`. See [redaction metrics](/docs/plugins/pii-redaction#limits-of-detection)
for the recorded fields and privacy boundaries.

## Downloads

NDJSON downloads use the same structured event as the raw request viewer. CSV and Parquet
retain nested objects as JSON strings in their columns.
