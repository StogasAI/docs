Each model has one or more deployments. A deployment is one provider's offering of the model, with
its own price, limits, features and data handling. The request's `model` field names a model, a
group of models or a deployment, and the gateway sends the request to one eligible deployment.

## Find a model

Browse the [model catalog](https://stogas.ai/catalog), or list models from the API:

```console
curl https://api.stogas.ai/v1/models
```

[`/v1/models`](/docs/reference/catalog/listModels) lists every model, group and deployment ID that
selects one model. [`/v1/catalog`](/docs/reference/catalog/getCatalog) returns the catalog's root:
authors, groups and providers, a summary of every model, route and deployment, current or retired,
and scheduled changes. [`/v1/catalog/parts/{sha256}`](/docs/reference/catalog/getCatalogPart)
returns the parts that the root names, which hold models, routes and deployments in full with their
prices. These endpoints are public.

A deployment, a route or a provider can have a retirement date, which the provider names for the
shutdown of a model, an API or its whole service. Requests continue until that date has ended in
every time zone, at 12:00 UTC the next day. A deployment retires with its last route, and a model
with its last deployment. A request that names a retired deployment gets `model_retired` with the
date. A request that reaches a provider after its shutdown
[falls back](/docs/policies/routing#retries-and-fallbacks) to the next deployment. Policies keep
retired IDs, which match nothing.

Some deployments work only for accounts that the provider has approved. The catalog marks
them with `approvalRequired`, and the routing filter `!deployment.approvalRequired` excludes them.

### Search the catalog

Type words to search names, IDs and aliases, or filter with `field:value`. A space between filters
means `AND`; you can also use `OR`, `NOT` and parentheses. The suggestions list every routing field:
type a kind and a dot, such as `deployment.`, to see its fields.

| Filter                                                              | Matches                                                        |
| ------------------------------------------------------------------- | -------------------------------------------------------------- |
| `author:`, `group:`, `model:`, `deployment:`, `route:`, `provider:` | A name, ID or alias, such as `provider:azure`                  |
| `interface:`                                                        | An API interface, such as `interface:responses`                |
| Any [routing field](/docs/policies/routing-fields)                  | The field's value, such as `deployment.upstream.hosting:azure` |

| Search                                              | Finds                                        |
| --------------------------------------------------- | -------------------------------------------- |
| `deployment.dataHandling.zeroDataRetention:true`    | Deployments with zero data retention         |
| `deployment.contextWindowTokens>=1000000`           | Context windows of at least 1,000,000 tokens |
| `deployment.pricing.input_tokens.per_mill_tokens<1` | Input under $1 per million tokens            |
| `model.groupIds=claude NOT provider:anthropic`      | Claude models from other providers           |

- `:` finds text that contains the value, and numbers or `true`/`false` that equal it. `=`, `!=`,
  `<`, `<=`, `>` and `>=` compare. Text ignores case.
- A list, such as `deployment.inputModalities`, matches when one of its entries matches.
- `!=` also matches deployments that do not state the field; other comparisons do not. Routing
  policies treat these values differently; see [Missing values](/docs/policies/expressions#missing-values).

## Choose a model

The `model` field takes an ID, as every OpenAI and Anthropic client sends it. To choose where the
request runs as well, add terms, separated by spaces:

| Form                | Example                         | Sends the request to                          |
| ------------------- | ------------------------------- | --------------------------------------------- |
| Model ID            | `gpt-5.6-sol`                   | Any eligible deployment of the model          |
| Group ID            | `gpt-6`                         | Any eligible deployment of the group's models |
| Deployment ID       | `openai-gpt-5.6-sol`            | Exactly that deployment                       |
| Author and model    | `openai/gpt-5.6-sol`            | Any eligible deployment of the model          |
| Provider and model  | `provider:azure gpt-5.6-sol`    | That provider's deployments of the model      |
| Author and provider | `author:anthropic provider:aws` | AWS's deployments of Anthropic's models       |

Each term is one of these:

- An ID alone. It names a model, by its ID or an alias, a group or a deployment. No two of them
  share an ID.
- `author/ID`, the form that OpenRouter uses. The gateway checks that the author made the model.
- A kind and an ID: `author:`, `provider:`, `route:`, `model:`, `group:` or `deployment:`.

Each kind can appear once, and the field can name one model, group or deployment. IDs ignore case,
and a dot or an underscore matches a hyphen, so `GPT-5_6-Sol` names `gpt-5.6-sol`. The text before
a slash is always an author: `azure/gpt-5.6-sol` returns `invalid_request` with a message that
suggests `provider:azure gpt-5.6-sol`.

A deployment ID stays fixed: the gateway never moves the request to another tier, region or
provider.

The response's `model` field names the model that served the request by its model ID, such as
`gpt-5.6-sol`, whichever form you sent and whichever provider served it. You can send that ID to
select the same model again. Each attempt's
[`catalog_chain_hash`](/docs/request-records#catalog-history) in the request record identifies the
deployment.

### Groups

Models belong to groups, such as `claude-opus` for every Claude Opus model and `claude` for every
Claude model.

A group ID selects among the group's models that your credentials and policies allow, in
[routing order](/docs/policies/routing#ordering). The
[default order](/docs/policies/routing#default-order) puts the newest model first, by release date,
so requests move to a new model on the day it joins the catalog. To stay on one model, send its
model ID. Terms work on groups too: `provider:openai gpt-6` selects among the GPT-6 models that
OpenAI serves.

- When models share a release date, the next criterion decides. For example, GPT-5.6 Luna, Sol and
  Terra came out on the same day, so the default order selects the cheapest of them.
- When the criteria leave the group's models tied, the request returns `model_ambiguous` with
  their IDs.
- Groups and `author:` leave out deployments that need approval. Send their model or deployment ID
  instead.

```json title="The cheapest model of any group, whatever its age"
{
	"routing": {
		"sort": [{ "by": "blended_price(3, 1)" }]
	}
}
```

To limit a key to one group, filter on `model.groupIds` in its
[routing policy](/docs/policies/routing):

```cel
'claude-opus' in model.groupIds
```

### How the gateway chooses a deployment

For a model ID, the gateway:

1. Removes deployments that cannot serve the request, for example because they lack a requested
   feature, have no credential on your API key, or are excluded by a [policy](/docs/policies/routing).
2. Orders the rest by the [sort criteria](/docs/policies/routing#ordering) of the key's policies,
   with the request's `provider.order` after the required ones.
3. Sends the request to the first deployment.

Only policies order deployments. With the
[default order](/docs/policies/routing#default-order), the cheapest deployment comes first, with
input weighed three times output, like
[`blended_price(3, 1)`](/docs/policies/expressions#blended-price). For example, OpenAI and Azure
both charge $2 for input and $10 for output on `gpt-6-sol`. With credentials for both, the request
goes to `azure-gpt-6-sol`, whose ID sorts first, then to `openai-gpt-6-sol`, and
`azure-gpt-6-sol-us`, which costs 10% more, comes after both. When the criteria leave deployments
tied, the request returns [`deployment_ambiguous`](/docs/policies/routing#ties).

Chat Completions and Responses requests can leave out `model`. The gateway then considers the
Standard tier, or the tier in `service_tier`, of every model that your credentials and policies
allow, except deployments that need approval, and the sort criteria choose the model. With the
default order, that is the newest model.

There is no automatic preference for the model author's own provider. To limit or order providers
for one request, add `provider`:

```jsonc
{
	"model": "gpt-5.6-sol",
	"input": "Hello",
	"provider": {
		"only": ["azure", "openai"], // Never use another provider.
		"order": ["azure"] // Try Azure first when both can serve the request.
	}
}
```

A string such as `"provider": "azure"` allows only that provider. `order` applies after the
required sort criteria of the key's policies and before their defaults. The gateway removes
`provider` before it calls the provider. To apply the same rules to every request from a key, use a
[routing policy](/docs/policies/routing).

## Tiers and variants

A provider can offer one model in several versions that differ in speed, price or where inference
runs, such as a cheaper Flex tier or US-only inference. Each version is a separate deployment with
its own price, and its ID adds a suffix to the standard deployment ID, such as `-flex`, `-fast`,
`-pro`, `-us` or `-eu`. The [provider pages](/docs/providers) list each provider's options.

To select one:

- Send its deployment ID.
- Set `service_tier` to choose a [service tier](/docs/service-tiers) of a model ID.
- Set `reasoning.mode` to choose [Pro mode](/docs/reasoning#select-pro-mode) of a model ID.
- Filter on `deployment.upstream` or `deployment.dataHandling.processingLocation` in a
  [routing policy](/docs/policies/routing).
