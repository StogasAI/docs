The gateway writes one record for each request. [Analytics](/docs/analytics), record downloads and
[Export](/docs/export) show the same record. It has no prompt, response, raw error message or
credential.

## Fields

The [request log reference](/docs/reference/dashboard/analytics/listRequests) describes each field.
The sections below explain the ones that need more than a line.

## Policy hashes

Each `policy_versions` entry's `sha512` is the SHA-512 of the policy revision as saved, in RFC 8785
canonical JSON without a final newline. An encrypted section is hashed as its ciphertext, and a
policy with no settings is hashed as `{}`. A later edit gets a new revision and a new hash, so a
record always names the exact policies that applied. The dashboard shows each version that a record
names, and we keep every version while your organization exists.

## Provider attempts

`provider_attempts` has one entry for each provider call, including each
[retry and fallback](/docs/policies/routing#retries-and-fallbacks), in call order. A candidate that
the gateway refused before it called the provider has no entry.

`provider_request_id` is the ID that the provider gave the call, also when it answered with an
error, so you can ask the provider about the call. Some providers give none, and then the field is
empty.[^no-request-id]

`provider_attempts` and `gateway_error` record different failures:

| What happened                                                                                     | `provider_attempts`        | `gateway_error`             |
| ------------------------------------------------------------------------------------------------- | -------------------------- | --------------------------- |
| Every provider call failed                                                                        | Each failed call           | `null`                      |
| A provider call failed, and the gateway's refusal of another candidate was the error you received | Each failed call           | The error that you received |
| The provider succeeded, but the gateway could not finish pricing, encoding or a requested receipt | Ends with a `success` call | The gateway error           |
| The gateway stopped before any call, such as when provider evidence did not verify                | Empty, and usage is zero   | The error that you received |
| The gateway rejected the request before billing authorization                                     | Empty, and usage is zero   | The error that you received |

When every call fails, the error that you received can be an earlier call's. See
[Retries](/docs/reference/errors#retries).

### Provider results

The gateway sets each call's `status` from the provider's structured error type, code and HTTP
status. Only failures that providers mark in no other way are read from the start of the message:
Anthropic's spend limits, low credit and workspace region refusals, and prompts longer than the
deployment's context window. An unrecognized failure is `provider_error`.

| Result                                                                             | Meaning                                                                   |
| ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| `success`                                                                          | The provider completed the call.                                          |
| `authentication_error`, `permission_error`                                         | The provider rejected the credential or access.                           |
| `over_budget`, `rate_limited`                                                      | The provider account is out of credit, or rate limited.                   |
| `invalid_request`, `context_length_exceeded`, `request_too_large`, `invalid_image` | The input is invalid or above a provider limit.                           |
| `content_filter`                                                                   | The provider blocked or refused the content.                              |
| `timeout`, `connection_error`                                                      | The call timed out, or the connection failed.                             |
| `provider_unavailable`, `provider_overloaded`, `model_unavailable`                 | The provider or model was unavailable.                                    |
| `model_retired`                                                                    | The provider retired the model.                                           |
| `invalid_response`                                                                 | The response could not be used.                                           |
| `cancelled`, `unknown`, `provider_error`                                           | The call was cancelled, its outcome is unknown, or it failed another way. |

## Request settings

`request_settings` records the settings that control what the model generates, as the gateway sent
them to the provider. It includes values that the gateway adds, such as the output limit that
Anthropic requires. Chat Completions and Responses use the same names, and a format or tool choice
keeps only its type:

```json title="Responses request"
{
	"model": "gpt-5.5",
	"input": "...",
	"max_output_tokens": 2048,
	"reasoning": { "effort": "low", "summary": "auto" },
	"text": { "format": { "type": "json_schema", "name": "invoice", "schema": {} } }
}
```

```json title="request_settings in its record"
{
	"max_output_tokens": 2048,
	"reasoning_effort": "low",
	"reasoning_summary": "auto",
	"response_format": "json_schema"
}
```

| Group            | Names                                                                                                     |
| ---------------- | --------------------------------------------------------------------------------------------------------- |
| Length           | `max_output_tokens`, `task_budget_tokens`, `verbosity`                                                    |
| Reasoning        | `reasoning_enabled`, `reasoning_effort`, `reasoning_max_tokens`, `reasoning_summary`, `reasoning_display` |
| Sampling         | `temperature`, `top_p`, `top_k`, `frequency_penalty`, `presence_penalty`, `repetition_penalty`, `seed`    |
| Response content | `response_format`, `include`, `logprobs`, `top_logprobs`                                                  |
| Tools            | `tool_choice`, `parallel_tool_calls`, `max_tool_calls`, `hosted_tools`                                    |
| Context          | `truncation`                                                                                              |
| Access programs  | `cyber_access_program`, the OpenAI program that the request chose                                         |

Other fields record the remaining settings:

| Setting                        | Field                                             |
| ------------------------------ | ------------------------------------------------- |
| Streaming                      | `stream`                                          |
| Service tier, speed and region | Each attempt's [catalog chain](#catalog-history)  |
| Caching                        | The cache meters in [`usage`](/docs/usage#meters) |

`hosted_tools` lists the [hosted tools](/docs/model-tools#hosted-tools) that the request let the
model call, such as `["web_search"]`, and is missing when there were none.

The record never keeps prompts, instructions, stop sequences, tool definitions, schemas or
identifiers such as `user`. It also leaves out a text value that is longer than 64 characters or
not printable ASCII, a list with more than 16 entries, and an integer above 9007199254740991 or
below -9007199254740991.

## Metadata

Send a `metadata` object with a Chat Completions or Responses request to label it, for example by
team or feature:

```json title="Chat Completions request"
{
	"model": "gpt-5.5",
	"messages": [{ "role": "user", "content": "Summarize this ticket: ..." }],
	"metadata": { "team": "support", "feature": "ticket-summary" }
}
```

The record keeps the metadata, so you can find these requests with the analytics filter
[`metadata.team:support`](/docs/analytics#filters), compare the values of a key in
[analytics groups](/docs/analytics#groups), and get it in downloads and exports.

A client that can add headers but not body fields, such as a coding agent, can send the same
object as JSON in the `Stogas-Request-Metadata` header:

```http title="Request header"
Stogas-Request-Metadata: {"team": "support", "agent": "codex"}
```

The record keeps the keys of both. A key in the body replaces the same key in the header, and the
limits below apply to the keys of both together.

| Part       | Limit                                      |
| ---------- | ------------------------------------------ |
| Pairs      | Up to 16                                   |
| Each key   | A string of 1 to 64 bytes of UTF-8         |
| Each value | A string of up to 512 bytes of UTF-8       |
| Characters | No control characters, such as line breaks |

- The gateway rejects other metadata with `invalid_request`, as it does a header that is not a
  JSON object or that is sent twice.
- The gateway never sends metadata to the provider. [PII redaction](/docs/pii-redaction) does not
  scan it, so keep personal data out of it.
- Rejection records have no metadata.

## Sessions

Send a session ID to group the requests of one conversation or task, then find them with the
analytics filter [`session:`](/docs/analytics#filters):

```json title="Chat Completions request"
{
	"model": "gpt-5.5",
	"messages": [{ "role": "user", "content": "..." }],
	"session_id": "ticket-4821"
}
```

The gateway reads the first of these sources that has a value:

| Source                             | If the value is invalid                                              |
| ---------------------------------- | -------------------------------------------------------------------- |
| `session_id` field in the body     | The gateway rejects the request with `invalid_request`.              |
| `X-Session-Id` header              | The gateway rejects the request, also when the header is sent twice. |
| `Session-Id` header, sent by Codex | The gateway ignores the header.                                      |

- A session ID has up to 256 bytes of UTF-8 and no control characters, such as line breaks.
- OpenCode sends `X-Session-Id` without any setup.
- The gateway never sends the session ID to the provider, and PII redaction does not scan it.
- Rejection records have no session ID.

## Traces

OpenTelemetry clients name the trace of each request in a
[W3C `traceparent` header](https://www.w3.org/TR/trace-context/#traceparent-header):

```http title="Request header"
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
```

The record keeps the header's trace ID, `4bf92f3577b34da6a3ce929d0e0e4736` here, as `trace_id`, so
the analytics filter [`trace:`](/docs/analytics#filters) finds the requests of a trace.

- The gateway serves a request whose header is missing, invalid or repeated, and records no trace
  ID.
- The gateway never sends the header to the provider.
- Records that count [repeated rejections](#grouped-rejections) have no trace ID.

## Apps

Send the attribution headers that OpenRouter and Vercel AI Gateway read to name the app that makes
a request:

```http title="Request headers"
HTTP-Referer: https://desk.example.com
X-Title: Support Desk
```

| Header                               | Record field                                                    |
| ------------------------------------ | --------------------------------------------------------------- |
| `HTTP-Referer`                       | `app_url`, without credentials, query, fragment and final slash |
| `X-OpenRouter-Title`, else `X-Title` | `app_title`                                                     |

The analytics filter [`app:`](/docs/analytics#filters) and the app breakdown use the title, or the
URL when a request has no title.

- Roo Code sends both headers without any setup.
- Each value has up to 512 bytes of UTF-8 and no control characters, and the URL starts with
  `http://` or `https://`. The gateway serves a request whose headers are missing, invalid or
  repeated, and records no app from them.
- The gateway never sends the headers to the provider.
- Rejection records have no app.

## Encryption keys

`encryption_key_ids` lists the identifiers of the
[customer encryption keys](/docs/customer-encryption) of every encrypted credential and policy
setting that the request could use, including credentials that no attempt reached. The analytics
filter [`encryption_key:`](/docs/analytics#filters) finds these requests by a key's label or
identifier.

- A request refused with `encryption_key_required` lists the keys that it did not send.
- The record keeps identifiers, not labels, so it still names a key after you remove the key's
  registration.

## Catalog history

Each attempt's `catalog_chain_hash` identifies the exact author, model, deployment, route and
provider settings used for accounting. If the provider served a different offering than the one
your request resolved to, such as another service tier, `resolved_catalog_chain_hash` records the
resolved one. It is omitted when both are the same.

A chain states its route's [hosted tools](/docs/model-tools#hosted-tools) and what each changes,
whether or not a request can call them. When the tools that your request let the model call change
the chain's data handling, the attempt's `data_handling` holds the result, such as a longer
retention with web search. Without it, the chain's own data handling applied.

Paste a chain hash into catalog search to open its historical settings and the catalog releases
that contain it. Lookup checks the content against the hash and never falls back to the current
catalog.

## Timing

The request clock starts when the gateway receives the decoded request body and stops when it
writes the record. It excludes connection setup, upload, final transmission and settlement, so it is
shorter than the latency your client sees.

The [example](#example) record has this timeline:

```text title="Request clock of the example"
   0 ms  The gateway receives the request.
  14 ms  The OpenAI call starts.               provider_start_ms
 110 ms  OpenAI answers 429.
 118 ms  The Azure call starts.
 702 ms  The first token arrives.              first_output_ms, ttft_ms
1958 ms  The Azure call ends.                  provider_ms = 1958 - 14
1975 ms  The gateway writes the record.        total_ms
```

`provider_ms` includes upstream connection setup, waits between calls and, for streams, response
backpressure. The time outside it is gateway preparation and response processing.

`first_output_ms` is when the provider's first output reached the gateway, and `ttft_ms` is when the
gateway passed the first generated token on to your client, so `ttft_ms` is never earlier. Output
other than tokens, such as citations, can make them differ by more than the gateway's own handling.
A response that is not streamed arrives whole, so its `first_output_ms` is when the provider call
ended, and it has no `ttft_ms`.

### Tool calls

`performance.tool_calls` lists the tool calls in the response, in output order.
`performance.answered_calls` lists the calls whose results the request sent. Records keep no tool
names, arguments or results.

| `type`                              | Who runs it                                                                  |
| ----------------------------------- | ---------------------------------------------------------------------------- |
| `function_call`, `custom_tool_call` | Your app                                                                     |
| `shell_call`, `apply_patch_call`    | Your app                                                                     |
| `mcp_approval_request`              | Your app, which approves or denies the provider's call                       |
| `web_search_call`, `web_fetch_call` | The provider                                                                 |
| `mcp_list_tools`, `mcp_call`        | The provider, on a [remote MCP server](/docs/model-tools#remote-mcp-servers) |

For a call that your app runs, `latency_ms` is the time the model took to write the call. Your
app's time with it runs from the end of the request until a later request sends its result, and
that request lists the same hash in `answered_calls`. Those hashes come from the results in the
latest turn of the input: Chat Completions `tool` messages, Responses `function_call_output` and
`custom_tool_call_output` items, and `mcp_approval_response` items, by the ID of the approval
request. A turn ends at an assistant message or reasoning item, and at a message that your app adds
after results.

A record keeps the first 32 calls of a response and the last 32 results of a request. To find the
hash of a call ID:

```sh
printf %s call_1 | sha256sum | cut -c1-16
```

This prints `74196fe72e4cdc13`. The analytics filter `tool_call:` takes a call ID or its hash and
finds both the request that made the call and the one that sent its result.

## Plugin metrics

- An entry is missing when the plugin recorded nothing, for example when no scan ran.
- Plugin times overlap the request timeline. Do not add them to `total_ms`.

## Grouped rejections

Requests that the gateway rejects before billing authorization, such as for credit, policy or
validation errors, appear once the gateway can tell which API key sent them. Repeated rejections
share records. In each UTC minute, rejections with the same key, `interface`, `stream`, `transport`,
`policy_versions`, `encryption_key_ids`, error code and HTTP status are recorded like this:

| Rejections      | Record                                                                        |
| --------------- | ----------------------------------------------------------------------------- |
| First five      | One record each, which appears within seconds                                 |
| Sixth and later | One shared record with a `request_count`, which appears after the minute ends |

- Charts sum `request_count`. Costs and usage are recorded once, so do not multiply them by it.

- A grouped record keeps the first request ID and the first and last times. The other request IDs
  that it counts have no record of their own.
- A grouped record has no model or catalog IDs, so it counts toward key and organization totals but
  not model totals.
- Successful requests and provider errors are never grouped.

Each gateway groups its own requests, so a client whose requests reach several gateways can see more
single records. On each gateway, only an organization's first 32 groups in a minute keep single
records, and its later groups have only the shared record. After 32 groups of one key, or 256 groups
of one organization, the gateway records none of their new groups until the minute ends.

Records are delivered asynchronously. A gateway crash, a burst larger than the gateway can group, or
a storage failure can lose rejection records, so grouped history is not a complete audit of every
request. Requests that fail before the gateway can identify the key, such as with an invalid key,
do not appear.

    `provider_instance_id` names the instance that ran the call or turned it away, which Chutes can
    find with the call's time.
