A receipt proves that a verified gateway received a request and returned a response. The gateway
signs it with a key bound to its hardware evidence. Use receipts when you or an auditor must check a
request later. You can prove the response without revealing the request, or the other way round.

## Get a receipt

Send this header with an inference request:

```http
Stogas-Metadata: v2
```

The response then ends with a `stogas` object. It has usage, routing and provider details, a
compact receipt and two salts:

```jsonc
{
	"id": "chatcmpl-...",
	"choices": [ ... ],
	"usage": { ... }, // The standard usage field does not change.
	"stogas": {
		// Usage, routing and provider details.
		"policy_versions_sha512": "6a0f...", // The policies that applied.
		"receipt": {
			"schema": "stogas.receipt.v2",
			"boot_sha256": "9f2c...", // The gateway boot that signed it.
			"request_commitment": "41d7...",
			"response_commitment": "c08e...",
			"signature": "..."
		},
		"salts": { "request": "5b1e...", "response": "e73a..." } // Only you receive these.
	}
}
```

A stream sends the `stogas` object in a `: stogas {...}` SSE comment before the last event.
Ordinary SSE parsers ignore it.

The [SDK](/docs/sdk-overview) and [CLI](/docs/cli) check the receipt before they report that the
request completed. Streamed output arrives before that check.

## What the signature covers

One signature covers:

- a commitment to the request,
- a commitment to the response, and
- the `stogas` object, without its `receipt` and `salts`.

Each commitment covers the meaning of its side, not its bytes, so whitespace and key order don't
change it. A receipt covers:

- the request body that you sent, without its top-level `encryption_keys`,
- a buffered response, without its `stogas` object,
- the `chat.completion` that a Chat Completions stream's chunks add up to, however the reply was
  split into chunks, and
- the `response` of a Responses stream's last event, `response.completed` or
  `response.incomplete`.

The [receipt format](/docs/reference/security#receipt-format) lists each field and how each
commitment is computed.

## Keep your content private

Each commitment also covers a random salt that only you receive, in `salts`. The gateway keeps
neither salt, and request records and [exports](/docs/export) don't have them. Without a salt,
nobody who holds a receipt can confirm a guessed prompt or reply.

To prove one side, share its content and its salt. Leave out the other side's salt, and its
commitment reveals nothing about it. For example, to show an auditor what the model replied
without revealing your prompt, share the response and the `stogas` object with only
`salts.response`. The [CLI](#share-a-proof) writes such a proof for you.

## Numbers in a receipt

A receipt holds integers from -9007199254740991 to 9007199254740991, the range that every JSON
parser reads exactly, and other numbers from -1.7976931348623157e308 to 1.7976931348623157e308. A
request that sends `Stogas-Metadata` with a number outside these ranges fails with a `400` error
before it runs. Send such numbers as strings, for example `"seed": "9007199254740993"`. Requests
without the header are not affected.

## Check which policies applied

`policy_versions_sha512` is the SHA-512 of the RFC 8785 canonical JSON of the request record's
[`policy_versions`](/docs/request-records#policy-hashes). Each entry there names a policy revision
and the hash of its content, so the signature covers the exact policies that applied while the
receipt stays small. To check it, hash the canonical form of that list and compare.

## Check a receipt later

Save the request body, and the response with its `stogas` object. Their formatting doesn't matter.
Then run:

```console
stogas proof --request request.json --response response.json --json
```

Add `--stream` for a stream saved as it arrived. Leave out `--request` to check only the response.
If you saved the `stogas` object on its own, pass it with `--proof metadata.json`.

The command downloads the boot record named by `boot_sha256` and the evidence it was verified with,
then checks the receipt against them. It uses the evidence that was valid when the boot was logged,
so later key changes and expired revocation lists do not invalidate a saved receipt. The
[Trust Center](/docs/verification#trust-center) shows the same boot records.

### Share a proof

To let someone else check a receipt, add `--share` with a directory:

```console
stogas proof --request request.json --response response.json --share proof/ --hide request
```

This writes `metadata.json` and `response.json` to `proof/`, and prints the command that checks
them. `--hide request` leaves out the request and its salt, so the proof reveals nothing about your
prompt. Without `--hide`, the proof also has `request.json`, without your `encryption_keys`. For a
stream, `response.json` is the response that the stream adds up to.

### Check without network access

These records never change. To keep them with your saved receipts, download them once:

```console
stogas download-evidence --boot <boot_sha256> --output evidence/
```

Then pass them to the check, which then makes no network requests:

```console
stogas proof --boot evidence/boot.json --evidence evidence/evidence.json \
  --request request.json --response response.json --json
```

The SDKs offer the same offline check, for example `verify_receipt` in [Python](/docs/python) and
`VerifyReceipt` in [Go](/docs/go).

## Prove a request log

Each gateway boot also signs its [request records](/docs/request-records) with its receipt key. It
signs them in batches, one batch a minute, and each record names its place in a batch in
`log_batch`. A proof of a record shows that the attested gateway wrote exactly that record, and
that it has not changed since.

To get a proof, open the request in [Analytics](/docs/analytics) and choose **Download proof**, or
call `GET /api/{orgId}/analytics/proof?requestId=<request_id>` with an
[access token](/docs/reference/dashboard#access-tokens). Then run:

```console
stogas proof --proof request-<request_id>-proof.json
```

The command checks that the record belongs to its batch, downloads the boot record that the batch
names and its evidence, and checks the batch's signature against them. It prints the record's batch
and index, and when the batch was open. Add `--boot` and `--evidence` to check it without network
access, as for a receipt.

When the request asked for a receipt, the record's `receipt_commitments` are the receipt's
`request_commitment` and `response_commitment`. So a proof of the record also ties it to the request
and response that you saved.

- A batch reaches Analytics a few minutes after its minute ends. Until then, its records have no
  proof.
- A record whose `log_batch` is `null` has no proof.
- A proof shows how many records that gateway signed in the same minute, and nothing else about
  them.
- A proof covers one record. It doesn't show that Analytics holds every record that a gateway
  signed.

## What a receipt does not prove

- When the request ran.
- That the client used a verified confidential connection. Receipts work with ordinary HTTPS too.
- That the provider ran the model in a TEE.
- That a new connection can trust the same gateway. A new connection needs fresh evidence.

## If a check fails

A failed check means that the receipt cannot prove what the gateway returned. It does not mean that
the model did not run, and the request can still be billed. Do not retry it automatically: a retry
is a new request.
