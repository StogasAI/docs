---
title: E2EE over HTTPS
description: Carry encrypted requests through ordinary HTTPS while verifying their gateway locally.
---

Browser and Fetch integrations use binary end-to-end encryption over HTTPS. A fresh attested
session binds its encryption keys to an approved gateway. HTTPS carries the encrypted records;
the outer TLS connection is not the proof of which gateway handles them.
The API key remains an inner `Authorization: Bearer` header, carried inside the
encrypted request metadata rather than the outer HTTP headers.

## Connect from an application

Follow [Browser and Workers](/docs/browser-workers) or the
[JavaScript](/docs/javascript) and [TypeScript](/docs/typescript) guides. Native SDKs can also select
`e2ee`. Reuse one transport across requests and close it at application shutdown.

The verifier requires the selected hybrid construction and fails closed when it is unavailable.
Records are binary, without base64 expansion of request bodies. Responses stream as they arrive.
Native uploads stream; browser uploads use a replayable ciphertext body to accommodate Fetch limits.
Every request data record except the last carries the full 65,515 bytes; the gateway rejects a
short record followed by more data.

Browser and Fetch runtimes use WebCrypto AES-256-GCM for records larger than 256 bytes. Smaller
records, where importing a fresh key costs more than it saves, use the portable Rust
implementation, as does any runtime without the service or algorithm. The first incoming record
is authenticated in Rust so concurrent requests update shared session state atomically. Each
record uses its own key; WebCrypto keys are non-exportable and released after the operation.
Rust owns the session secrets, counters and record rules;
an authentication failure always closes the request. WebCrypto provides no explicit key-erasure
operation, so releasing a browser key does not guarantee immediate erasure from memory.

## Session keys and concurrency

E2EE uses a Double Ratchet with full X25519 and ML-KEM-768 exchanges and fixed-size encrypted
ratchet headers. Each new alternating turn mixes fresh DH and KEM secrets through HKDF-SHA512.
Every request and response start derives an independent directional chain, including messages
sent in a concurrent burst. Each record consumes a new AES-256-GCM key from an HKDF-SHA256
chain, including metadata, data, keepalive and completion records. The old chain state and
used key are discarded; later chain state cannot recreate erased earlier record keys.
This adds no network messages or record bytes. Capturing the current chain still exposes the
remaining records in that direction; recovery requires a later fresh hybrid exchange.
Application-held plaintext and browser-managed key copies remain outside this erasure guarantee.

A request that arrives ahead of another causes the gateway to retain the missing request's
individual key for up to one minute, within a 256-number window. Once admitted, an upload or
response keeps its normal deadline; this one-minute wait does not limit inference duration.
The client retains bounded delayed reply keys for requests awaiting their first response and
discards that cache when the last such request completes or is cancelled.
The SDK manages numbering, concurrent requests and session renewal automatically.

The gateway retires a session after 2³⁰ cryptographic start attempts, including failed
authentication. Malformed framing and known replays do not use keys or spend this budget.
Accepted streams retain their keys and can finish. Sending chains also stop at 2²⁴ messages;
these are key-use limits, separate from request rate limits. A rejected submission is never
automatically replayed; later work establishes a fresh session.

During terminal gateway drain, encrypted response metadata carries an authenticated `closing`
flag. The SDK preserves that response's status and body, stops assigning new requests to the
session, and establishes a fresh attested session for later work. Responses already admitted
retain their own keys and can finish. Ordinary provider errors do not close the session, and the
transport does not replay inference.
An authenticated request start receives an encrypted acknowledgement immediately, returning
ratchet feedback and freeing the SDK's pending-start capacity. Both streaming and buffered
requests use it. [Keepalives](/docs/keepalives#encrypted-acknowledgements) explains what this
acknowledgement establishes and how it differs from SSE comments.
Under gateway memory pressure, fully idle E2EE sessions can be reclaimed after one minute;
sessions with unfinished requests remain available. The next attempt on a reclaimed session
can fail. The SDK then retires that session so later requests establish a fresh one; it never
automatically repeats submitted inference.

Fresh session setup uses X-Wing HPKE and binds the gateway's initial X25519 and ML-KEM public
keys to the session evidence. Each subsequent alternating turn sends complete public keys and
one complete ML-KEM ciphertext. A turn requires authenticated traffic in the opposite direction;
several requests sent together can share one turn while still using different message keys.
The SDK needs no extra update request or configurable KEM chunk size.

The first record in each direction carries a fixed 2,336-byte encrypted ratchet header. Its
fixed size and encryption conceal ratchet counters, public keys and turn changes. The visible
request number serves as the header's encryption nonce, so the header carries no nonce. The outer session
identifier, request number, message sizes and timing remain visible. Later records in the same
request or response do not repeat the ratchet header.

Erasure protects past encryption keys after their use. It does not promise that every plaintext
or temporary key copy has vanished from process memory. After theft of current state, fresh
alternating exchanges can restore protection once the attacker loses endpoint access and honest
messages are delivered. Full ML-KEM runs each turn; recovery is not guaranteed after each request,
during one-way traffic or while the attacker continues to control an endpoint.

## Scope and failure handling

Encryption ends inside the attested gateway. The model provider receives the forwarded request;
this mode does not hide it from that provider or independently verify provider execution.

A fresh session needs attestation and cryptographic setup. Reuse amortizes that work; it does not
make a cold connection cost the same as ordinary HTTPS. Your OpenAI SDK controls retries:
a connection loss after submission can leave execution uncertain, and another attempt can execute again.

Authenticated request and response starts advance the ratchet even when the inner
HTTP status is an error, including rate-limit and provider errors. An outer rejection
before encrypted-record authentication does not advance the gateway's ratchet.

[Gateway verification](/docs/verification) covers receipts and evidence checks. The
[trust model](/docs/confidential-security-model) states the hardware and evidence assumptions.
