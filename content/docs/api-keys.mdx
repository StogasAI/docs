An API key authenticates inference requests. Each key belongs to one organization and has its own
[policy](/docs/policies), [provider credentials](/docs/byok) and usage.

| Key type                     | Owner            | Use it for                                                   |
| ---------------------------- | ---------------- | ------------------------------------------------------------ |
| [Service key](#service-keys) | The organization | Servers, applications and CI jobs that must outlive a member |
| [Member key](#member-keys)   | One member       | A member's own work, within the limits of a grant            |

A [grant](/docs/grants) lets selected members create member keys. It has no secret and cannot call
the API.

## Service keys

Organization-wide API key managers and folder managers create service keys, and
[roles](/docs/members#permission-reference) give other members access to them. **Use** lets a
member reveal the secret again.

- Removing someone's access hides the secret from them at once, but a copy they saved keeps working
  until you rotate the key. Requests with an old secret fail with
  [`key_secret_replaced`](/docs/reference/errors#401-unauthorized).
- Access does not change a key's owner, and the policies of members with access do not apply to its
  requests.
- A disabled key can still be rotated, and rotating does not enable it.

## Member keys

A member creates member keys from a grant assigned to them, and manages their own keys.
Administrators can manage every key in the organization.

**Allow key policy edits by default** on the grant sets `delegation.keys`, which decides whether
members can edit their keys' policies, and keeps any
[exceptions by ID](/docs/policies/delegation#exceptions-by-id). When it is off, key policies can no
longer add or change sections, and sections that keys already set keep applying until someone
removes them. Request policies have their
[own permission](/docs/policies/request-policies#grant-permission).

## Leaked secrets

GitHub reports API key secrets that it finds in public repositories and other public GitHub
content. If the secret still belongs to a key, we replace it at once. The key keeps its ID, settings
and history, and requests with the old secret fail with `key_secret_replaced`. Reveal the new
secret and update your apps. [Activity](/docs/activity) keeps the report.

An organization with keys that are meant to be public can turn off **Replace secrets that GitHub
finds in public** in Settings. A found secret then keeps working, and its key shows a warning until
someone rotates the secret or dismisses the warning. Turning replacement back on leaves secrets
found before as they are. Personal organizations always replace found secrets.

## Policies and credentials

Every request must pass the key's policy, the policies above it and the organization balance. See
[Scopes and inheritance](/docs/policies/scopes) for how the levels combine.

New keys start with Stogas-managed credentials for providers that offer them, which today is
Chutes. Other providers start with an empty credential list, which turns them off for the key until
you [add a credential](/docs/byok).

## Folders

Folders group service keys and grants. Member keys follow their grant's folder. Folder policies,
permissions and shared limits apply to everything inside.

- An organization can have up to 50 folders, or as many as we agreed for it. Folder names are
  unique regardless of case, and folders cannot contain other folders.
- Moving a key or grant needs Admin on both folders, or organization-wide Admin for the
  organization root. A move changes the inherited policies, permissions and shared limits.
- Deleting a folder moves its keys and grants to the organization root.
- A move or deletion deletes a member's keys under a grant if the member loses their last **Use**
  on that grant. Other keys keep their IDs and secrets.
