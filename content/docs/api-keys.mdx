---
title: API keys and grants
description: Create organization service keys or let members create their own keys through grants.
---

Stogas has two API key types and one access control:

| Resource        | Purpose                                                                   |
| --------------- | ------------------------------------------------------------------------- |
| **Service key** | A credential for an organization-owned server, application, or CI job     |
| **Member key**  | A credential that one member creates and owns through an assigned grant   |
| **Grant**       | Permission for selected members to create a limited number of member keys |

A grant is not an API key. It has no secret and cannot call the inference API.
In the dashboard Playground, a member selects a usable API key directly. The dashboard does not
reveal its secret.

## Service keys

A service key belongs to the organization. Use one for work that must continue independently of one
member, such as a production service, deployment, or CI job.

Members with organization-wide API key management can create, configure, rotate, disable, and delete
service keys. The secret is shown only when the key is created or rotated.

## Grants

An administrator creates a grant on the separate **Grants** page. A grant controls:

- which members may use it;
- how many keys each assigned member may create;
- whether it is enabled; and
- whether members may change their key configuration.

A member starts with no grant. An assigned member creates keys only when they need them, up to that
grant's per-member allowance. The same grant may be assigned to many members, and each member has an
independent allowance.

Lowering an allowance does not delete existing keys. It stops the member from creating another key
until their key count is below the new allowance.

An administrator can select members directly or select roles as a shortcut. Role selection adds the
members who have those roles when the grant is saved. Later role changes do not silently add or remove
grant access.

Select grant icons to enable, disable, or delete several grants at once. The header selects all grants
matching the current filter. Deletion confirms the number of attached keys that will also be deleted.

Disabling a grant immediately rejects new requests from all keys under it without deleting the keys.
Removing a member from a grant deletes that member's keys under the grant. Deleting the grant deletes
all keys under it. The dashboard asks for confirmation before either destructive change.

## Member keys

A member key is a normal inference credential owned by one member under one grant. A member can give
each key a separate name, rotate its secret, disable it, or delete it. Administrators can see and
manage all organization keys, including member keys. A disabled key or grant does not prevent an
authorized secret rotation; rotation leaves the enabled state unchanged.

When **Allow user to narrow final policy** is enabled on the grant, the member may also change the key's routing,
access, limit, and redaction configuration. When it is disabled, only an administrator may change the
configuration. Each key keeps its own configuration; organization and grant policies also apply.

## Key status

Open a key to view **Overview**: enabled state, lifetime and recurring spend, pending holds,
remaining allowance, reset times, request capacity, lifecycle dates, and the last admission failure.
Counters reflect the displayed update time; refill timing assumes no further requests. Shared
organization and grant allowances apply separately from per-key counters.

The enabled switch saves immediately. **Settings** contains the name, policy, and secret actions;
**Credentials** contains provider assignments. Changing status does not save an unfinished settings draft.

## Policies

Each usable key can have these optional controls in one versioned JSON document:

- catalog filters and sorting;
- an allowed set of catalog node IDs;
- up to three candidates checked before provider dispatch;
- access deny periods and expiration;
- multiple request rates and burst capacities;
- lifetime and recurring spend limits;
- token quotas and concurrent-request limits; and
- additional PII redaction patterns.

Every request must satisfy its applicable policies and the organization balance. Start with
[Edit a policy](/docs/policies/editing), or see [Scopes and inheritance](/docs/policies/scopes)
to understand which restrictions and shared allowances apply.

## Provider credentials

Every service or member key owns one credential choice for each provider. Members with BYOK and
organization-wide API key management configure these choices.

Managed service is currently available for Chutes. OpenAI and Anthropic therefore need a stored or
pass-through credential. Azure accepts one stored, discovered credential per API key or remains
unassigned; it does not accept pass-through. A disabled or unavailable selected credential fails
closed.

See [Bring your own provider key](/docs/byok) to set the credential mode, send a provider key,
connect Azure, or rotate and revoke credentials. Disabling a named pass-through ID also blocks that
ID for open pass-through modes; deleting its record removes that block.
