---
title: API key types
description: Choose a key for a service, a group, or a person.
---

Stogas has three API key types:

| Key type | Use it for |
| --- | --- |
| **Service key** | Work owned by the organization, such as a server, application, or CI job |
| **Provisioning key** | A team, department, project, or other group that needs one shared policy |
| **Assigned key** | One person working under a provisioning key's policy |

Only service keys and assigned keys have secrets that can call the API.

## Service key

A service key belongs directly to the organization. Use it for organization-owned activity rather
than for one person.

Good examples include a production server, internal application, automation, or CI job.
Administrators create the key, set its limits, and rotate its secret. The secret is shown only when
it is created or rotated.

## Provisioning key

A provisioning key represents a group of people who should follow the same policy. The group might
be a team, department, project, cost center, or customer account.

The provisioning key is not an inference credential and has no secret. Instead, administrators use
it to create one assigned key for each member. Its policy can set common expiration, rate, and spend
limits for those assigned keys.

For example, create a provisioning key named **Research team**, set the team's limits once, then
assign a child key to every researcher.

## Assigned key

An assigned key belongs to one member and is created under a provisioning key. The member generates
their own secret and uses it to call the API. Administrators can manage the assignment and its
policy, but cannot see the member's secret.

Members can give their key a private name. Administrators continue to see the member relationship,
such as `Alex's key`, so the assignment stays clear.

## Policy options

By default, a provisioning key supplies settings to its assigned keys. Administrators can also:

- **Share enforcement** so the group uses common rate and spend limits.
- **Delegate unset fields** so members can choose only the limits the administrator leaves open.

Changing or revoking one assigned key does not reveal or rotate another member's secret.
