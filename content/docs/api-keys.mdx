---
title: API keys and upstream credentials
description: Choose a key for a service, a group, or a person, and optionally use your own provider account.
---

Stogas has three API key types:

| Key type             | Use it for                                                               |
| -------------------- | ------------------------------------------------------------------------ |
| **Service key**      | Work owned by the organization, such as a server, application, or CI job |
| **Provisioning key** | A team, department, project, or other group that needs one shared policy |
| **Assigned key**     | One person working under a provisioning key's policy                     |

Only service keys and assigned keys have secrets that can call the API.
In the dashboard Playground, members select a usable service or assigned key directly; no API
secret is required or revealed.

## Service key

A service key belongs directly to the organization. Use it for organization-owned activity rather
than for one person.

Good examples include a production server, internal application, automation, or CI job.
Administrators create the key, set its limits, and rotate its secret. The secret is shown only when
it is created or rotated.

## Provisioning key

A provisioning key represents a group of people who should follow the same policy. The group might
be a team, department, project, cost center, or customer account.

The provisioning key is not an inference credential and has no secret. Instead, administrators use
it to create one assigned key for each member. Member limits apply independently to every assigned
key. Shared limits can separately cap the combined rate and spend of the whole group.

For example, create a provisioning key named **Research team**, set the team's limits once, then
assign a child key to every researcher.

## Assigned key

An assigned key belongs to one member and is created under a provisioning key. The member generates
their own secret and uses it to call the API. They may add an earlier expiration or stricter personal
rate and spend limits. Administrators manage the group policy and can suspend or revoke the
assignment, but cannot see the secret or edit the member's private settings.

Members can give their key a private name. Administrators continue to see the member relationship,
such as `Alex's key`, so the assignment stays clear.

## Limits

A provisioning key has two independent sets of optional controls:

- **Member limits** apply separately to each assigned key.
- **Shared limits** apply to combined usage from every assigned key.

Every usable API key also has the platform's 60 requests-per-second ceiling when no lower key or
member rate is configured. A combined rate may be higher because it covers many independently
rate-limited keys. Clearing a member's private limit restores the provisioning limit; it does not
remove organization policy.

Changing or revoking one assigned key does not reveal or rotate another member's secret.

## Upstream credentials

Administrators can add an upstream credential on the **Credentials** page, then select it for the
matching provider from an API key's **Credentials** tab. A service key owns its assignments
directly. A provisioning key's assigned children inherit its assignments and cannot override them.

| Provider  | Available credential modes |
| --------- | -------------------------- |
| OpenAI    | Your credential only       |
| Anthropic | Your credential only       |
| Azure     | Your credential only       |
| Chutes    | Stogas or your credential  |

Assignments are provider-specific. A key may use your Chutes credential while another key uses the
Stogas Chutes credential. OpenAI, Anthropic, and Azure requests require a matching assigned
credential. If an assigned credential is disabled or unavailable, matching requests fail instead
of falling back to a Stogas credential.

### Azure credentials

For Azure, select **Azure OpenAI** or **Azure AI Foundry**, then enter the resource name and API
key. Enter only the resource name, such as `my-resource`, not a domain or URL. Stogas constructs the
trusted `*.openai.azure.com` or `*.services.ai.azure.com` origin from that selection.

The form does not ask for deployment aliases. Your Azure resource must contain deployments named
with the canonical Stogas model IDs, such as `gpt-5.6-sol`. Chat Completions requests use Azure's
native Chat Completions endpoint, and Responses requests use Azure's native Responses endpoint.

The provider secret is accepted only when the credential is created, encrypted at rest, and
decrypted in the confidential gateway for matching requests. The dashboard later returns its name
and short preview, never the secret. To rotate it, create a new credential, reassign keys, then
delete the old credential after it is no longer assigned.

Requests made with your provider credential are billed at 2% of the upstream request cost. Stogas
reserves 2% of the estimated cost and settles 2% of the provider-reported cost, rounding up to the
nearest USD atom. Azure GPT-5.6 cache writes are the documented exception because Azure does not
report their token quantity; see [Prompt caching](/docs/prompt-caching). Key spend limits and balances
use the billed amount. Analytics separately shows upstream cost and billed cost and can filter
requests or API keys by upstream credential.

Request logs identify the selected upstream credential as `stogas` or its credential ID. For
bring-your-own-key requests, Stogas does not add its managed OpenAI `safety_identifier` or Anthropic
`metadata.user_id` to the provider request.
