---
title: Keepalives
description: Keep quiet requests active and understand what acknowledgements establish.
---

A model can spend time reasoning or preparing its first output without returning content.
Stogas sends keepalives during quiet waits so an idle connection can remain active.
They report gateway activity; they do not establish provider acceptance, generated output or completion.

## Streaming comments

Quiet SSE responses receive a processing comment every 15 seconds. Ordinary HTTPS and attested
TLS also send these comments during provider startup. E2EE uses encrypted control records until
the provider returns response headers:

```text
: STOGAS PROCESSING

```

This is a standard SSE comment. OpenAI clients and SSE parsers can ignore it safely. If you
parse the response yourself, skip comments before parsing JSON. Do not count them as model
output or display them as chat content.

Keepalives are automatic for streaming requests over ordinary HTTPS, attested TLS and E2EE.
No header or SDK option is required. Their arrival can be delayed by network or proxy buffering.
If your application forwards a stream to another client, preserve keepalives or provide a
downstream keepalive while no output is available.

## HTTP status and errors

The first SSE comment is response body data. Sending it requires the gateway to send the
response headers, including HTTP 200. That status cannot change afterward.

| When a failure occurs                             | What the client receives                          |
| ------------------------------------------------- | ------------------------------------------------- |
| Before response headers                           | The normal HTTP error status and JSON error body. |
| After a comment or model output starts the stream | HTTP 200 with an error in the SSE stream.         |

For example, a provider rejection after 100 ms can still return HTTP 429. If the gateway has
already sent a processing comment during a long wait, the same rejection must arrive as a
stream error. Ordinary HTTPS and attested TLS behave identically here.

SDK status-based retries and typed HTTP exceptions do not apply to those later stream errors.
Catch failures during iteration as well as stream creation. HTTP-only monitoring sees 200,
so record the stream's outcome separately. [Streaming](/docs/streaming#handle-errors) covers
failure handling and completion.

## Encrypted acknowledgements

E2EE also has a control record outside the response's SSE or JSON body. After authenticating
the encrypted request start, the gateway sends this acknowledgement immediately for both
streaming and buffered requests.

The acknowledgement does not commit the encrypted HTTP status. Authorization, the complete
upload and provider dispatch can still be pending, and a later rejection can retain its normal
status. During provider startup, both streaming and buffered E2EE requests receive encrypted
control keepalives every 15 seconds. These records remain outside the application body and do
not commit its headers. A provider returning HTTP 429 after 30 seconds still reaches the OpenAI
client as HTTP 429, with its supported headers such as `Retry-After`.

Once the provider opens the application stream, SSE comments inside E2EE follow the HTTP status
rules above. Errors after that point remain stream errors. Buffered ordinary HTTPS and attested
TLS responses do not carry either kind of keepalive in their JSON body.

The native loopback bridge and Fetch adapter consume control records internally. They do not
expose an HTTP response until encrypted response metadata arrives. These records keep the outer
encrypted connection active; they do not send bytes through a downstream HTTP bridge or reset an
SDK's response-header, read or total timeout. Configure those deadlines for the expected provider
wait. An acknowledgement or keepalive is not permission to retry.

The JavaScript/TypeScript Fetch transport exposes the initial encrypted acknowledgement through
`onProgress`. SSE comments are not forwarded by standard OpenAI clients as progress events.
See [Request progress](/docs/request-progress) for per-message UI updates and
[E2EE sessions](/docs/e2ee#session-keys-and-concurrency) for session behavior.
