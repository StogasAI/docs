---
title: PII Redaction
description: Remove sensitive text from prompts before sending them to a provider.
---

Use `stogasRedaction` to remove personally identifiable information (PII), secrets and custom
text from requests before they reach a provider. Redaction is off by default; provider responses
are unchanged.

## Enable redaction

Add this configuration to an API key or another [policy scope](/docs/policies/scopes).
It redacts email addresses, banking and healthcare identifiers, and employee IDs such as `EMP-123456`:

```json title="policy.json"
{
	"plugins": {
		"stogasRedaction": {
			"email_address": true,
			"bank_identifiers": true,
			"health_identifiers": true,
			"customPattern": "\\bEMP-[0-9]{6}\\b"
		}
	}
}
```

[Save the policy](/docs/policies/editing), then send a request with synthetic text such as
`Contact élise@stogas.ai.`. That text becomes `Contact <EMAIL_ADDRESS>.` before provider dispatch.
Reserved domains such as `example.com` are excluded from email detection.
In **Analytics → Requests**, open the request and check **Stogas redaction** for its match count.

Keep only the options you need. Preset flags are optional Booleans; within a configured plugin,
omitted flags are off. `customPattern` is one optional string; `literals` is an optional array.
An empty `stogasRedaction` object replaces redaction defaults without adding rules.
Required redaction from other policies still applies.

A `false` flag adds no requirement at this scope. [Inherited requirements](#combining-scopes)
still apply. Remote rule lists and arbitrary scripts are not supported.

## Presets

Choose from these nine flags. Each enables the whole category; identifiers within a category
are not separate options. Every preset is off unless an applicable policy enables it.

| Preset                   | Detects                                                                                  |
| ------------------------ | ---------------------------------------------------------------------------------------- |
| `email_address`          | Email addresses, including plus-addressing and subdomains.                               |
| `phone_number`           | Formatted phone numbers, including international numbers.                                |
| `social_security_number` | U.S. Social Security numbers.                                                            |
| `credit_card_number`     | Payment card numbers.                                                                    |
| `ip_address`             | IPv4 and IPv6 addresses.                                                                 |
| `api_keys_and_secrets`   | Labeled credentials, private keys, JWTs, credential URLs, and recognized service tokens. |
| `bank_identifiers`       | IBANs and U.S. ABA routing numbers.                                                      |
| `national_identifiers`   | The national, tax, and business identifiers listed below.                                |
| `health_identifiers`     | The healthcare and health-insurance identifiers listed below.                            |

SSNs and payment cards have their own flags: `national_identifiers` does not include U.S. SSNs,
and `bank_identifiers` does not include payment cards.

Detection checks format, checksum, and nearby context where applicable. These checks reduce
false positives; they do not verify that an identifier was issued or is active. Ambiguous
numbers may need a label such as `ITIN`, `NHS`, or `routing number` to match.

Phone numbers and numeric identifiers such as SSNs also recognize Unicode decimal digits, including full-width and Arabic-Indic
digits, and common Unicode spaces and hyphens. The same format, checksum, and context rules apply.
Only matched values are replaced; we do not normalize the rest of your text.

### Test examples

Use these synthetic fixtures without substituting personal records or working credentials.
With only the named preset enabled, each positive replaces the value with the shown placeholder
and preserves its label; each negative stays unchanged. The expected match counts are **1**
and **0**, respectively.

| Preset                   | Positive input                         | Placeholder                      | Negative input                           |
| ------------------------ | -------------------------------------- | -------------------------------- | ---------------------------------------- |
| `email_address`          | `Email qa.fixture+redaction@stogas.ai` | `<EMAIL_ADDRESS>`                | `Email qa.fixture+redaction@example.com` |
| `phone_number`           | `Call +44 7700 900123`                 | `<PHONE_NUMBER>`                 | `Call +0 7700 900123`                    |
| `social_security_number` | `SSN: 856-45-6789`                     | `<US_SSN>`                       | `SSN: 123-45-6789`                       |
| `credit_card_number`     | `Card: 4532 0151 1283 0366`            | `<PAYMENT_CARD>`                 | `Card: 4242 4242 4242 4242`              |
| `ip_address`             | `IP: 198.51.100.24`                    | `<IP_ADDRESS>`                   | `IP: 198.51.100.256`                     |
| `api_keys_and_secrets`   | `password=stogas-qa-only-7X!`          | `<CREDENTIAL>`                   | `password=********`                      |
| `bank_identifiers`       | `IBAN GB82 WEST 1234 5698 7654 32`     | `<IBAN>`                         | `IBAN GB81 WEST 1234 5698 7654 32`       |
| `national_identifiers`   | `National Insurance AB 12 34 56 C`     | `<UK_NATIONAL_INSURANCE_NUMBER>` | `National Insurance QQ 12 34 56 C`       |
| `health_identifiers`     | `NPI 1234567893`                       | `<US_NPI>`                       | `NPI 1234567894`                         |

SSNs accept the `NNN-NN-NNNN` form; compact or space-separated forms need a nearby `SSN` or
`social security` label. Zero groups, zero serials, area `000`, `666` or `900`–`999`, repeated
digits, and the sample values `078-05-1120`, `123-45-6789` and `987-65-4320` are excluded.
Adding a label does not make an excluded value match.

Payment cards need a supported network prefix and length, a valid Luhn checksum, and recognized
digit grouping or a nearby card label. Known test values, including `4242 4242 4242 4242` and
`4111 1111 1111 1111`, are excluded even with a label and valid checksum. The negative IBAN and
NPI examples have invalid checksums; the negative National Insurance example has an invalid prefix.
Documentation-reserved IP addresses still match, while reserved email domains are excluded.

Check **Stogas redaction** in the request details after the
[saved policy takes effect](/docs/policies/scopes#when-changes-take-effect). Other scanned fields
or inherited rules can add matches. An absent plugin metric is not a measured zero, and the
aggregate count does not reveal the exact provider-bound text. A model's reply is not evidence
of what redaction removed.

## Literal text

Use literals for project names, phrases, domains or URLs. They are plain text: punctuation such
as `.` or `*` has no special meaning. Matches become `<CUSTOM_PII>`.

```json title="policy.json"
{
	"plugins": {
		"stogasRedaction": {
			"literals": [
				{
					"values": ["Project Aurora", "Project Borealis"],
					"ignoreCase": true,
					"fuzzy": true
				},
				{
					"values": ["InternalCodename"]
				},
				{
					"values": ["internal.example.com"],
					"ignoreCase": true,
					"wholeWord": false
				}
			]
		}
	}
}
```

Each group under `plugins.stogasRedaction.literals` applies the same settings to every string
in `values`. Use separate groups when the settings differ:

<PolicyFields section="literalRule" />

`ignoreCase` treats ASCII `A`–`Z` and `a`–`z` as equal; other Unicode letters retain their case.
With `wholeWord: true`, neither adjacent character may be a Unicode letter, number, combining
mark, or underscore.

Fuzzy rules require **8–64 printable ASCII bytes**, a letter, digit or underscore at both ends,
and `wholeWord: true`. A fuzzy match must also begin and end with those word characters.
Spaces and punctuation inside a phrase count as characters; there is no whitespace normalization.
Fuzzy matching does not correct Unicode text, replace homoglyphs, decode URLs or expand abbreviations.
Exact rules likewise do not normalize Unicode: composed and decomposed spellings can differ.

Set `wholeWord: false` for an exact substring, including a URL inside longer text. URL and domain
rules are text matching, not URL parsing: percent-encoding, alternate host spellings and unrelated
text containing the same substring are not distinguished.

Each source accepts at most **1,000 strings and 65,536 UTF-8 bytes of literal text** across all groups. The combined
set of applicable policies has the same bounds after safe deduplication. Each distinct
rule with its options counts once; internal search seeds and case variants do not count as rules.
The byte allowance is shared, so 1,000 rules cannot each contain 256 bytes.

Use a custom pattern for a bounded family such as `patent_name1` through `patent_name20`:
`\\bpatent_name(?:[1-9]|1[0-9]|20)\\b` in JSON. Regex rules are not fuzzy and do not expand into
the literal count. They have their own limits below. Literal rules are redaction rules, not
toxicity or prompt-injection detection, and do not prove that the remaining input is safe.

## Custom pattern

Use a custom pattern for identifiers with a clear structure, such as an employee or account ID.
Each expression matches text to replace with the fixed placeholder `<CUSTOM_PII>`.
Custom replacements and capture-group substitutions are not supported.

For custom-only redaction, set just `customPattern`. Use alternation to match more than one format:

```json title="policy.json"
{
	"plugins": {
		"stogasRedaction": {
			"customPattern": "\\b(?:EMP-[0-9]{6}|ACCT-[A-Z]{2}-[0-9]{8})\\b"
		}
	}
}
```

Expressions use [Go's RE2 syntax](https://pkg.go.dev/regexp/syntax). Character classes,
alternation, groups, repetition, and supported flags such as `(?i)` are available. Lookarounds
and backreferences are not. JSON needs an extra backslash: write `"\\bEMP-[0-9]{6}\\b"`
for the expression `\bEMP-[0-9]{6}\b`. Writing `\b` with a single backslash inside JSON
encodes a backspace instead of a word boundary.

Counted repetitions are limited to 1,000 by the regex syntax, and the instruction limit may
reject a smaller repetition. `\C` is not supported. Regex `\b` uses ASCII word characters;
literal `wholeWord` checks use the Unicode boundaries described above. Regex `(?i)` uses Go's
Unicode simple case folding, while a literal's `ignoreCase` folds ASCII only.

| Bound                                                | Maximum                   |
| ---------------------------------------------------- | ------------------------- |
| Custom expressions per scope                         | 1                         |
| Unique custom expressions across applicable policies | 3                         |
| Size of one expression                               | 512 UTF-8 bytes           |
| Combined expression size                             | 1,536 UTF-8 bytes         |
| Total compiled matcher size                          | 4,096 instructions        |
| Shared scan-work budget per request                  | 67,108,864 weighted units |

Every expression must consume text. We reject empty, zero-width, invalid, overly complex,
or placeholder-matching expressions. For example, `.*` is too broad and can match empty text.
Each expression uses leftmost-longest matching on the original text. We merge overlapping
matches before replacement, so one scope cannot hide another scope's match. Client-supplied
placeholders do not exempt surrounding text from redaction. The complexity bound can reject
short expressions with large repetitions; narrow the expression to the identifier you need.

Across scopes, exact duplicates count once.
Saving validates the edited policy and its known parents. If a later parent edit makes a
descendant's combined rules exceed a bound, that descendant cannot execute until its policies
are repaired. Its saved source remains available for editing.

## What is scanned

Model, provider, service-tier, catalog restrictions, and output-bound checks run before redaction.
Redaction then runs on Chat Completions and Responses text before token estimation and provider
conversion, after the deployment and credential have been selected. Token estimates do not
affect routing. Redaction covers message and input text, instructions, tool definitions and
arguments, text-format definitions, and supported stop sequences. It scans string values inside
these containers while preserving protocol fields and accepted signed or encrypted reasoning replay.

Model selectors, routing policies, authentication headers, sampling controls, cache controls,
and request metadata are not prompt-text redaction targets. Do not put sensitive prompt content
in metadata. Image, audio, and file scanning are not supported.

Built-in matches become typed placeholders such as `<EMAIL_ADDRESS>`; custom matches become
`<CUSTOM_PII>`. Replacement is irreversible. We keep no map for restoring the original values,
and it does not restore placeholders in the response. This plugin redacts request text, not newly
generated provider output.

The match bounds are 65,536 candidate matches per text value, before overlaps are merged, and
100,000 replacements per request. JSON nesting is limited to 128 levels. Exceeding a bound
rejects the request before dispatch.

### Token estimates and context limits

Typed placeholders preserve where a value was removed. Literal and custom-pattern matches
become `<CUSTOM_PII>`; preset matches use their category's placeholder. Replacements can increase
the token count, especially when many short values match.

The gateway selects a deployment, applies its complete redaction policy, then estimates input
tokens once for reservations, token quotas and request metrics. Local estimates do not reject
or truncate requests, even when they exceed the catalog context window. The provider checks
its actual context limit. A provider rejection does not retry another deployment or weaken
redaction. Gateway byte and processing bounds still apply to the transformed request.

For inline UTF-8 text files, enable [text extraction](/docs/input-files#text-extraction) before redaction.

## Combining scopes

Save redaction at any saved scope or in a permitted request policy. A preset enabled by any
active requirement stays enabled. A child's `false` or omission cannot cancel that requirement.
Default redaction applies only when no active requirement supplies the plugin.

Custom expressions also combine: a match in **any** scope is redacted. Exact duplicate
expressions run once. The text does not have to match every expression. Conditional redaction
applies only to the selected candidate's matching rules. Conditions cannot inspect redacted
output or token estimates.

Literal rules combine the same way. We remove duplicates and rules fully covered by another
rule with the same text. It preserves each remaining rule's options: case-insensitive exact
matching plus case-sensitive fuzzy matching does **not** enable case-insensitive fuzzy matching.
All scanners read the original text; overlapping matches become one replacement covering their union.

For example, organization email detection, grant banking detection, and a key custom
pattern all run on the same request. Removing an option from one scope removes it only when
no other scope requires it.

## Encrypt private rules

To keep custom patterns and literal values private when saved, [encrypt the plugin settings](/docs/cli#encrypt-plugin-settings)
with your own key. This encrypts the entire `plugins` object, including any export destinations.
Supply the required key with each request over attested TLS or E2EE to keep it private from TLS intermediaries.

## ASCII-only input

To reject non-ASCII prompt text instead of redacting it, set the separate input restriction:

```json title="policy.json"
{ "input": { "asciiOnly": true } }
```

`input` requires the Boolean `asciiOnly`. Omit the object or set `asciiOnly: false` to add no
ASCII restriction at this scope. A request policy can set it when `delegation.request` permits `input`.

<PolicyFields section="input" />

This checks the original decoded strings in the [scanned fields](#what-is-scanned), before any
redaction. JSON escapes do not bypass it: `"\u00e9"` represents a non-ASCII character.
A rejection returns HTTP 400 with `input_ascii_required` before provider dispatch or a hold.
ASCII control characters remain allowed where the request schema permits them.

Any scope's `true` requires this check; a child's `false` or omission cannot cancel it.
Protocol fields, object property names, metadata, binary content and opaque reasoning replay are
outside this text check. It is not a blanket ban on Unicode anywhere in the HTTP request.

## Scan cost and rejected requests

Unbounded repetitions such as `+` and `*` remain available within a valid, nonempty expression.
For predictable cost, prefer a literal prefix and a realistic length bound, such as
`EMP-[0-9]{1,12}`. A short expression is not necessarily cheap: a pattern such as `a.*z|a` can
repeatedly search the same text.

We meter custom matching, literal scanning and candidate verification, and variable lookahead
in credential and private-key detection. All scanned text fields and inherited rules share one request budget. Repeated
reads count again, and more complex expressions cost more per character. These weighted units
are not bytes, tokens, or milliseconds; actual latency also depends on the input and hardware.

If a request exceeds the budget, scanning stops and the request fails with **HTTP 413** before
provider dispatch or a spend hold. No partially redacted or original text is sent as a fallback.
Narrow the expression or reduce the input before retrying. Passing policy validation means the
expression is allowed, not that it can scan every possible input within the budget.

If we cannot safely process a request at the moment, we return **HTTP 503**. Retry with
bounded exponential backoff and jitter. Required redaction is never skipped to complete a request.
These temporary capacity errors are separate from your saved spend, token, and request limits.

## Request metrics

For a logged request, the plugin reports only `items_redacted` and `duration_us` under
`plugins.stogas_structured_pii_redaction`. It does not log original values, replacement maps,
offsets, or per-category counts. The log name differs from the policy name, `stogasRedaction`.

In **Analytics → Requests**, redacted requests show the number of replaced items. Open a request
to see **Stogas redaction**, with its match count and duration in microseconds.

The duration covers scanning and replacing the selected request fields. It is part of request
admission time, not an additional interval to add to total duration. Loading a policy, compiling
its matcher, and counting tokens are separate work and are not included in the plugin duration.

Use the analytics search bar to filter requests, charts, and exports:

| Filter                   | Matches                                                                      |
| ------------------------ | ---------------------------------------------------------------------------- |
| `redaction:redacted`     | One or more items were replaced.                                             |
| `redaction:no_matches`   | Redaction ran and reported zero replacements.                                |
| `redaction:not_recorded` | The log has no redaction metrics. This does not mean redaction was disabled. |

Combine filters, for example `redaction:redacted AND provider:openai` or
`NOT redaction:not_recorded`. A replacement count is not a count of distinct people or detector
categories. Original text is never included in these metrics.

## Detector coverage

### Email addresses

Covers ordinary addresses, plus-addressing, subdomains, and Unicode letters and combining marks
in local parts and domains, such as `élise@bücher.de`. Reserved example and test domains stay
unchanged. Quoted local parts, address literals, and arbitrary obfuscated addresses are not supported.

### Phone numbers

Covers formatted North American numbers, such as `(415) 555-2671`, `415.555.2671`, and
`+1 415-555-2671`, plus supported international formats such as `+44 20 7946 0958`.
This is not a catch-all for bare digit strings or every local phone-number format.
Full-width punctuation and non-breaking spaces are supported. A marked extension of up to ten
decimal digits is included in the replacement: `ext`, `ext.`, `extn`, `extension`, `x`, `#`, or
`;ext=`. An unmarked number after a phone number is not treated as an extension.

### Banking

`bank_identifiers` covers IBANs with supported country lengths and checksum validation,
including spaced forms, and nine-digit U.S. ABA routing numbers with routing context and
checksum validation. It does not detect arbitrary bank account numbers, SWIFT/BIC codes,
or cryptocurrency wallet addresses.

### National, tax, and business identifiers

`national_identifiers` enables all of the following. U.S. SSNs remain a separate preset.

| Country        | Identifiers                                                                               |
| -------------- | ----------------------------------------------------------------------------------------- |
| Australia      | Tax File Number (TFN), Australian Business Number (ABN), Australian Company Number (ACN). |
| Brazil         | Individual taxpayer number (CPF), business taxpayer number (CNPJ).                        |
| Canada         | Social Insurance Number (SIN).                                                            |
| China          | Resident identity card number.                                                            |
| Finland        | Personal identity code (HETU).                                                            |
| Germany        | Tax identification number (Steuer-ID), social security number (RVNR).                     |
| India          | Aadhaar number.                                                                           |
| Israel         | National ID number.                                                                       |
| Italy          | Fiscal code (codice fiscale), VAT number (partita IVA).                                   |
| Nigeria        | National Identification Number (NIN).                                                     |
| Poland         | PESEL number.                                                                             |
| Singapore      | National Registration Identity Card (NRIC) or Foreign Identification Number (FIN).        |
| South Africa   | National ID number.                                                                       |
| South Korea    | Resident or foreigner registration number, business registration number.                  |
| Spain          | National identity number (DNI) or foreigner identity number (NIE).                        |
| Sweden         | Personal identity number (personnummer).                                                  |
| Thailand       | National ID number.                                                                       |
| Türkiye        | National identity number (TCKN).                                                          |
| United Kingdom | National Insurance number (NINO).                                                         |
| United States  | Individual Taxpayer Identification Number (ITIN).                                         |

This is a closed list, not a detector for every government-issued identifier. Passport numbers,
driver's license numbers, and formats from unlisted countries are not included.

### Healthcare

`health_identifiers` enables all five identifier types:

| Country        | Identifiers                                                                |
| -------------- | -------------------------------------------------------------------------- |
| Australia      | Medicare number.                                                           |
| Germany        | Health-insurance identifier (KVNR).                                        |
| United Kingdom | NHS number.                                                                |
| United States  | National Provider Identifier (NPI), Medicare Beneficiary Identifier (MBI). |

This preset detects identifiers, not diagnoses, medical narratives, or arbitrary patient-record numbers.

### API keys and secrets

`api_keys_and_secrets` covers:

- Labeled passwords, API keys, access tokens, client secrets, and related credential assignments,
  including supported Bearer and Basic authorization text inside scanned content.
- PEM private-key blocks and JSON Web Tokens (JWTs).
- Credentials in HTTP, HTTPS, FTP, FTPS, and SFTP URLs.
- Credential-bearing PostgreSQL, CockroachDB, MySQL, MariaDB, MongoDB, SQL Server, Redis, and AMQP URLs.
- Recognized service-token formats from AWS and Bedrock, GitHub, GitLab, Google, Slack, Stogas,
  Anthropic, OpenAI, Stripe, Hugging Face, Groq, npm, PyPI, Doppler, 1Password, PlanetScale,
  Pulumi, Sentry, Vault, Databricks, DigitalOcean, Perplexity, Twilio, Shopify, Linear,
  Atlassian, age, SendGrid, Telegram, and Notion.

This is format detection, not a credential-validity check. An arbitrary secret without a recognized
format or label may not match. Request authentication headers themselves are not scanned.

## Limits of detection

The built-in detectors exclude inferred person names, street addresses, locations, UUIDs, ordinary dates,
and unformatted numbers. IP addresses also stay unchanged unless you opt in. Redaction does not
guarantee that every sensitive value will be found. Check representative inputs, including values
that should stay unchanged, before relying on a custom expression.

Each request is scanned once against its original text. Sending the redacted result in a later
request can produce different matches if nearby context has changed. Typed placeholders do not
act as identifier labels or exempt surrounding text from redaction.
