---
title: Export
description: Send request and response JSON to your own webhook.
---

The `stogasExport` plugin sends one JSON record to each configured webhook when a request finishes.
Use it to keep your own request history or process requests in another service.

Enabling export includes the full processed request and the public response. For
streaming requests, it includes the ordered JSON events instead of an assembled
response. Each record uses the canonical request-log fields for usage, cost,
timing, provider attempts, and errors, with content and final response metadata added.

## Configure a webhook

```json
{
	"plugins": {
		"stogasExport": {
			"destinations": [
				{
					"url": "https://receiver.example.com/events",
					"headers": {
						"Authorization": "Bearer YOUR_RECEIVER_TOKEN"
					}
				}
			]
		}
	}
}
```

Use the complete HTTPS URL. Stogas appends no path. Headers are optional and apply
only to webhook delivery. Hosted gateways require a public destination; loopback
HTTP is available only in local development.

Save the plugin in a [policy](/docs/policies). Required destinations from active
policies are combined, with exact duplicates sent once and at most eight combined
destinations. An empty `destinations` array replaces defaults but cannot remove an
inherited requirement. Request-level configuration requires delegation of
`plugins.stogasExport` or `plugins`.

Encrypt the plugin section to protect saved destination credentials. The
[CLI guide](/docs/cli) covers plugin encryption and supplying the key with
requests. Export sends request content to your receiver, so enable it only for
content you want that receiver to retain.

## Record content

Each POST has `Content-Type: application/json`, an `Idempotency-Key` header equal to
the record's `request_id`, and contains one object.

The root uses the same request event that supplies Stogas request history and
analytics. It includes `schema_version`, `request_id`, `created_at`, account/key
identifiers, `request_type`, catalog and policy versions, `provider_attempts`,
`performance`, `usage`, optional plugin metrics, and `gateway_version`.
`usage` contains meters, costs, and exact Standard Text Tokens. Unmeasured values are omitted.
`gateway_error` holds a Stogas processing failure or null, including a caller timeout
or receipt failure; upstream outcomes belong to `provider_attempts`. `cancelled`
records an observed client disconnect; it does not mean the provider stopped or that
usage was free. Unknown meters stay absent; observed zero remains explicit. Each
attempt records `byok` as its credential ID or null for managed access, and owns its
resolved `catalog_chain_hash`.

The export adds:

| Field      | Content                                                                                                                                                                  |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `request`  | Processed request JSON after input transformations and redaction, or null when preparation did not complete.                                                             |
| `response` | Public response JSON for a unary request, or the error that ended it. Stogas metadata is stored separately.                                                              |
| `events`   | Ordered public JSON stream events, including forced usage and the error that ended the stream. Replaces `response` when events were captured.                            |
| `stogas`   | Final contextual metadata: catalog selection, usage, costs, timing, node, and available provider metadata. Includes the signed `receipt` when the request asked for one. |

Every record includes `stogas`, whether or not the request sent `Stogas-Metadata: v1`.
It is the same object that header returns, and it appears once, outside `response`
and `events`. When the request asked for metadata, the record keeps the signed object
intact, even where its fields also occur in the canonical request event. Receipts bind
the original request and response framing; this processed JSON record is not a
byte-for-byte transcript.

Capture begins after policy and deployment selection; earlier rejections produce
no record. The request excludes policy documents, encryption keys, and unsupported
fields removed during processing. Inference authentication headers, provider
credentials, export credentials, and internal gateway state are never added to
the record. Any secrets within your own message content remain subject to your
configured input redaction.

Responses and events preserve their public JSON fields, including reasoning,
opaque reasoning data, and tool items supported by the API. Stream events remain
separate: terminal snapshots may repeat earlier deltas. SSE comments, keepalives,
and `[DONE]` are not JSON events and are omitted; the final metadata comment is
retained as `stogas`. Capture occurs before downstream writing, so it does not prove
the client received every captured byte.

A client disconnect or caller timeout ends only delivery to the client. The provider
continues to completion, and the record keeps its remaining output and final usage.
The caller's timeout error is not added to `response` or `events`; `gateway_error`
records it. Gateway resource and lifetime limits still apply.

## Delivery

`plugins.stogas_export.capture_us` records cumulative content-copy time during the request.
It excludes final record encoding and webhook delivery, which finish after event capture.

Each destination receives its record independently, so a slow receiver does not delay
other destinations. Any HTTP 2xx response acknowledges a record; the response body is
ignored. Redirects are not followed.

| Rule        | Behavior                                                                                                    |
| ----------- | ----------------------------------------------------------------------------------------------------------- |
| Retry       | One retry after a connection failure or HTTP 429, 502, 503, or 504. Other responses are final.              |
| Retry delay | `Retry-After` when present; otherwise about five seconds, randomized.                                       |
| Time limits | Ten seconds each to connect, complete TLS, and receive response headers after the upload.                   |
| Lifetime    | One minute from capture, including uploads and the retry. A longer `Retry-After` ends delivery immediately. |
| Shutdown    | Up to five seconds to finish in-progress deliveries.                                                        |

A retry can deliver a record your receiver already accepted, for example when its
acknowledgement was lost. Use `Idempotency-Key` or `request_id` to ignore duplicates.
There is no durable replay.

Exports yield gateway memory to requests. When requests need memory, the oldest
records awaiting delivery are dropped first. A capture that cannot fit is dropped
whole rather than failing its request; records are never truncated.

This is a JSON webhook format. A service that requires another ingestion schema
needs an adapter at your receiver.
