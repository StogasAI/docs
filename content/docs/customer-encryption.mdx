title: Customer encryption
description: Encrypt provider keys, exports and redactions with a key that only you hold.

---

Customer encryption keeps saved secrets private from everyone who lacks your key, including us. You
hold the organization key. We store only ciphertext, and the gateway decrypts it inside the verified
confidential VM for the request that sends the key.

Use it for:

- **Provider credentials** used by [BYOK](/docs/byok#customer-encryption). An organization can
  [require it](/docs/byok#require-customer-encryption) for every provider credential.
- **Export and redaction settings**: [Export](/docs/export) destinations and their credentials,
  and the terms that [PII redaction](/docs/pii-redaction) finds.

Limits, routing, access, delegation and text extraction stay readable.

## Create a key

<Steps>
<Step>

### Generate the key

[Install the CLI](/docs/cli#install) on your own machine, then run:

```console
stogas encryption-key create --organization YOUR_ORGANIZATION_ID --label providers
```

The command saves the key in your system keychain under the label that you will register it with,
and prints only its public identifier. Where there is no keychain, as on most servers, write the
key to a file with `--output org.key` instead. Keep a secure backup, such as a copy that
`stogas encryption-key export` writes. We cannot recover a lost key.

</Step>
<Step>

### Register the identifier

Register the identifier under the same label in the dashboard, or with
[Register an encryption key](/docs/reference/dashboard/encryption-keys/registerEncryptionKey).
Requests send the key under this label, and credentials and policies can use only registered keys.
Registering and removing keys needs organization management. The key works in requests
[within three minutes](/docs/policies/scopes#when-changes-take-effect).

A label is a lowercase letter followed by up to 47 lowercase letters, digits, underscores or
hyphens. Each identifier has one label, and an organization can register up to 32 keys. Use
separate keys when credentials, exports and redactions need different access.

</Step>
</Steps>

## Encrypt plugin settings

Encrypt a policy's export or its redaction, each on its own: the export to hide where requests go
and the tokens that deliver them, the redaction to hide the terms that it finds. Each can use its
own registered key. Text extraction stays readable, because it is only on or off.

<Steps>
<Step>

### Save the plugin's settings to a file

Save the object inside `plugins.redaction` or `plugins.export`, without the name around it:

```json title="redaction.json"
{
	"literals": [{ "values": ["Project Aurora"] }]
}
```

```json title="export.json"
{
	"destinations": [
		{
			"url": "https://receiver.contoso.com/stogas",
			"headers": { "Authorization": "Bearer YOUR_RECEIVER_TOKEN" }
		}
	]
}
```

</Step>
<Step>

### Encrypt the file

```console
stogas encrypt --key providers --organization YOUR_ORGANIZATION_ID \
  --purpose plugins/redaction --input redaction.json --output redaction.encrypted.json
```

`--key` names the label of a key in your keychain. For a key file, pass `--key-file org.key`
instead. Before it encrypts a plugin's settings, the command has a gateway check them over a
verified connection, so a mistake shows now, by name, instead of in the requests that need them.
Only the gateway sees the settings, and the check needs you signed in with `stogas login` or
`STOGAS_TOKEN`. A credential is encrypted without connecting anywhere. The command never
overwrites an existing output file. The `--purpose` decides which input it accepts:

| Purpose             | Input                                                                                                         |
| ------------------- | ------------------------------------------------------------------------------------------------------------- |
| `plugins/export`    | The object inside `plugins.export`.                                                                           |
| `plugins/redaction` | The object inside `plugins.redaction`.                                                                        |
| `byok/openai`       | The exact OpenAI credential, without a trailing newline.                                                      |
| `byok/anthropic`    | The exact Anthropic credential, without a trailing newline.                                                   |
| `byok/chutes`       | The exact Chutes credential, without a trailing newline.                                                      |
| `byok/aws`          | An [AWS credential document](/docs/providers/aws#customer-encryption).                                        |
| `byok/azure`        | An [Azure application](/docs/providers/azure#customer-encryption), as `az ad sp create-for-rbac` prints it.   |
| `byok/google-cloud` | A Google service account key file or [credential document](/docs/providers/google-cloud#customer-encryption). |

For a plugin, the output is the plugin's new value: the envelope in `encrypted`. For a credential,
it is the envelope in `encryptedSecret`, with the `preview` except for Azure, and for AWS and Google
Cloud the `target` that you register with it.

</Step>
<Step>

### Save the encrypted settings

Replace the plugin's value with the output, and keep the policy's other settings:

```jsonc title="Policy shape (replace placeholders)"
{
	"plugins": {
		"textExtraction": "always",
		"redaction": {
			"encrypted": {
				"version": 1,
				"keyId": "64_LOWERCASE_HEX_CHARACTERS",
				"salt": "BASE64URL_32_BYTES",
				"nonce": "BASE64URL_12_BYTES",
				"blob": "BASE64URL_CIPHERTEXT_AND_TAG"
			}
		}
	}
}
```

A rule's plugins take the output the same way, as in `rules.night.plugins.export`.
[Save the policy](/docs/policies/editing). `keyId` selects the registered key. Saving checks the
readable settings, the envelope format and that the organization registers the key.

</Step>
<Step>

### Send the key with each request

[Send the key](#send-the-key-with-a-request) with each request. The gateway decrypts and checks
the settings before it calls the provider, and rejects the request if the key is missing or wrong,
or the settings are invalid. To find problems first, use the
[policy check](/docs/policies/editing#check-a-policy-before-saving).

</Step>
</Steps>

[Policy size limits](/docs/policies/editing#document-rules) count the decrypted plugin bytes.

Encryption hides only the plugin's settings. Anyone who can read the policy still sees the rest:
which plugins are encrypted, a rule's name and `when` condition, which tell them when the hidden
settings apply, and the envelope's size, which shows roughly how large the settings are. Keep
revealing words out of rule names and conditions.

## Send the key with a request

Put each required key under its registered label in `encryption_keys` in the request body. Keep
your API key in the `Authorization` header:

```json title="Responses request body"
{
	"model": "chutes-gemma-4-31b",
	"input": "Hello",
	"encryption_keys": { "providers": "YOUR_PROVIDERS_KEY" }
}
```

- Send every key that the request could need: the keys of encrypted credentials it could use,
  including fallbacks, and of the encrypted policy settings that apply to it. A missing key fails
  the request with `encryption_key_required`, which names the key's label, before any provider
  call. To let the request use only the candidates whose keys it sends, set
  [`routing.missingEncryptionKeys`](/docs/policies/routing#missing-encryption-keys) to `skip`.
- Each label must match its registered identifier.
- To leave your application's requests unchanged, give the keys to the connection instead.
  [`stogas serve`](/docs/cli#send-your-encryption-keys) reads them from your keychain or from
  key files, and an SDK transport takes them as its
  [`encryption_keys` option](/docs/sdk-overview#options). Both add the keys to each request that
  sends none.
- An application that sends the keys itself needs them. To copy one from your keychain to the
  secret store that the application reads, pipe `stogas encryption-key export` with `--output -`
  to it. The CLI never prints a key on the screen.
- The gateway removes `encryption_keys` before it calls the provider, and never stores the keys.
- Send keys through the [SDK or CLI](/docs/connection-modes), so that only the verified gateway
  can read them. Ordinary HTTPS does not verify the gateway, and a TLS proxy can read the body.
- Keep keys out of URLs, command-line arguments and logs.

## Key sharing and rotation

Anyone with both a key and its ciphertext can decrypt that content. Only separate keys give
separate access, not separate labels. Removing a member does not make them forget a key they had.
Each caller must hold every key that the encrypted exports and redactions of their requests need.

Keep the original policies and provider credentials so you can encrypt them again. To rotate a key:

1. Generate a new key and register it under a new label.
2. Update your clients to send both keys.
3. Encrypt the exports, redactions and provider credentials again with the new key, and save
   them. The dashboard lists where each key is still used in the policies and credentials you can
   view, such as `plugins.redaction` or `rules.night.plugins.export`.
4. When the dashboard lists no more uses of the old key, filter analytics with
   [`encryption_key:`](/docs/analytics#filters) and its label to check that no recent request
   could still use it.
5. Remove the old key's registration, then stop sending it.

After you remove a registration, requests skip the credentials that the key encrypts, and requests
that need policy settings that it encrypts fail with `encryption_key_required`, which names the key's
identifier. You can still save a policy that uses the key, but no policy can start to use it until
you register it again.

## Encryption details

Each encryption uses a fresh salt and nonce to derive an AES-256-GCM key with HKDF-SHA-256. The
authenticated context binds the organization, the purpose and the key identifier, so a ciphertext
cannot be moved to another organization, plugin or credential: a redaction's envelope saved as
`plugins.export` fails every request that applies it.
