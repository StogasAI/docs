Customer encryption keeps saved secrets private from everyone who lacks your key, including us. You
hold the organization key. We store only ciphertext, and the gateway decrypts it inside the verified
confidential VM for the request that sends the key.

Use it for:

- **Provider credentials** used by [BYOK](/docs/byok#customer-encryption). An organization can
  [require it](/docs/byok#require-customer-encryption) for every provider credential.
- **Export and redaction settings**: [Export](/docs/export) destinations and their credentials,
  and the terms that [PII redaction](/docs/pii-redaction) finds. You can encrypt a whole plugin or
  any value inside it.

Other policy settings stay readable, because we check them when you save and the dashboard shows
what they do.

## Create a key

<Steps>
<Step>

### Generate the key

[Install the CLI](/docs/cli#install), then run:

```console
stogas encryption-key create --output providers.key
```

The command writes the key to a new file that only you can read, and prints the key's ID. Keep the
key where your applications read their secrets, and keep a backup, because we cannot recover a lost
key. To save the key in your system keychain instead, pass `--organization` and `--label` in place
of `--output`, as [the CLI](/docs/cli#encrypt-secrets) shows.

Settings can also generate a key in your browser and register it. That trusts the page that we
serve when you open it, while the CLI is a release that you install once and
[can verify](/docs/cli#verify-it).

</Step>
<Step>

### Register the ID

Register the ID under a label in Settings, or with
[Register an encryption key](/docs/reference/dashboard/encryption-keys/registerEncryptionKey).
Requests send the key under this label, and credentials and policies can use only registered keys.
Registering and removing keys needs organization management. The key works in requests
[within three minutes](/docs/policies/scopes#when-changes-take-effect).

A label is a lowercase letter followed by up to 47 lowercase letters, digits, underscores or
hyphens. Each ID has one label, and an organization can register up to 32 keys by default, as its
Limits card in Settings shows. Use separate keys when credentials, exports and redactions need
different access.

</Step>
</Steps>

## Encrypt plugin settings

Write the policy as usual:

```json title="policy.json"
{
	"plugins": {
		"export": {
			"destinations": [
				{
					"url": "https://receiver.contoso.com/stogas",
					"headers": { "Authorization": "Bearer YOUR_RECEIVER_TOKEN" }
				}
			]
		},
		"redaction": { "literals": [{ "values": ["Project Aurora"] }] }
	}
}
```

Then encrypt the parts that you want to hide:

```console
stogas encrypt --key-file providers.key --organization YOUR_ORGANIZATION_ID --policy policy.json \
  --path /plugins/export/destinations/0 --path /plugins/redaction/literals \
  --output policy.encrypted.json
```

Each part becomes an envelope in its place, and the rest stays as you wrote it:

```jsonc title="policy.encrypted.json (placeholders)"
{
	"plugins": {
		"export": {
			"destinations": [
				{
					"encrypted": {
						"version": 1,
						"keyId": "64_LOWERCASE_HEX_CHARACTERS",
						"salt": "BASE64URL_32_BYTES",
						"nonce": "BASE64URL_12_BYTES",
						"blob": "BASE64URL_CIPHERTEXT_AND_TAG"
					}
				}
			]
		},
		"redaction": { "literals": { "encrypted": { "version": 1, "keyId": "…" } } }
	}
}
```

[Save the policy](/docs/policies/editing) from the output. Saving checks the readable settings,
each envelope's format and that the organization registers its key.

- `--path` takes a [JSON Pointer](https://www.rfc-editor.org/rfc/rfc6901) to the `export` or
  `redaction` plugin, or to any value inside one, in the policy or in a rule, such as
  `/rules/night/plugins/export`. Repeat it for more parts. A path above a plugin, such as
  `/rules/night`, encrypts each export and redaction plugin under it, and without `--path` the
  command encrypts every one in the policy.
- Encrypt a destination's `headers` together with its `url`, by encrypting the destination or more.
  Someone who can edit the policy could otherwise move the headers beside another URL.
- Before it encrypts the parts, the command has a gateway check the plugins that hold them, over a
  verified connection, so a mistake shows now instead of in the requests that need them. The check
  needs you signed in with `stogas login` or `STOGAS_TOKEN`.
- Keep the policy without encryption, and encrypt from it whenever you change it. The command
  refuses a plugin that already holds encrypted values, because the check needs all of it.
- Each plugin can use its own registered key. A request needs the key of each encrypted part that
  applies to it, as [Send the key with a request](#send-the-key-with-a-request) shows.

[Policy size limits](/docs/policies/editing#document-rules) count encrypted parts at their
decrypted size. Anyone who can read the policy still sees:

- the readable settings around each encrypted part, which show where it is
- each rule's name and `when` condition, which tell when the hidden settings apply
- each encrypted part's size, rounded up to 256 bytes

Keep revealing words out of rule names and conditions.

## Send the key with a request

Put each required key under its registered label in `encryption_keys` in the request body. Keep
your API key in the `Authorization` header:

```json title="Responses request body"
{
	"model": "chutes-gemma-4-31b",
	"input": "Hello",
	"encryption_keys": { "providers": "YOUR_PROVIDERS_KEY" }
}
```

- Send every key that the request could need: the keys of encrypted credentials it could use,
  including fallbacks, and of the encrypted policy settings that apply to it. A missing key fails
  the request with `encryption_key_required`, which names the key's label, before any provider
  call. To let the request use only the candidates whose keys it sends, set
  [`routing.missingEncryptionKeys`](/docs/policies/routing#missing-encryption-keys) to `skip`.
- Each label must match its registered ID.
- To leave your application's requests unchanged, give the keys to the connection instead.
  [`stogas serve`](/docs/cli#send-your-encryption-keys) reads them from key files or your
  keychain, and an SDK transport takes them as its
  [`encryption_keys` option](/docs/sdk-overview#options). Both add the keys to each request that
  sends none.
- The gateway removes `encryption_keys` before it calls the provider, and never stores the keys.
- Send keys through the [SDK or CLI](/docs/connection-modes), so that only the verified gateway
  can read them. Ordinary HTTPS does not verify the gateway, and a TLS proxy can read the body.
- Keep keys out of URLs, command-line arguments and logs.

## Key sharing and rotation

Anyone with both a key and its ciphertext can decrypt that content. Only separate keys give
separate access, not separate labels. Removing a member does not make them forget a key they had.
Each caller must hold every key that the encrypted settings of their requests need.

Keep the original policies and provider credentials so you can encrypt them again. To rotate a key:

1. Generate a new key and register it under a new label.
2. Update your clients to send both keys.
3. Encrypt the policy settings and provider credentials again with the new key, and save them.
   [List the uses of an encryption key](/docs/reference/dashboard/encryption-keys/listEncryptionKeyUses)
   names each policy and credential that you can view and that still uses the old key, and where
   each policy holds it, such as `/plugins/redaction` or
   `/rules/night/plugins/export/destinations/0/url`.
4. Filter analytics with [`encryption_key:`](/docs/analytics#filters) and the old key's label to
   check that no recent request could still use it.
5. Remove the old key's registration, then stop sending it.

You can remove a registration only when no policy or credential uses the key. Until then the
removal fails with `ENCRYPTION_KEY_IN_USE`, including when the uses are in policies or credentials
that you can't view.

## Encryption details

Each encryption uses a fresh salt and nonce to derive an AES-256-GCM key with HKDF-SHA-256. The
authenticated context binds the organization, the setting and the key ID, so a ciphertext opens
only as the same setting of the same organization. For example, an export URL's envelope saved as
a redaction term fails every request that applies it. The CLI pads each policy part with spaces
to a multiple of 256 bytes before it encrypts it.
