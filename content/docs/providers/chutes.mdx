[Chutes](https://chutes.ai/docs) runs open-weight models. Most of them run in trusted execution
environments (TEEs) built on Intel TDX and NVIDIA confidential GPUs, which the gateway reaches with
end-to-end encryption. The rest are [Standard models](#standard-models). Every new API key can use
Chutes through our account. To use your own Chutes account instead, add a key in [BYOK](/docs/byok).

## End-to-end encryption

For a TEE deployment, the gateway encrypts each request for the TEE instance that runs the model.
Chutes' relay forwards the ciphertext and cannot read the prompt or the response.

<Steps>
<Step>

### Find instances

The gateway asks Chutes for running instances of the model. Each instance has an ML-KEM-768 public
key and one-use request tickets.

</Step>
<Step>

### Check the hardware evidence

The gateway checks a fresh Intel TDX quote against Intel's certificates and revocation lists, and
the NVIDIA GPU evidence through NVIDIA's attestation service. The quote must have debugging and
migration off, match a measurement that Chutes publishes for its runtime, and bind the instance's
ML-KEM key.

</Step>
<Step>

### Encrypt the request

The gateway encrypts the request to that key with ML-KEM-768 and ChaCha20-Poly1305. The instance
encrypts its response, including usage, with a fresh key. The gateway accepts only authenticated
output and usage.

</Step>
</Steps>

If no verified instance is available, the request fails. A TEE deployment never falls back to
plaintext.

- Chutes' relay sees the model and instance, timing, sizes and usage.
- The Chutes API key and that metadata travel only under the outer TLS connection, which prefers
  the post-quantum X25519MLKEM768 key exchange but accepts a classical one.

### What the evidence does not prove

Chutes decides which TEE measurements are acceptable, and no independent party checks them against
Chutes' published source code. The measurements cover Chutes' runtime, which starts only
containers signed with keys that Chutes controls, so the quote does not identify the container image
or the model weights. The catalog therefore lists TEE deployments with `tee: true` and `teeVerified: false`.

A model that runs on several GPUs can send data between them over NVLink without encryption,
depending on the GPU generation, and Chutes' evidence does not cover the switches that carry it.

## Standard models

Chutes' terms call some of its models Standard models. They do not run in a Chutes TEE, so the
gateway sends their requests without end-to-end encryption. The requests go to Chutes'
OpenAI-compatible API at `https://llm.chutes.ai/v1/chat/completions` over post-quantum TLS, with
the same API key. Chutes forwards each request to inference platforms that it does not name, and
their staff and systems can access content while they process it. Their IDs contain
`-unknown-hosted`, such as `chutes-glm-5.2-unknown-hosted`, because
[hosting](/docs/policies/routing-fields#companies) is `unknown`.

These fields differ between TEE and Standard deployments:

| Field                            | TEE deployments | Standard deployments |
| -------------------------------- | --------------- | -------------------- |
| `dataHandling.endToEndEncrypted` | `true`          | `false`              |
| `dataHandling.tee`               | `true`          | `false`              |
| `dataHandling.trainingUse`       | `false`         | missing              |
| `hosting`                        | `chutes`        | `unknown`            |

Chutes' terms let it, its network operators and its model providers keep content for as long as
processing needs it, and they name no storage place or retention period. The catalog therefore lists
the storage location as `unknown` and no retention on every Chutes deployment. To keep requests
on TEE deployments, filter on `deployment.dataHandling.endToEndEncrypted`.

Chutes does not say that it keeps prompt caches apart between accounts, so
`dataHandling.isolatedPromptCache` is `false` on every Chutes deployment. When another account
shares the cache, its request that starts with the same tokens as a recent one of yours shows
this in its cached token count and response time. To keep prompts out of caches that other
accounts can share, filter on `deployment.dataHandling.isolatedPromptCache`.

## Supported requests

Chutes supports Chat Completions with text messages, and Responses through
[the translation](/docs/providers#responses-through-chat-completions). It accepts these fields, or
their Responses equivalents:

- `stream` and `stream_options`
- `max_completion_tokens` or `max_tokens`
- `tools` with `function` tools, and `tool_choice`, where the deployment supports them
- `response_format` with `json_object` or `json_schema`, where the deployment supports it
- `reasoning_effort` and `reasoning`, on TEE deployments that support them
- `temperature`, `top_p`, `top_k`, `frequency_penalty`, `presence_penalty`, `repetition_penalty`,
  `seed` and `stop`

`logprobs`, `n` above 1, `parallel_tool_calls: false`, cache controls, hosted tools, service tiers,
images, audio and files are not available, even when the model supports them.

**If you omit the output limit, Chutes applies a low default of its own.** Set one for long
answers or heavy reasoning.

## Retries

When Chutes rejects an encrypted request before the model starts, for example because an instance is
at capacity, the gateway calls another verified instance at once. That call is one of the candidate's
[retries](/docs/policies/routing#retries-and-fallbacks), so it needs `routing.retries` of 1 or more.
Standard models have no instances, so this retry does not apply to them.

Chutes sends no request ID on encrypted calls. Each call's entry in the
[request record](/docs/request-records#provider-attempts) names its instance in
`provider_instance_id` instead, so Chutes can find the call by instance and time.

## When the client stops early

When your client disconnects, or a [timeout](/docs/policies/timeouts) ends a stream, on a TEE
deployment, the gateway stops the Chutes call. You pay for the usage up to the stop, because each
encrypted chunk carries the usage so far. Buffered requests and Standard models report usage only
when the call ends, so their calls run to the end and you pay for their full usage.
