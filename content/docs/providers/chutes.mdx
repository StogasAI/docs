Chutes runs open models such as Kimi, Qwen, GLM and DeepSeek in trusted execution environments
(TEEs) built on Intel TDX and NVIDIA confidential GPUs. Every new API key can use Chutes through our
account. To use your own Chutes account instead, add a key in [BYOK](/docs/byok).

## End-to-end encryption

The gateway encrypts every Chutes request to the TEE that runs the model. Chutes' relay forwards the
ciphertext and cannot read the prompt or the response.

<Steps>
<Step>

### Find instances

The gateway asks Chutes for running instances of the model. Each instance has an ML-KEM-768 public
key and one-use request tickets.

</Step>
<Step>

### Check the hardware evidence

The gateway checks a fresh Intel TDX quote against Intel's certificates and revocation lists, and
the NVIDIA GPU evidence through NVIDIA's attestation service. The quote must have debugging off,
match a measurement that Chutes publishes for its runtime, and bind the instance's ML-KEM key.

</Step>
<Step>

### Encrypt the request

The gateway encrypts the request to that key with ML-KEM-768 and ChaCha20-Poly1305. The instance
encrypts its response, including usage, with a fresh key. The gateway accepts only authenticated
output and usage.

</Step>
</Steps>

If no verified instance is available, the request fails. There is no plaintext fallback.

- Chutes' relay sees the model and instance, timing, sizes and usage.
- The Chutes API key and that metadata travel only under the outer TLS connection, which uses a
  classical key exchange.

### What the evidence does not prove

Chutes decides which TEE measurements are acceptable, and no independent party checks them against
Chutes' published source code yet. The measurements cover Chutes' runtime, which starts only
containers signed with keys that Chutes controls, so the quote does not identify the container image
or the model weights. The catalog therefore lists Chutes with `tee: true` and `teeVerified: false`.

## Supported requests

Chutes supports Chat Completions with text messages. It accepts:

- `stream` and `stream_options`
- `max_completion_tokens` or `max_tokens`
- `tools` with `function` tools, and `tool_choice`
- `response_format` with `json_object` or `json_schema`, where the deployment supports it
- `reasoning_effort` and `reasoning`
- `temperature`, `top_p`, `top_k`, `frequency_penalty`, `presence_penalty`, `repetition_penalty`,
  `seed` and `stop`

`logprobs`, `n` above 1, `parallel_tool_calls`, cache controls, hosted tools, service tiers,
images, audio and files are not available, even when the model supports them.

**If you omit the output limit, Chutes stops at 1,024 tokens.** Set one for long answers or heavy
reasoning.

## Retries

When Chutes rejects a request before the model starts, for example because an instance is at
capacity, the gateway calls another verified instance at once. That call is one of the candidate's
[retries](/docs/policies/routing#retries-and-fallbacks), so it needs `routing.retries` of 1 or more.

Chutes sends no request ID on encrypted calls. Each call's entry in the
[request record](/docs/request-records#provider-attempts) names its instance in
`provider_instance_id` instead, so Chutes can find the call by instance and time.
