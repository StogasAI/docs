Azure deployments run GPT, Claude and open models from your Microsoft Foundry deployments,
including Azure OpenAI. The gateway calls them with a Microsoft Entra application that you create.
Azure bills you for inference, and we charge the [BYOK fee](/docs/byok#billing).

| Deployment ID suffix   | Azure deployment type                      | Where inference runs                   |
| ---------------------- | ------------------------------------------ | -------------------------------------- |
| None                   | Global Standard                            | Any Azure region                       |
| `-us`                  | US Data Zone Standard                      | United States                          |
| `-eu`                  | EU Data Zone Standard                      | Europe, under Azure's EU Data Boundary |
| `-apac`                | Asia Pacific Data Zone Standard            | Asia Pacific                           |
| `-instant`             | Instant access                             | A Foundry project in West US 3         |
| `-anthropic-hosted`    | Claude hosted by Anthropic                 | Anthropic                              |
| `-fireworks-hosted-us` | US Data Zone Standard, hosted by Fireworks | United States                          |

For example, `azure-gpt-5.5-2026-04-23-us` runs GPT-5.5 only in the United States. Microsoft
describes each
[deployment type](https://learn.microsoft.com/en-us/azure/foundry/foundry-models/concepts/deployment-types).
[Instant access](https://learn.microsoft.com/en-us/azure/foundry/concepts/instant-models) needs a Foundry project in West US 3 that the credential can reach.

`-fireworks-hosted-us` runs MiniMax M3 with Fireworks. Microsoft shares request data
with Fireworks, which runs the model under its own compliance and data handling rules.

## Connect your account

Create an Entra application that
[trusts](https://learn.microsoft.com/en-us/entra/workload-id/workload-identity-federation) your
organization's [issuer](/docs/byok#federation), and give it the
[**Foundry User**](https://learn.microsoft.com/en-us/azure/foundry/concepts/rbac-foundry) role on your model accounts, or on a resource group or subscription
that holds them. [BYOK](/docs/byok) shows the issuer URL and the subject when you add an Azure
credential.

```bash
appId=$(az ad app create --display-name stogas-gateway --query appId --output tsv)
az ad sp create --id $appId
az role assignment create --assignee $appId \
  --role 53ca6127-db72-4b80-b1b0-d745d6d5456d \
  --scope /subscriptions/<subscription-id>/resourceGroups/<group>
az ad app federated-credential create --id $appId --parameters '{
  "name": "stogas",
  "issuer": "https://app.stogas.ai/api/federation/<organization-id>",
  "subject": "organization:<organization-id>",
  "audiences": ["api://AzureADTokenExchange"]
}'
```

Enter your tenant ID and `$appId` in [BYOK](/docs/byok) as the tenant ID and client ID. The
application has no secret. Entra can take a few minutes to accept a new federated credential, so
finding your accounts can fail until then.

### Use a client secret instead

```bash
az ad sp create-for-rbac --name stogas-gateway \
  --role 53ca6127-db72-4b80-b1b0-d745d6d5456d \
  --scopes /subscriptions/<subscription-id>/resourceGroups/<group>
```

Enter `tenant`, `appId` and `password` from the output in [BYOK](/docs/byok) as the tenant ID,
client ID and client secret.

## Customer encryption

With [customer encryption](/docs/byok#customer-encryption), we store only the encrypted
application, and only a gateway can open it with your key.

1. Save the application, then encrypt it. The CLI also takes `tenantId`, `clientId` and
   `clientSecret` in a JSON object, without `clientSecret` for an application that trusts your
   organization's issuer.

   ```bash
   az ad sp create-for-rbac --name stogas-gateway \
     --role 53ca6127-db72-4b80-b1b0-d745d6d5456d \
     --scopes /subscriptions/<subscription-id>/resourceGroups/<group> > app.json
   stogas encrypt --key-file providers.key --organization <organization-id> \
     --credential azure --input app.json
   ```

   Then delete `app.json`, which holds the secret.

2. Add what the CLI printed in [BYOK](/docs/byok) as a customer-encrypted credential. Each account
   that you connect becomes its own credential.
3. [Check the credentials](/docs/cli#check-a-credential) where you keep the key:

   ```bash
   stogas byok check <credential-id>... --organization <organization-id>
   ```

   The check signs in with the application and saves each account's deployments as targets.

Gateways look for new deployments once a day while requests use the credential, and each check
looks at once. A replaced application keeps its targets until the next check.

## Targets

You choose which of your Azure deployments serves each catalog deployment. A target is one exact
model version, and the gateway never sends a request to a deployment that you did not choose. If a
target stops serving, the gateway tries the next candidate that your
[routing](/docs/policies/routing#retries-and-fallbacks) allows.

Azure can upgrade a deployment to a new model version, as its `versionUpgradeOption` allows.
Your choice follows the deployment. Within 20 minutes of an upgrade, requests use the
deployment as a target of the new version, when your policies allow that version. Until then,
requests for the old version use your next candidate or fail with `byok_target_unavailable`.

The gateway reads your account's deployments every 10 minutes while requests use the credential.
A reply that Azure answered from the new version before that read reaches you unchanged, and its
request log names the version that answered.

A check fails when an account has more than 20,000 targets, or when it would take the targets of
all your organization's Azure credentials past the organization's limit, which is 20,000 by
default and which we can raise. The credential then keeps the targets of its last check. Requests
through an API key whose Azure credentials have more than 20,000 chosen targets together fail with
`key_configuration_too_large`.

## Prompt caching

GPT deployments take the same cache fields as [OpenAI](/docs/providers/openai#prompt-caching).
DeepSeek deployments cache automatically and receive `prompt_cache_key`, which gives each key its
own cache. Azure returns `400` for `prompt_cache_retention` on a model that is not GPT.

## Claude on Azure

[Claude on Azure](https://platform.claude.com/docs/en/build-with-claude/claude-in-microsoft-foundry)
accepts the same request fields as on [Anthropic](/docs/providers/anthropic). Claude that Azure
runs, in deployments without `-anthropic-hosted`, takes no file IDs, so send files inline or by URL.
