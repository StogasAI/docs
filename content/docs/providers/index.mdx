Every catalog deployment belongs to one provider. The feature pages describe what all providers
share, and each provider's page lists its own setup, limits and data handling. The provider sees
your prompt and handles it under its own terms, as the [security model](/docs/security-model)
explains.

| Provider                                     | Credential            | Responses        | Service tiers         | Prompt caching                  | Hosted tools                      | Connection                                  |
| -------------------------------------------- | --------------------- | ---------------- | --------------------- | ------------------------------- | --------------------------------- | ------------------------------------------- |
| [OpenAI](/docs/providers/openai)             | API key               | Yes              | Flex, Fast, Ultrafast | Automatic, optional breakpoints | Web search, remote MCP            | Post-quantum TLS                            |
| [Anthropic](/docs/providers/anthropic)       | API key               | Yes              | Fast                  | `cache_control`                 | Web search, web fetch             | Post-quantum TLS                            |
| [Azure](/docs/providers/azure)               | Entra application     | Yes[^translated] | Flex, Fast            | As OpenAI or Anthropic          | Web search, web fetch for Claude  | TLS 1.3                                     |
| [AWS](/docs/providers/aws)                   | Access key or API key | Yes              | None                  | `cache_control`                 | Web search, web fetch[^anthropic] | TLS 1.3                                     |
| [Google Cloud](/docs/providers/google-cloud) | Service account key   | Yes              | Fast[^anthropic]      | `cache_control`                 | Web search, web fetch[^anthropic] | Post-quantum TLS                            |
| [Chutes](/docs/providers/chutes)             | Ours, or your API key | Yes[^translated] | None                  | Automatic                       | None                              | E2EE to a verified TEE, or post-quantum TLS |

Every provider serves Chat Completions, some OpenAI and Azure deployments [through
Responses](#chat-completions-through-responses). The [catalog](https://stogas.ai/catalog) shows
each deployment's price, context window, input types, reasoning levels and data handling. [Routing
policies](/docs/policies/routing) can filter on them, for example to allow only zero data retention
deployments.

## Companies

A provider belongs to a company, and another company can run its models.
[Routing policies](/docs/policies/routing-fields#companies) name each company by its ID.

| Provider     | `provider.companyId` |
| ------------ | -------------------- |
| OpenAI       | `openai`             |
| Anthropic    | `anthropic`          |
| Azure        | `microsoft`          |
| AWS          | `amazon`             |
| Google Cloud | `google`             |
| Chutes       | `chutes`             |

The catalog names the company that runs each deployment in `deployment.hosting`, which is
`unknown` when the provider does not name it.

## Request fields

The gateway checks each request against the selected deployment before it calls the provider. A
field that the deployment cannot honor, or that the gateway cannot price, returns `400` with no
charge, and so does an unknown top-level field. A deployment runs a request without a
[setting that it lacks](/docs/reference/provider-behavior#settings-that-a-deployment-lacks), such
as `seed`. The [compatibility notes](/docs/reference/provider-behavior) list fields that the
gateway never accepts.

## Translated requests

Some deployments take only one of Chat Completions and Responses. The gateway translates a request
on the other API, and returns the reply, or each streamed event, on the API that you called:

| You call         | Deployments                                                  | The gateway calls |
| ---------------- | ------------------------------------------------------------ | ----------------- |
| Responses        | Azure and Chutes deployments that take only Chat Completions | Chat Completions  |
| Chat Completions | OpenAI and Azure deployments that take only Responses        | Responses         |

OpenAI and Azure deployments that take both APIs also get a Chat Completions request through
Responses when its `reasoning_details` hold encrypted reasoning that the gateway returned from
OpenAI or Azure, or when it has `tools` or `reasoning.display` set to `summarized` with any
reasoning effort but `none`. OpenAI's Chat Completions refuse function tools while the model
reasons, and only Responses return reasoning summaries and take back earlier reasoning. A request
that Responses cannot carry keeps Chat Completions, which return no reasoning summaries.
Otherwise a deployment that takes the API that you call gets it. A route in `model` chooses the API,
as in `route:openai-chat-completions gpt-5.6-sol`.

The request record's `interface` shows the API that you called, and each attempt's
[catalog chain](/docs/request-records#catalog-history) names the route that the gateway called.
Routing leaves out a deployment that takes only the other API when it cannot take the request, so
another deployment can serve it.

### Responses through Chat Completions

A translated request returns `400` for what Chat Completions cannot carry:

- `include` values other than `message.output_text.logprobs` and `reasoning.encrypted_content`
- `max_tool_calls`
- hosted and custom tools, such as `web_search`, and tool choices that name them
- a `reasoning.summary` other than `auto` or `none`
- input items other than messages, function calls, their outputs and reasoning
- a function call whose `namespace` and `name` name no tool in `tools`
- file URLs and image file IDs
- `stream_options.include_obfuscation` set to `true`

The deployment's Chat Completions limits apply as well, so Chutes returns `400` for log
probabilities. Reasoning comes back as text, which `reasoning.encrypted_content`
does not change. A streamed reply sends reasoning as `response.reasoning_text` events, and its
function calls arrive whole when the reply ends. Log probabilities cover only the output text, so
a reply that also has reasoning or tool calls has none when the provider's tokens do not join into
exactly that text.

### Chat Completions through Responses

A translated request returns `400` for what Responses cannot carry:

- `stop`, `logit_bias` and `web_search_options`
- `n` above 1

OpenAI and Azure deployments return their reasoning encrypted in `reasoning_details`. Send it back
unchanged in the assistant message, and the model continues from that reasoning.

[^anthropic]: Only on deployments that Anthropic runs, whose IDs contain `-anthropic-hosted`.

[^translated]: Partly [through Chat Completions](#responses-through-chat-completions).
