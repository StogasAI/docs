Before the SDK sends your API key or prompt, it checks on your device that the gateway runs an
approved release on genuine AMD SEV-SNP hardware. Native packages and browser WebAssembly use the
same Rust verifier. If a check fails, the SDK sends nothing. Dates are checked against your device
clock, so a wrong clock makes verification fail.

## What the SDK checks

| Evidence                                                              | Shows                                                                                     |
| --------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| Key manifest, signed by our root key                                  | Which online signing keys we have authorized                                              |
| Evidence document, signed by an online key                            | Which gateway releases, catalogs and hardware policies are approved                       |
| Rekor inclusion proofs for the key manifest and the evidence document | Both are in the public [Sigstore Rekor](https://docs.sigstore.dev/logging/overview/) log  |
| Sigstore's current keys, signed by Sigstore's root keys               | Which Rekor keys check the inclusion proofs                                               |
| GitHub and GitLab build proofs in the evidence document               | Each approved release was [built from its public source](/docs/reproducible-builds)       |
| AMD certificate chain and revocation list                             | The hardware report comes from a genuine AMD chip that AMD has not revoked                |
| SEV-SNP hardware report                                               | The VM booted an approved release, with debugging and migration off, on approved firmware |
| A fresh challenge from your client, signed into the report            | The report was made now, for this connection, and binds the connection's keys             |
| The gateway's boot record and its Rekor inclusion                     | The gateway's boot is in the public log                                                   |

The SDK has our root key, Sigstore's root keys and AMD's root certificates built in. Downloaded
evidence cannot replace them. The evidence document names the exact Sigstore keys, so the SDK
keeps working when Sigstore changes its keys.

The gateway's TLS, E2EE and receipt-signing keys are generated inside the VM and never leave it. A
public boot record alone does not prove that a connection reaches that gateway. Only the fresh
challenge does.

## Batched attestation

The gateway puts the challenges of connections that arrive together into a Merkle tree, and the
chip signs one report over the tree's root. Your client gets that report and a proof, at most 644
bytes, that its challenge is in the tree. Every connection still gets a report made after its
challenge, and one report serves up to 1,024 new connections. Other clients' challenges appear in
the proof only as hashes.

## Hardware policy

The hardware policy lists the approved chip models and the minimum firmware and microcode versions
for each. Each release also fixes its own VM settings, such as debugging off. A gateway must meet
both.

During a firmware update, the policy can allow more than one configuration for the same chip. A
gateway must meet every requirement of one of them. When the update is done, we remove the old
configuration, and gateways that still use it lose their approval.

## Evidence updates

The SDK loads evidence when it starts, and once more if a connection needs newer evidence. It does
not poll in the background. Evidence comes from `evidence.stogas.ai`, with an independent copy at another cloud provider
as a fallback. The SDK checks everything it downloads, so a server cannot make it trust invalid
evidence. Each change to the evidence gets the next revision number. Under one key manifest, the
SDK rejects evidence older than the newest revision it has seen. Call `refreshEvidence`
(`refresh_evidence` in Rust and Python, `RefreshEvidence` in Go) to load new evidence now.

Gateways check the evidence about every two minutes. When we withdraw a release, or required
evidence expires, the gateway stops accepting new requests. Requests that are running finish.

### Revocation

AMD signs its revocation lists with an expiry date. A publisher that holds back a newer list can
delay a revocation only until the older list expires. Once the SDK has seen a revocation, an older
copy of the evidence cannot undo it.

## Trust Center

The dashboard's Trust Center shows the current evidence and its history, checked in your browser
with the same verifier.

- Rekor logs the hash of the whole signed evidence document, so one entry covers every catalog,
  gateway release, hardware policy and Sigstore key in it. The key manifest and each build proof
  have their own entries.
- Staging releases are built without GitHub and GitLab, so a build placeholder lists their files
  instead. We approve a release only when GitHub's proof and GitLab's name the same files. To
  check a release yourself, see
  [Reproducible builds](/docs/reproducible-builds).
- AMD signs its own certificates and revocation lists, so they need no Rekor entry.
- History lists each release, catalog and key manifest at the evidence revision that first listed
  it, and the hardware policy at each revision that changed it, including a change back to an
  earlier policy.
- Past boots stay checkable after keys rotate or AMD lists expire, because we keep the original
  evidence and the verifier checks it as of the time Rekor logged the boot. New connections always
  need current evidence.

## Search Rekor yourself

Every key manifest, evidence revision and boot record is in the public Rekor log. Our root's Rekor
submission key logs key manifests, and the SDK has it built in with the root key. Each online
signing key has its own submission key, listed in the verified key manifest, which logs evidence
revisions and boot records. The SDK rejects an entry that any other key submitted, so a search with
these keys covers every entry it accepts. Save a submission public key as
`stogas-rekor-public.pem`, then use [rekor-cli](https://docs.sigstore.dev/logging/cli/):

```console
rekor-cli search --rekor_server https://rekor.sigstore.dev \
  --pki-format x509 --public-key stogas-rekor-public.pem
rekor-cli get --rekor_server https://rekor.sigstore.dev --uuid <entry-uuid>
```

Search with each key that was in use during the period you want to check.

- Rekor's search index is best effort. An empty result does not prove that an entry does not exist.
- A search result does not prove that we signed the document. Check the document's
  signature and its digest against the log entry.
- A submission key cannot approve anything on its own. The SDK also requires our signature.
