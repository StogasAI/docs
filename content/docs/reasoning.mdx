The gateway accepts one effort scale on every provider and converts it to the control of the
selected deployment:

`none` · `minimal` · `low` · `medium` · `high` · `xhigh` · `max`

## Set an effort

```json tab="Chat Completions"
{
	"model": "gpt-5.6-sol",
	"messages": [{ "role": "user", "content": "Find the bug in this function." }],
	"reasoning_effort": "high"
}
```

```json tab="Responses"
{
	"model": "gpt-5.6-sol",
	"input": "Find the bug in this function.",
	"reasoning": { "effort": "high" }
}
```

If you omit the effort, the provider uses its default. `none` turns optional reasoning off.

Chat Completions also accepts `"reasoning": { "enabled": true }`, which selects the level nearest
to `medium`. `false` means `none`, and a value that conflicts with the effort is rejected.

## Select Pro mode

Some models also have a Pro deployment[^pro], which does more work per request at its own price. Set
`reasoning.mode`:

```json tab="Chat Completions"
{
	"model": "gpt-5.6-sol",
	"messages": [{ "role": "user", "content": "Review this migration plan." }],
	"reasoning": { "mode": "pro", "effort": "high" }
}
```

```json tab="Responses"
{
	"model": "gpt-5.6-sol",
	"input": "Review this migration plan.",
	"reasoning": { "mode": "pro", "effort": "high" }
}
```

- `pro` selects the model's Pro deployment, and `standard` its standard deployment.
- Without `reasoning.mode`, a model ID selects standard mode, and a deployment ID such as
  `openai-gpt-5.6-sol-pro` keeps its own mode.
- A mode that your key cannot use returns `reasoning_mode_unavailable`, also when you name a
  deployment in that mode. Other values return `unsupported_reasoning_mode`.
- Pro deployments take only Responses, so the gateway translates a Chat Completions request
  [through Responses](/docs/providers#chat-completions-through-responses).
- Pro combines with a [service tier](/docs/service-tiers), such as Pro at Flex.

## How the gateway converts an effort

| The deployment                       | The gateway                                                      |
| ------------------------------------ | ---------------------------------------------------------------- |
| Lists the effort                     | Sends it unchanged.                                              |
| Lists other levels                   | Sends the nearest level. A tie goes to the higher level.         |
| Has reasoning on or off only         | Turns reasoning on for any effort, and off for `none`.           |
| Accepts only a token budget          | Converts the effort to a budget, as described below.             |
| Does not reason                      | Accepts `none`, and leaves the deployment out for other efforts. |
| Requires reasoning                   | Leaves the deployment out for `none`.                            |
| Requires reasoning but has no levels | Leaves the deployment out for any effort.                        |

The request uses its other candidates. When the effort leaves out every candidate, the request fails
with `400`.

For example, `minimal` on a deployment with `low`, `medium` and `high` becomes `low`.

## Check a deployment

Each deployment in the [catalog](/docs/models#find-a-model) has three reasoning fields:

| Field                | Value                                                                                    |
| -------------------- | ---------------------------------------------------------------------------------------- |
| `reasoning`          | `unsupported`, `optional` or `required`.                                                 |
| `reasoningEfforts`   | The levels you can select. Empty when reasoning is only on or off, or not available.     |
| `reasoningMaxTokens` | `{ "minimum", "maximum" }` when the deployment accepts a token budget, otherwise `null`. |

Levels can differ between Chat Completions and Responses, so each deployment lists
`reasoningEfforts` under each of its `routes`.

## Set a token budget

Some deployments accept a maximum number of reasoning tokens:

```jsonc
{
	"model": "claude-sonnet-4-6",
	"messages": [{ "role": "user", "content": "Plan the migration." }],
	"max_completion_tokens": 16000,
	"reasoning": { "max_tokens": 8000 } // Must be below the output limit.
}
```

The budget must be within the deployment's `reasoningMaxTokens`. Send a budget or an effort, not
both.

When a deployment accepts only a budget, the gateway converts the effort to a position between the
deployment's `minimum` and the output limit:

| Effort    | Position |
| --------- | -------- |
| `minimal` | 2.5%     |
| `low`     | 15%      |
| `medium`  | 42.5%    |
| `high`    | 80%      |
| `xhigh`   | 92%      |
| `max`     | 100%     |

The budget is `minimum + floor(position × (output limit − minimum))`, and at most the
deployment's `maximum`. `max` stays one token below the output limit, which Anthropic requires, so
every provider gets the same budget. `none` turns reasoning off.

## Show or hide the reasoning summary

Some models can return a summary of their reasoning. On Responses, set `reasoning.summary`[^summary].
Omit it to keep the provider's default. The summary changes what you see, not what you pay.

## Send reasoning back

In a tool loop, send the model's reasoning back with the tool results:

```json tab="Responses"
{
	"model": "claude-sonnet-5",
	"include": ["reasoning.encrypted_content"],
	"input": [
		{ "role": "user", "content": "What's the weather in Paris?" },
		{ "type": "reasoning", "id": "rs_...", "summary": [], "encrypted_content": "..." },
		{
			"type": "function_call",
			"call_id": "call_1",
			"name": "get_weather",
			"arguments": "{\"city\":\"Paris\"}"
		},
		{ "type": "function_call_output", "call_id": "call_1", "output": "18°C and cloudy" }
	]
}
```

```json tab="Chat Completions"
{
	"model": "claude-sonnet-5",
	"messages": [
		{ "role": "user", "content": "What's the weather in Paris?" },
		{
			"role": "assistant",
			"reasoning_details": [
				{ "type": "reasoning.text", "text": "...", "signature": "...", "index": 0 }
			],
			"tool_calls": [
				{
					"id": "call_1",
					"type": "function",
					"function": { "name": "get_weather", "arguments": "{\"city\":\"Paris\"}" }
				}
			]
		},
		{ "role": "tool", "tool_call_id": "call_1", "content": "18°C and cloudy" }
	]
}
```

- On Responses, `include: ["reasoning.encrypted_content"]` returns reasoning items that you can
  send back. Send each item back unchanged, in its place in `input`.
- On Chat Completions, send `reasoning_details` back unchanged on its assistant message.
- A signed or encrypted entry that you change returns `400`[^claude].
- Each deployment gets only the reasoning that it can read, and the gateway leaves out the rest,
  such as another model family's reasoning or reasoning that you got from a provider directly. A
  conversation can move to another model or credential[^credential], and the model continues
  without what it cannot read.

## Billing

Reasoning tokens are a separate [usage meter](/docs/usage), billed at the deployment's output rate
unless the catalog lists a reasoning rate. The hold before the request covers the full output limit,
including reasoning.

[^pro]:
    GPT models on [OpenAI](/docs/providers/openai#tiers-and-pro) and
    [Azure](/docs/providers/azure).

[^summary]:
    Anthropic models accept `auto` or `none`, and on Chat Completions also
    `reasoning_display: "summarized"` or `"omitted"`. OpenAI models accept
    [OpenAI's values](https://developers.openai.com/api/docs/guides/reasoning#reasoning-summaries).

[^claude]:
    Claude also checks the system prompt, tools and earlier messages before its reasoning. See
    [Anthropic](/docs/providers/anthropic#reasoning).

[^credential]:
    GPT models read encrypted reasoning only through the credential that returned it, and on
    [Azure](/docs/providers/azure) only from a deployment in the same Azure account.
