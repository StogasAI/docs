Bring your own key (BYOK) sends requests through your provider account. Your API key still
authenticates every request to us, and the provider credential authenticates only the gateway's
call to the provider. The provider bills you, and we charge a [2% fee](#billing).

| Credential         | Where the secret is       | Providers      | Each request sends              |
| ------------------ | ------------------------- | -------------- | ------------------------------- |
| Stogas managed     | Our provider account      | Some           | Your API key                    |
| Stored             | Saved and encrypted by us | Every provider | Your API key                    |
| Customer encrypted | Encrypted on your device  | Every provider | Your API key and encryption key |

New keys start with the Stogas-managed credential, which reaches the deployments that the catalog
marks `stogasManaged`. Every other deployment needs a credential of your own.
Each [provider page](/docs/providers) shows what its credential needs. A stored credential for a
cloud account can hold no secret at all, through [federation](#federation).

## Checks

We check a stored credential with a free call to the provider when you save it, and every 23 hours
after that. A rejected credential is not saved. If a check fails, requests keep using the
credential, because a provider can reject a check for a short time. We check again after an hour,
and double the wait while the checks keep failing, up to 23 hours. When a provider rejects the
credential in a request, we check it again within 5 minutes, or an hour after its last check if that
is later. A check does not prove quota or access to every model. A customer-encrypted credential is
checked only when you run [`stogas byok check`](/docs/cli#check-a-credential) with its encryption
key, which the gateway uses for that check only and never stores. An Azure credential's check also
finds its account's deployments, which become its [targets](/docs/providers/azure#targets).

A provider can still refuse one model through a credential that passes its check, such as a
model that your provider account can't use. The request's
[result](/docs/request-records#provider-results) names the refusal, and
[Analytics](/docs/analytics) filtered by the credential shows every refused call. To limit a
credential to some models yourself, give it a [policy](/docs/policies/scopes).

## Federation

```json title="Token that the gateway signs for your cloud"
{
	"iss": "https://app.stogas.ai/api/federation/<organization-id>",
	"sub": "organization:<organization-id>",
	"aud": "sts.amazonaws.com",
	"iat": 1795000000,
	"nbf": 1795000000,
	"exp": 1795000300,
	"jti": "0d6f3a52c1b94e7f8a21"
}
```

A cloud account can trust your organization instead of giving us a secret. The gateway signs a
token as your organization, and your cloud exchanges it for access that lasts up to one hour. The
credential that you save names only what to sign in to, such as a role, so nothing in it can leak
or needs rotation. The provider pages of the clouds that support federation show the setup.

| Value      | What it is                                               |
| ---------- | -------------------------------------------------------- |
| Issuer     | `https://app.stogas.ai/api/federation/<organization-id>` |
| Subject    | `organization:<organization-id>`                         |
| Audience   | Set by your cloud. Its provider page gives the value     |
| Signature  | RS256. `kid` names the key                               |
| Token life | 5 minutes                                                |
| Discovery  | `<issuer>/.well-known/openid-configuration`              |
| Keys       | `https://app.stogas.ai/api/federation/jwks`              |

- Each organization has its own issuer, so a cloud that trusts yours accepts no other
  organization's token.
- The subject is the organization. Every member who can add a credential can use what trusts it,
  so give the role or account in your cloud only the access that the organization needs.
- Let your cloud read the keys from the issuer. We replace them without notice, and a copy that you
  upload stops working.
- To revoke the access, remove the trust in your cloud. Access that your cloud already gave ends
  within one hour.

## Customer encryption

With customer encryption, we store only ciphertext, and each request sends the key that unlocks it.

1. [Create an organization key](/docs/customer-encryption#create-a-key) and register it.
2. Encrypt the credential on your machine:

   ```console
   stogas encrypt --key-file providers.key --organization YOUR_ORGANIZATION_ID --credential openai
   ```

   The CLI asks for the API key without showing it, and prints the credential to add. AWS and
   Google Cloud take a credential document, and Azure takes an
   [application](/docs/providers/azure#customer-encryption), which you pass with `--input` and the
   CLI checks before it encrypts them.

3. Add what the CLI printed as a customer-encrypted credential. Saving does not contact the
   provider.
4. [Send the key](/docs/customer-encryption#send-the-key-with-a-request) with each request.

A request that could use the credential but doesn't send its key fails with
`encryption_key_required`. To let it use the key's other credentials instead, set
[`routing.missingEncryptionKeys`](/docs/policies/routing#missing-encryption-keys) to `skip`.

### Require customer encryption

An external organization can turn off **Allow stored credentials** to keep every provider secret of
its own unreadable to us. Members can then add only customer-encrypted credentials. Turning it off
needs **Organization → Manage** and works only once the organization has no stored credentials.
Personal organizations always allow them. To move an organization over:

1. Save each account again as a customer-encrypted credential.
2. Put it in place of the stored credential in each key's [list](#order-credentials).
3. Delete the stored credentials, then turn off **Allow stored credentials**.

After that, the dashboard takes a provider secret only as `stogas encrypt` prints it. A call to the
dashboard API that sends a secret in plain text gets `409 STORED_CREDENTIALS_NOT_ALLOWED`, and we
neither store that secret nor send it to the provider. That request still carried the secret to
us, so replace it at the provider if your rules forbid that.

## AWS and Google Cloud

The CLI and the dashboard API take an AWS or Google Cloud credential as a JSON document, which the
[AWS](/docs/providers/aws#customer-encryption) and
[Google Cloud](/docs/providers/google-cloud#customer-encryption) pages show.

Each of these credentials has a public target: the hostings that it serves and, for AWS, its
Region, such as `{"hosting":["amazon","anthropic"],"region":"us-east-1"}`. Routing reads the target
instead of the secret. To keep a customer-encrypted credential off a hosting, remove the hosting
from its target.

## Account options

```cel title="A filter that an account with zero data retention passes"
deployment.dataHandling.zeroDataRetention == true
```

An account option is something that your provider account has and that changes how the provider
handles your requests, such as a zero data retention agreement or a business associate agreement.
The catalog states the data handling of an account without options. Turn on the options that your
account has when you edit the credential.
[Data handling fields](/docs/policies/routing-fields#data-handling) then hold what your account
gets for requests through that credential.

Each provider's page in the [catalog](https://stogas.ai/catalog) lists its options, with the routes
that each one covers and the facts that it sets.

- An option changes only the deployments that list it under `accountOptions`. A provider can leave
  a deployment out of an agreement, such as a preview.
- An option sets whole values. A [hosted tool](/docs/model-tools#data-handling-of-hosted-tools)
  that the request lets the model call still joins its own data handling afterward, so a tool
  that stores content removes zero data retention. So does a request that
  [stores its response](/docs/providers/openai#stored-responses).
- An option can add the certification [`hipaa`](/docs/policies/routing-fields#certifications) to
  deployments that list `hipaa-eligible`.
- Options that are values of one setting exclude each other.
- Stogas-managed credentials have no options.

### Declared and reported options

Some providers report an option when we [check](#checks) the credential. The credential then shows
the report and follows it. You can change any option, and your choice replaces the report.

We cannot verify an option that you turn on yourself. Turn one on only when your account has it,
because policies and request records then state its data handling as fact.
[`credential.declaredAccountOptions`](/docs/policies/routing-fields#credential) lists the options
that you turned on and the provider did not report, so a policy can refuse them.

- A change needs **Manage** on the credential. [Activity](/docs/activity) records the option's ID
  with its old and new value.
- Each provider attempt in a [request record](/docs/request-records#account-options) lists the
  options that applied.

## Order credentials

Each API key has an ordered credential list for each provider. [Routing](/docs/policies/routing)
chooses the deployment, and the gateway uses the first credential in the list that can serve it,
under that credential's [policy](/docs/policies/scopes). A
[fallback](/docs/policies/routing#retries-and-fallbacks) tries the deployment's next credential
before the next deployment. An empty list turns the provider off for that key.

For example, put a customer-encrypted Chutes credential before Stogas managed, and set
[`routing.missingEncryptionKeys`](/docs/policies/routing#missing-encryption-keys) to `skip`.
Requests that send its key then use your account, and the others use Stogas managed.

- Adding a credential to a key needs **Manage** on the key and **Use** on the credential. Reordering
  or removing needs only **Manage** on the key.
- Removing a member's **Use** stops new assignments, and existing assignments keep working. Disable
  the credential to stop them all.
- If a key's policies and credentials grow too large, requests fail with
  `key_configuration_too_large`.

## Allowlist the gateway's IP address

Requests and [checks](#checks) come from `15.204.217.217`.

- Every customer's requests come from this address.
- A planned change appears on our [Notices](https://stogas.ai/notices) page 30 days before it takes
  effect.

## Rotate or revoke a credential

- A replaced secret keeps the credential's ID, assignments and history.
- A disabled credential rejects new requests. Requests that already started finish.
- Requests through a key that has no credential left for a provider fail with `byok_required`.

For routine rotation, keep the old secret valid until running requests finish. To revoke a key
urgently, disable the credential, then revoke the key with the provider.

## Security

- We encrypt stored secrets before we save them. The dashboard and API never show a secret or its
  ciphertext again.
- The confidential gateway decrypts a secret only for requests from keys that the credential is
  assigned to, and for its [checks](#checks). Our control service decrypts a stored Azure
  application only to connect another account with it.
- Only the gateway can decrypt customer-encrypted secrets. Your key travels with each request and
  is never written to databases or analytics.
- Request records keep the credential ID, never the secret.
- No request field or header takes a provider secret.

## Billing

BYOK requests cost 2% of the usage at catalog rates, charged to your balance. Spending limits count
the full usage at catalog rates, not only the fee. Your provider bills you separately, and
negotiated provider prices do not change the fee. See [Billing](/docs/billing) for funding fees.
