title: Bring your own provider key
description: Configure BYOK with a stored provider credential or a key your organization controls.
---

Bring your own key (BYOK) lets us route a request through your provider account. You still
authenticate every request with a Stogas API key. The provider credential only authenticates the
upstream provider request.

## Choose a credential method

| Method                 | Secret storage           | Request requirement                     |
| ---------------------- | ------------------------ | --------------------------------------- |
| **Stored BYOK**        | Encrypted by us          | Stogas API key                          |
| **Customer encrypted** | Encrypted on your device | API key and organization encryption key |
| **Stogas managed**     | Supplied by us           | Stogas API key                          |

Managed service is available for Chutes. OpenAI, Anthropic and Chutes support customer encryption.
Azure uses stored Microsoft Entra credentials so we can discover deployments.

## Store a provider credential

1. Open **BYOK** in the dashboard.
2. Select **Add** and choose the provider.
3. Enter a name and the provider credential. For Azure, enter the tenant ID, application client ID,
   client secret, and the subscription IDs that we may inspect.
4. Open a service or member API key and select the stored credential for that provider.

Before saving or replacing a secret, we check it through authenticated metadata calls, not
paid inference. OpenAI and Anthropic use their model-list operation; Chutes uses its account-quota
operation. Azure uses its management API to discover targets. A rejected credential is not saved. If the
provider is unavailable or rate-limits the check, try again. A successful check does not guarantee
quota or access to every model.

The dashboard never returns the stored secret. You can replace any stored provider credential in
place. Its stable credential ID, API-key assignments, and analytics history do not change.

## Credential access

In a shared organization, add the credential in **Members → Roles** and select its permissions:

| Permission | Allows                                                                            |
| ---------- | --------------------------------------------------------------------------------- |
| **View**   | Read metadata, assignments and policies.                                          |
| **Use**    | View, plus attach the credential to API keys you manage.                          |
| **Manage** | View, plus change settings, replace the secret, disable or delete the credential. |
| **Admin**  | Use, Manage, and authority to assign existing roles within that scope.            |

Use and Manage are independent and can be combined. Creating credentials requires
organization-wide credential Manage. Provider secrets and encrypted blobs are never returned.

Removing Use prevents new assignments. Existing assignments continue to work, and key managers
can still reorder or remove them. Disable the credential to stop all its assignments.
Credential access does not grant access to API keys or inherit from their folders.

## Customer encryption

[Generate and register an organization key](/docs/cli#encrypt-credentials-and-plugins), or use
the existing `org.key`. Encrypt the provider credential locally:

```console
stogas encrypt --key-file org.key --organization YOUR_ORGANIZATION_ID \
  --purpose byok/openai --input provider-secret.txt --output credential.json
```

The input file must contain the exact credential, without a trailing newline. Use `byok/openai`,
`byok/anthropic`, or `byok/chutes` to match the provider.

1. Open **BYOK → Add → Customer encrypted**, choose the provider, and paste `credential.json`.
2. Assign the saved credential to an API key. Registration does not contact the provider.
3. Include the contents of `org.key` under its registered label in `encryption_keys` in each request's JSON body.

Keep your API key in `Authorization`. Ordinary HTTPS, attested TLS, and binary E2EE are supported;
[choose your transport before sending the key](/docs/cli#send-the-key-with-a-request).
We recommend a locally verified transport to protect it from TLS intermediaries. No provider-secret
header is accepted.

The management API returns only credential metadata and a preview, never its encrypted blob or secret.
API callers can use assigned credentials with the matching registered root. An omitted credential
root excludes that credential from routing; a wrong supplied root or invalid encrypted content
fails the request, even when local fallback is enabled. Roots required by applicable encrypted
policies must also be supplied.
See [key sharing and rotation](/docs/cli#key-sharing-and-rotation) for the shared trust boundary,
backups, and replacement procedure.

## Connect Azure

Create one Microsoft Entra application for the Azure accounts that one Stogas credential may use.
Grant its service principal **Reader** on the selected subscriptions and **Foundry User** on the
model accounts or projects that it may call. Scope inference access to the resources you intend to
use. Azure role changes can take several minutes to apply.

When you save the credential, we read Azure Resource Manager to find accessible model accounts,
locations, deployments, exact model versions, hosting modes, SKUs, and supported Foundry projects.
Discovery does not execute a paid request or establish inference permission, quota, or account
eligibility for every model. Azure checks those when a request runs. Customer deployment names,
resource IDs, endpoints, and physical resource locations remain private binding data; they do not
become public catalog nodes.

Azure Instant access is separate from a normal Azure deployment. We discover supported Instant
models through an accessible West US 3 Foundry project and bind the exact versioned model name to
that project endpoint. Use **Refresh Azure deployments** after you add, remove, or change Azure
deployments or projects.

Each Stogas API key can order stored Azure credentials. An empty list means that Azure requests
fail. At request time, we match the selected catalog deployment to an exact discovered model,
version, hosting mode, and deployment type inside that credential. Open **Azure targets** to choose
one physical target for each matching offering. A unique target is selected when the credential is
created; duplicates require your choice. Refreshing preserves that choice, and newly discovered
targets remain unselected. If the selected target disappears, it stays visible as unavailable and
requests cannot use another target until you choose it. We never guess a customer deployment name
or fall back to another provider.

The catalog represents material Azure choices such as Global Standard, US or EU Data Zone Standard,
Azure-hosted or partner-hosted inference, and Instant access. It does not duplicate every physical
Azure resource region. Pro and Priority are request controls on the same physical deployment, so
they do not require separate Azure deployments. A region filter can select only catalog deployments
whose documented data handling satisfies it; unknown regions do not satisfy a narrow filter.
An applicable catalog guarantee of no ordinary-content storage does not require Azure to report a
storage region. It does not establish a separate zero-data-retention agreement.

## Choose and order credentials

Every service or member API key owns an ordered credential list for each provider. Adding a
credential requires **Manage** on the key and **Use** on the credential. Reordering or removing
existing choices requires only key **Manage**. See the [permission reference](/docs/members#permission-reference).
An empty list disables that provider for the key. New keys start with Stogas-managed Chutes assigned.

| Choice                 | Result                                                           |
| ---------------------- | ---------------------------------------------------------------- |
| **Stogas managed**     | Use our Chutes account. Do not supply a provider key.            |
| **Stored credential**  | Use the selected encrypted secret. Do not supply a provider key. |
| **Customer encrypted** | Unlock the assigned credential with its labeled encryption key.  |

Each candidate includes its own credential policy. A customer-encrypted credential is unavailable
when the request omits its matching encryption key. Credential order chooses between credentials
for the same deployment; [routing settings](/docs/policies/routing) choose between deployments.
For example, put a customer-encrypted Chutes credential before Stogas managed to prefer it when
its key is supplied.

Only an explicit `routing.maxAttempts` greater than one allows another
local credential attempt if the first usable choice cannot be prepared. There is no fallback by
default, and failures after selection, including provider errors, never switch credentials.
Encrypted plugins open after selection. Missing plugin keys or invalid plugin content reject that
request, including when another credential could have served the same deployment.

Azure accepts ordered stored credentials with discovered targets. It does not accept
customer-encrypted or Stogas-managed credentials.

### Configuration caching

Credential lists and ciphertexts are cached with the API key's policy. Changed generations reject
stale requests before dispatch and start a refresh. Every authorization checks the exact selected
assignment, ownership, status, and applicable policy revisions again. Saving a list requires the
key's current `configGeneration`; a stale save leaves the current list unchanged.

Distinct candidate policies share the [combined policy budgets](/docs/policies/editing#document-rules).
The complete snapshot also has a 96-MiB memory accounting allowance, charging shared source JSON
once at eight times its bytes and credential metadata at three times its bytes, plus object
overhead. `key_configuration_too_large` means the assigned policies or target metadata exceed
that allowance. Reduce the assignments or their content; retrying the same configuration cannot fix it.

## Rotate or revoke a credential

- **Replace a stored secret:** Open the credential, choose **Edit**, and replace its secret. We
  validate the replacement. Its ID, assignments, and analytics history stay the same.
- **Rotate a customer-encrypted credential:** Encrypt the replacement locally and replace the saved
  encrypted JSON. Its credential ID and assignments remain the same.
- **Disable a credential:** Block new requests that select it.
- **Delete a credential:** Remove its assignments first. Its old ID remains in request history.

To revoke a provider key everywhere, revoke it with the provider. Keep an old secret valid during
routine rotation while cached requests finish.
For urgent revocation, disable the credential first. Changes do not cancel requests that were
already authorized.

## Security and billing

- Policy and credential management receive ciphertext and a public key identifier. Requests supply
  the key to the gateway. Transport privacy depends on your chosen connection; see
  [sending the key](/docs/cli#send-the-key-with-a-request). A fleet restart does not lose customer-held keys.
- Customer roots and plaintext credentials are not written to databases or analytics. A request never creates a dashboard
  credential row. Only the scoped credential ID is recorded.
- Provider secrets are used in confidential gateway memory. Chutes also reuses credential-specific
  connection and ticket pools across requests. Each gateway retains at most 2,048 customer pools;
  idle pools are retired after five minutes, with bounded cache reuse. Active requests and
  streams keep their pool until they finish. The managed Chutes pool lasts for the gateway process.
- Azure access tokens are cached separately from client secrets: at most 2,048 tokens per gateway,
  retired after five minutes idle or before their actual expiry. Client-secret SDK objects are not
  retained across token loads. Every inference request still requires current authorization.
- Azure does not accept customer-encrypted credentials. Its stored Entra application secret and discovered
  bindings are used only when that exact credential is assigned to the Stogas API key.
- Stored secrets are encrypted before database storage. Dashboard responses contain only the name,
  status, and a short preview.
- BYOK requests reserve and settle 2% of the usage cost calculated from catalog rates, rounded upward to 36 USD decimal places, against the organization balance. Organization, grant, and key spend limits count the full upstream usage cost, before our fee calculation.
- The provider bills you separately. Catalog rates do not include your private discounts or capacity
  reservations and are not a statement of your provider invoice.
- Analytics shows upstream cost and our billed cost separately. Both credential kinds
  use their saved UUID in filters and exports; managed requests use `null`.

## Troubleshooting

- **BYOK credential required:** Assign a credential for this provider and supply its matching
  labeled key if it is customer-encrypted.
- **Customer-encrypted BYOK is unavailable:** Check the active organization root and the registered
  credential assigned to your Stogas key, or the provider does not support that credential mode.
- **Provider authentication or permission error:** Confirm the credential, provider permissions,
  account quota, and model deployment with the provider. For Azure, confirm management read access,
  Cognitive Services User access, and then refresh the credential.

See the [API reference](/docs/reference) for the complete header schemas.
