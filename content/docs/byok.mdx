Bring your own key (BYOK) sends requests through your provider account. Your API key still
authenticates every request to us, and the provider credential authenticates only the gateway's
call to the provider. The provider bills you, and we charge a [2% fee](#billing).

| Credential         | Where the secret is       | Providers      | Each request sends              |
| ------------------ | ------------------------- | -------------- | ------------------------------- |
| Stogas managed     | Our provider account      | Chutes         | Your API key                    |
| Stored             | Saved and encrypted by us | Every provider | Your API key                    |
| Customer encrypted | Encrypted on your device  | Every provider | Your API key and encryption key |

New keys start with Stogas-managed Chutes. Every other provider needs a credential of your own.
Each [provider page](/docs/providers) shows what its credential needs.

## Checks

We check a stored credential with a free call to the provider when you save it, and every 23 hours
after that. A rejected credential is not saved. If a check fails, requests keep using the
credential, because a provider can reject a check for a short time. We check again after an hour,
and double the wait while the checks keep failing, up to 23 hours. A check does not prove quota or
access to every model. A customer-encrypted credential is checked only when you run
[`stogas byok check`](/docs/cli#check-a-credential) with its encryption key, which the gateway uses
for that check only and never stores. An Azure credential's check also finds its account's
deployments, which become its [targets](/docs/providers/azure#targets).

A credential also lists each deployment that refused a call through it in the last 7 days with the
[result](/docs/request-records#provider-results) `authentication_error`, `permission_error` or
`model_unavailable`, such as a model that your provider account can't use. A deployment leaves the
list once a later call to it through the credential succeeds or you replace the secret.

## Customer encryption

With customer encryption, we store only ciphertext, and each request sends the key that unlocks it.

1. [Create an organization key](/docs/customer-encryption#create-a-key) and register it.
2. Encrypt the credential on your machine:

   ```console
   stogas encrypt --key providers --organization YOUR_ORGANIZATION_ID \
     --purpose byok/openai --input provider-secret.txt --output credential.json
   ```

   The purpose is `byok/` and the provider ID. Save a plain key without a trailing newline. AWS
   and Google Cloud take a credential document, and Azure takes an
   [application](/docs/providers/azure#customer-encryption), which the CLI checks before it
   encrypts them.

3. Add `credential.json` as a customer-encrypted credential. Saving does not contact the provider.
4. [Send the key](/docs/customer-encryption#send-the-key-with-a-request) with each request.

A request that could use the credential but doesn't send its key fails with
`encryption_key_required`. To let it use the key's other credentials instead, set
[`routing.missingEncryptionKeys`](/docs/policies/routing#missing-encryption-keys) to `skip`.

### Require customer encryption

An external organization can turn off **Allow stored credentials** to keep every provider secret of
its own unreadable to us. Members can then add only customer-encrypted credentials. Turning it off
needs **Organization → Manage** and works only once the organization has no stored credentials.
Personal organizations always allow them. To move an organization over:

1. Save each account again as a customer-encrypted credential.
2. Put it in place of the stored credential in each key's [list](#order-credentials).
3. Delete the stored credentials, then turn off **Allow stored credentials**.

## AWS and Google Cloud

The CLI and the dashboard API take an AWS or Google Cloud credential as a JSON document, which the
[AWS](/docs/providers/aws#customer-encryption) and
[Google Cloud](/docs/providers/google-cloud#customer-encryption) pages show.

Each of these credentials has a public target: the hostings that it serves and, for AWS, its
Region, such as `{"hosting":["anthropic","aws"],"region":"us-east-1"}`. Routing reads the target
instead of the secret. To keep a customer-encrypted credential off a hosting, remove the hosting
from its target.

## Order credentials

Each API key has an ordered credential list for each provider. [Routing](/docs/policies/routing)
chooses the deployment, and the gateway uses the first credential in the list that can serve it,
under that credential's [policy](/docs/policies/scopes). A
[fallback](/docs/policies/routing#retries-and-fallbacks) tries the deployment's next credential
before the next deployment. An empty list turns the provider off for that key.

For example, put a customer-encrypted Chutes credential before Stogas managed, and set
[`routing.missingEncryptionKeys`](/docs/policies/routing#missing-encryption-keys) to `skip`.
Requests that send its key then use your account, and the others use Stogas managed.

- Adding a credential to a key needs **Manage** on the key and **Use** on the credential. Reordering
  or removing needs only **Manage** on the key.
- Adding a credential fails when its policy
  [does not combine](/docs/policies/scopes#policies-that-do-not-combine) with the key's policies.
- Removing a member's **Use** stops new assignments, and existing assignments keep working. Disable
  the credential to stop them all.
- If a key's policies and credentials grow too large, requests fail with
  `key_configuration_too_large`.

## Allowlist the gateway's IP address

Requests to providers come from `15.204.217.217`.

- Every customer's requests come from this address.
- A planned change appears on this page 30 days before it takes effect.
- The [checks](#checks) of a stored credential come from other addresses. A provider account that
  restricts IP addresses rejects them, so the credential is not saved. Use a
  [customer-encrypted](#customer-encryption) credential, whose checks come from the gateway's
  address.

## Rotate or revoke a credential

- A replaced secret keeps the credential's ID, assignments and history.
- A disabled credential rejects new requests. Requests that already started finish.
- Requests through a key that has no credential left for a provider fail with `byok_required`.

For routine rotation, keep the old secret valid until running requests finish. To revoke a key
urgently, disable the credential, then revoke the key with the provider.

## Security

- We encrypt stored secrets before we save them. The dashboard and API never show a secret or its
  ciphertext again.
- The confidential gateway decrypts a secret only for requests from keys that the credential is
  assigned to. Our control service also decrypts stored secrets to run the [checks](#checks).
- Only the gateway can decrypt customer-encrypted secrets. Your key travels with each request and
  is never written to databases or analytics.
- Request records keep the credential ID, never the secret.
- No request field or header takes a provider secret.

## Billing

BYOK requests cost 2% of the usage at catalog rates, charged to your balance. Spending limits count
the full usage at catalog rates, not only the fee. Your provider bills you separately, and
negotiated provider prices do not change the fee. See [Billing](/docs/billing) for funding fees.
