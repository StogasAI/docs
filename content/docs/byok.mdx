Bring your own key (BYOK) sends requests through your provider account. You still authenticate
every request with your API key from the dashboard; the provider credential authenticates only the
gateway's call to the provider. The provider bills you directly, and we charge a 2% fee.

## Choose a credential type

| Type                   | Where the secret is       | Providers                        | Each request needs              |
| ---------------------- | ------------------------- | -------------------------------- | ------------------------------- |
| **Stogas managed**     | Our provider account      | Chutes                           | API key                         |
| **Stored**             | Saved and encrypted by us | OpenAI, Anthropic, Chutes, Azure | API key                         |
| **Customer encrypted** | Encrypted on your device  | OpenAI, Anthropic, Chutes        | API key and your encryption key |

New keys start with Stogas-managed Chutes. OpenAI, Anthropic and Azure need a credential of your
own.

## Store a provider credential

<Steps>
<Step>

### Add the credential

Open **BYOK**, select **Add** and choose the provider. Enter a name and the credential. For Azure, you
connect accounts that an Entra application can read; see
[Connect your Azure account](/docs/providers/azure#connect-your-account).

</Step>
<Step>

### Wait for the check

We check the credential with a free metadata call before saving it: the model list for OpenAI
and Anthropic, the account quota for Chutes and deployment discovery for Azure. A rejected
credential is not saved. If the provider is unavailable or rate-limits the check, try again. A
successful check does not prove quota or access to every model.

</Step>
<Step>

### Assign it to a key

Open a service or member API key, then select the credential under **Credentials**.

</Step>
</Steps>

The dashboard never shows a stored secret again. Replacing it keeps the credential's ID,
assignments and analytics history.

We repeat the free check for every stored credential once a day. If it fails, the BYOK list shows
when and why, and we check again an hour later. Requests keep using the credential, because a
provider can reject a check for a short time. To check at once, for example after you fix the
account, select **Check credential** in the credential's menu. Customer-encrypted credentials are
not checked, because we cannot decrypt them.

## Customer encryption

With customer encryption, we store only ciphertext, and your requests send the key that unlocks it.

<Steps>
<Step>

### Install the CLI

The `stogas` CLI encrypts the credential on your machine. Download and verify it as described in
[Install the CLI](/docs/cli#install).

</Step>
<Step>

### Create an organization key

```console
stogas encryption-key --output org.key
```

Register the printed identifier in the organization policy, as described in
[Create a key](/docs/customer-encryption#create-a-key). Keep a secure backup of `org.key`.

</Step>
<Step>

### Encrypt the credential

Save the exact credential in a file without a trailing newline, then encrypt it locally:

```console
stogas encrypt --key-file org.key --organization YOUR_ORGANIZATION_ID \
  --purpose byok/openai --input provider-secret.txt --output credential.json
```

Use `byok/openai`, `byok/anthropic` or `byok/chutes` to match the provider.

</Step>
<Step>

### Save and assign it

Open **BYOK → Add → Customer encrypted**, choose the provider and paste `credential.json`. Then
assign the credential to an API key. Saving does not contact the provider.

</Step>
<Step>

### Send the key with each request

Put the contents of `org.key` under its registered label in `encryption_keys` in the request body.
See [Send the key with a request](/docs/customer-encryption#send-the-key-with-a-request) for the
format and the safest connection.

</Step>
</Steps>

If a request leaves out the key, the gateway skips that credential when it chooses one. A wrong key or
damaged ciphertext fails the request. No header accepts a provider secret. For backups and
rotation, see [Key sharing and rotation](/docs/customer-encryption#key-sharing-and-rotation).

## Choose and order credentials

Each API key has an ordered credential list for each provider. An empty list turns the provider off
for that key. The gateway uses the first credential in the list that can serve the deployment, with
its own credential policy. [Routing settings](/docs/policies/routing) choose the deployment; the
credential order chooses between credentials for it.

For example, put a customer-encrypted Chutes credential before Stogas managed to use it whenever
the request sends its key.

When a call fails, a [fallback](/docs/policies/routing#retries-and-fallbacks) uses the deployment's
next credential before the next deployment.

Adding a credential to a key needs **Manage** on the key and **Use** on the credential. Reordering or
removing needs only **Manage** on the key. If a key's policies and credentials grow too large,
requests fail with `key_configuration_too_large`.

## Credential access

In an external organization, add a credential to a role in **Members → Roles**. **Use** lets members
assign the credential to keys they manage. The
[permission reference](/docs/members#permission-reference) lists all permissions. Creating
credentials needs organization-wide **BYOK → Manage all**.

Removing someone's **Use** stops new assignments; existing assignments keep working. Disable the
credential to stop all of them. Credential access does not give access to API keys, and credentials
are not in folders.

## Rotate or revoke a credential

- **Replace a stored secret:** open the credential, choose **Edit** and enter the new secret. We
  check it. The ID, assignments and history stay the same.
- **Rotate a customer-encrypted credential:** encrypt the new secret locally and replace the saved
  JSON. The ID and assignments stay the same.
- **Disable a credential:** new requests that would use it are rejected.
- **Delete a credential:** remove its assignments first. Request history keeps its old ID.

For routine rotation, keep the old secret valid until running requests finish. To revoke a key
urgently, disable the credential, then revoke the key with the provider. Disabling does not cancel
requests that already started.

## Security

- We encrypt stored secrets before we save them. The dashboard and API show only the name,
  status and a short preview, never the secret or ciphertext.
- For customer-encrypted credentials, we store ciphertext and a public key identifier. Your
  key travels with each request to the gateway and is never written to databases or analytics.
- The confidential gateway decrypts a secret only for requests from keys that the credential is
  assigned to. Our control service also decrypts stored secrets to run the
  [checks](#wait-for-the-check). Only the gateway can decrypt customer-encrypted secrets.
- Request records keep the credential ID, never the secret.

## Billing

BYOK requests cost 2% of the usage at catalog rates, charged to your balance. Spending limits
count the full usage at catalog rates, not only the fee. The provider bills you separately, and
your negotiated provider prices do not change the fee. [Analytics](/docs/analytics) shows the
provider cost and our charge separately. See [Billing](/docs/billing) for funding fees.

## Troubleshooting

| Problem                                     | Check                                                                                                                   |
| ------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `byok_required`                             | The key has no usable credential for this provider. Assign one, and send its key if it is customer encrypted.           |
| Customer-encrypted credential not used      | The request must send the registered key, and the credential must be assigned to the API key.                           |
| Provider authentication or permission error | Check the credential, provider permissions, quota and model access with the provider.                                   |
| Azure permission error                      | Check the [Azure roles](/docs/providers/azure#grant-roles), then open **Azure targets** and select **Refresh targets**. |
