---
title: Bring your own provider key
description: Use an encrypted stored credential or send a provider credential with each request.
---

Bring your own key (BYOK) lets Stogas route a request through your provider account. You still
authenticate every request with a Stogas API key. The provider credential only authenticates the
upstream provider request.

## Choose a credential method

| Method             | Where the provider secret is supplied | Best for                                     |
| ------------------ | ------------------------------------- | -------------------------------------------- |
| **Stored BYOK**    | Once in the Stogas dashboard          | Services that should not carry provider keys |
| **Pass-through**   | On each API request                   | Secrets that Stogas must never store         |
| **Stogas managed** | By Stogas                             | Providers where managed service is available |

Managed service is currently available for Chutes. OpenAI and Anthropic accept stored or
pass-through credentials. Azure accepts only a stored Microsoft Entra application credential.

## Store a provider credential

1. Open **BYOK keys** in the dashboard.
2. Select **Add BYOK key** and choose the provider.
3. Enter a name and the provider credential. For Azure, enter the tenant ID, application client ID,
   client secret, and the subscription IDs that Stogas may inspect.
4. Open a service or provisioning API key and select the stored credential for that provider.

Stogas sends one free, authenticated metadata request to the provider before it encrypts and saves
the credential. OpenAI and Anthropic use their model-list operation. Chutes uses an authenticated
account-quota operation because its model catalog is public. Azure uses the management and model
data APIs described below. A provider rejection blocks the save; a timeout, provider rate limit, or
provider outage asks you to try again.

The dashboard never returns the stored secret. You can replace an Azure application credential in
place, so its API-key assignments do not change. For another provider, add the replacement, update
API-key policies, and delete the old credential after it is no longer assigned.

## Send a pass-through credential

Add the provider key to an ordinary authenticated request:

```console
curl https://api.stogas.ai/v1/responses \
  -H "Authorization: Bearer $STOGAS_API_KEY" \
  -H "X-Stogas-Upstream-API-Key: $OPENAI_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"openai/gpt-5-mini","input":"Hello"}'
```

| Header                       | When it is required                                                 |
| ---------------------------- | ------------------------------------------------------------------- |
| `Authorization`              | Every request. Use `Bearer <Stogas API key>`.                       |
| `X-Stogas-Upstream-API-Key`  | Every pass-through request. Use the provider credential value.      |
| `X-Stogas-Upstream-Provider` | Every pass-through request. Use `openai`, `anthropic`, or `chutes`. |

Do not put the provider key in `Authorization`; that header always contains the Stogas API key.
The same headers work with Chat Completions and Responses.
The provider header is a routing constraint. Stogas rejects a request when its `provider` or
`rules.only` selection conflicts with the pass-through credential provider. It never retries that
credential against another provider. Pass-through credentials are not preflighted; the normal
upstream request checks them.

## Connect Azure

Create one Microsoft Entra application for the Azure accounts that one Stogas credential may use.
Grant its service principal read access to the selected subscriptions or narrower resource groups,
and grant **Cognitive Services User** on each model account that it may call. Keep each assignment at
the narrowest practical scope. Azure role changes can take several minutes to apply.

When you save the credential, Stogas reads Azure Resource Manager to find accessible model accounts,
locations, deployments, exact model versions, hosting modes, SKUs, and supported Foundry projects.
It also checks Microsoft Entra access to each trusted model endpoint. Customer deployment names,
resource IDs, endpoints, and physical resource locations remain private binding data; they do not
become public catalog nodes.

Azure Instant access is separate from a normal Azure deployment. Stogas discovers supported Instant
models through an accessible West US 3 Foundry project and binds the exact versioned model name to
that project endpoint. Use **Refresh Azure deployments** after you add, remove, or change Azure
deployments or projects.

Each Stogas API key can select one stored Azure credential. **Unassigned** means that Azure requests
fail. At request time, Stogas matches the selected catalog deployment to an exact discovered model,
version, hosting mode, and deployment type inside that credential. If several Azure resources expose
the same exact target, the request ID selects one deterministically. Stogas never searches another
credential, guesses a customer deployment name, or falls back to another provider.

The catalog represents material Azure choices such as Global Standard, US or EU Data Zone Standard,
Azure-hosted or partner-hosted inference, and Instant access. It does not duplicate every physical
Azure resource region. Pro and Priority are request controls on the same physical deployment, so
they do not require separate Azure deployments. A region filter can select only catalog deployments
whose documented data handling satisfies it; unknown regions do not satisfy a narrow filter.

## Set the API key policy

A service API key owns one policy per provider. Assigned member keys inherit each policy from their
provisioning key.

| Policy                 | Result                                                               |
| ---------------------- | -------------------------------------------------------------------- |
| **Any credential**     | Use a supplied key. Without one, use managed service when available. |
| **Managed only**       | Reject a supplied key and require Stogas managed service.            |
| **Stored credential**  | Require the selected encrypted credential.                           |
| **Any pass-through**   | Require any validly formed provider credential on the request.       |
| **Named pass-through** | Require the pass-through credential with the selected credential ID. |

Policy resolution and the billing hold happen in one database call. A selected credential that is
missing, disabled, or not valid for the provider fails closed. Stogas does not silently change to a
managed credential after an upstream provider rejects a BYOK credential.

Azure exposes only **Unassigned** and one named **Stored credential** in this policy picker. It does
not accept pass-through or Stogas-managed credential modes.

## Name a pass-through credential

For each pass-through request, the confidential gateway computes an opaque, deterministic
credential ID in memory. The ID is scoped to the organization, workspace, and provider. Request
logs contain the ID, never the provider secret.

After a successful request, select its unknown credential ID in Analytics. The BYOK page verifies
that request observation and asks for a name. This adds only the name and ID to the BYOK list; the
provider secret is not sent to the control plane. You can then restrict an API key to that exact
pass-through credential.

To store it later, open the credential actions, select **Store secret**, and explicitly upload the
provider credential. Stogas validates the upload and requires it to produce the selected ID before
it adds encrypted storage to that row. Its ID does not change, so stored and pass-through usage stays
grouped without updating old logs.

## Security and billing

- Pass-through secrets are not written to PostgreSQL or Tinybird. The gateway keeps the plaintext
  only for the authorized upstream dispatch.
- Azure does not accept pass-through secrets. Its stored Entra application secret and discovered
  bindings are used only when that exact credential is assigned to the Stogas API key.
- Stored secrets are encrypted before database storage. Dashboard responses contain only the name,
  status, and a short preview.
- BYOK requests reserve and settle 2% of the upstream request cost, rounded up to the nearest USD
  atom. API key spend limits and the organization balance use that billed amount.
- Analytics shows upstream cost and Stogas billed cost separately and can filter by credential ID.

## Troubleshooting

- **BYOK credential required:** The selected provider has no managed service, or the API key policy
  requires stored or pass-through BYOK.
- **Pass-through BYOK is not allowed:** The API key is set to managed-only or stored-only for that
  provider.
- **Provider authentication or permission error:** Confirm the credential, provider permissions,
  account quota, and model deployment with the provider. For Azure, confirm management read access,
  Cognitive Services User access, and then refresh the credential.
- **Named pass-through mismatch:** Send the exact provider credential that produced the selected ID
  in this organization and workspace.
