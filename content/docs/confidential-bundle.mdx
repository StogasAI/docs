---
title: Confidential Bundle
description: How the Stogas confidential gateway evidence bundle is structured.
---

The confidential bundle is the public evidence set for gateway nodes. Clients verify each release and node, derive a fresh local trust set, and refresh against the earlier bundle or node-freshness deadline. They accept only fresh nodes whose TLS keys, certificate hashes, report data, and quotes pass the complete verifier policy.

## Files

Control publishes two object types:

| Object           | Purpose                                                                     |
| ---------------- | --------------------------------------------------------------------------- |
| Immutable bundle | Versioned evidence file, such as `bundles/v/42/bundle.json`.                |
| Latest bundle    | Stable full bundle copy at `bundles/latest.json` for efficient CDN serving. |

Control uploads and checks the immutable object before conditionally replacing `bundles/latest.json` with the same checksummed envelope. An older publisher cannot regress the latest sequence.

## Bundle Body

Each bundle contains:

- schema, sequence, creation time, expiry time, and TTL
- the active and rollback IGVM/release slots from Control policy, including descriptive release metadata, launch measurement, IGVM SHA-256, launch policy values, Stogas signature, and GitHub in-toto evidence
- one entry per currently trusted gateway node
- AMD verifier evidence and exact chip/TCB collateral when available
- a body checksum for transport and storage integrity

The bundle has no fleet signing key. Release authorization is verified through the Stogas release signature and GitHub provenance, while every node key is bound into its AMD-signed SNP report. The checksum is not an authority: changing or omitting evidence can only remove trust because unverifiable additions are rejected.

Node entries bind:

- node ID derived from the in-guest boot identity
- chip ID and exact reported TCB policy evidence
- TLS public key hash
- accepted certificate hash slot or slots
- HPKE public key
- Ed25519 response-proof public key
- report-data values and report-data hash
- full quote and quote verification timestamp

The report-data values are the public preimage for the SEV-SNP `REPORT_DATA` hash. They include `schema`, `catalog_hash`, `tls_spki_sha256`, `active_cert_sha256`, `accepted_cert_sha256`, `hpke_public_key`, `ed25519_public_key`, and the current drand Quicknet beacon.

Vendor collateral entries expose active KDS/verifier material by type, chip scope, source URL, fetch time, SHA-256, and payload. Clients that verify raw quotes can use the bundled collateral or fetch vendor collateral independently.

The release stack has at most two slots. It is the active/rollback policy, not just a summary of the currently live nodes. Control refuses to publish a node whose quoted release measurement is outside this stack. `launch_policy.vcpu_count` describes the number of measured virtual-processor states in the IGVM; it does not prove host CPU placement. Memory size and socket/core/thread topology are infrastructure configuration and are intentionally absent from attestation evidence.

## Cert Hash Slots

Most nodes have one accepted certificate hash. During ACME renewal a node temporarily publishes two:

| Slot   | Meaning                                        |
| ------ | ---------------------------------------------- |
| Active | Certificate currently served by the gateway.   |
| Next   | Renewed certificate allowed before switchover. |

Control begins renewal 30 days before expiry. The node switches only after every still-valid bundle containing it accepts the new hash. The old hash is pruned after the replacement is active and every still-valid bundle can authenticate it. The 48-hour window is an emergency readiness cutoff, not the normal renewal start.

## Refresh Policy

Gateway quotes refresh every 10 seconds. Each quote refresh attempts a verified drand Quicknet fetch with a 4-second total budget and 2-second per-relay request deadlines. Nodes heartbeat every 30 seconds. Control checks and publishes the bundle every minute, or sooner when an operator explicitly publishes after a change.

Clients refresh against the earlier of `expires_at` and the verifier's returned node-trust deadline. Official clients choose a random 30-to-60-second bundle lead or 15-to-30-second node lead and add the 10-second shared-cache allowance. Bundle validity is at most three minutes and is shortened to the earliest included certificate or AMD-evidence deadline. Node trust ends no later than three minutes after its verified drand round, never three minutes plus the bundle lifetime; callers may tighten that policy to one minute. A verified generation remains publishable through transient heartbeat loss for up to 24 hours, but clients exclude stale node evidence locally. Control does not use guest heartbeat health as a load-balancing signal. A new node receives a traffic-admission lease only after it is fully provisioned, appears in the latest bundle, and every older unexpired bundle that excludes it has expired.
