---
title: Confidential Bundle
description: How the signed Stogas confidential gateway evidence bundle is structured.
---

The confidential bundle is the public trust set for gateway nodes. Clients poll it periodically, verify its signatures and evidence, then accept only nodes whose TLS keys, certificate hashes, report data, and quotes appear in the verified bundle.

## Files

Control publishes three object types:

| Object           | Purpose                                                                       |
| ---------------- | ----------------------------------------------------------------------------- |
| Immutable bundle | Versioned evidence file, such as `bundles/v/42/bundle.json`.                  |
| Latest bundle    | Stable full bundle copy at `bundles/latest.json` for efficient CDN serving.   |
| Latest pointer   | Signed pointer at `bundles/latest.pointer.json` to one immutable bundle hash. |

The latest bundle is copied from the immutable object after readback verification. The pointer lets clients additionally prove which immutable key and checksum the latest publication resolved to.

## Bundle Body

Each bundle contains:

- schema, sequence, creation time, expiry time, and TTL
- the active and rollback IGVM/release slots from Control policy, including launch measurement, IGVM SHA-256, launch policy values, Stogas signature, and GitHub in-toto evidence
- one entry per currently trusted gateway node
- AMD/Intel verifier evidence and active vendor collateral when available
- Control body checksum and signature

Node entries bind:

- node ID derived from the in-guest boot identity
- chip ID policy evidence
- TLS public key hash
- accepted certificate hash slot or slots
- HPKE public key
- Ed25519 response-proof public key
- report-data values and report-data hash
- full quote and quote verification timestamp

The report-data values are the public preimage for the SEV-SNP `REPORT_DATA` hash. They include `schema`, `catalog_hash`, `tls_spki_sha256`, `active_cert_sha256`, `accepted_cert_sha256`, `hpke_public_key`, `ed25519_public_key`, and the current drand Quicknet beacon.

Vendor collateral entries expose active KDS/verifier material by type, chip scope, source URL, fetch time, SHA-256, and payload. Clients that verify raw quotes can use the bundled collateral or fetch vendor collateral independently.

The release stack has at most two slots. It is the active/rollback policy, not just a summary of the currently live nodes. Control refuses to publish a node whose quoted release measurement is outside this stack.

## Cert Hash Slots

Most nodes have one accepted certificate hash. During ACME renewal a node temporarily publishes two:

| Slot   | Meaning                                        |
| ------ | ---------------------------------------------- |
| Active | Certificate currently served by the gateway.   |
| Next   | Renewed certificate allowed before switchover. |

After clients have had time to refresh the bundle, the node switches to the renewed certificate and the old hash is pruned.

## Refresh Policy

Gateway quotes refresh every 10 seconds. Each quote refresh attempts a verified drand Quicknet fetch with a 4-second total budget and 2-second per-relay request deadlines. Nodes heartbeat every 60 seconds. Control checks the bundle every 3 minutes and republishes when evidence changes, collateral changes, the refresh interval elapses, or the latest bundle approaches expiry.

Clients should poll every 5 minutes. Bundle validity is 10 minutes so routine refresh jitter does not cause avoidable outages.
