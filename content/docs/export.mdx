The `export` plugin posts one JSON record to your webhook when each request finishes. The
record has the request, the response or stream events, and every field of the
[request record](/docs/request-records). Use it to keep your own history of prompts and responses,
or to process them in another service.

<Callout type="warn">
	Export sends prompt and response content to your receiver. To send a receiver only the request
	record and metadata, set `"content": false` on its destination.
</Callout>

## Add a webhook

Add a destination to a [policy](/docs/policies/editing):

```jsonc title="policy.json"
{
	"plugins": {
		"export": {
			"destinations": [
				{
					"url": "https://receiver.contoso.com/stogas", // The full URL. No path is added.
					"headers": { "Authorization": "Bearer YOUR_RECEIVER_TOKEN" }, // Optional.
					"content": true // Optional. false leaves out request and response bodies.
				}
			]
		}
	}
}
```

<PolicyFields section="exportDestination" />

- The URL must use HTTPS and reach a public address.
- Headers go only to your webhook. To keep them private,
  [encrypt the export](/docs/customer-encryption#encrypt-plugin-settings).
- Destinations from every policy that applies to a request add together, up to eight. Destinations
  with the same URL and headers get one record. They get it if any of them would, and it has bodies
  if one of them that would get it sends bodies.
- An empty `destinations` array replaces
  [default export destinations](/docs/policies/rules#defaults), but it cannot
  remove a destination that another scope requires.
- A [request policy](/docs/policies/request-policies) can add a destination when delegation permits
  `plugins.export` or `plugins`.

## Send some of the records

```jsonc title="policy.json"
{
	"plugins": {
		"export": {
			"destinations": [
				// One record in ten.
				{ "url": "https://receiver.contoso.com/sample", "sample": 0.1 },
				// Every failure and rejection, and no other record.
				{ "url": "https://receiver.contoso.com/alerts", "sample": { "failed": 1, "rejected": 1 } },
				// Every failure, and one success in twenty.
				{ "url": "https://receiver.contoso.com/review", "sample": { "failed": 1, "success": 0.05 } }
			]
		}
	}
}
```

`sample` is the share of records that a destination gets, above 0 and at most 1. An object gives
a share for each [outcome](/docs/request-records#outcomes) that the destination gets, and the
destination gets no record of an outcome that the object leaves out.

- The gateway chooses by request ID, so destinations with the same share get the same records, and
  a higher share gets every record that a lower share gets.
- You can repeat the choice. Take the first eight hexadecimal digits of the SHA-256 of the
  `request_id` as a number and divide it by 2<sup>32</sup>. The destination gets the record when the
  result is below the share for the record's outcome.
- A request that no destination can get is not copied, so a low share also lowers the time that
  export adds to requests.
- To export only some models, providers or keys, put the destination in a
  [rule](/docs/policies/rules) or in the policy of a key or folder.

### Send bodies with some of the records

```jsonc title="policy.json"
{
	"plugins": {
		"export": {
			"destinations": [
				// Every record. Bodies with every failure and with one success in a hundred.
				{
					"url": "https://receiver.contoso.com/records",
					"content": { "failed": 1, "success": 0.01 }
				}
			]
		}
	}
}
```

`content` takes a share in the same form as `sample`. The destination gets bodies with that share
of records, chosen in the same way, and gets the other records without bodies. A record that
`sample` leaves out is not sent, whatever `content` says.

## Record format

Each record is the request record with these fields added:

```jsonc
{
	"schema_version": 1,
	"request_id": "req_...",
	// ...the other request record fields, such as usage, performance and provider_attempts.
	"request": { "model": "...", "input": "..." }, // Your request after redaction and policy changes.
	"response": { "id": "resp_...", "output": [ ... ] }, // A buffered request.
	"events": [ ... ], // A stream. Replaces "response".
	"stogas": { ... } // Usage, routing, gateway and provider details, and the receipt if requested.
}
```

| Field      | Content                                                                                                                                                |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `request`  | The request after redaction and other changes, without policies, encryption keys or removed fields. `null` if the request was rejected.                |
| `response` | The response of a buffered request, or the error that ended it.                                                                                        |
| `events`   | Each JSON event of a stream, in order, including the error that ended it. Comments, keepalives and `[DONE]` are left out.                              |
| `stogas`   | The object that [`Stogas-Metadata: v2`](/docs/receipts) returns, without its `salts`. Every record has it, whether or not the request sent the header. |

- A record without bodies has no `request`, `response` or `events`.

- Records don't carry file contents. Each inline file in the request, such as a base64 image,
  audio clip or PDF, is replaced by an object with its declared `media_type`, and the `size` in bytes
  and hex `sha256` of the decoded file. Use the hash to match a file that you keep. File URLs and
  file IDs stay as sent.

  ```json
  {
  	"media_type": "image/png",
  	"size": 48213,
  	"sha256": "9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08"
  }
  ```

- Requests that fail before the gateway selects a deployment have no record.
- A rejected request costs nothing, so its record has `"request": null` and the error in
  `response`. Repeated rejections are exported as their
  [request records](/docs/request-records#grouped-rejections) are kept: the first five in a group
  each at once, and the rest in one record with their `request_count` when the minute ends. That
  record has the `response` and `stogas` object of the first rejection that it counts, and goes to
  that rejection's destinations.
- If the client disconnects, the provider still finishes, and the record has the whole output and
  final usage.[^chutes]
- The record never contains API keys, provider credentials or webhook headers. Your prompt text is
  only [redacted](/docs/pii-redaction) if a policy turns redaction on.
- A record has no salts, so it cannot prove a request or response, and its request is the one after
  redaction and policy changes. To [check a receipt](/docs/receipts#check-a-receipt-later), keep
  the request, the response and the `stogas` object that the client received.

## Delivery

Each record is a `POST` with `Content-Type: application/json` and an `Idempotency-Key` header equal
to its `request_id`. Any `2xx` response acknowledges it. The gateway ignores the response body and does
not follow redirects. Each destination receives records on its own, so a slow receiver does not
delay the others.

| Rule        | Behavior                                                                                         |
| ----------- | ------------------------------------------------------------------------------------------------ |
| Retry       | One retry after a connection failure or `429`, `502`, `503` or `504`. Other responses are final. |
| Retry delay | `Retry-After` if present. Otherwise about five seconds, randomized.                              |
| Time limits | Ten seconds each to connect, finish TLS, and receive response headers after the upload.          |
| Lifetime    | One minute from capture, including the retry. A longer `Retry-After` ends delivery.              |
| Shutdown    | A gateway that shuts down has five seconds to finish deliveries in progress.                     |

A retry can send a record that your receiver already accepted, so ignore duplicate
`Idempotency-Key` values. The gateway does not store records for later delivery. If the gateway needs
memory for requests, it drops the oldest records that wait for delivery. It never cuts a record
short, and an export never makes a request fail.

## Insert records into ClickHouse

```jsonc title="policy.json"
{
	"plugins": {
		"export": {
			"destinations": [
				{
					"url": "https://YOUR_HOST:8443/?query=INSERT%20INTO%20stogas_records%20FORMAT%20JSONEachRow&date_time_input_format=best_effort&async_insert=1",
					"headers": { "X-ClickHouse-User": "YOUR_USER", "X-ClickHouse-Key": "YOUR_PASSWORD" }
				}
			]
		}
	}
}
```

```sql
CREATE TABLE stogas_records (
	request_id String,
	created_at DateTime64(3),
	usage JSON,
	request JSON,
	response JSON,
	events Array(JSON)
) ENGINE = ReplacingMergeTree ORDER BY request_id
```

The HTTP interface of ClickHouse reads each record as one row, so the webhook needs no receiver in
between. Add a column for each field that you keep. ClickHouse ignores the other fields.
`ReplacingMergeTree` removes the second row that a retry can insert.

## Find missing records

To find records that did not arrive, compare the `request_id` values that your receiver accepted
with the [request records](/docs/request-records) of the requests that your export policies cover.
The record of each request that ran has a `plugins.export` entry when a destination's
[sample](#send-some-of-the-records) includes it, even when the gateway dropped its export. Its
`duration_us` is the time that export added to the request, mostly to describe attached files.
Rejections have no plugin entries. Each of their records is exported to the destinations whose
sample includes it, including the [grouped](/docs/request-records#grouped-rejections) record of
repeated ones.

[^chutes]:
    On [Chutes](/docs/providers/chutes#when-the-client-stops-early) TEE deployments, the gateway
    stops a stream that no client receives, and the record has the output and usage up to the stop.
