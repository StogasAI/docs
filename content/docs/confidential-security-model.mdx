---
title: Security and trust model
description: The guarantees and limits of our confidential gateway connections.
---

Our gateways run the complete request path inside AMD SEV-SNP confidential virtual machines.
The hardware protects guest memory from the host. The host can still stop, delay or observe traffic
patterns; attestation does not prevent denial of service or eliminate hardware vulnerabilities.

A gateway's configured region is an operator declaration delivered during encrypted startup.
Regions use country codes, with state codes for US locations, such as `FR` or `US-VA`.
AMD attestation identifies hardware and its security state; it does not prove geographical location.

## Verification chain

The SDK starts with compiled Stogas, Sigstore and hardware-vendor authorities. Downloaded evidence
cannot replace those roots.

1. Our root authorizes an online signing key. Separate keys and build profiles keep staging
   from authorizing production.
2. The online key signs a complete approval manifest selecting gateway releases, catalogs and the
   hardware policy. It cannot authorize itself or another signing key.
3. Build evidence links approved artifacts to their public source and workflow. GitHub attests both
   the IGVM and manifest. Our countersignature records approval of the same manifest.
4. AMD evidence authenticates the guest measurement, hardware identity, security state and bound
   keys. Vendor certificate chains and signed revocation lists are checked locally.
5. Fresh session attestation binds the client's challenge to the protected connection. The session
   also commits to the gateway's logged boot evidence.

Our release signatures use the `stogas signed document v1` purpose label and canonical manifest
contents. A release identity hashes its unsigned manifest, so key rotation does not turn unchanged
software into a different release. Online-key changes require a root-signed key manifest.
The root-signed authorization expires after 30 days and is renewed before expiry. A newer verified
manifest can retire a key sooner; a publisher hiding that update can replay the older authorization
only until its signed deadline. Renewal does not change gateway identities or invalidate historical receipts.

Signatures prove authorization and provenance. They do not prove that an independent rebuild took
place or that approved source has no vulnerabilities.

## Native attested TLS

The native SDK verifies fresh hardware evidence carried in the TLS certificate and checks the TLS
handshake signature. No credentials or inference content leave the client before that succeeds.
The profile requires TLS 1.3 with X25519MLKEM768 and an ML-DSA-65 handshake signature.
Unsupported peers fail closed.

Fresh ephemeral session keys provide forward secrecy. A byte-for-byte relay can carry the encrypted
connection without reading it. The measured gateway constructs attestations from its own connection
state; it does not expose an endpoint that attests arbitrary caller-provided values.

## E2EE over HTTPS

Browser APIs do not let browser JavaScript inspect the certificate used by `fetch`. Our Fetch SDK
therefore verifies a fresh application handshake and encrypts directly to the selected gateway.
Native applications can select the same E2EE mode.

The hybrid X-Wing setup establishes reusable session secrets. Directional keys and record counters
protect binary request and response records, including API keys, provider credentials, status,
headers and streaming content. The gateway alone owns those session secrets. Replays, duplicate
starts, modified records, missing terminal records and trailing bytes fail verification.

The L7 load balancer sees the outer connection and an opaque owner identifier. It cannot decrypt
inner credentials or prompts. Connection loss may require a new session; it does not justify
repeating an inference that may already have executed.

## Quantum protection

Native attested TLS requires hybrid TLS 1.3 support. E2EE supplies its own inner hybrid key exchange,
independent of whether outer HTTPS uses TLS 1.2 or TLS 1.3. Both combine classical and post-quantum
key establishment. Classical-only HTTPS remains vulnerable to future decryption of recorded traffic
by a sufficiently capable quantum adversary.

Stogas root authorizations, approvals, hardware policies, release countersignatures and receipts use
ML-DSA-65. Rekor records a SHA-512 commitment to each logged signed document using a classical
submission key; that key cannot authorize a Stogas document. AMD attestation, GitHub build proofs,
Rekor's own signatures and ordinary HTTPS certificates retain their external cryptographic assumptions.
The complete verification chain therefore cannot be described as quantum-safe.

## Evidence and availability

The current bundle contains signed decisions and supporting evidence, rather than a changing list
of live nodes. The SDK prefers our R2 origin and can recover from our independent AWS replica.
It verifies locally and reuses unchanged objects. A validly signed revocation constrains affected
nodes even if another part of the update cannot be installed.

Our gateways check approved releases regularly and stop accepting requests if their release is
withdrawn. The SDK refreshes evidence when needed, without background polling. Fleet updates allow
active requests to finish and establish fresh connections for new work. Temporary failed downloads
do not erase usable evidence; expired required evidence cannot authorize new work.

Revocation freshness is bounded by AMD's signed CRL validity. A publisher can withhold a newer CRL
until the older one expires. Once a client learns an authentic revocation, a lagging replica cannot
restore the revoked identity.

## Receipts and provider boundaries

The same signed response receipt is available through `Stogas-Metadata: v1` in either confidential
mode. One signature covers the exact request and response hashes and the canonical `stogas`
metadata, excluding the receipt itself. This includes usage, routing and any provider-specific fields. A receipt does not prove that a client-verified confidential connection was used.

Ordinary HTTPS relies on our routing and TLS endpoint. After-the-fact receipts and public boot
history do not add the connection confidentiality supplied by attested TLS or E2EE.

The gateway enforces each provider's supported verification and encryption. A gateway receipt does
not prove an upstream model ran in a TEE. Provider evidence varies; we return only useful information
that the selected provider actually supplies.
