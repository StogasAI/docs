---
title: Security and trust model
description: The detailed guarantees and limits of Stogas gateway verification.
---

Stogas runs each API gateway inside an AMD SEV-SNP confidential virtual machine. The surrounding
host can stop or delay the gateway, but the hardware is designed to prevent it from reading the
gateway's memory, private keys, provider credentials, or plaintext requests.

## The verification chain

1. **Release provenance:** GitHub Actions and Stogas independently authorize the same public source, IGVM hash, launch policy, and SNP measurement.
2. **Hardware attestation:** AMD-signed SNP evidence proves an approved measurement booted on genuine hardware at an accepted security version.
3. **Workload binding:** SNP report data binds the TLS key, public certificate hashes, and application keys to that measured guest. The quote-bound signing key signs the active catalog in every heartbeat and the catalog used in every response receipt.
4. **Freshness:** every trusted node's signed drand round is at most two minutes older than the locally accepted bundle creation time. The verifier clock separately rejects delayed, future-dated, or expired bundles.

No root of trust is accepted from the downloaded bundle. The verifier ships the AMD, Sigstore, drand, and Stogas release roots it trusts.
Because the freshness checks use the local wall clock, follow the
[client clock guidance](/docs/verification#keep-the-client-clock-accurate) for servers,
containers, browsers, and managed runtimes.

## Request path

Verification and evidence publication happen outside the inference request path. Once a bundle is active, requests use the normal OpenAI-compatible endpoints. This avoids a live dependency on GitHub, Sigstore, Rekor, AMD KDS, drand, or the evidence service for each model request.

The managed native SDK transport additionally checks that the upstream TLS connection presents a certificate hash and public key belonging to the same verified node.

If that exact pin check fails, the native transport immediately verifies the latest bundle and
retries once only when the accepted bundle changes. The failed TLS handshake sends no inference
request bytes. Network, WebPKI, and other TLS failures are not retried automatically.

Browser and optional native E2EE encrypt the complete inner inference request once under a random content key, then wrap that key independently to every node in the verified bundle. The request E2EE media type selects this mode before the gateway reads the body. Outer credentials have no authority in E2EE mode. Random L4 routing therefore requires no session affinity or plaintext-aware intermediary. The selected guest decrypts inside confidential memory and encrypts response metadata, body or SSE records, errors, and an authenticated terminal record.

The outer request exposes only the normal destination, inference endpoint, E2EE protocol version, random request ID, bundle hash, short acceptance deadline, recipient key wraps, ciphertext length, and network timing. One ciphertext contains the API key, complete OpenAI request body, relevant content negotiation, optional provider credential, and receipt preference. The encrypted response contains its status, safe response headers, body or SSE records, and terminal state. This keeps routing, freshness checks, and recipient selection outside the ciphertext while keeping credentials and inference semantics inside it.

The E2EE wire is version 1. Encrypted responses start with
`STGE || 0x01 || nonce[12]`. The nonce is public random data, not a secret. It is the base AES-GCM
nonce; each implicit record sequence is XORed into its final eight bytes and bound with the request
transcript in authenticated data. Each record contains only a four-byte ciphertext length and the
ciphertext. Record 0 contains metadata, later non-empty records contain body bytes, and the first
authenticated empty record terminates the response. The client rejects truncation. Later outer bytes
are ignored because they cannot change the authenticated response. The random nonce prevents reuse if
the same encrypted request can produce responses on more than one verified node.

The same signed response receipt, `stogas.response-proof.v1`, travels inside the encrypted response when `Stogas-Receipt: v1` is selected. E2EE does not introduce a second proof format. The receipt binds the request ID, canonical creation time, node ID, hashes of the exact plaintext request and response bytes, catalog digest and ordered selection IDs, settled pricing, timing, and the E2EE transcript when present. Active-bundle verification requires the exact node and catalog to be in the accepted bundle. AEAD protects the live exchange; the node signature remains the durable receipt. Encrypted request IDs are claimed once before provider execution to reject replay.

## Release authorization

The production Stogas release public key is:

```text
MCowBQYDK2VwAyEAByVn3LvWVbf3YkokMZPvir70vcDu0nNflgXoM0Y8aQU=
```

Gateway and catalog releases use one evidence format:

- `schema`: `stogas.release-evidence.v1`, identifying the envelope format;
- `manifest`: the release identity, artifact hashes, and applicable policy;
- `signature`: the Stogas approval, containing `key_id` and an Ed25519 `signature`;
- `attested_builds`: the build provenance, currently one GitHub Actions Sigstore bundle.

Stogas signs `stogas signed document v1\n` followed by compact, recursively key-sorted manifest JSON without a trailing newline. The manifest's signed `schema` is `stogas.gateway.release.v1` or `stogas.catalog.release.v1`. Manifest files add one newline, which is included in their GitHub-attested hash. The outer schema versions the evidence packaging; the signed manifest schema authenticates the independently published release document's type and format. Unsupported envelope versions are rejected.

The fleet entrypoint, `bundles/latest.json`, uses the outer schema `stogas.confidential-bundle-envelope.v1` with `body` and `body_sha256`. Its body retains `stogas.confidential-bundle.v1`. The checksum identifies the body bytes; trust comes from the individual proofs inside them.

The gateway build measures the completed IGVM with `igvmmeasure --check-kvm gateway.igvm measure`, then records its launch measurement and SHA-256 hash in the manifest. GitHub attests both the IGVM and manifest. The launch policies are embedded in that manifest and need no separate signature or attestation. The offline verifier compares each SNP report with the authenticated manifest measurement and the policy for its exact chip ID.

For catalogs, GitHub attests the manifest and both runtime and public artifact hashes. Stogas rebuilds the tagged source and signs the same manifest after matching the results. Its signature proves approval; the current evidence does not prove that Stogas independently rebuilt either release. The verifier checks the pinned GitHub source and workflow identities as well as both signatures.

The global hardware document remains separate. Stogas signs it as Ed25519 DSSE and publishes that signed envelope to public Rekor v1. The bundle carries the complete inclusion proof for offline verification. This records an operator policy decision, which has no build to attest. Hardware and launch policies do not refer to each other. GitHub's build-log entry records GitHub's attestation, not the later Stogas approval signature.

Production verification rejects the separate staging signing key and staging build placeholders. Staging verification also accepts production releases. A staging placeholder binds the same artifact and manifest hashes and still requires a valid Stogas signature.

## Availability

A verified bundle can contain older records kept for recovery. The verifier reports them separately and never adds them to the trusted set.

A valid bundle can therefore have an empty trusted set. Managed transports treat it as an explicit
unavailable-fleet state: they stop protected requests and poll both evidence origins every four to
eight seconds. When a non-empty bundle is active, both official origins must return verified empty
candidates before they can replace it. The transport does not retain the older trust set after that
replacement.

When no previously routable gateway still has fresh evidence, a verified replacement can restore
server capacity before the next bundle is published. The first recovery bundle fixes that initial
cohort. Later gateways still wait until every unexpired client trust set can authenticate them.
Clients do not trust the replacement early: they must verify the recovery bundle before connecting.

Bundles are delivered through independent Cloudflare/R2 and AWS CloudFront/S3 origins. Managed
clients select an origin randomly and fail over to the other when delivery or verification fails.
Both origins carry the same public evidence; neither origin can create trust because every bundle
is checked locally against roots shipped with the verifier.

The verifier fails closed after bundle expiry. Confidential verification can authenticate a reachable gateway, but it cannot prevent a network, host, or service outage.

## What is not proven

Confidential verification does not:

- prove that reviewed code has no vulnerabilities;
- hide traffic timing or destination metadata;
- hide ciphertext length;
- make an upstream AI provider confidential unless that provider offers its own verified confidential execution;
- prevent the host or operator from stopping service;
- let browser JavaScript inspect the certificate used by `fetch`;
- protect API keys from malicious same-origin browser script.

The v1 E2EE recipient profile uses HPKE with the hybrid MLKEM768-X25519 (X-Wing) KEM, HKDF-SHA-256, and AES-256-GCM. The same suite protects Control-to-guest secret release. Stogas does not claim complete post-quantum security: AMD SNP, drand, WebPKI, Sigstore, and existing signing keys still depend on classical cryptography.

The public gateway listener uses TLS 1.3 and offers hybrid ML-KEM key exchange first while retaining classical fallback for standard clients. Managed native transports require X25519MLKEM768 with no classical fallback. E2EE protects application payloads when a browser or other standard client negotiates classical TLS. These controls do not make the complete attestation trust chain post-quantum.

The recipient key exists only in one guest generation and is destroyed when that guest stops. Because v1 uses a non-interactive static HPKE recipient key, compromise of that key while the generation is alive could expose requests recorded for that generation; v1 does not claim interactive forward secrecy.
