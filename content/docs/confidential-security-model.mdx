---
title: Confidential Security Model
description: How Stogas uses confidential compute to reduce trust in the host, operator, and edge infrastructure.
---

The confidential gateway assumes the host is untrusted. The host may schedule the VM, drop packets, delay packets, or stop the VM. It must not learn plaintext customer requests, provider credentials, or in-guest private keys.

## Trust Boundary

Inside the measured guest:

- TLS private key
- HPKE private key
- Ed25519 response-proof key
- Control-released provider/runtime secrets
- request and response plaintext

Outside the measured guest:

- host kernel and hypervisor
- object storage
- CDN cache
- network load balancing
- Control Worker storage and publication path

External systems distribute evidence. Clients verify that evidence before trusting a node.

## Control Plane Exposure

Gateway-node Control endpoints are private operational surfaces. In staging and production they are placed behind Cloudflare Access service auth and a strict source policy before Control performs quote verification. Admin endpoints use separate Access credentials.

The public client surface is the signed bundle in R2/CDN and the gateway API itself. Heartbeat, CSR, and admin routes are not customer APIs; traffic readiness is exposed only on the guest-private listener.

## Why It Is Stronger

Traditional API gateways terminate TLS on infrastructure controlled by the operator or cloud provider. Stogas terminates customer TLS inside a measured guest whose keys are generated after boot and bound into SEV-SNP report data.

This gives clients independent checks for:

- which public source release built the guest
- which IGVM hash launched
- which TLS certificate hash is acceptable
- which response-proof signing key processed the request
- whether the node quote was recent enough

The operator can remove a node or publish new evidence, but cannot silently substitute an unmeasured node that passes client verification.

## Availability Model

The bundle and quote windows are chosen for high availability with at least two guest VMs:

- quote refresh is background and non-blocking
- transient drand or Control issues keep serving the last valid quote while it remains inside policy
- Control omits stale nodes from newly published bundles before clients would fail freshness checks
- old immutable bundles remain available while clients refresh
- guest-private readiness fails closed when the Control admission lease expires

## Performance Model

The confidential checks are kept off the request hot path:

- gateway quotes refresh in the background and are served from memory
- clients fetch one CDN-cached bundle instead of asking each node for fresh attestation
- expensive release provenance verification can be cached by IGVM hash
- response proofs are a small Ed25519 signature plus the current quote/report-data values
- gateway request routing remains the normal OpenAI-compatible API path after the node is trusted

The result is a conventional low-latency gateway request path with extra evidence attached, rather than a per-request remote-attestation handshake.

## Remaining Assumptions

Confidential compute does not hide traffic metadata, guarantee upstream provider privacy, prevent denial of service, or prove real hardware in local/native development. Real SEV-SNP staging is required to validate chip IDs, AMD collateral, launch measurements, and guest report device behavior.
