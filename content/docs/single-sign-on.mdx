An external organization can connect one identity provider, such as Okta, Microsoft Entra ID or
Google Workspace, through OpenID Connect or SAML 2.0. Members can then sign in through it, the
organization can require that, and people at its verified domains can join. Set it up in
**Settings → Single sign-on**, which needs **Organization → Manage**.

## Register Stogas with your provider

### OpenID Connect

Create a web application that uses the authorization code flow, with the redirect URI
`https://app.stogas.ai/auth/sso/callback`. Sign-in asks for the `openid`, `email` and `profile`
scopes, or only the first two when the provider's discovery document lists its scopes without
`profile`.

The issuer's OpenID Connect discovery document must name exactly that issuer. A multi-tenant
endpoint, such as Microsoft's `common`, lets any tenant sign in, so it is refused. For Microsoft
Entra ID, use `https://login.microsoftonline.com/<tenant-id>/v2.0` and add the `xms_edov` optional
claim to the ID token, because Entra ID doesn't send `email_verified`.

### SAML

| Your provider asks for                   | Give it                                                               |
| ---------------------------------------- | --------------------------------------------------------------------- |
| ACS URL, reply URL or single sign-on URL | `https://app.stogas.ai/api/auth/sso/saml/<organization-id>/acs`       |
| Entity ID, audience or identifier        | `https://app.stogas.ai/api/auth/sso/saml/<organization-id>/metadata`  |
| Name ID                                  | A persistent identifier, or the email address                         |
| Attributes                               | `email`, and `displayName` or `firstName` and `lastName`              |
| Signing or encryption certificate        | The certificate in the metadata, which Settings also offers as a file |

Each organization has its own entity ID, so several organizations can use one Microsoft Entra ID
tenant. The entity ID is also the address of the service provider metadata. In Stogas, enter the
provider's issuer, its sign-in URL and its signing certificate as PEM or base64.

Each organization also has its own certificate. Stogas signs every sign-in request with its key, and
your provider can encrypt assertions to it. A provider that reads the metadata has the certificate.
Upload the file where your provider asks for a signature verification or encryption certificate. The
certificate is valid for 10 years and stays the same when you change the provider's settings.

| Rule                  | Value                                                                                               |
| --------------------- | --------------------------------------------------------------------------------------------------- |
| Signature             | The response or the assertion, with RSA-SHA256 or RSA-SHA512. SHA-1 is refused.                     |
| Start of sign-in      | At Stogas, or from your provider's list of apps after one more click at Stogas                      |
| Name ID               | Any format except transient, which changes at every sign-in.                                        |
| Email                 | The `email` or `mail` attribute, otherwise a Name ID that is an address and is not persistent       |
| Provider certificates | 2 at most. To renew, add the new certificate below the current one.                                 |
| Response size         | 128 KiB                                                                                             |
| Sign-in requests      | Signed with RSA-SHA256. A provider that checks the signature needs your organization's certificate. |
| Encrypted assertions  | AES-GCM or AES-CBC, with the key under RSA-OAEP. RSA 1.5 is refused.                                |
| RSA-OAEP hashes       | The same hash for the digest method and the mask generation function, such as SHA-256 for both      |
| Not supported         | Encrypted Name IDs, single logout                                                                   |

Stogas also reads the attribute names that Microsoft Entra ID sends by default.

## Require single sign-on

Once a test sign-in succeeds, you can require single sign-on. Each member then signs in through
your provider to open the organization, and a sign-in counts for 24 hours unless you choose another
length from 15 minutes to 30 days. A new length also applies to current sign-ins, and signing out
all members ends every sign-in at once. Saving another issuer, client ID or protocol turns the
requirement off until the next test.

Members whose role has **Organization → Skip single sign-on** need no sign-in, for example
contractors who have no account at your provider. **Organization → Manage** includes it, so a
broken connection can't lock everyone out. API keys don't use single sign-on.

## Choose who can join

| SCIM          | Who can join                                                            |
| ------------- | ----------------------------------------------------------------------- |
| Not connected | Anyone with an invitation link, and people at your verified domains     |
| Connected     | Anyone with an invitation link, and active users that the provider sent |

Each person who joins through your provider takes one of the **Seats for single sign-on**, from 0
to 1,000, and nobody joins that way at 0. These seats count as [used seats](/docs/members#invitations)
while you hold them. Changing them needs **Members → Manage**. Holding more also needs free seats, a
verified domain, a test sign-in that succeeded and the permissions to assign the default role.

While single sign-on is required, a person joins with an invitation link through your provider,
unless the invitation gives a role that lets them skip single sign-on. Such a join takes the
invitation's use instead of a seat for single sign-on, and needs no verified domain. While SCIM is
connected, the provider must have sent the person as an active user.

## Access tokens

While single sign-on is required, an access token can act in the organization only if you created
it, or approved its `stogas login`, after signing in through the provider. The token keeps working
when that sign-in's length ends, until a manager signs out all members or saves another issuer, or
you leave the organization. Other tokens get `403 SSO_REQUIRED`, and tokens of members who can
skip single sign-on need no sign-in. To refuse every access token, turn off **Allow access
tokens**.

A manager's access token can manage every single sign-on setting through the
[Dashboard API](/docs/reference/dashboard), including the identity provider. A new issuer, client
ID or protocol still waits for a test sign-in in the dashboard.

## Provisioning

```http
POST /api/scim/v2/<organization-id>/Users HTTP/1.1
Host: app.stogas.ai
Authorization: Bearer scim_stogas_v1_...
Content-Type: application/scim+json

{
  "schemas": ["urn:ietf:params:scim:schemas:core:2.0:User"],
  "userName": "ada@example.com",
  "name": { "givenName": "Ada", "familyName": "Lovelace" },
  "emails": [{ "value": "ada@example.com", "primary": true }],
  "active": true
}
```

Your identity provider can send the people that it assigns to Stogas through SCIM 2.0. Connect
SCIM in the Single sign-on settings, which show the secret once.

| Your provider asks for       | Give it                                               |
| ---------------------------- | ----------------------------------------------------- |
| Base URL or tenant URL       | `https://app.stogas.ai/api/scim/v2/<organization-id>` |
| Bearer token or secret token | The SCIM secret                                       |
| Token endpoint               | The base URL followed by `/token`                     |
| Client ID                    | The organization ID                                   |
| Client secret                | The SCIM secret                                       |

The last three rows are for a provider that uses the OAuth 2.0 client credentials grant, whose
tokens last 1 hour. Use `userName` as the unique identifier. Replacing the secret ends the old
secret and its tokens at once.

While SCIM is connected:

- A person joins through your provider only when it sent an active user whose `userName` or
  primary email is the address that the person signs in with.
- When the provider deactivates or deletes a user, the member who signs in as that person is
  removed, as when an admin [removes a member](/docs/members#remove-access). [Activity](/docs/activity) names
  **Identity provider** as the actor. The last member who can manage roles stays.
- A user that the provider activates again is not a member. The person joins again and takes a
  seat for single sign-on.
- A provisioned user takes no seat until the person joins.
- A member links to their user by email once. A later change of address at the provider keeps the
  link.

Disconnecting SCIM keeps every member, and saving another issuer disconnects SCIM.

### SCIM limits

| Limit           | Value                                                                                                     |
| --------------- | --------------------------------------------------------------------------------------------------------- |
| Resources       | Users. `GET /Groups` returns an empty list, and group changes return `501`.                               |
| Attributes kept | `userName`, `externalId`, `name.givenName`, `name.familyName`, `displayName`, the primary email, `active` |
| Filters         | `userName eq`, `externalId eq`, `emails.value eq`                                                         |
| Changes         | `POST`, `PUT`, `PATCH` with `add`, `replace` and `remove`, `DELETE`                                       |
| Users           | 50,000 for each organization                                                                              |
| Page size       | 100 by default, 200 at most                                                                               |
| Request body    | 64 KiB                                                                                                    |
| Not supported   | Bulk requests, sorting, ETags, password changes                                                           |

Stogas accepts every other attribute and leaves it out. Assign [roles](/docs/members#roles) in Stogas.

## Domains

People join with the email address that your provider sends, which must be at a verified domain.
They can't join with an address that the provider marks unverified in its `email_verified` or
`xms_edov` claim.

A domain stays verified, so you can remove its TXT record once it is. When another organization
verifies the same domain with its own record, the domain moves to that organization. After you
remove a verified domain, people can no longer sign in with a work email at it or join with one.

## Accounts

| You signed in with                                     | You can open           |
| ------------------------------------------------------ | ---------------------- |
| Your provider                                          | That organization only |
| Your provider, then your passkey or authenticator code | Your whole account     |
| Your password                                          | Your whole account     |

Single sign-on is another way to sign in to a Stogas account, and every account has a password,
including an account created through single sign-on, which shows it once. Keep that password. Your
provider vouches for you in its own organization only, so your personal organization, your other
organizations and your account settings return `428 PASSWORD_REQUIRED` until you enter it. After
you leave the organization, or after it disconnects the provider, the password is the only way to
sign in.

Signed in through your provider alone, `stogas login` creates a token for that organization only,
and replacing or deleting the identity provider asks for your password first.

A sensitive change, such as creating an API key, asks you to confirm it's you unless you proved it
in the last 10 minutes. An account without a passkey or authenticator app confirms with its
password. For a change in the organization, a sign-in at its provider also counts, from the time
that the provider says it signed you in, which it states in the `auth_time` claim or the SAML
`AuthnInstant`. A provider that only continues a session it already had proves nothing new, so
Stogas asks it to sign you in again. Some providers send `auth_time` only when you add it as an
optional claim of the ID token. The members of a provider that sends no sign-in time, or that
doesn't sign people in again on request, confirm with the password.

An account links to its person by the provider's subject identifier, or by the Name ID with SAML,
never the email, which some providers let people change. A provider that gives each client its own
identifiers sends new ones after you save another client ID, so each member links their account
again at their next sign-in. Saving another issuer or protocol unlinks every member.

A person who joins takes their name from the provider's `name` claim or SAML name attributes, or
their email when the provider sends no name, and can change it later. The members list shows the
email that the provider sent at each member's latest sign-in, and `email:` finds members by it.

A member's [picture](/docs/members#pictures) comes from the provider's `picture` claim when it
names a JPEG or WebP image over HTTPS. The members of a provider that sends none, as with SAML,
upload their own.

Stogas stores the issuer, the client ID and encrypted client secret or the SAML sign-in URL and
certificate, and each linked member's subject identifier, email, last sign-in and any picture taken
from the provider. With SCIM, it also stores a hash of the SCIM secret and each provisioned user's
kept attributes.
[Activity](/docs/activity) records each change to single sign-on and each member who joins or links
through it, never the secret.
