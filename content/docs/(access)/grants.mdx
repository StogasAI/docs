---
title: Grants
description: Give members their own API keys under shared access rules and individual key allowances.
---

A grant lets selected members create their own API keys. It has no secret and cannot call
inference itself. Each member key carries its owner's identity into request history.
Use a [service key](/docs/api-keys#service-keys) for an application that should run independently
of a member.

## Create and assign a grant

Open **Grants** in the dashboard and create a grant. It controls:

- which members may use it;
- how many keys each assigned member may create;
- whether it is enabled; and
- whether saved key policies may be edited.

Members need Use on the grant, its folder, or all organization resources. An assigned member creates keys only when they need them, up to that
grant's per-member allowance. The same grant may be assigned to many members, and each member has an
independent allowance.

Lowering an allowance does not delete existing keys. It stops the member from creating another key
until their key count is below the new allowance.

A grant administrator can assign member or role permissions. Members gain access when they receive a
linked role. Direct assignments remain independent of role changes. A role with no organization permissions can
group members; its grant Use is sufficient to create their own keys.

When a member loses their last source of grant Use, their keys under that grant are deleted.
Another direct, role, folder, or organization grant of Use preserves those keys. Restoring access does not
restore deleted keys. Role removal and deletion dialogs warn about this consequence.

Select grant icons to enable, disable, or delete several grants at once. The header selects all grants
matching the current filter. Deletion confirms the number of attached keys that will also be deleted.

Disabling a grant immediately rejects new requests from all keys under it without deleting the keys.
Removing a member's last source of Use on a grant deletes that member's keys under the grant. Deleting the grant deletes
all keys under it. The dashboard asks for confirmation before either destructive change.

## Policies and shared limits

Organization, folder, grant, the owning member, all of that member's roles, the key and the selected
provider credential can constrain a member-key request. A grant's shared limits count
requests across its keys; each key can also have its own limits. See
[Scopes and inheritance](/docs/policies/scopes) for composition and
[Limits](/docs/policies/limits) for spending, rates and token allowances.

## Access permissions

**View** covers grant settings, its member-key settings and usage. **Use** adds permission to create
personal keys, within the per-member allowance. **Manage** adds configuration and lifecycle actions.
Use and Manage are independent and each includes View. **Admin** includes both and permits assigning
access. See [API-key permissions](/docs/api-keys#service-keys).

Folder permissions apply to grants in that folder. Organization-wide API permissions apply across
the organization. Managers still obey parent policies. Moving a grant requires Admin on both
containing folders. Grants and shared access are available only in external organizations.

## Follow an individual request

Open **API keys** and filter by grant or member. Each member key can be rotated or disabled
independently. In **Analytics**, filter by `grant:` or `member:` to follow the corresponding usage.
See [Member keys](/docs/api-keys#member-keys) for key lifecycle and
[Members and roles](/docs/members) for organization membership.
