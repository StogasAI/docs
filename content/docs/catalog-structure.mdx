The catalog is the public routing data used by the gateway. It answers four questions before a request is sent upstream:

- Which public model slug did the caller request?
- Which provider and upstream endpoint can serve it?
- Which request fields are allowed for that model and endpoint?
- Which pricing meters apply?

The catalog is data, not executable code. It declares facts and attaches named policy profiles. The Go gateway owns the runtime semantics for those profiles.

## The Graph

A flat model list hides where facts come from. The catalog keeps those facts in a graph:

```text
API endpoint -> Provider -> Provider endpoint -> Deployment
Author ------> Model ----------------------------^
```

The important node types are:

| Node                      | Owns                                                                 |
| ------------------------- | -------------------------------------------------------------------- |
| `graph.stogasEndpoints`   | Public API paths, methods, accepted client headers, and profile IDs  |
| `graph.providers`         | Provider identity, privacy claims, capabilities, and default prices  |
| `graph.providerEndpoints` | Concrete upstream URLs, region claims, and endpoint profile IDs      |
| `graph.models`            | Canonical model slugs, aliases, context windows, modalities, authors |
| `graph.deployments`       | Provider/model pairings, service tiers, profile IDs, and prices      |

This structure prevents drift. For example, a model context window is stored on the model node; every deployment of that model inherits the same fact unless a real override exists.

## A Small Example

This is a tiny catalog fragment, not a complete release:

```json
{
	"graph": {
		"stogasEndpoints": {
			"stogas-chat-completions": {
				"schema": {
					"method": "POST",
					"path": "/v1/chat/completions",
					"parameters": {
						"model": { "required": true, "type": "string" },
						"messages": { "required": true, "type": "array" }
					}
				}
			}
		},
		"providers": {
			"openai": {
				"name": "OpenAI",
				"streamingSupported": true
			}
		},
		"models": {
			"gpt-5.5-2026-04-23": {
				"canonicalSlug": "gpt-5.5-2026-04-23",
				"contextWindowTokens": 1050000,
				"modelSlugs": ["gpt-5.5-2026-04-23", "gpt-5.5", "gpt-5.5-latest"],
				"reasoning": true
			}
		},
		"deployments": {
			"gpt-5.5": {
				"providerId": "openai",
				"modelId": "gpt-5.5-2026-04-23",
				"serviceTier": "default"
			}
		}
	}
}
```

## Request Policy Profiles

Endpoint and deployment nodes attach named policy profile IDs. The public JSON describes those profiles for inspection, but executable behavior lives in the measured Go gateway.

```json
{
	"policyProfiles": ["openai.responses.text_only_mvp", "openai.responses.no_unbilled_hosted_tools"]
}
```

Simple facts stay on the nodes themselves. For example, a deployment can declare the provider model, public slug variants, service tier, prices, and region. Runtime edge cases such as tool rejection, input-shape validation, and service-tier application are enforced by Go policy profiles.

Authentication aliases are also gateway behavior. A caller may send `x-api-key`, but the measured gateway canonicalizes it to the standard authorization header according to the compiled catalog and Go resolver:

```json
{
	"acceptedAuthHeaders": ["authorization", "api-key", "x-api-key", "x-goog-api-key"]
}
```

## Pricing

Pricing stays on the node that owns it. Provider-wide prices belong to `graph.providers`; deployment-specific prices belong to `graph.deployments`.

```json
{
	"pricing": {
		"input_tokens": {
			"per_mill_tokens": "5000000000000000000"
		},
		"output_tokens": {
			"per_mill_tokens": "30000000000000000000"
		}
	}
}
```

Amounts are integer USD atoms. The catalog stores rate facts only; billing algorithms, reserves, and settlement logic live in the gateway.

## Compiled Form

Catalog source files are YAML, validated by CUE, then compiled to stable JSON. Stable JSON means:

- object keys are sorted
- insignificant whitespace is removed
- one trailing newline is included
- the same logical catalog always produces the same bytes

A tiny canonical catalog might be exactly these bytes:

```json
{
	"graph": {
		"models": {
			"gpt-5.5-2026-04-23": {
				"canonicalSlug": "gpt-5.5-2026-04-23",
				"contextWindowTokens": 1050000,
				"modelSlugs": ["gpt-5.5-2026-04-23", "gpt-5.5", "gpt-5.5-latest"]
			}
		}
	}
}
```

The public catalog output includes a catalog version so clients can detect the response shape. Release verification is centered on the `gateway.igvm` hash; because the catalog is embedded into that measured artifact, catalog integrity follows the verified gateway release.
